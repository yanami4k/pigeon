# 执行层提速：文件变化改由 git 找候选、容器每次工具调用一次执行、零碎开销 审计

- 基线：5bbd0ec
- 分支：exec-speed
- 范围：决策 348（run_command 文件变化报告改由 git 找候选）、349（容器执行端每次工具调用合成一次执行）、352（执行层零碎开销）。报告的接口与语义不变：`ExecEvidence.fileChanges` 的形状与显示照旧，空报告即命令没改动工作区（git 工作区里不含被忽略的文件）

## 一、run_command 的文件变化（决策 348，提交 a015d72）

现状：`run-command.ts` 在命令前后各调执行端的 `listFiles` 做全量清单比对；本机为同步的 `readdirSync` 加逐文件 `statSync`（遍历期间进程卡住），容器为一次 `find`；只跳过 `.git`、`node_modules` 与根下 `.pigeon`。

改法：
- 执行端接口（`tools/workspace-host.ts`）：`listFiles` 保留；新增可选的 `fileState(limit, before?)` 与 `execObserved(plan, options, limit)`。取证 `HostFileState` 两种：git（git status 报出的路径、状态与签名）与 scan（全量清单）。纯函数 `parseGitStatus`（去掉工作区在仓库里的前缀、去掉根下治理目录；同一路径既跟踪又未跟踪时记跟踪）与 `gitFileState`（超过上限标不完整；命令后的那次把命令前报出、这次没报出的路径补上，状态记 clean）本机与容器共用。
- git 的取法：`git -c core.fsmonitor= status --porcelain=v1 -z --untracked-files=all --no-renames -- .`，含未跟踪、不含被忽略、只看工作区子树。没有加 `--no-optional-locks`：加了时 git 不能回写刷新过的索引，修改时间晚于索引的文件每次都要重算内容哈希（服务器上本仓库一次约 100 毫秒）；不加时 git 顺带刷新索引里的文件状态（与人在终端里跑 git status 相同，索引被别的进程锁着时只是不刷新），之后一次约 8 毫秒。签名为大小与修改时间（本机 `lstat`）。
- 比对（`run-command.ts` 的 `diffStates`）：签名变了即有变化；命令前没报出的路径在命令前是干净的——未跟踪即原本不存在（新增），跟踪的原本存在（修改或删除）；命令后不再报出的路径按补查的签名判断（改回原样记修改）。命令前已改、命令又改的按签名变化识别。两次取法不一（命令中途建了或删了版本库）报不完整。
- 本机执行端：工作区在仓库里的前缀会话内取一次（`git rev-parse --show-prefix`）；不是 git 工作区或 git 失败时退回扫描。扫描改为异步：同时读至多 8 个目录，一个目录里的文件并发取 stat。
- 跳过名单（一处常量 `LISTING_SKIPPED_DIRS`）扩充：`.venv`、`venv`、`dist`、`build`、`target`、`.tox`、`.nox`、`.mypy_cache`、`.pytest_cache`、`.ruff_cache`、`__pycache__`、`.gradle`、`.next`、`.nuxt`、`.turbo`、`.parcel-cache`、`coverage`。只用于非 git 工作区的扫描与 `listFiles`。
- run_command 按执行端能力取证：有 `execObserved` 合成一次；有 `fileState` 前后各取一次；只有 `listFiles` 的执行端（测试替身）照旧比对清单。
- `docs/configuration.md` 补文件变化的口径。
- 已知限制：只改索引、不改文件内容的操作作用在命令前干净的文件上（例如 `git rm --cached`），命令后它以跟踪状态出现，报为修改。

## 二、容器执行端每次工具调用一次执行（决策 349，提交 42a33fb4）

现状：读文件 3 次进容器（解析、`test -f`、`cat`），改文件 5 次（受保护路径判定、写前解析、`test -f`、`cat`、写入），跑命令 3 次（前后 `find` 加命令；设了内存上限时再加前后两次读 oom 计数）。

改法（`execution/container-host.ts`）：
- 检视：一次执行输出"输入本身是否符号链接、链接内容、解析结果、类型（文件、读不了的文件、目录、其他、不存在）、cksum、原文"，以 NUL 分隔；原文先拷进容器内的临时文件，cksum 与交回的原文出自同一份字节。检视用的路径按工作区根写成绝对路径，含 `..` 段的不折叠，与受保护路径判定（`application/protected-paths.ts`）同一写法，同一个文件经两处得到同一个键。
- 最近一次检视：`resolveExisting` 每次现做一次检视（读文件与受保护路径判定都经这里）；`resolveForWrite` 在同一路径刚检视过、其间没有 exec 与写入时直接取用（符号链接照样据检视结果拒写）；`isFile` 与 `readText` 对同一解析结果取检视里的结果；exec、`execObserved` 与写入时作废。读文件因此 1 次；改文件的受保护路径判定、审批预览与执行时的预检共用一次检视，加写入共 2 次（人工审批时同样 2 次）。
- 写入守卫与审批前内容不写回：写入的内容出自检视交回的原文时，写入脚本带上检视时的 cksum。脚本在同一次执行里依次复核：目标不是符号链接、仍存在、重新解析仍得到它自己（决策 334），再比当前文件的 cksum 与检视时的是否相同；不同即不写，就地重做一次检视交回（退出码 7）。执行端把它留作最近一次检视并抛 `WorkspaceContentChangedError`（属写入拒绝一族）。编辑工具经 `planAndWrite`（`tools/workspace-host.ts`）收到它即按新原文重算一次再写，与原先"执行时重新预检"同一语义。所以审批之后原文被改动时，按审批前原文算出的内容不会写回：cksum 不同就不写，只会写按新原文算出的内容（hashline 模式的快照预检照样兜底）。复核与写入之间只剩脚本里比完 cksum 到截断重写的间隔，与原先路径复核的间隔同处一次执行。`planAndWrite` 另在预检失败时先刷新检视（`resolveExisting`）再预检一次，免得在审批前的过期原文上误报；本地执行端每次现读，两处重试的结果与原先相同，失败路径多读一次。
- 观测执行：命令、命令前后的取证与内存计数合成一个脚本，一次执行。标准输入第一行是本次的随机串（不进命令行与环境，命令读不到），其余行是只取证时调用方给出的要补查的路径。输出以"换行 + 随机串 + 标记"分段：取证（git 为工作区前缀、git status 原始输出与 stat 段；否则为全量清单，同 `listFiles`）、oom、cmd、end（退出码）、done。命令以原来的 PATH、空标准输入执行；脚本自己用的工具从系统目录解析，git 屏蔽全局与系统配置、关掉 fsmonitor，这些变量与函数都不进命令的环境。程序不存在、不可执行在脚本里先判（`command -v`、`[ -x ]`），记 missing / denied，执行端还原为 ENOENT / EACCES。输出分流时只把 cmd 与 end 标记之间的字节交给输出收集器（末尾留不足一个标记长的尾巴），输出字节数与哈希只算命令自己的输出。超时与中止仍是杀客户端并重启容器（335 不变），这时没有命令后的取证，run_command 另经 `fileState`（同一脚本经辅助调用执行）补取；后台进程在命令结束后写出的内容打乱了末段、没等到 done 标记时同样补取。
- 内存计数随观测执行一起读；判定与提示同原先（`execWithMemoryCheck` 仍用于钩子等其余执行）。
- 每个容器首次调用的探测照旧；工作区根与治理目录的解析每个容器各一次。

## 三、执行层零碎开销（决策 352，提交 77044b7）

- 启动时的 `git ls-files --error-unmatch .pigeon/settings.local.json`：文件不在即不起进程（`application/session-settings.ts`）。
- 命令检查的程序查找：本机执行端在 Windows 上按"查找方式 + PATH + 程序名"缓存 `windowsScript` 的结果，会话内有效（新执行端即新缓存）；找到的脚本取用前确认仍在，没找到的结果在命令报"程序不存在"时作废（`forgetLauncherScript`）。查找方式现为 `root-and-path`（工作区根加 PATH）。审批时与执行时的两遍检查因此只查一次。
- 真实路径：工作区根的真实路径按根的写法缓存（`tools/paths.ts` 的 `realRootOf`）；本机受保护路径判定的两个根各取一次。根下 `.pigeon` 的真实路径照旧每次现取（它可能在会话中途被建或被换成链接，属第一道防线）。本机的受保护路径判定与写前解析不共享目标的解析结果；容器上两者共用一次检视（第二节）。
- 钩子：`docs/configuration.md` 钩子一节写明每次命中起一个进程的代价与配置建议，协议不改。
- 跑批网关（`eval/model-gateway.ts`）：请求体里没有 `"custom"` 字样即不解析（Pigeon 自己的请求都是这样）；响应只解析带 `"usage"` 的 data 行（message_start、message_delta），正文增量不解析；花费累计文件记一笔后至多 5 秒合并落盘一次，到上限停批时与网关关闭时立即写定。进程意外退出时最多少记最近 5 秒内的花费。

## 补记：git status 不刷新索引；受保护判定不共享目标解析

- git status 改为加 `--no-optional-locks`（本机的 `GIT_STATUS_ARGS` 与容器观测脚本里的 git 同改）：不取可选的锁、不刷新使用者的索引。刷新索引要短暂占住 `.git/index.lock`，使用者同时在终端或编辑器里跑 git 时可能报锁已存在；本轮的主要收益（取证期间进程不再停顿）不靠刷新。代价是修改时间晚于索引的文件每次都要重算内容哈希。第一节"没有加 `--no-optional-locks`"的说法以本节为准。
- 改后的实测（同一台服务器、同一脚本，前后各取一次证的总耗时，5 次中位数；最长停顿为取证期间事件循环的最长停顿）：

| 用例 | 旧：同步遍历 | 新 | 最长停顿 旧 → 新 |
| --- | --- | --- | --- |
| 本仓库 745 个文件（git） | 12.5 ms | 10.9 ms | 12.6 → 2.0 ms |
| 合成 2,000（git，5 个改动） | 20.4 ms | 39.3 ms | 20.4 → 2.1 ms |
| 合成 10,000（git） | 125.2 ms | 192.6 ms | 125.3 → 4.6 ms |
| 合成 20,000（git） | 243.0 ms | 348.8 ms | 243.0 → 10.1 ms |
| 合成 2,000（非 git） | 20.0 ms | 31.7 ms | 20.1 → 3.0 ms |
| 合成 10,000（非 git） | 131.7 ms | 236.8 ms | 131.7 → 7.9 ms |
| 合成 20,000（非 git） | 271.7 ms | 573.1 ms | 271.7 → 9.4 ms |

  合成仓库的文件与索引在同一时刻写成，索引里的这些文件一直处在需要重算哈希的状态，git 取证的总耗时因此高于旧做法；实际工作区里需要重算的通常只是最近改过的文件。第五节里 git 用例的旧数字是允许刷新索引时测的，以本表为准。
- 本机的受保护路径判定与写前解析保持不共享目标的解析结果，只缓存工作区根的真实路径。受保护判定发生在审批之前、写前解析发生在写入之时，共享解析结果会在判定与写入之间留下目标被换掉的空档；决策 334 的写前复核本就要求写入时重新解析。决策 352 原话要求"受保护路径判定复用写前解析的结果"，这里以安全为先偏离原话。容器上受保护判定与写工具共用一次检视，写入脚本在写入的同一次执行里重新复核路径、符号链接与 cksum（第二节），不留这一空档。

## 补记：验收意见的修正（提交 a0b2910）

安全：
- 版本库元数据不可写：本机写前解析（`tools/paths.ts` 的 `resolveWorkspaceWritePath`）与容器执行端的 `resolveForWrite` 在解析结果的任一级名为 `.git`（不分大小写），或落在工作区根下 `.git` 实际所在的目录里（`.git` 是符号链接时为它的指向，是 gitfile 时为其中 gitdir 的指向）时一律拒写，不经审批、不受放权与 yolo 影响。容器上根下 `.git` 的所在与工作区根的解析在同一次执行里取到（每个执行端一次），不增加进容器的次数。本分支没有 write_file；凡经 `resolveForWrite` 的写工具都受这一条约束。
- Pigeon 在后台起的 git 统一加固（`tools/git-hardening.ts` 一张表）：`-c core.fsmonitor=`、`-c core.hooksPath=/nonexistent/pigeon-no-hooks`，git 认 `--attr-source` 时另加 `--attr-source=<空树 4b825dc642cb6eb9a060e54bf8d69288fbee4904>`（每个进程探测一次；服务器的 git 2.43 认），工作区与仓库里 `.gitattributes` 指派的过滤不再执行；不认的较旧 git 只有前两项。接上的地方：本机的 status、rev-parse、check-ignore，容器取证脚本（按同一张表拼参数、在容器里探测 `--attr-source`），代码快照（`orchestration/checkpoint.ts`）、退出快照（`execution/workdir-snapshot.ts`）、脚本快照的 update-ref、启动时的设置层跟踪检查、最近会话的 for-each-ref。本分支的搜索工具不起 git。代价：Pigeon 自己的 status 与快照不再应用工作区的属性（LFS、换行转换等过滤），LFS 管理的文件在重算哈希时可能报为修改，快照存原始内容；SHA-256 格式的仓库里空树的编号不同，git 会报错，status 退回全量扫描（下面第 4 条），快照失败按原有的快照失败处理。
- 观测脚本的命令改经 `env --` 执行，只执行外部程序：预检按原来的 PATH 逐个目录找可执行文件（与 `env` 的查找一致），内建命令（eval、.、cd 等）与脚本自己的函数一律按程序不存在处理，既读不到当次的随机串，也绕不过"经 shell"的确认；`true`、`echo` 这类同时有外部程序的照常执行外部程序。
- 路径含换行或控制字符的一律拒绝：两个执行端的输入路径，以及容器里的解析结果。容器脚本取 readlink 结果时先补一个哨兵字符再去掉，结尾的换行不再被吞掉、指到别的文件。写入复核的内容哈希：容器里有 sha256sum 即用它，没有退回 cksum（CRC32，能被有意造出碰撞；busybox 与常见镜像都带 sha256sum）。

正确性：
- git status 失败（命令删了 `.git`、弄坏了索引等）时改用全量扫描并注明：`FileChanges` 新增可选的 `note`，结果文字的"文件变化"一行附上说明。命令前后都改用扫描的照常比对、注明"git status 失败，改用全量扫描"；命令前是 git 取证、命令后改用扫描的两次取证对不上，报不完整并注明。空报告因此仍等于命令没改动工作区（没有注明、没有标不完整时）。
- 工作区根本身被外层仓库忽略（`git check-ignore -q -- .`）时按非 git 工作区全量扫描。status 报出的目录里有 `.git` 的（未跟踪的嵌套仓库、子模块），逐个在里面取它自己的 status（最多往下三层），路径加上目录前缀；取不到的、更深的那棵子树整棵扫描，文件按未跟踪记。命令前干净、命令后变了的子模块会在命令后的 status 里出现并被往下取证。本机与容器同一口径。
- 容器取证：候选去重后超过上限只留前 limit 个、标不完整；输出按块收下，命令前后各段最后拼接一次，找标记时只把不足一个标记长的尾巴与下一块拼起来，不再逐块整段拼接；命令的限时只从 cmd 标记算到 end 标记，整次执行另设兜底（命令限时加两个辅助限时）；命令已结束、命令后的取证超过辅助限时的，杀客户端并重启容器，退出码仍按 end 标记交回、不算命令超时，命令后的取证另取。
- 取证不完整时（全量清单或 git 候选超过上限）只报命令前后都在、签名变了的文件，不再报出不存在的增删。网关关闭之后才记上的花费立即写定。

## 补记：空树按仓库算出；过滤不生效的影响写入配置说明

裁决：过滤（LFS 等）在 Pigeon 自己的 git 里不生效，接受，影响写进 `docs/configuration.md`；SHA-256 仓库要修。

- 不再写死 SHA-1 的空树编号。`tools/git-hardening.ts` 的 `hardenedGitArgs(cwd)` 在该目录里跑 `git hash-object -t tree --stdin`（输入为空，不写入对象库，带前述两项加固），得到的编号随仓库的对象格式（SHA-1 为 40 位、SHA-256 为 64 位），再探测 git 是否认 `--attr-source`；结果按目录缓存在本进程内，一个会话里同一目录只算一次。不是仓库、算不出或 git 不认时只有 fsmonitor 与钩子两项。所有调用处改为传入这条 git 的工作目录：本机取证、代码快照、退出快照、脚本快照、启动时的设置层跟踪检查、最近会话。
- 容器取证脚本同样不写死：每个仓库（工作区根与逐个取证的嵌套仓库）进目录后先算本仓库的空树、探测 `--attr-source`，再取 status，所以外层 SHA-1、嵌套 SHA-256 的混合情形也各用各的编号。
- 前一节"SHA-256 格式的仓库里空树的编号不同，git 会报错，status 退回全量扫描，快照失败"这一代价随之消除。
- `docs/configuration.md`：在 run_command 文件变化的说明之后写明 Pigeon 自己起的 git 不执行仓库配置的过滤、钩子与 fsmonitor，影响为文件变化报告照常；用 LFS 一类过滤的仓库里，快照存进大文件的真实内容而不是指针，本地对象库会变大。

测试：
- `tools/git-workspace.test.ts` 新增 SHA-256 仓库用例（`git init --object-format=sha256`）：一个文件的修改时间往后拨、内容不变（迫使 status 重算哈希，git 只在这时读属性来源，编号不对才会报错），命令新增一个文件、追加一个文件，变化照常报出且未标不完整；随后代码快照（beforeChange、改文件、afterChange）成功，提交编号为 64 位。
- `execution/container-round-trips.test.ts` 新增容器上的 SHA-256 仓库用例，同样拨修改时间，变化照常报出、未改用扫描。
- 服务器上 git 2.43 的实测：在 SHA-256 仓库里以 SHA-1 空树作 `--attr-source`，文件大小变了的 status 不报错（不读属性），需要重算哈希的 status 与 `git add` 报 "bad --attr-source"。这就是用例要拨修改时间的原因。
