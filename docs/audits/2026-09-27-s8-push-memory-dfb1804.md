## 一、记忆文件格式与编号（`src/memory/learned.ts`、`src/memory/learned-store.ts`）

文件：治理根下 `.pigeon/learned/MEMORY.md`。文件头为标题一行加注释一行、再空一行；条目每条三行：

```
- [L<编号>] 事实：<一句陈述句>
  引用：<引用 1>, <引用 2>
  理由：<一句理由>
```

- 解析与序列化逐字往返：解析保留文件头原文（第一个以 `- ` 开头的行之前的全部内容，不校验）与"最后一条之后有没有换行"；未改动的文件序列化回去逐字相同。
- 条目区（第一个 `- ` 行起到文件尾）必须是规范的三行一组：事实行 `- [L<正整数>] 事实：…`、两格缩进的引用行与理由行，各项非空、编号不重复；条目之间不许空行，文件尾只许一个换行。第一处不合规即给出行号（从 1 起，文件头计入）。
- 编号 L<n> 由工具分配、删除后不复用。下一个编号另存在 `.pigeon/learned/next-id`（与 MEMORY.md 同目录，跑批器按步快照整个目录时一并带上；不进推送文字）。下一个编号取"另存的值"与"现有最大编号加一"的较大者；人删了 next-id 或写坏了，按现有最大编号续。写入顺序为先写 next-id、再写 MEMORY.md，两者之间崩溃只会让编号多跳一个。
- 写入：原子写（同目录临时文件写满、fsync 后改名，复用 `persistence/atomic-write.ts`）。工具写入时文件头不以换行结尾即补一个，末尾一律带换行。文件不在时新建，文件头取冻结原文。

## 二、上限与锁

- 上限只计条目区、不计文件头，单位为字符，按 Unicode 码点计（代理对算一个）。缺省 12,000（223 按校准实测定取值规则之前的临时值），可配置：`RuntimeDeps.learnedMemory.limitChars`、headless 的 `memoryLimitChars`、日常入口的 `--memory-limit`、`pigeon eval stream` 的 `--memory-limit`。
- 写满判定按写入后的条目区总字符数：新增或替换之后超过上限即拒绝，删除总是放行。
- 跨进程锁：`.pigeon/learned.lock`（在 learned/ 目录之外，快照不带它），用 `persistence/exclusive-lock.ts` 的独占锁（不可重入，同进程再取一样被拒）。锁被占时每 20 毫秒重试，等满 10 秒仍拿不到即报错。每次调用在锁内现读文件、现判写满、现写，写满判定因此在锁内（Q13）。

## 三、记忆工具 update_memory（`src/memory/update-memory-tool.ts`）

- 工具说明、五个参数的说明、八种情形的返回文字逐字照冻结文字（228、232）。参数 schema 里五项除 action 外都可选，必填与否随动作由工具自查、按冻结文字回话。
- 动作：add；按编号 replace；按编号 remove。编号写 L3、l3 或 3 都认，回话一律写 L3。
- 每项文字里的换行并成一个空格、去首尾空白；refs 空项丢弃。refs 里的 `user`（不分大小写）换成"用户要求（会话 {会话编号}）"；复盘会话里写入时补的是被复盘的来源会话的编号。
- 事实、引用、理由三项都相同（引用逐项、按顺序）即"完全相同"，回"与 {id} 完全相同，未新增。"。只对 add 判。
- 格式被人改坏：拒绝写入，回"MEMORY.md 第 {行号} 行起格式不对……"，文件原样不动。
- 缺字段：fact、reason 为空或 refs 没有非空项即回冻结的缺字段文字，不读文件、不写。replace 与 remove 的编号缺失或不存在即回"没有 {id}；现有条目编号：……"（编号列表以顿号相接；编号缺失时 {id} 处为空）。
- 只靠文字约束、不做程序拦截的：引用为用户要求的条目只在用户改口时改写或删除；不记密钥；引用是否存在（228、232）。
- 注册：治理档位写，路径活动范围为 `.pigeon/learned/`，执行串行。工具注册元数据新增可选项 `approvalFree`；`tools/policy.ts` 的排律在 grant 之后、yolo 之前加一档"免审批的写档工具自动放行"（deny 清单照样拒），账本记 `policy:auto`，因此不计入需审批次数，无审批通道的非 yolo 会话里也照常执行（Q12）。没有新增审批或放权机制。
- 只在推送开着时注册；推送格里干活的 agent 与复盘都带；不推送的格子不注册（217）。

## 五、复盘（`src/application/memory-review.ts`、`src/memory/review-text.ts`）

### 5.1 分叉与请求

- 分叉：读来源会话主分支，目标为最后一条消息条目，经 `forkSessionFile`（上游 repo.fork，位置 at，含目标这一条）建复盘会话的文件；分叉前来源写者已落盘（收尾复盘在运行面释放之后，压缩前复盘在压缩读主分支时已等写入队列落盘，另显式 flush 一次）。复盘会话的初始消息由分叉出的文件按会话树还原。
- 请求：复盘运行面与来源同一份装配参数（工具定义因此相同，含会话检索、update_memory 与 MCP 工具），系统提示取来源 Run 开始时冻结的原文（`RuntimeDeps.reviewSession.systemPrompt`，不重读记忆段），末尾追加一条用户消息，即复盘指令 v1 的冻结文字（221、230、232、233）。{当前记忆全文} 在复盘开始时现读 MEMORY.md 原文（去掉末尾换行）；文件不在时给新建文件的文件头。
- 收尾复盘的运行面经 `createDetachedRuntime` 重开（来源运行面已释放，MCP 按配置另起一份，复盘结束一并关）；压缩前复盘的运行面在装配根内以同一份参数再装一次，与来源共用 MCP 会话，释放时只停运行面、关会话文件，不关 MCP。
- 复盘运行面不带验证、回炉、失败重试、压缩前回调与会话来历；预算取复盘上限；推送照开、不再嵌套压缩前复盘。

### 5.2 {验证结论} 的填法（决策 242 所定文字的实现位置：`src/memory/review-text.ts` 的 `reviewVerdictText`）

按最后一次验证（回炉开着时为回炉里最后一次，关着时为运行面释放后补做的那次）：

| 情形 | 填法 |
|---|---|
| 通过、没有工具故障 | 通过 |
| 未通过 | 未通过：{失败摘要} |
| 没有运行验证门 | 本次没有运行验证门 |
| 通过、部分步为工具故障 | 通过（{步名} 的检查工具自身崩溃，未计入结论） |
| 各步全是工具故障 | 无法判定：{步名} 的检查工具自身都崩溃了，没有得出结论 |

失败摘要与回炉反馈为同一份：`repair-loop.ts` 抽出 `repairFailureSummary`（回炉反馈标题与修正要求之间的部分），回炉反馈改为调用它，文字不变。步名多个时以顿号相接。另有一种冻结文字未覆盖的情形：结论为无法判定但不是全体工具故障（超时、被信号终止、拉不起来），现填"无法判定：{失败摘要}"。

### 5.3 工具放行（决策 240 所定文字的实现位置：`src/memory/review-text.ts` 的 `REVIEW_TOOL_REFUSAL`，闸在 `memory-review.ts` 的 `gateReviewTools`）

复盘运行面的治理前加一道闸：工具名不是 read_file 或 update_memory 的调用，在治理判定之前拦下，回"复盘中只能使用 read_file 与 update_memory，这次调用没有执行。"，不执行。拦下的调用不进治理账本与熔断计数。放行的两件照常经治理（read_file 为读档自动放行，update_memory 为免审批写档）。请求里的工具定义不删，前缀与来源一致。

### 5.4 模型、预算、存档与失败

- 同一模型、同一设置、同一模型接入（跑批时即同一网关、同一计量与花费上限，235）；复盘运行面的温度、推理档位与单轮输出上限与来源相同。
- 预算：复盘另设轮数与墙钟上限，缺省 40 轮、15 分钟（243 的临时值），可配置（headless 的 `reviewBudget`，`pigeon eval stream` 的 `--review-max-turns`、`--review-wall-clock-min`）。每次复盘各自计；撞上限即中止、记 turn-limit 或 wall-clock-limit。复盘不占这一步的上限：复盘的轮数与 token 另数；压缩前复盘期间这一步的墙钟暂停，结束后截止时刻顺延；收尾复盘在这一步的计时停止之后。
- 存档：复盘会话是普通的新会话（文件头的父会话为来源），Run 开始条目新增可缺省字段 `memoryReview`：`{ kind: "closing" | "pre-compaction", template: "v1" }`（注入快照同名字段）。
- 失败：复盘失败（分叉失败、请求报错、空回复、被中止）或撞上限都不改变这一步的结果。经 `warnings.ts` 的去重告警写标准错误输出（"收尾复盘失败：……；这一步的结果不受影响，记忆可能没有更新"或"……撞上复盘上限（轮数 / 墙钟）而中止：已写入的记忆照常保留……"，同一类只说一次），并记进 headless 结果的 `reviews`（种类、复盘会话号、终态、轮数、token、墙钟、是否撞上限、失败原因）。

### 5.5 收尾复盘的时机

headless 在最后一次验证之后、返回之前做收尾复盘，复盘做完才算这一步结束；`pigeon run` 同样适用。这一步没有 Run（运行面没装起来）或被外部中止（跑批器作废这一步）时不做。失败自动分叉重试的每次尝试同样推送、带工具、各自收尾复盘。

## 六、压缩前复盘（207）
