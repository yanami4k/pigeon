## 一、改动清单

### 1. 日常沙箱容器的资源上限（333，`src/execution/sandbox.ts`、`src/execution/container-host.ts`、`src/tools/workspace-host.ts`、`src/tools/run-command.ts`、`src/application/sandbox-session.ts`、`src/tui/main.ts`）

- 取值：`resolveSandboxLimits(设置, MemTotal)`。内存缺省 = `docker info --format '{{.MemTotal}}'` 的一半，向下取整到 MiB；进程数缺省 `SANDBOX_DEFAULT_PIDS_LIMIT = 4096`；CPU 缺省不限。设置里任一项写 0 为不限。MemTotal 取自 Docker 守护进程（`dockerMemTotal`），不用本进程的 `os.totalmem()`。
- docker 参数：`sandboxLimitArgs` 生成 `--memory <字节> --memory-swap <同值>`、`--pids-limit <N>`、`--cpus <N>`，取值为 0 的那项不带。`openSandbox` 把它接在 `docker run` 的参数末尾。
- 读不到 MemTotal（`docker info` 失败或输出不是正整数）：不设内存上限，开工时打一行"读不到 Docker 所在机器的内存总量（docker info 的 MemTotal），本次沙箱不设内存上限"；进程数上限照设。
- 设置的接入点：`OpenSandboxOptions.limits?: SandboxLimitSettings`（`memoryBytes`、`pids`、`cpus`，缺项取缺省）。第一步没有来源，恒取缺省；第二步由 settings 的 sandbox 一节填入。
- `Sandbox.limits` 记生效的上限；就绪提示带一段摘要，如"内存上限 8 GiB、进程数上限 4096、CPU 不限"（`sandboxLimitsSummary`）。
- 超限判定（容器执行端 `exec`）：`ContainerHostOptions.memoryLimit` 在场时，每条命令前后经辅助命令读容器 cgroup 的 oom_kill 计数（依次读 `/sys/fs/cgroup/memory.events`、`/sys/fs/cgroup/memory/memory.oom_control`，取第一个读得到且有 `oom_kill` 行的）：
  - 计数增加：`memoryLimitExceeded = { limit, certain: true }`；
  - 前后任一次读不到、命令以 137 结束：`{ limit, certain: false }`；
  - 读得到而未增加：不报（退出码 137 也不报）；超时与中止（容器重启、计数归零）、程序没起来：不判。
- 提示：同一句由 `memoryLimitText` 给出——确定时"超出沙箱内存上限 <数值>：命令或它起的进程被内核终止（OOM）。原样重试多半还会被杀，先减少并行度或内存占用"；不确定时"可能超出沙箱内存上限 <数值>：命令以退出码 137 结束（被 SIGKILL 终止），读不到容器的内存事件计数，无法确认"。
  - agent：`run_command` 的结果文字在"退出码"一行之后加这一句；`ExecEvidence.memoryLimitExceeded` 随结果记进会话存储。
  - 人：执行端经 `onNotice` 报一行（附命令行）。沙箱把 `OpenSandboxOptions.notice`（缺省同 `log`）接给执行端；终端界面传入告警出口（壳接管终端期间落消息区），命令行对话与 `pigeon run` 沿用 `log`。
  - 会话验证命令经同一执行端运行，同样判定与提示。
- 测试注入：`OpenSandboxOptions.oomCounterFiles`、`ContainerHostOptions.memoryLimit.counterFiles`。
- 去能力与禁止提权未做（不在本条范围）；日常沙箱容器仍不加 `--rm`。

### 2. 编辑工具写入前复核路径（334，`src/tools/paths.ts`、`src/tools/local-host.ts`、`src/execution/container-host.ts`、`src/tools/workspace-host.ts`、`src/tools/edit-file.ts`、`src/tools/replace-edit.ts`）

- 执行端接口新增 `resolveForWrite(inputPath)`：同 `resolveExisting`，另在模型给的路径本身（最后一级）是符号链接时拒写，报出 `<路径> → <指向>`；路径上的目录是符号链接的照常解析。两种编辑工具（hashline 与 replace）的预检改用它。
- `writeText(resolvedPath, …)` 写入前复核：`resolvedPath` 是检查时解析出的真实路径，重新解析须仍得到它自己；目标成了符号链接（报出指向）、已不存在、或解析到别处（报出新的解析结果）即拒写，告知"路径已变 … 请重新 read_file 后再编辑"。
  - 本机：`assertWritePathUnchanged`（`lstat` + `realpath`）后 `writeFile`。
  - 容器：复核与写入在同一次 `docker exec` 的同一段脚本里（`[ -L ]`、`[ -e ]`、`readlink -f` 比对、`cat >`），经固定 PATH 的 shell 运行；退出码 5 为符号链接、3 为不存在、6 为解析结果变了。
- 拒写的错误类 `WorkspaceWriteRefusedError`（`WorkspacePathError` 的子类，错误归类沿用路径围栏的口径）。
- 不做逐级安全打开目录；检查与写入之间的空隙仍在（决策 334 的理由）。

### 3. 容器辅助命令的超时（335，`src/execution/container-host.ts`）

- `containerHelperExec`：辅助命令经 `/bin/sh -c 'exec "$0" -k 2 <秒> "$@"' <timeout 的绝对路径> <命令…>` 在容器内限时；到时先 TERM、2 秒后 KILL，只终止该命令，不重启容器。秒数为毫秒限时向上取整（至少 1 秒）。客户端超时 = (秒数 + 2) 秒 + 3 秒，作兜底。经 `/bin/sh` 起 timeout、以 `$0` 传绝对路径：命令自己的环境与 PATH 不变。
- 认定容器内超时：退出码为 124、137 或 143（GNU 与 busybox 的写法）且实际耗时不短于限时；结果标 `timedOut`，标准错误末尾加"辅助命令超过 N 秒，已在容器内终止"。
- 探测：每个容器首次使用时以固定 PATH 执行 `command -v timeout`，结果（绝对路径或"没有"）按"docker 调用前缀 + 容器名"缓存在内存里；起容器与删容器时作废。守护进程层面的失败与探测超时不缓存，下次再探。
- 退回：没有 timeout 时，客户端到时杀掉并重启容器（`restartContainer`）；有 timeout 而客户端兜底仍到时，同样重启。标准错误末尾写明"辅助命令超过 N 秒未结束，已重启容器"。
- 覆盖面：容器执行端的全部辅助调用（解析路径、写工具解析、判文件、读写文件、文件清单、取起点与还原受保护文件、读 oom_kill 计数），以及 `containerExec`（沙箱开工的检查与建仓库、交回的提交与打包，跑批器 `dockerStreamShell` 的命令）。agent 命令（`exec`）照旧"杀客户端并重启容器"。
- `dockerOnce` 的结果在客户端被杀时带 `timedOut: true`。
- 测试替身随之调整：`sandbox-docker-fixtures.ts` 认出 timeout 包装、按里面的命令判有没有 git，并支持 `info` 子命令与 `--memory-swap`、`--pids-limit`、`--cpus`；三个记录 docker 调用的跑批器用例（stream-workspace、stream-profiles、stream-agents）把探测调用排除在断言之外（`TIMEOUT_PROBE_SCRIPT`）。
