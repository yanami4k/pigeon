## 二、Q4 三项的现算口径

**工具级失败分类**（按调用逐个，state/session-judge.ts 的 storeToolOutcomes）：

| 情形 | 分类 |
|---|---|
| 工具结果不是错误 | 非失败 |
| 没有工具结果，或只有续跑补的"结果未知"工具结果 | 未知 |
| 策略拒绝：工具在 deny 清单上，或结果正文是 prompt 档无审批通道时的固定拒绝理由 | 非失败（治理闭环） |
| 所在 Run 末条助手消息以中止收尾 | 取消（收尾条目结束方式为熔断时标熔断子类） |
| 上游在审批闸之前拦下：工具名不存在、参数校验失败、输出撞上限而参数可能截断（上游固定文案），或工具不在该 Run 的广告名单里 | 业务失败 |
| 其余执行出错 | 未知 |

工具抛错时的域 / 环境归类原本记在工具落定事件上，该事件停写后没有来源；人工拒绝在消息上与执行出错不可分。两者都落未知（见第四节预期差异 1、2）。prompt 档无审批通道时的拒绝理由改为从 state/session-judge.ts 导出的常量，审批闸与分类共用同一文案。

**需审批次数**：Run 开始条目的审批模式为 yolo 时，写档与命令档（档位取运行面已注册工具的风险档位）、不在 deny 清单上、有工具结果、结果不是上游拦截、也不是续跑补的"结果未知"的调用数，即有人在场时会被问几次。档位缺失的工具不计。固化规则命中的调用同样计入（规则匹配不在会话存储里，见预期差异 4）。

**worker 收尾结果的回执号**：删除（1.3 节）。

## 三、续跑与悬空工具调用

流程（决策 183）：

1. application/resume.ts：按会话号在新存储里找文件。没有文件而旧账本有记录的（双写之前的旧会话）明确报错"创建于新会话存储启用之前，不能续跑"；都没有的报"会话不存在"并列出新存储里已有的会话。
2. 报告将还原的上下文：buildSessionContext 还原的消息条数、没有收尾条目的 Run 数、末条助手消息里悬空的工具调用（名字与个数）。
3. 进入续会话入口。运行面装配（session-runtime.ts，入口参数由 restoreGrants 改为 resume，同时恢复授权与上下文）：写者打开会话文件后读主分支，经 pi 的 buildSessionContext 还原消息；末条助手消息里每个没有工具结果的调用补一条工具结果——正文"进程在执行途中中断，这次工具调用的结果未知：请自行核实（例如重新读取相关文件、查看命令的效果）后再决定下一步。"，isError 为真，details 带标记 pigeonInterrupted；补的结果先写进会话文件（位于原 Run 的消息之后、续跑的第一个 Run 开始条目之前），再连同还原的消息经 Adapter 新增的 restoreMessages 交给 Agent。会话文件没打开（新存储故障）时报错并释放运行面，不做没有上下文的续跑。
4. 此后的输入照常开新 Run，接着原对话。

删除：execution/recovery.ts（哈希三方比对与确证记录）；resume.ts 的人工确认菜单、落盘缺口汇总与确证报告；resume-view.ts 与 tui/main.ts 里为哈希比对准备的确证读取根（workspaceRootFor）与菜单问答；cli resume 的对应参数。

补的"结果未知"工具结果只写新存储，不写旧账本（它不属于任何一次运行中的 message_end）。

## 四、Run 收尾条目的结束方式

| 结束方式 | 判定（pi-runtime/adapter.ts） |
|---|---|
| completed | 末条助手消息停止原因为 stop、length、deferred |
| turn-limit / wall-clock-limit / token-limit | Run 确以中止收尾，且撞上限的一方随中止请求交来了原因（headless 的三种上限与 worker 的上限经 interrupt(原因) 交给运行面） |
| breaker | Run 确以中止收尾、无上限原因、本 Run 熔断落闸 |
| aborted | Run 确以中止收尾、无上限原因、未熔断（含外部中止） |
| error | 末条助手消息停止原因为 error 或终态不明；本段新增：Run 以异常结束（上游抛错，如没有消息时的 continue）也写收尾条目，结束方式记出错、错误文本为异常文本 |
| empty-reply | 只留枚举值，识别另行施工 |

撞上限原因的入口（interrupt 带原因）第一段已交付，收尾条目一次写全；本段的读者据此取撞上限，不再依赖 headless 在 Run 返回后补写的 run.limit-hit（旧账本照写）。Adapter 另加 settled()：等当前 Run 彻底收尾、收尾条目已交给写者；run.ended 事件先于收尾条目到达，事件回调里要读收尾条目的读者先等它。

## 五、对照结果与预期差异

### 5.1 对照工具

src/application/reader-compare.ts：同一个会话，旧读法（物化旧账本）与新读法（读新存储）逐项比较，覆盖本段迁移的全部读者——各 Run 的失败分类、成败标签及其事实（运行结束、悬账数、撞上限、验证结论）、回炉一步、尝试切片（Run 与条目范围、轮次、标签、验证记录所在会话、有无结束时刻）、运行指标（首个 Run、轮次、工具调用、用量、需审批次数、失败分类）、工具级失败分类、生效授权、worker 与分支会话来历、分叉记录、每个可分叉位置之前最近的快照、续跑还原的消息条数（非分支会话）。已知的预期差异在差异上标出原因，未标原因即读法改错；命令行入口以未预期差异的会话数决定退出码。

### 5.2 结果

- 测试（application/reader-compare.test.ts，4 例）：失败自动分叉重试的来源与分支、撞上限、回炉一步、上游拦截（参数校验失败）、prompt 档无审批通道的策略拒绝、授权建立与撤销，各会话零差异；工具域错误（找不到替换原文）只出现一条预期差异 1；新文件的验证结论与收尾条目被篡改时报出失败分类、成败标签、运行指标的未预期差异；新存储里没有文件时直接报出。
- 命令行（服务器上以一次性脚本造 6 个双写会话：分叉重试的来源与分支、回炉、撞轮数上限、上游拦截、prompt 档拒绝）：每个会话比较 24–34 项，差异 0，退出码 0。
- 施工中对照工具报出过一处真实差异并已修正：分叉点正好是发起改动的助手消息时，新读法取到了该次改动之后的快照。旧记录的快照条目号取"落定时的条目号加一"（快照归到紧随其后的工具结果那一条），新读法原先按"前面已有几条消息"计，少了一；改为同一口径后零差异。
- 本段迁移的读者没有真实运行的双写数据可比（双写之后尚无真实模型运行）；证据限于上述由假模型产生的双写会话。

### 5.3 预期差异清单

1. 工具执行出错的域 / 环境归类随工具落定事件停写，新读法落未知（旧读法：域错误为业务失败，环境异常为基础设施错误）。
2. 人工拒绝与执行出错在消息上不可分，新读法落未知（旧读法凭审批决定记为非失败）。
3. 旧 eval.verified 随 184 停写，新读法的验证结论只认验证记录条目。
4. 需审批次数：固化规则命中的调用，旧读法不计（回执批准来源为 policy:config），新读法按 yolo 批发授权计入。
5. Run 以异常结束：新存储记出错收尾，旧账本没有运行结束记录；失败分类与标签两边都是未知，"运行结束"事实不同。
6. 续跑补的"结果未知"工具结果只写新存储，续跑还原的消息条数比旧账本多。
7. 尝试切片的结束时刻、验证记录号取自不同记录，只比有无与所在会话。

第一段的双写对照（dual-write-compare）因第 5、6 项多出两类预期差异：新存储多一条消息；异常结束的 Run 新存储有收尾而旧账本没有。已写入 spikes/ledger-migration/README.md。
