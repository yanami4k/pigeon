## 一、终端界面退出（`src/application/tui-exit.ts`、`src/tui/main.ts`）

- 基线上终端界面退出本来就不做复盘（推送记忆前半段只有 `pigeon run` 的收尾复盘与压缩前复盘）。本段把退出收尾收成 `closeTuiSession`，由终端界面入口调用：取消在跑的 worker 并等其收尾记录落盘（上限 5 秒，同前）→ 释放运行面 → 沙箱会话交回并删除容器（决策 245，同前）→ 记退出条目。全程不调用模型、不新建会话。/quit、双击 Ctrl+C、SIGINT、SIGTERM 走同一条路径。
- 退出条目：新增自定义条目 `pigeon.exit`（`ExitDataSchema`，版本 1，加法式；会话原生视图不投影它，旧会话照常可读）。数据为退出时刻与工作目录三种情形之一：
  - `snapshot`：本机 git 工作区，沿用 278、279 的 `snapshotWorkdir`（受跟踪文件的当前内容加未被忽略的新文件，`.pigeon` 还原成 HEAD 的样子，以 HEAD 为父）。另建了快照提交时挂在 `refs/pigeon/exit/<会话号>` 上防回收，条目带 `ref`；没有未提交改动时即 HEAD，不建提交、不挂引用。
  - `sandbox`：沙箱会话不另拍，记交回的分支与提交。
  - `none`：非 git 工作区、仓库还没有提交、拍快照失败、沙箱交回失败，记原因。
- 这次会话一次运行都没跑过（会话文件里没有 Run 开始条目）即不记、不拍。
- 写入时机：运行面释放后写者已关，另开一个写者续写同一会话文件（取同一把会话锁）再关上。退出条目写不成只告警，不挡退出。
- /resume 换绑：换走的会话在本进程里到此结束，释放后同样记一条退出条目。
- 退出时先叫停后台补做（见第二节），等它交还租约、删掉临时工作树，上限 2 秒，超时照常退出（租约到期后自然失效）。

## 二、启动时后台补做（`src/application/review-backfill.ts`）

- 终端界面启动、壳接管终端之后，下一轮事件循环开始补做，不挡输入；推送记忆关着（`--no-pushed-memory`）时不补。进度每补完一个在消息区给一行：`后台补做复盘：已完成 k/n`，有失败时加 `（其中 f 个失败，留待下次启动重试）`。补做本身出错（如配置畸形）时在消息区给一行原因。状态栏显示未做。
- 找未复盘的会话：扫会话存储，以"有没有以该会话为父、跑完了的收尾复盘"为准（192 的口径），不另设登记。
  - 复盘会话按 Run 开始条目里的复盘标记认出（分叉复制来的来源历史也在文件里，取带标记的那次 Run）。
  - 跑完：复盘那次 Run 的收尾条目为 completed，或撞复盘上限（turn-limit、wall-clock-limit、token-limit）。复盘失败、被中止、没有收尾的不算，会话留待重试。
  - 只认种类为收尾的复盘；压缩前复盘不算复盘过。
  - 候选：没有父会话的顶层会话（worker、分叉分支、复盘会话自己都不在内），跑过运行、最近一次运行开着推送记忆、有消息。本进程的当前会话不补；会话锁被别的存活进程持有（还开着）的这次跳过。
- 补做：沿用现有复盘运行面 `runMemoryReview`，种类记收尾，指令用收尾版本；验证结论取来源主分支上最后一条验证记录，按 242、250 的同一填法，没有验证记录填"本次没有运行验证门"。系统提示取来源最近一次运行冻结的原文；只放行 read_file 与 update_memory，上限取复盘缺省（40 轮、15 分钟）。模型、推理档位与记忆上限取本次启动的参数。补做的运行面不起 MCP server。
- 读代码的根（283）：
  - 本机会话：从退出条目的快照提交检出分离头指针的临时工作树（系统临时目录下），作为复盘运行面的工作区根，read_file 读的是退出那一刻的文件。
  - 沙箱会话：退出条目记的交回提交；没有退出条目但仓库里有 `pigeon/sandbox-<会话号>` 分支时，取该分支的最新提交。
  - 无快照（`none`、没有退出条目、提交已不在仓库里）：读当前工作目录，原因写进复盘记录。
  - 临时工作树用完即删（`git worktree remove`，删不掉再删目录并 `worktree prune`）。补做完成或判为过时后删除退出快照引用；失败时保留，重试照样读快照。
- 复盘记录：复盘会话的 Run 开始条目的复盘标记加 `backfill.readFrom`（`exit-snapshot` 带提交、`sandbox-branch` 带分支与提交、`workdir` 带原因）。

## 三、三道闸（284）与配置

- 闸一：首次以新版本启动时在治理根记下上线时刻（`.pigeon/review-backfill/since.json`，以独占创建写入，并发首次启动以先写成的为准）；只补创建时刻（会话文件名里的时刻）不早于它的会话。
- 闸二：会话主分支上最后一条条目的时刻距今超过 7 天即视为过时，写一条跳过记录（`records/<会话号>.json`，`status: stale`），删除退出快照引用，以后不再补。
- 闸三：每次启动最多补 5 个，按最后动静从新到旧；领不到租约或还开着的跳过、不占名额，其余留到下次。
- 配置：`.pigeon/review-backfill.json`（人手写，可缺省；形态同 `web.json`，缺失即缺省，畸形或多余字段响亮失败）：`maxAgeDays`（缺省 7）、`maxPerLaunch`（缺省 5）、`leaseMinutes`（缺省 30）。

## 四、租约与失败重试（`src/persistence/review-backfill-store.ts`）

- 租约文件 `.pigeon/review-backfill/leases/<会话号>.json`：持有者标识（进程号加本次启动的随机串）、进程号、领取时刻、到期时刻（领取时刻加租约时长，缺省 30 分钟，即复盘墙钟上限的两倍）。过了到期时刻即视为失效，别的进程可以接手。
- 读、判、写三步在按会话号的独占锁（`leases/<会话号>.lock`，沿用 `exclusive-lock.ts`，持有进程已死即接管）里完成；锁只在这三步之间持有，复盘期间靠租约文件挡住别的进程。交还时只删自己的租约。
- 领到租约后再核对一次该会话是否已有跑完的收尾复盘，有即跳过：另一个进程可能在本进程扫描之后补完并交还了租约。这一步由双进程用例发现（未加时两个进程在全文件连跑中出现过同一会话补两次），加上后该文件在服务器上连跑 6 次全绿。
- 失败：写失败记录（`status: failed`，次数累加、最近一次原因与时刻），交还租约，之后的启动重试；补成后删除记录。终端界面退出打断的补做不算失败、不写记录。

## 五、复盘覆盖到哪一条记录（283 补充）

- `runMemoryReview` 分叉时的目标是来源主分支上最后一条消息条目；它的条目号与序号（seq）作为 `covers` 交给装配方，写进复盘会话 Run 开始条目的复盘标记（`MemoryReviewTagSchema` 加可缺省的 `covers` 与 `backfill`，旧会话照常可读；注入快照里的同名字段同步）。
- 收尾复盘（headless）、压缩前复盘（装配根的压缩前回调）、补做三处都写。
