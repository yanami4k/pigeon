# 压缩的摘要请求走缓存（决策 424）审计

基线 1c6b868。施工提交：cb201bd（实现）、d47e1a5（测试）、efddcd5（文档）；并入集成线的合并提交 b3fb935。本审计在并入后补写。

## 一、改了什么

- `src/pi-runtime/compaction.ts`：摘要请求有两种发法。
  - 接续式（缺省）：沿用下一次主请求的模型对象、系统提示、工具定义与消息（由运行面按主请求的转换给出），请求选项同主请求（推理档位、温度等），末尾追加一条摘要指令（用户消息），前缀与上一次主请求逐字节相同，可命中服务方的前缀缓存。请求带 `toolChoice: "none"`，只取一条回复。摘要指令沿用上游摘要提示词的要求（结构、该保留什么），另加"只写摘要、不要调用工具"；切开一轮时的处理与上游 compact 对应（见 `summaryInstruction` 的注释）。
  - 独立式：上游 `compact` 的做法（待摘要部分另组成一条请求、配专门的摘要系统提示、不请求推理）。用于：因上下文超长触发（决策 422）、整段放不下（`fitsWindow`：这段会话此刻的 token 数 + 摘要指令 + 摘要输出上限 超过模型窗口）、没有会话可接、接续式作废（请求出错或被拒、回复里有工具调用、回复没有文字）。
  - 两种发法的切点（`prepareCompaction`）、保留段、压缩条目与还原（`buildSessionContext`）相同；压缩条目的 details 另记 `summaryRequest`（发法；独立式另记原因）。
- `src/pi-runtime/adapter.ts`、`src/application/runtime.ts`：运行面把与主请求同口径的会话（token 数与按需组装的接续式请求）交给压缩器。
- `docs/configuration.md`：压缩一节写明两种发法与退回条件。

## 二、测试

- `src/pi-runtime/compaction.test.ts`"摘要请求的两种发法（决策 424）"：接续式时会话原样在前、末尾一条摘要指令，选项同会话另带输出上限与 `toolChoice: "none"`，切点、保留段与还原同独立式；超长触发、整段放不下、回复里有工具调用时走独立式。
- `src/application/runtime-compaction.test.ts`：接续式摘要请求经同一个模型接入发出、温度同主请求；主请求开思考时，接续式沿用主请求的推理档位。
- `src/pi-runtime/adapter-compaction.test.ts`：超长出错时的压缩重试（决策 422）仍成立。
- 接续式"回复没有文字""请求出错"退回独立式这两条，代码有处理，没有单独的用例。
- 施工方报告关键判定的变异验证全部变红并已还原（本审计未复核）。
