# 回炉接入容器施工记录（基线 2d2a56d）

分支 `stream-repair` 自 `stream-runner`（`2d2a56d`）拉出，合入 `repair-loop` 当时的头 `758d6dc`；回炉合并进 main 后整体变基到 main、线性化。本记录只写事实、选项、权衡与证据。（文中提交号均为当前分支历史里的提交；分支拉出时的起点只写分支名。）

## 一、执行端的"回到这一步起点"（决策 154②）

`repair-loop` 的撤回（`orchestration/checkpoint.ts`）直接调宿主 git 与宿主文件系统，遇到容器执行端即拒绝开回炉。本块在执行端接口上加一对可选能力，由容器实现提供：

- `markStepStart()`：开工时记下当前提交，以及当时已被忽略的路径（`git ls-files -z --others --ignored --exclude-standard --directory`，整个被忽略的目录只占一项）。
- `restoreStepStart(mark)`：先确认起点提交仍在库里，不在即抛 `StepStartLostError`，不做部分恢复；再 `git reset --hard <起点>`（agent 自己的提交一并撤掉）并 `git clean -fd`（不带 `-x`）；最后列出现在被忽略的路径，删掉开工时清单里没有的——即 agent 新建的被忽略文件与目录。

取舍：只做 reset 加不带 `-x` 的 clean 更简单，但会留下 agent 新建的被忽略文件（构建产物、缓存目录等），不满足"agent 新建的一概清掉"；带 `-x` 又会删掉开工时已被忽略的依赖目录。故采用开工时记下的忽略清单。集合差在跑批进程里算，要删的路径作为参数交给 `rm -rf`：容器里的 sh 为 dash，逐项处理 NUL 分隔的路径不便，且避免路径被 shell 拆分。按 `--directory` 的粒度，开工时已被忽略的目录之下后来多出的文件同样不动。撤回在容器里以镜像缺省的非 root 用户执行，文件属主保持一致。

证据：

- 用例（假 docker CLI 在本机执行命令，对着真实 git 仓库）："回到这一步起点：回到起点提交（agent 自己的提交也撤掉），删掉 agent 新建的一切含被忽略的，开工时已被忽略的不动"；"回到这一步起点：起点提交已不在库里即报错，不做部分恢复"。
- 变异均变红：不删 agent 新建的被忽略路径；开工时已被忽略的也删；不回到起点提交（只复原文件）；起点丢失不单独报错。
- 在 `pigeon-stream-strands:v3` 容器里实测：以 uid 10001 执行；agent 提交一次并新建未跟踪文件、被忽略文件与目录后撤回，提交数回到 1、已跟踪文件复原、新建的全部删除、开工时已被忽略的 `build/` 与 `pre.log` 保留，撤回后各文件属主仍为该用户。

## 二、两条流的分步验证配置

分步验证的形状与 `.pigeon/verify.json` 的分步配置一致（`version: 1`、`steps: [{name, command, cwd?}]`、`timeoutMs`）。每条流的运行方式带上自己的分步，跑批器在每个作业开始时把它写进该作业治理根下的 `.pigeon/verify.json`。这份文件只供事后查看这个作业验证的是什么，Pigeon 的验证不读它：跑批器每步把分步配置（各步名称、命令与执行目录）直接交给步 agent，Pigeon 步 agent 原样传给 headless 的分步验证（见本文"分步验证接到 Pigeon"一节）。strands 仓库也不忽略 `.pigeon/`，写进容器工作区会被当成 agent 的改动落地提交，故不写进容器工作区。

- 本仓库四步：格式（`npm run lint`）、类型（`npm run check`）、测试（`node --test --test-timeout=120000 "src/**/*.test.ts"`）、分层（`npm run deps`）。逐提交核对：清单范围内 93 个提交（起点加各步）的 `package.json` 里 lint、check、test、deps、verify 五个脚本逐字相同，没有缺失或不一致。
- strands 三步，都在 `strands-py` 下执行：ruff（`ruff format --check && ruff check`）、mypy、pytest（与原验证门的单测一步相同：带 `--continue-on-collection-errors`，报告写出后等 5 秒杀掉进程，看报告里有没有失败或出错的用例）。
- 验证门（维护步的判定）改由同一份分步派生：各步全跑、各带标题，任一步失败即不通过；失败之后的步照样执行，反馈里有每一步的结论。原先本仓库的验证门是 `npm run verify`，测试一步没有单用例超时；现在与分步一致。

mypy 的检查范围：在 v3 容器里对人的代码实跑派生的验证门，s1 起点 `003bd9f44` 上 ruff 通过、pytest 5289 条全过，但 mypy 报 "cannot read file 'tests_typing'"。该提交的 CI 只跑 `mypy ./src`，类型测试目录 `tests_typing` 由 `577a9d6a1`（2026-09-01）才加入。写死两个目录会让人的代码在窗口前段也过不了验证门，维护步随之判错，次要指标的类型错误数也取不到。改为 `mypy ./src $(test -d tests_typing && echo ./tests_typing)`，验证门与次要指标共用这一条。

用例："分步验证：本仓库四步……测试步带 120 秒单用例超时；strands 三步……都在 strands-py 下执行"（含 mypy 的写法与次要指标共用）；"验证门由分步派生：各步全跑、各自带标题，任一步失败即不通过（失败之后的步照样跑）"；跑批器用例增加断言：作业治理根下的 `.pigeon/verify.json` 与运行方式的分步一致。

变异均变红：测试步不带单用例超时；验证门遇到失败即停；pytest 步不在 strands-py 下（另使"strands 验证门……"变红）；验证门无视失败（同上）；验证配置不写进治理根。

对人的代码实跑派生的验证门（v3 镜像、2g 上限）的其余发现：

- strands 的 ruff 步：末端 `381ab48ab` 上 `ruff check` 通过，`ruff format --check` 报 8 个文件需要重新格式化（ruff 0.16.8，在其依赖声明的 0.13 至 0.17 范围内）。其 CI 的 lint 作业只跑 `hatch fmt --linter --check`（即 `ruff check` 与 mypy），不做格式检查。ruff 步改为只跑 `ruff check`；格式偏差仍计入次要指标。变异"ruff 步加上格式检查"变红分步验证的用例。

- strands 的 pytest 步：`003bd9f44` 上 5289 条全过，`381ab48ab` 上 6643 条通过、31 条跳过。

## 三、容器上的回炉与结果行

- headless：执行端提供"回到这一步起点"时，允许在容器工作区上开回炉（原先一律拒绝）；执行端不提供时启动即报错。第一个 Run 之前经执行端记下起点；每个 Run 结束后的验证经执行端在容器的工作区根执行（一行命令交 `sh -c`），取全量输出后按本地同一口径留尾部、计字节数与哈希；修满轮数或预算耗尽仍失败即经执行端撤回到起点，撤回失败如实记为 `restoreError`。容器工作区不在宿主占位目录上打快照。
- 延续式跑批："完整 Pigeon"与"去掉记忆"两个条件以回炉开启（3 轮）运行；验证命令由这条流的分步验证派生，与写进治理根的 `.pigeon/verify.json` 同源。回炉结果带回轮数、最后一次验证的结论（无法判定记 null）、是否撤回、撤回是否因预算先于轮数用尽、撤回失败的原因；结果行新增 `repairBudgetExhausted`，撤回失败的原因写进结果行的 `error`（跑批器随后仍按本步起点复原工作区）。
- 题面：开头每行一个本题测试文件的路径（相对仓库根），其后是提交信息与各测试文件全文。全文过长被截断时路径仍在；每一步落地后都提交，前面各步改过的测试不会被当成本题的题面测试。

测试用的容器以一个在本机执行命令的假 docker CLI 代替（`local-docker-fixtures.ts`），工作区是真实的 git 仓库。Windows 宿主上"容器内"的路径取 MSYS 形式，与 `readlink` 解析出的形式一致，路径围栏才比得对。

用例："容器上的回炉：验证经执行端在容器里执行，第一次失败、回炉一轮修好即通过"；"容器上的回炉：修满轮数仍失败即经执行端撤回——回到开工时的提交，agent 的提交、新建文件与新建的被忽略文件都清掉"；"容器上的回炉：执行端没有回到起点的能力即启动报错"；"Pigeon agent：开回炉的条件按分步验证在容器里回炉，修满轮数仍失败即撤回到这一步起点，结果带回回炉字段"；"Pigeon agent：不开回炉的条件不验证、不撤回，结果不带回炉字段"；题面生成与跑批器用例相应更新。原有的本地 git 回炉用例（38 条）照常通过。

变异均变红：执行端没有起点能力也放行；回炉验证不经执行端；撤回不经执行端；开跑前不记起点；回炉条件不开回炉；回炉结论不带回；题面不列测试路径（3 条用例）；预算耗尽不记进结果行。

## 五、结构化记忆经执行端读文件的接口形状

结构化记忆核验时要读文件、列出受跟踪的文件、用 git log 追踪改名。读文件执行端已有（`resolveExisting` 加 `readText`）；另两项作为可选能力加到执行端接口上，由容器实现提供，本地工作区待结构化记忆接入时补：

- `listTracked()`：`git ls-files -z`，路径相对工作区根；不含未跟踪与被忽略的文件。
- `fileHistory(path, limit?)`：`git log --follow --name-only`，新在前，每项给出提交与该提交上的路径（跨改名追踪）；不受跟踪即空。

用例："执行端的 git 查询：受跟踪的文件（不含未跟踪与被忽略的）；文件历史跨改名追踪，给出每个提交上当时的路径"（含带空格的旧文件名）。变异均变红：文件历史不跨改名；受跟踪清单混进未跟踪文件；文件历史不限条数。

## 六、v4 镜像定义与时过时不过的用例

v3 上对人的代码实跑验证门暴露的三件环境问题（第二节末），按以下方式在 v4 里处理：

- strands 的依赖按日期解析：每套组合按其起始提交的日期（UTC）解析依赖，uv 的 `--exclude-newer` 只取当时已发布的版本，替代原先按构建当天冻结的版本约束（删去 `constraints-*.txt`）。构建上下文新增 `env-dates.txt`（每行"组合 日期"）。原因之一：V0 环境里按构建当天解析出的 `aws_sdk_bedrock_runtime` 已没有 `BedrockRuntimeClient`，`test_nova_sonic.py` 在人的代码上整文件收集失败。
- strands 的 lint 环境：每套组合另建一个 Python 3.10 的 lint 环境（与其 CI 的 lint 作业同一版本；环境标记按 3.10 求值），装 ruff、mypy 与类型检查所需的依赖；运行环境（Python 3.13）不再装 ruff 与 mypy。PATH 上运行环境在前、lint 环境在后，`python` 落到运行环境，`ruff` 与 `mypy` 落到 lint 环境，验证门、次要指标与 agent 自己的命令都不写死路径。
- strands 选依赖组合：先找依赖声明与某组合起始提交完全相同的组合（各组合正是在依赖声明变化处切出来的，与"起始日期不晚于该提交的最新一套"一致，且不需要在运行时知道提交日期——agent 工作区里 HEAD 的日期是落地时间）；没有完全相同的，退回原先的偏好顺序。运行环境与 lint 环境一起切换。
- 本仓库镜像加 `NODE_OPTIONS=--max-old-space-size=1536`，所有 Node 进程统一生效。

时过时不过的用例：

- 探针对失败的用例重跑两次：本提交上重跑后通过即算通过；父提交上每次都失败才算父败。strands 的运行方式本就带 `--reruns 2`；本仓库的运行方式在给了重跑次数时，把含失败用例的测试文件再跑，原先失败、其间通过的用例改记通过，其余用例的结果不动。
- strands 的逐用例运行（探针、判题、全量测量、人的基准）与验证门的 pytest 步都带 `--reruns 2`，与其 CI 一致（五套组合的 pyproject 都声明了 `pytest-rerunfailures>=15.0,<16.0`）。`-v` 进度里 `RERUN` 行不算完成，以其后的最终结果为准；重跑途中被杀，这一条即正在跑的用例。
- 本仓库的验证门不加重试（其 `verify` 没有这一步）。已知的时过时不过用例：`src/persistence/event-log.test.ts` 的 `listSessionIds`（按字典序比较同一毫秒内生成的两个 ULID）；人的基准两遍对照会把这类用例标为时过时不过，不进 B 分母。

用例："-v 进度解析：--reruns 的 RERUN 行不算完成……"；"pigeon 逐用例结果：要求重跑时（探针），有失败的测试文件重跑至多两次……"（真实的 `node --test`，含跳过的用例）；取事实用例增加断言：探针每次都要求重跑两次；分步验证用例增加断言：验证门与逐用例运行都带 `--reruns 2`；"镜像构建上下文（strands）……与各组合起始提交的日期"。

变异均变红：探针不要求重跑；本仓库不重跑失败的文件；重跑把跳过的也改记通过（补了跳过的用例后变红）；strands 不带 `--reruns`；RERUN 行当成完成；构建上下文不带日期。

## 七、开跑前置检查

人的基准命令顺带做开跑前置检查：对每个要测的提交，人的代码在参考工作区里跑一次验证门（这条流运行方式里分步验证派生的命令），结果按提交落盘为 `<提交>.gate.json`（是否通过、没过的步、耗时、输出尾部），与用例基准同一排队、同一断点续算。`--check cases|gate|both` 选择算什么（缺省两者都做；本仓库那条流只做验证门）。结束时列出人的代码上验证门没过的提交、步序与没过的步，有则以非零退出——这些必须清零或逐个定夺，否则不开正式实验。

没过的步从验证命令的输出里取：分步派生的命令在某步失败时另打一行"== 步名 未通过 =="。

用例：基准命令用例增加断言：以"只在 src/b.txt 存在时通过"的验证门做检查，人的代码在前三个提交上没过、没过的步准确；重跑时结果从落盘读回（换成恒失败的命令结果不变）；分步派生用例增加断言：没过的步可解析。变异均变红：验证门没过的不进汇总；验证门结果不从落盘读回；验证脚本不标没过的步（2 条用例）。

## 八、结构化记忆经执行端访问工作区

本分支自 `structured-memory` 分支拉出，摘入执行端的"回到这一步起点"与只读 git 查询，只做记忆这一侧经执行端的改造，不碰回炉文件。结构化记忆原先碰工作区的地方全部直接走宿主文件系统与宿主 git；工作区在容器里时，派生会因"取不到工作区"把测试步的红转绿一律判为未知。改造如下：

- 执行端新增同步执行 `runSync`（容器实现为同步的 `docker exec`）：结构化记忆的探针与派生是同步的，经它在容器里查文件、跑 git。
- 工作区访问（`WorkspaceAccess`）：工作区在不在、在里面跑 git、取探针。本地实现即原有做法；执行端实现（`hostWorkspaceAccess`）把 git（`core.quotePath=false`）、文件在不在（`test -f`）与读文件（`cat`）都放在容器的工作区根执行，git 超时同样抛超时错误、探针照原规则锁定。探针的"文件在不在"与"读文件"改为可注入。
- 派生：开工时的脏文件、相邻快照间的改动、题面文件的认定都经工作区访问；派生与读取入口接受"按验证记录里的工作区路径取访问方式"的工厂，缺省本地。
- 挑选与核验：记忆推送给了执行端时，探针用执行端实现；以往会话记录里的工作区等于执行端的工作区根即经执行端派生（同一作业各步共用一个容器）；报错里的路径以执行端的工作区根为基准。
- 验证经执行端：分步配置各步在容器工作区里按各自的 `cwd` 执行（`cd <cwd> && <命令>`），单条命令同样；取全量输出后按本地同一口径留尾部、计字节数与哈希；验证记录里的工作区记执行端的工作区根。
- 开工时的树：执行端记下起点时，在临时索引上 `add -A`（不含被忽略的文件）写成树、挂在起点提交之下，得到"开工时的树"的提交（不动真实索引与工作区）。它与起点提交之差即开工时的脏文件（例如跑批器预置、尚未提交的人写测试），与宿主快照的改前基线同形；撤回时回到起点提交、清掉新建的之后，再检出这棵树并取消暂存，开工时预置的文件回到开工时的样子。把它按快照记录的同一形状写进账本，由 headless 在开跑前做，留到回炉合并之后接。

用例（容器以本机执行命令的假 docker 代替）：

- "经执行端派生：开工时的脏文件、快照间的改动、题面文件都在容器里查，与本地访问得出同样的事实"（并断言确实经执行端跑了 `diff-tree`）；
- "经执行端挑选与核验：开局按题面挑中、核验在容器里读文件通过；名字从报错所在文件里消失即被拦下"；
- "执行端探针：文件在不在、读文件、受跟踪清单、改名追踪都在容器里做；git 超时抛超时错误"；
- "经执行端验证：分步配置各步在容器工作区里按各自的 cwd 执行、各出结论……"与"单条命令的配置同样在容器工作区里执行"；
- 执行端 git 查询用例增加同步执行的断言；回到起点用例增加"开工时的树"与撤回后预置文件还原的断言；
- 原有结构化记忆用例（派生、挑选、题面测试、子目录）照常通过。

变异均变红：记忆推送不装执行端阶段；执行端 git 超时不报；派生不经执行端；验证不经执行端（2 条）；探针文件在不在不走注入（2 条）；经执行端验证不进子目录；撤回不还原开工时的改动；起点不记开工时的树。

## 十、容器上的起点记进账本与测试步的红转绿

第九节留下的缺口：容器模式没有宿主快照，起点的"开工时的树"不在账本里，派生对测试步的红转绿一律判为未知。裁决取 run.started 负载加可选字段，不新增记录种类。

- 形状：`run.started` 负载加可选的 `stepStart: { commit, baseCommit? }`（git 对象号），属尚未发布的账本 v17 的加法式演进（版本注释与 v16 → v17 迁移说明同步），不升版本。
- 写入：headless 在容器工作区开启回炉时，由执行端在第一个 Run 之前记下起点（`markStepStart`），经运行面装配以取值函数交给 adapter，每个 Run 开始时写进 `run.started`；一步里的每个 Run 同值。本地工作区不带本字段，起点照旧由快照记录的改前基线给出。
- 用途：`commit` 是这一步开工时的提交，`baseCommit` 是"开工时的树"挂在它之下的提交；两者之差即开工时的脏文件（跑批器预置、尚未提交的人写测试）。结构化记忆派生认定开工时的脏文件时，先取快照记录的改前基线，没有时取本字段的 `baseCommit`，经执行端在容器里比较。两者都没有（旧记录）按原规则判为未知，这一会话不产出测试步的红转绿。

用例（`structured-memory-container.test.ts` 第二条）："容器里的测试步：题面以外的已有测试被改坏、回炉修好记红转绿；跑批器预置未提交的题面测试首轮失败、回炉通过不记"。首轮改 `a.ts` 弄坏已提交的 `other.test.ts`，同时跑批器预置、未提交的 `preset.test.ts` 首轮失败；回炉一轮两者都修好。断言两个 Run 的 `run.started` 都带同值的起点且有 `baseCommit`，派生经执行端得出 `other works` 的测试步红转绿，`preset` 不记。

变异均精确变红：

- 派生不读新字段、缺起点时按"开工时没有脏文件"处理 → 预置的题面测试被误记（断言"预置的题面测试不记"变红）；
- 派生不读新字段、缺起点按未知 → 测试步红转绿判为未知（断言"题面以外的已有测试记红转绿"变红）；
- headless 不写新字段 → 起点断言变红；略过该断言后，"题面以外的已有测试记红转绿"变红（判为未知）。

相关用例（结构化记忆题面测试、容器上的回炉、本节两条端到端）照常通过。

## 十一、延续式跑批的完整条件接上结构化记忆

`CONDITION_SPECS` 里完整条件标着开启记忆，但 Pigeon 的步 agent 调 headless 时没有传结构化记忆的配置（留着"尚未建、暂时等同于关闭"的注释），完整条件实际与去掉记忆的条件相同。修法：

- 步 agent 按条件传配置：完整条件传开启、正常挑选（开局按题面指到的文件、回炉按报错指纹；固定挑选只用于定点对照的单步重跑），去掉记忆的条件传关闭。过时注释删除。
- 治理根的隔离：作业目录即 agent 的治理根，按"流-条件-遍次"命名，每个组合一个。结构化记忆从治理根里的以往会话派生，所以只在同一条流里沿步累积，不跨条件、遍次或流串用。跑批器在建作业目录处写明这一约束。

用例：

- "Pigeon agent：完整条件接入结构化记忆（开启、按题面与报错正常挑选），去掉记忆的条件关闭"：本机假 docker 上各跑一步，读账本里 `run.started` 的结构化记忆留痕，完整条件为开启且自动挑选，去掉记忆的条件不为开启。
- "治理根按条件 × 流 × 遍次隔离：……"：两个条件、两个遍次、每个作业两步，假 agent 记下收到的治理根；同一作业两步共用一个，四个作业两两不同。

变异均精确变红：完整条件不传配置（留痕缺席）；去掉记忆的条件也传开启（断言"不为开启"变红）；作业目录名去掉遍次（四个作业只剩两个治理根）。相关用例文件（步 agent、跑批器）照常通过。

## 十二、strands 的单条超时与重跑

现象：v4 清单探到第 148 步（562ada431，bidi 事件队列重构）时，探针在父提交一侧反复挂住，每一轮都挂到 960 秒的外层上限才被杀，靠"收回已完成用例、卡住的记为失败、剔除后续跑"逐条推进，两个多小时没探完这一个提交。

诊断（在 v4 与 v3 容器里分别复现，父提交一侧即父提交的代码配本提交的两个测试文件）：

- 本提交一侧在 v4 上 47 条用例 1.4 秒全过；父提交一侧缺少本提交的改动，若干用例在 asyncio 事件循环里挂住，v3 与 v4 表现相同，不是依赖版本问题（两边的 pytest、pytest-asyncio、websockets、pytest-timeout、pytest-rerunfailures 版本完全相同）。
- strands 的 pyproject 从区间起点到终点都配置了 `timeout = 90`（Linux 下缺省为 signal 方式），在 strands-py 下运行时一直生效。不带 `--reruns` 时，挂住的用例按超时判失败、接着跑下一条，一次运行写出完整报告（7 败 40 过）；带 `--reruns 2` 时，超时失败的用例被重跑，重跑里再挂住时超时不再生效，一直挂到外层上限。加 `--rerun-except Timeout` 后一次运行写出完整报告，普通失败照常重跑，超时失败不重跑。
- v3 清单里这个提交的探针记录（父 40 过 7 败、本提交全过）与上面的结果一致。

修法：

- strands 的 pytest 外壳（探针、判题、全量测量与人的基准共用）与验证门的 pytest 步都显式带 `--timeout <秒> --timeout-method signal --rerun-except Timeout`。单条超时：验证门、判题、全量测量与人的基准为 90 秒（与其仓库配置一致，同一口径）；探针为 30 秒（人的基准里最慢的用例为 4 秒）。外壳的单条超时作为参数传入，调用方不给时取 90 秒。
- 与其 CI 的差别：超时失败的用例不再重跑，其余失败照常重跑两次。
- "收回已完成用例、卡住的记为失败、剔除后续跑"保留为兜底，处理超时也打断不了的挂住。
- 已落盘的 26 个人的基准不重算：当时生效的是仓库配置的 90 秒 signal 超时加 `--reruns 2`，逐个检查没有任何卡死的用例，最慢一条 4.0 秒，重跑与超时的相互作用没有被触发，与新设置口径相同。

用例（假 pytest 增加一种"会挂住、但能被单条超时打断"的用例：只有给了 signal 方式的超时且超时失败不重跑时才按超时判失败，否则挂住）：

- "strands 逐用例结果：挂住的用例按单条超时（signal）判失败、照常写报告，不进卡死清单也不重跑；缺省 90 秒，探针给 30 秒"；
- 分步验证用例加断言：验证门的 pytest 步带 90 秒 signal 超时与 `--rerun-except Timeout`，外壳带传入的单条超时与同样的开关；
- 取事实用例加断言：探针的单条超时为 30 秒；人的基准用例加断言：人的基准与全量测量不另给单条超时（取 90 秒缺省）。

变异均精确变红：去掉 `--rerun-except`（挂住的用例落到兜底路径、记为卡死，验证门命令不符）；外壳不用传入的单条超时（探针的 30 秒变成 90 秒）；探针不给 30 秒；全量测量给 30 秒。步 agent、跑批器、取事实、逐用例运行、pytest 韧性运行的用例文件照常通过。

运行事实（清单续跑前的一处操作失误）：诊断时停掉了清单的后台任务，但它的 node 进程没有随之退出，诊断却在同一个探针容器的工作区里检出代码、杀掉 pytest。这期间该进程在同一容器里继续探了第 148、149 步，结论不可信；删除容器后它探完三个无测试的提交即退出。处理：检查点里第 148（562ada431）、149（83982c2e5）两条删除、续跑时重探（删除前另存备份），第 150 至 152 步无测试、不用容器，保留。之后停后台任务时，先按进程号确认进程已退出，再动它的容器。

## 十三、限额与上游故障的处理对两种 agent 对等

现状：Pigeon 在模型服务以错误收尾时自报被打断；最简 agent 只在限额控制器进入暂停时被看守杀掉（500 毫秒轮询状态），被上游 5xx 打断时启动器照常写出结果、按失败判分。跑批器只在"agent 报被打断、且全局限额信号数变了"时重做，其余被打断直接停下作业。两种 agent 遇到同一种故障，一个作废重做、一个判分，不对等。

修法：

- 网关按作业计上游故障：上游 5xx、连不上上游、200 之后中途断流各记一次；客户端自己断开（agent 撞上限被中止）不算。403 并发受限与额度仍交限额控制器，记为限额信号。
- 跑批器在每一步取得一路之后、agent 开始之前记下限额信号数与本作业的计量，agent 结束后比较：限额信号数变了（暂停、停止、并发受限降路）、本作业有上游故障，或 agent 自报被打断，这一步一律回到起点作废重做、不判分，不看是哪种 agent，也不看 agent 自己怎么处理了那次故障。前两种（有信号）不限次数，等放行后重做；只有 agent 自报、期间没有任何信号的，连续重做 3 次后第 4 次停下作业并说明，避免无限重做。
- 上游 5xx 按作业计，不进全局限额信号：一个作业撞上 5xx 只作废它自己的这一步，不连带作废并行作业的在途步骤。
- 限额控制器提供订阅：信号与状态一有变化即通知。最简 agent 的看守订阅它，这一步期间有任何限额信号（不只是暂停）即立刻杀掉启动器，500 毫秒轮询保留为兜底；这一步结束即退订。

用例：

- "限额与上游故障一律作废重做：……"（跑批器、假 agent）：两种 agent 各跑一个作业，第 1 步前四次分别遇到并发受限降路、本作业上游故障、5 小时额度暂停、agent 自报被打断，都写下会判错的改动、除自报那次外都不报被打断；第五次正常完成。两种 agent 各调用 5 次，各留一行、判为通过。
- "agent 连续自报被打断、期间没有任何限额信号或上游故障：重做三次后停下作业并说明，不无限重做"。
- "网关：上游 5xx 记为出事作业的上游故障、不算限额；403 并发受限与 403 额度记为限额信号"（真实网关、假上游）：5xx 只记在出事的作业上、别的作业为 0、限额信号不变；403 并发受限使信号加一、降一路、不暂停；403 额度使信号加一并暂停；403 不算上游故障。
- "命令式 agent：状态没变、只来了限额信号（例如并发受限只降路）也立即杀掉启动器，由订阅通知、不等轮询"，并断言一步结束即退订。
- 原有"被打断的一步整题作废不留行……"用例按新口径改为：没有信号的被打断重做 3 次、第 4 次停下作业。

变异均精确变红：跑批器不比较限额信号（前四次里写下的错改动被判分，两个作业都判为失败）；跑批器不看本作业的上游故障（同上）；网关不计上游 5xx（故障数为 0）；看守只看状态不看信号（启动器没被杀，结果里没有被打断）。

## 十四、正式开跑前的修复项

### 最简 agent 启动器的环境里没有真 key（决策 155）

启动器原先继承跑批进程的全部环境变量，真 key（KIMI_API_KEY 等）随之进入 mini-swe-agent 与 litellm 所在的进程。修法：拉起启动器时显式传入去掉密钥类变量的环境（名字里含 API_KEY、TOKEN、SECRET、PASSWORD、CREDENTIAL、PRIVATE_KEY、AUTH 的一律去掉），启动器只拿到请求文件里的网关地址与占位 key。

用例"命令式 agent：启动器的环境里没有密钥类变量（真 key 只在网关里），普通变量照常"：宿主环境里放几个密钥类变量，启动器把自己看到的环境写回，断言密钥类变量都不在、任何值里都不带密钥，普通变量与 PATH 照常。变异：拉起时传原样的宿主环境，用例精确变红（KIMI_API_KEY 进入了启动器的环境）。

### Pigeon 各条件一律无人值守放权

`eval stream` 原先把命令行的 `--yolo` 原样交给 Pigeon 步 agent：调用方忘了传，prompt 档的写与执行在无审批通道时一律被拒，条件就不再是"完整 Pigeon"。修法：装配层以 `streamPigeonOptions` 拼出 Pigeon 步 agent 的参数，放权固定为 yolo，调用方传了 false 也不算数；命令行不再传 `--yolo`，用法说明同步去掉。

用例"延续式跑批的 Pigeon 各条件一律无人值守放权（yolo），不依赖调用方传；调用方传了 false 也不算数"。变异：调用方的值覆盖固定值，用例精确变红（得到 false）。

### 本仓库流的验证门不走 npm run 脚本

本仓库流的四步验证原先是 `npm run lint`、`npm run check`、`npm run deps` 与测试命令，agent 改 package.json 里的脚本就能放松验证门。修法：写成与这几个脚本等价的显式命令——`node_modules/.bin/biome check .`、`node_modules/.bin/tsc -p tsconfig.json --noEmit`、`node --test --test-timeout=120000 "src/**/*.test.ts"`、`node_modules/.bin/dependency-cruiser src`。清单范围的首尾提交上这四个脚本逐字相同；工具取依赖目录里的可执行文件（npm run 同样是把它放进 PATH），在 v4 镜像里核对过三者都在且能执行。

用例：分步验证用例断言四步的命令逐字等于上述显式命令、都不含 npm。变异：格式一步改回 `npm run lint`，用例精确变红。

### 维护步用这条流的分步验证判定（决策 159）

### 最简 agent 在容器里的进程随一步结束清干净（决策 148）

### 暂存的改名不再中止作业（决策 148）

agent 用 `git mv` 一类方式暂存了测试文件的改名时，改动清单只给出新路径、且把它当作 HEAD 里已有的文件，于是"从本步起点恢复"对新路径执行失败、整个作业中止；被移走的人写测试也没有恢复。修法：改动清单对暂存的改名同时给出新路径（记为新建，并带原路径）与原路径；复制只记新路径（原路径没动）。还原测试时，从测试或测试辅助文件改名而来的新路径删掉（它正好是人在这一步写的文件时除外），原路径恢复成本步起点的版本。

用例"agent 暂存了人写测试的改名：原路径恢复成本步起点的版本、改名后的路径删掉，作业不中止"（落地的历史里原测试在、改名后的文件不在）。变异即改动前：用例精确变红（作业因"从本步起点恢复文件失败：pathspec 'src/moved.test.sh' did not match"中止）。

### 作废重做时清掉上一次尝试的痕迹（决策 144、160）

现象：一步作废时只把工作区回到本步起点，治理根（作业目录）下 `.pigeon/sessions` 里这次尝试的会话仍在。重做时会话检索能搜到上一次尝试的改动与报错，完整条件的结构化记忆还会从作废的会话派生事实；最简 agent 重做则从零开始，条件不对等。

修法：每次尝试前记下治理根里的会话文件清单；这一步作废时，把本次尝试新产生的会话文件移到输出目录下、治理根之外的 `voided/<作业>/step-<步序>-attempt-<次>/`（保留备查），并删掉结构化记忆缓存（`.pigeon/cache`），下次由其余会话重建（结构化记忆重建时本就丢掉账本里已不在的会话）。进程死在一步中途（被杀、整机重启）时同样有残留：每步完成时另记一份会话文件清单 `sessions-<步序>.json`（与 `passing-<步序>.json` 一样先于结果行写），续跑时不在上一个完成步清单里的会话一律移出。

用例："作废一步时清掉这次尝试的痕迹"（第一次尝试真实地跑一次 headless，会话落进治理根、生成结构化记忆缓存后报被打断；重做时会话检索按原文关键词搜不到、缓存不在、重建后的缓存里没有那次会话，隔离目录里有它）；"进程死在一步中途留下的会话"。变异：作废时不移出（重做时检索命中 2 条、缓存仍在）；续跑时不移出（残留会话仍在治理根）。

### 入库内容里的旧提交号

### agent 新建的 conftest 不影响判题与测量（决策 148）

strands 仓库 pytest 根目录下的 `strands-py/conftest.py` 对全部用例生效，归为测试辅助。判题之前（还原人写测试时），工作区里凡是测试辅助、又不在人在该步树中的文件一律删掉，因此也不会落地；候选取被跟踪的、相对本步起点有改动的与被忽略的未跟踪路径（agent 可以改 `.gitignore` 把自己的 conftest 藏起来）。全量测量的副本本就按人的测试与测试辅助集合同步（多出的先删），根 conftest 归类之后同样被删。选定"判题前从工作区删"而不是"在只含人写测试的干净副本里判题"：前者与既有的还原人写测试同一处、同一口径，判题仍在 agent 的工作区里做。

用例："agent 新建的 conftest 不影响判题与测量"（玩具仓库里用例脚本先加载 conftest，agent 写的 conftest 把 sh 换成恒成功的函数；错的实现照样判为不过，判题与测量时都没有 agent 的 conftest，下一步开始时也不在工作区里）；strands 归类用例加根 conftest。变异：判题前不删（错的实现判为通过）；不看被忽略的路径；根 conftest 不算测试辅助。

### pytest 一律用人在该步的配置

pytest 还读配置文件：agent 新建 `strands-py/pytest.ini`（优先级最高），或在 `pyproject.toml` 的 `[tool.pytest.ini_options]` 里加 `addopts`、`testpaths`，同样能改变用例的收集。修法：判题、全量测量、人的基准、开跑前检查与验证门的 pytest 步，一律按 pytest 自己找配置的先后（`pytest.ini` 有即用；`pyproject.toml`、`tox.ini`、`setup.cfg` 要含 pytest 段；一份都没有给空的 `pytest.ini`）从人在该步的树里取出那一份，原名写到工作区 `.git/pigeon-human-pytest/` 下（不在工作树里），pytest 以 `-c` 指定它、`--rootdir` 固定为 `strands-py`；找不到这份配置即报错退出，不退回工作区里的配置。`pyproject.toml` 的其余部分不替换（依赖环境本就按人的声明选）。跑批器在切依赖时写这份配置（agent 运行前、判题前、测量副本里）；参考工作区（人的基准、开跑前检查、生成清单时的探针）检出的就是人的树，从工作区里取。本仓库流用 `node --test`，没有这类配置文件。

用例："人的 pytest 配置按 pytest 自己的先后取"；"跑用例一律用人的 pytest 配置"与"验证门的 pytest 步同样用人的配置"（假 pytest 在没给 `-c` 时像 pytest 一样在当前目录找配置，配置里带 `-k nothing` 即一条都不跑；没写人的配置时验证门报错不通过）；"测试配置按人在该步的版本写入"；"等价表里的新摘要就是当前 strands 跑用例外壳的摘要"。变异：跑用例的外壳不带 `-c`；验证门的 pytest 步不带 `-c`；配置不按 pytest 的先后；跑批器写配置时读工作区而不是人的树。

输出目录里已有结果行、报告、作业目录或隔离目录，却没有 `identity.json`：认不出它们属于哪一次身份，拒绝续跑并报错，不补写身份头。用例一条；变异：不看已有结果、直接补写。

### 作废重做设上限（决策 144、160）

同一步因限额信号或上游故障被作废，累计 5 次向标准错误告警一次，累计 10 次停下作业并报错。计数在一次跑批进程之内，续跑重新计。用例一条；变异：多重做一次才停；第 5 次起每次都告警。

### 限额信号到来即中止在途的 Pigeon 步（决策 144、155）

### 还原时防绕过

- 跑批器还原人写测试之前先去掉工作区索引里全部条目的两种标记；回到本步起点（作废、撤回）时同样先去掉，否则 `reset --hard` 会跳过它们。
- 跑批器与执行端自己的 git 操作一律带 `core.hooksPath=/dev/null` 与 `core.fsmonitor=false`（跑批器经环境变量给出，优先于仓库的 `.git/config`），agent 放进 `.git/hooks` 的钩子与 fsmonitor 程序不被执行；agent 与判题的命令照旧。

用例："验证前还原受保护的文件"（执行端）；"还原人写测试防绕过"（跑批器：agent 给已落地的人写测试设标记再把它改成恒过、同时把代码改坏，维护步照样判为不过；装进 `.git/hooks` 的钩子没有被执行）。变异：还原前不去掉标记；工作区内部的 git 操作不屏蔽钩子；执行端沿用工作区索引比对；执行端不屏蔽钩子。

### 镜像 ID 与 Docker 的镜像存储

Docker 用 containerd 镜像存储时，`docker image inspect` 的 `{{.Id}}` 是 manifest 摘要；经典存储（overlay2 等）下是 config 摘要。人的基准、镜像等价表与身份头记的都是经典存储下的 config 摘要，`docker save` / `docker load` 在经典存储之间保持不变。取镜像 ID 之前先看镜像存储（`docker info` 的驱动状态里有 containerd 快照器即是），是 containerd 存储即响亮报错、说明改回经典存储的做法，不静默地换一套 ID。选这一做法而不是改取另一种摘要：已记下的 ID 全是 config 摘要，换一种摘要会让已算的人的基准与等价表全部对不上。既然 containerd 存储下一律拒绝，身份头不另记存储驱动。用例一条（假 docker 分别报两种存储）；变异：不认 containerd 存储。

## 二十一、多账号网关与单步内并发的确认

背景：正式实验改为 6 路并行，一个账号的并发上限不够用，模型服务改为多个账号共用。原网关是"双 key 轮换加共享退避"，任一 key 的限额信号都经控制器影响整批（并发受限降一路、额度用完整批暂停）。

修法（网关，只听回环地址的那一个进程内服务）：

- 一个 key 一个账号：`KIMI_API_KEY` 为账号 1，`KIMI_API_KEY_2`、`KIMI_API_KEY_3`… 依次为后续账号，编号须连续（跳号即报错，免得漏掉账号）；各账号的并发上限缺省 2，可用 `KIMI_API_KEY_<编号>_CONCURRENCY` 单独设。同一账号内不轮换 key。key 只在网关里注入，告警与交回客户端的正文里只出现账号编号。
- 派发：请求挑在途占比最低的可用账号；各账号都满即排队（先来先派），排队时间计入该步墙钟，也按作业记下。
- 429：该账号逐级退避（5、15、45 秒），退避期间请求派给其他账号；退避用满仍撞，该账号暂时不可用、请求换号。成功一次即退避级数归零。
- 403 额度：只停该账号，同一请求透明换号重试；按文案分出的 5 小时、每周、每月三种原因记在该账号上，每月额度用完的账号不再恢复。
- 403 并发受限：该账号的并发上限降 1 后重试；已是 1 仍受限，该账号暂时不可用。
- 暂时不可用的账号按 5 至 30 分钟的间隔单独探测，通过即恢复。
- 全部账号都不可用才交给限额控制器整批暂停（全部都是每月额度用完则停下）；控制器的探测经网关逐个探测账号，通过的恢复。控制器随之不再"并发受限降一路"：路数固定，并发由各账号的上限管。
- 单个账号不可用时，其余账号上的请求照常，不发限额信号，在途的步不作废；只有整批暂停才按原口径作废重做。
- 结果行新增 `gateway` 列：本步等空闲账号的累计毫秒、各账号成功转发的次数（按账号编号，不含 key）、本步内同一作业同时在途的模型请求数峰值（跑批器每步开始时重记）。身份头的 info（只记不比）增记账号数与各账号并发上限，路数原已记录。

单步内并发的确认：

- 三个 Pigeon 条件交给模型的工具恰为 read_file、edit_file、run_command、search_sessions、read_session_entry（跑批不给 skill、不配 MCP），没有派生子 agent 或 worker 的工具。工具要让模型看见，须同时在工具清单、放行清单与治理注册表里登记，缺一即不广告或启动报错。
- headless 的模型接入只有 agent 循环一个使用者；一轮里的多个工具调用在模型回复之后执行，不产生并行的模型请求；回炉的验证是命令，不调模型。
- 最简 agent（mini-swe-agent）每一步先请求模型、再执行动作，没有线程，一次只有一个请求在途。
- 正式跑里每行的 `gateway.peakInFlight` 给出四个条件的实测值；各账号的并发上限兜底。

用例与变异（均精确变红，变异后已复原）：

- 网关："多账号：一个账号 429 退避用满即该账号暂时不可用、请求换号，整批不暂停……"；"多账号：一个账号额度 403 只停该账号，同一请求透明换号重试；全部账号额度用完才整批暂停；探测恢复通过的账号"；"多账号：每月额度用完的账号不再恢复；全部账号都是每月额度用完即停下"；"多账号：每个账号在途不超过它的并发上限，满了排队；排队时间记到作业上……"；"多账号：作业的在途峰值……"；"账号配置：……"；单账号的 429、403 并发与 5xx 用例按新口径改写。变异：不看账号并发上限（排队用例红）；单个账号不可用即整批暂停（三条多账号用例红）；全部不可用不交控制器（五条红）；额度 403 不换号、原样交回（两条红）；排队时间不记（排队用例红）；并发 403 不降上限（单账号并发用例红）；探测不恢复账号（额度用例红）。
- 控制器："路数固定：限额信号不再降路……全部账号并发受限报来时整批暂停"。
- 跑批器：限额用例的假网关按步累加在途峰值，结果行断言 `gateway` 列；变异"每步开始不重记在途峰值"，该用例红（峰值 3，应为 1）。
- Pigeon 三个条件各一条"一步之内同时在途的模型请求至多 1 个（含一轮多个工具调用与回炉），工具清单里没有派生 agent 或 worker 的工具"：计数的模型接入让每次请求至少在途 20 毫秒，一轮两个工具调用加三轮回炉。变异：同一轮多发一个并行的模型请求（三条红，峰值 2）；给一个 skill 使工具清单多出 load_skill（三条红）；只在工具清单里加一个未登记的 spawn_worker 并放行（三条红，启动即报"广告的工具未在注册表登记"）。

## 二十二、合并前第三轮修复

以下各项均先补用例、再改代码，承重处做变异（改坏后对应用例精确变红，改回后通过）。本节改动了第二十节"agent 新建的 conftest 不影响判题与测量"与"pytest 一律用人在该步的配置"两处的做法，以本节为准。

### 判题前只删会影响人写测试收集的 conftest（决策 148）

现象：第二十节的做法在判题前删掉"人的树里没有的全部测试辅助文件"，候选里被忽略的路径用 `--directory` 列出，整个被忽略的目录（例如 pytest 一跑就会生成的 `__pycache__/`）只报一项、带结尾斜杠，被归为测试辅助送去 `rm -f`，删目录报错，作业停下。删除范围也过宽：agent 自己测试依赖的 helper 模块、数据文件、`__init__.py` 一并被删，后续维护步的验证门与回炉验证会因此失败。

修法：运行方式声明测试框架自动加载、会改变用例收集的辅助文件名（strands 为 `conftest.py`；本仓库流用 `node --test`，没有这类机制，不声明，也就不删任何测试辅助）。判题之前，工作区里叫这个名字、不在人在该步树里、且所在目录的子树里有人在该步的测试文件的，删掉，也就不会落地；只作用于 agent 自己测试目录的保留，其余测试辅助一律不动。候选按文件名逐个列出，被跟踪的、未跟踪的与被忽略的都列到（被忽略的目录往下展开，不折叠成目录；agent 可以改 `.gitignore` 藏它）。测量副本本就只放人的测试集，照旧。

用例："agent 新建的、落在人写测试目录树上的 conftest 不影响判题与测量"（错的实现照样判为不过，被 `.gitignore` 藏起来的也删）；"agent 自己测试的辅助文件保留"（helper、`__init__`、数据文件与只作用于自己测试目录的 conftest 都在，agent 自己依赖 helper 的用例使后续维护步的验证门照常通过；被忽略的 `__pycache__/` 与 agent 在 `.gitignore` 里写的整目录不让作业停下）。变异：一律删人的树里没有的测试辅助（后续维护步判为不过）；不删覆盖人写测试的 conftest（错的实现判为通过）。

### 人的 pytest 配置放到 agent 不可写的位置

现象：第二十节把人的 pytest 配置写在工作区 `.git` 下。判题、测量与人的基准之前跑批器会重写，那几处不受影响；但 Pigeon 回炉的验证门也读这份配置，agent 改了它就能骗过验证门，改坏的代码不被撤回。

修法：跑批器以 root 身份（`docker exec -u 0`）把人在该步的 pytest 配置写到容器里的 `/opt/stream/human-pytest/`（归 root、其他用户只读；v6 镜像里 `/opt/stream` 本身归 root 且不可写，stream 用户既改不了其中的文件，也删不掉、换不掉这个目录）。判题、全量测量、人的基准、开跑前检查与验证门（含 Pigeon 回炉的验证）一律从那里以 `-c` 读取；跑批器每次切依赖时重写。选这一做法而不是"每次验证之前重写一遍"：后者要在 Pigeon 回炉的每一轮验证前插入跑批器的操作，且两次重写之间 agent 仍可改它。

在 v6 容器里核对：root 写入后，以 stream 用户改写配置、在目录里新建文件、删除目录、改名目录一律被拒；工作区里放着 agent 写的 `pytest.ini`（`-k nothing`），旧位置（工作区 `.git` 下）也放一份同样的配置，验证门的 pytest 步照人的配置跑了两条用例、一过一不过，验证门不通过。

用例："人的 pytest 配置以 root 写到容器里 agent 不可写的位置，不写进工作区"（假 docker 记下参数：唯一一次调用带 `-u 0`、目标为 `/opt/stream/human-pytest`）；"容器里的 root 操作以 docker exec -u 0 执行，平常的命令不带"；验证门用例补上 agent 在旧位置写配置不起作用。变异：写配置不以 root 执行；pytest 读工作区 `.git` 下的配置（验证门被骗过）。

### 外部中止的空档（决策 144、160）

在记下这一步起点之后、第一轮运行之前再看一次外部中止，已中止即一轮都不跑；验证进行中收到中止，验证一结束即停，不再回炉，也不撤回（修满轮数后的最后一次验证中收到中止同样不撤回，由跑批器作废回滚）；没开回炉时收尾后的独立验证也不再做。用例一条（开工前控制器已暂停：模型一次都没被请求；修满三轮后的最后一次验证中途来了信号：没有撤回）。变异：开工前不看外部中止（模型被请求 2 次）；验证后不立即停（被撤回）。

### agent 留下的未解决冲突不再停下作业

现象：agent 留下未解决的 merge 或 stash pop 冲突时，去索引标记报"Unable to mark file"，作废时的回滚因此停下作业；合并进行中时"把 HEAD 挪回本步起点"的 soft reset 也会拒绝执行。修法：去标记、回滚与挪回起点之前，先去掉进行中的合并状态（MERGE_HEAD、CHERRY_PICK_HEAD、REVERT_HEAD 等），冲突路径按工作区里的样子暂存，使索引没有未解决的条目。用例一条（merge 与 stash pop 两种冲突，各在作废重做与照常收工两种情形下，作业都不停）。变异：挪回起点前不收冲突；去标记与回滚前不收冲突。

## 二十三、合并前第四轮修复

### conftest 的加载边界保持在 strands-py

现象：人的 pytest 配置移到 `/opt/stream/human-pytest` 之后，pytest 缺省的 confcutdir 变成配置文件所在的目录，工作区根（strands-py 之外）与测量副本根下的 conftest 从"不加载"变成"加载"，回炉验证门因此会加载 agent 放在工作区根的 conftest。

修法：strands 的全部 pytest 调用（判题、测量、人的基准、开跑前检查、验证门）显式带 `--confcutdir "$PWD"`，与 `--rootdir "$PWD"` 同指 strands-py，恢复原来的加载边界。在容器里核对（pytest 9.1.1）：工作区根放一个让用例全部跳过的 conftest，不带 `--confcutdir` 时两条用例都被跳过，带上后一过一不过。

用例："conftest 的加载边界保持在 strands-py：工作区根放一个让用例全部跳过的 conftest，跑用例与验证门都不加载它"。变异：不带 `--confcutdir`（该用例红）。

### 等价表跟上新命令

跑用例命令的摘要随上一项变为 `7d0b7803e11a57b5`（验证门命令摘要为 `79b6c71439beab9b`）。人的基准的等价表把此前的三个摘要 `da2746ca28858993`、`47c962cd27b0eefe`、`70f10b887f6bfdc1` 都对应到新摘要：同一份人的配置，rootdir 与 confcutdir 都是 strands-py，只是配置文件的位置不同；仍只在结果没有挂起迹象时读回。开跑前检查的结果不做等价，在服务器上重算。

### 每次回炉验证之前也删覆盖人写测试的 conftest

现象：第二十二节只在判题前删 agent 放的、覆盖人写测试的 conftest；Pigeon 回炉期间 agent 放的这类 conftest 照常生效，可以让失败的用例被跳过、骗过验证门而不被撤回。

修法：容器模式下每次验证（首轮与各轮回炉）之前，按与判题前相同的规则删除：名为 `conftest.py`、不在人在该步的树里、所在目录的子树里有人在该步的测试文件。候选改由文件系统遍历（`find`）列出，不只依赖 `git ls-files`，嵌套的 git 仓库与符号链接目录里藏的文件也列到；删除用 `rm -rf` 且不跟随链接：名为 `conftest.py` 的目录整个删，指向别处的符号链接只删链接本身，路径含空格、非 ASCII 字符或位于工作区根的都照常处理，作业不停下。

用例："Pigeon agent：每次回炉验证之前删掉 agent 放的、覆盖人写测试的 conftest——验证照样失败，修满轮数后撤回"；"删覆盖人写测试的自动加载辅助文件：按文件系统列（嵌套的 git 仓库里的也删），名叫 conftest 的目录整个删、符号链接只删链接本身；agent 自己目录的与人的保留"（另含空格、非 ASCII 与根目录路径）。变异：回炉验证前不删（回炉用例红）；候选只看版本库（嵌套仓库里的留下）；删除时不按目录删（名为 `conftest.py` 的目录留下）。

### Pigeon 验证前还原受保护文件遇到未解决冲突

与第二十二节跑批器一侧的做法相同：执行端在验证前还原受保护文件之前，先去掉进行中的合并状态，冲突路径按工作区里的样子暂存，再去标记与还原；不因 agent 的 stash pop 或 merge 冲突把这一步记成服务故障。去标记分两次执行（`--no-skip-worktree` 与 `--no-assume-unchanged` 各一次），因为同一次 `update-index` 调用只生效其中一个标志。用例："验证前还原受保护的文件：agent 留下未解决的合并冲突也照样还原，不报错"。变异：还原前不收冲突（该用例红）。

### 验证前的还原与清理期间到达的中止

还原受保护文件与验证前的清理（删覆盖人写测试的 conftest）之后、验证之前再看一次外部中止，已中止即不跑这次验证、不回炉，终态记 aborted。用例："容器回炉：验证前的还原与清理期间来了外部中止，不跑这次验证、不回炉，终态记 aborted"。变异：验证前不再看中止（跑了验证）。

### Pigeon 在容器里起的进程按步标记并清理

Pigeon 的容器执行端在这一步执行的每条命令都带环境变量 `PIGEON_STEP_MARKER`（每步随机生成），与最简 agent 同一做法；一步结束后按这个标记清掉仍在运行的进程，反复清到一轮里找不到为止，至多五轮；清不净或清理命令本身失败即报被打断，这一步作废重做。这样 agent 起的后台进程不会在步与步之间重新生成被删的 conftest 等文件。用例："Pigeon agent：这一步在容器里执行的每条命令都带本步标记，步结束后按同一标记清理残留进程；清不净即报被打断，这一步作废"（假 docker 记下每次调用的参数，清理命令分别回答 0 与 1）。变异：命令不带标记；清不净也照常交判题（该用例各自红）。

### strands 验证门与跑用例命令的最终形式

验证门三步，均在 `strands-py` 下执行：


跑用例（判题、测量、人的基准与开跑前检查共用；参数依次为报告路径、整体时限秒数、单条超时秒数与用例列表，单条超时缺省 90 秒）：

## 二十四、预算定值、试跑结果行与无人值守的重启

### 每步预算定为 150 轮、30 分钟（决策 147 的校准）

在正式实验的服务器上以完整 Pigeon、v6 镜像、5 路并发试跑 10 步：轮数第 90 百分位 78、墙钟第 90 百分位 857,745 毫秒（约 14.3 分钟）。按判据乘 1.5 后分别为 117 轮与 22 分钟，两项都低于下限，由下限起作用，定为每步 150 轮、30 分钟。正式跑批的缺省墙钟由 46 分钟改为 30 分钟，CLI 说明同步。预算属于身份头的比对项，以旧缺省开跑的输出目录不能以新缺省续跑。用例："正式跑批的预算缺省为每步 150 轮、30 分钟（147 校准）"。建议预算的判据用例仍用一组墙钟高于下限的数，以测乘 1.5 的一支。

### 试跑结果行带 gateway 列

试跑结果行新增 `gateway`，与正式结果行同形：本步等空闲账号的累计毫秒、各账号成功转发的次数、同时在途的请求数峰值，不经网关为 null。用例："试跑：……轮数与 token 取网关计量……"补断言。变异：结果行不带 gateway（该用例红）。

### 续跑接管已存在的流容器

现象：续跑时一律删掉残留的流容器，由镜像加导出的流历史重建。进程被杀或整机重启后，容器里被忽略的文件（agent 装的依赖、构建产物等）随之丢失，续跑的作业与没中断的作业状态不同。

修法：续跑时先看这个作业的容器在不在、用的是不是当前镜像（按镜像 ID 比）。是则停止的启动、仍在运行的重启（清掉上次留下的进程），核对库里有上一个完成步的提交，再把工作区回到那个提交：在途步的提交与改动一律作废，与作废重做同一口径，被忽略的文件保留。容器不在、镜像不同，或接管中任何一步出错，即退回原来的做法，由流历史重建，并记一行日志。限额控制器与网关的状态（暂停、各账号的可用与并发上限）只在内存里，重启后按网关当时的探测结果重新计算，不落盘。

用例："续跑接管已存在的流容器：停止的启动、仍在运行的重启；回到上一个完成步，在途步的提交与改动作废，被忽略的产物保留，不重建"；"续跑时残留容器用不上即由流历史重建：镜像不是当前的、库里没有上一个完成步的提交、容器已不在"。变异：接管不核对镜像（镜像不同时仍接管）；接管不回到上一个完成步（在途步的提交留下）。

### SIGTERM：在途的步作废，跑批停下

限额控制器新增 `shutdown(reason)`，与每月额度用完同一路径：计一次限额信号、通知在途的看守、状态置为已停止。两种 agent 在途的这一步随即中止并作废（回到本步起点、会话移入隔离目录、不留结果行），作业在取下一步时停下并记下原因；已完成的步保留，同一输出目录重跑即从作废的那一步续跑。

正式跑批的 CLI 收到第一次 SIGTERM 时交给控制器收尾，并设 90 秒的硬时限（低于单元的 TimeoutStopSec 120 秒）：正在判题或全量测量的步到时收不完即以退出码 143 直接退出，与进程崩溃同一续跑口径；再收到一次立即退出。按时收尾时作业以"停止"结束，进程退出码为 3。

用例："停止信号：与每月额度用完同一路径……重复收到不再计"；"停止信号（SIGTERM）：在途的一步作废、不留行，作业停下并说明；已完成的步保留，同一输出目录续跑从作废的那步重做"；"SIGTERM：第一次交给控制器收尾并设硬时限，到时仍没退出即以 143 退出；再收到一次立即退出；卸下后不再响应"。变异：停止信号不计信号（在途的步照常落地，用例红）；不设硬时限（用例红）。

### 输出目录的落盘

输出目录由 `--out` 指定，内容为：`identity.json`（身份头）、`results.jsonl`（结果行）、`report.md`（报告）、`streams/<作业>/`（流历史、测量基线、会话清单与治理根）、`voided/`（作废尝试的会话）；不给 `--baseline` 时另有 `reference/`（人的基准缓存）。

- 流历史、测量基线与每步的会话清单先写临时文件再改名；三者都写完才追加这一步的结果行。两者之间被杀时，断点仍指向上一步，续跑按上一步恢复，并把会话清单之外的会话移入隔离目录。
- 结果行逐行追加。进程死于写到一半会留下没有换行的半行，此前之后追加的整行会接在它后面、一起读不出来；现在开跑前先补一个换行把它隔开，读时照常丢弃这半行。用例："结果文件末尾留着写到一半的行（进程被杀）：续跑前隔开它，之后追加的结果行照常读得出"。变异：开跑前不隔开（第 2 步的结果行读不出）。
- 身份头改为先写临时文件再改名：原先写到一半被杀，续跑会因读不出身份头而一直被拒。
- 报告每次跑完整份重写，由结果行生成，不承载状态。
- 从外部拷走输出目录时，拷到的 `results.jsonl` 末尾可能带半行，按上面的口径读时丢弃即可。

### 正式实验的命令行与 systemd 单元

工作目录为仓库根，`ExecStart` 须用绝对路径。正式实验的命令行（尖括号为服务器上的路径）：

```
ExecStart=/usr/local/bin/node src/cli/index.ts eval stream --manifest <清单> --repo <人的仓库> --image pigeon-stream-strands:v6 --out <输出目录> --baseline <人的基准目录> --conditions full,no-memory,no-gate,minimal --concurrency 6 --mini-python <mini-swe-agent 的 python>
```

预算用缺省（每步 150 轮、30 分钟），不另给 `--max-turns` 与 `--wall-clock-min`；模型用缺省（kimi-for-coding）。账号从 `EnvironmentFile` 读：`KIMI_API_KEY`、`KIMI_API_KEY_2` 等依次为账号 1、2……，各账号的并发上限取 `KIMI_API_KEY_<编号>_CONCURRENCY`（缺省 2）。

与单元设置有关的事实：

- 作业停下（每月额度用完、同一步累计作废 10 次、连续被打断等）时进程以退出码 3 结束。`Restart=on-failure` 会在 30 秒后重启并续跑；每月额度用完时，重启后很快又会停下，每 30 秒重复一次。若不希望如此，可在单元里加 `RestartPreventExitStatus=3`。
- `systemctl stop` 发出的 SIGTERM 按上文收尾；systemd 不会因此重启。
- 容器由 docker 守护进程管理，不在服务的 cgroup 里，停服与重启都不会删掉它们；续跑按上文接管。

## 二十五、开跑前第五轮修复

以下各项均先补用例、再改代码，承重处做变异（改坏后对应用例精确变红，改回后通过）。符号链接与目录权限的用例在 Linux 上才建得出原生符号链接、才能让 chmod 生效，其余平台跳过；这几条的变异在 Linux 容器里跑。

### 人写文件路径上的符号链接（必须修）

现象：find 缺省不进入符号链接目录。某步新增人写测试目录（例如 `strands-py/tests/x/`）时，agent 把它换成指向别处的链接，在那边放一个跳过全部用例的 conftest；跑批器写人的文件用的是 `mkdir -p` 加 `cat >`，会顺着链接写到工作区之外，删 conftest 时又列不到链接那边，pytest 按链接路径加载那个 conftest，错的实现判为通过，链接还随落地提交。

修法：写入或删除人的文件之前（判题前的还原、每步开工时写入本步人的文件、测量副本里的写入），路径上凡是符号链接的一级（各级目录与文件本身）只删链接本身、不跟随，再建真目录；删不掉不让作业停下。判题前与各轮验证前列 conftest 候选时，路径上是人写测试的上级目录、本身却是符号链接的，一并按不跟随的方式删掉。回炉验证前还原受保护文件用的是 `git checkout`，它遇到路径上的符号链接会换成真目录、不顺着写（已在容器里核对），不另处理。

用例："写入人写测试之前，路径上被换成符号链接的目录与文件换成真的：不顺着链接写到工作区之外，按判题的方式加载 conftest 加载不到，错的实现照样失败；测量副本同样"；"删覆盖人写测试的 conftest 时不跟随符号链接：名为 conftest 的链接只删链接；人写测试的上级目录被换成链接的删掉链接本身，链接那边的目录与其中的 conftest 不动；agent 自己目录的链接保留"。第二十三节那条删 conftest 用例里"链接指向的文件不动"一句恒成立（链接名不是 conftest，本就不在候选里），已删去，由后一条用例覆盖。变异：写入前不删路径上的链接；上级目录上的链接不算候选；测量副本写入前不删链接（各自对应的用例红）。

### 作废尝试的痕迹对重做不可见（必须修）

现象：接管只做 reset 与 clean。最常见的接管发生在测量途中硬时限到、以 143 退出：此时测量副本里是第 N 步落地后的整份解，reflog 与 ORIG_HEAD 里有落地提交 N，重做第 N 步的 agent 能直接看到。作废重做同样只回滚工作区，agent 在被打断的尝试里自己做的提交留在 reflog 里。

修法：新增"丢弃作废的尝试"：回到断点提交，删掉 ORIG_HEAD、FETCH_HEAD、MERGE_HEAD 等伪引用与序号大于断点的开工树引用，清空 reflog，回收因此不可达的对象；接管时另清空测量副本。接管、作废重做与测量时依赖选择失败的作废三处都走它。agent 自己建的分支与 stash 不动，仍属第二十二节列出的已知限制。

用例："续跑接管已存在的流容器……作废那一步落地的提交在 reflog、伪引用、开工树引用、对象库与测量副本里都不留痕迹"（场景改为第 2 步已落地、正在测量时被停）；"作废重做前丢掉那次尝试在库里的痕迹：agent 在被打断的尝试里提交过，重做时 reflog 与对象库里都找不到那个提交"。变异：不清 reflog、不回收对象；接管只回到断点；作废重做只回滚工作区；不删多余的开工树引用；接管不清测量副本；不删 ORIG_HEAD（各自对应的用例红）。

### 回炉前删 conftest 与判题前同一口径（必须修）

现象：回炉验证前按"人写的测试与测试辅助文件"判断哪些 conftest 是人的，仓库根的人写 conftest.py（归为其他类）会在回炉时被删，并随 agent 的提交落地。

修法：跑批器把人在该步树里的全部路径交给 agent，回炉前删 conftest 按它判断，与判题前一致。

用例："Pigeon agent：回炉验证之前删 conftest 与判题前同一口径——人在该步树里的（例如仓库根的 conftest，不属于测试文件）不删、不改"；跑批器用例补断言交给 agent 的人树即人在该步树里的全部路径。变异：回炉前仍按人写测试文件判断；跑批器不交人树（各自对应的用例红）。

### 停止信号的代码侧兜底（必须修）

限额控制器单独记下"收到过停止信号"及原因（不借用信号计数，暂停也会加计数）。一步做完、写流历史与结果行之前，若这一步开始之后收到过停止信号，即丢弃这次尝试（回到本步起点，清理同上），按作废处理、不写行；作业在取下一步时停下。不论 systemd 的 KillMode 如何，被停止信号打断的判题或测量都不会写出错行。

用例："停止信号在判题或测量期间到达：这一步作废、不写行，作业停下；续跑重做这一步"（两处各一遍）；控制器用例补"暂停不算停止信号"。变异：写行之前不看停止信号；控制器不记停止原因（各自对应的用例红）。

### 因停止信号停下时留着作业容器（应修）

第二十四节"停服与重启都不会删掉它们"一句在本修复之前不属实：作业因停止信号停下时照常删掉作业容器，重启后一律由流历史重建，接管在最常见的场景下不会发生。现改为因停止信号停下的作业不删容器；排队的作业在开容器（接管或重建）之前先等限额控制器，已停下即不再开。用例："因停止信号停下：在途作业的容器留着（续跑接管），排队的作业不再开容器"。变异：停下也删容器；开容器之前不看控制器（各自红）。

### 回炉各轮验证之前清进程并删验证门报告（应修）

Pigeon 回炉的每次验证之前，先按本步标记清掉 agent 留在容器里的后台进程，再删掉验证门的报告（`/tmp/pigeon-gate-junit.xml`），最后删覆盖人写测试的 conftest；清不净即中止这一步、报被打断。验证前的这组清理挪到还原受保护文件之前，后台进程因此来不及在还原之后再改受保护的文件。防的是后台进程在验证期间重建被删的 conftest，或预先写一份全过的报告被验证门采信。用例："每次回炉验证之前先按本步标记清一遍后台进程、删掉验证门的报告，步结束后再清一遍"（按调用顺序断言）；"回炉验证之前清进程清不净即中止这一步、一次验证都不跑，报被打断"。变异：验证前不清进程；不删报告；清不净也照常验证（各自红）。

### 输出目录单实例锁（应修）

正式跑批与试跑开始时对输出目录取排他锁（`run.lock`，与项目里其余跨进程锁同一做法：锁文件记持有进程，持有者仍在即拒绝并报出其 pid 与锁文件路径，已不在的残留锁由下一个进程接管），结束时释放。用例："输出目录单实例：另一个跑批进程正占着同一输出目录即拒绝，报出占用者；持有者已不在的残留锁照常接管"。变异：不取锁（用例红）。

### 列候选时容忍不可读的目录（应修）

agent 把目录改成不可读（chmod 000）时，find 以退出码 1 结束，原先会让作业停下。列 conftest 候选与列符号链接时容忍这类报错，照样用列出来的（以同一身份运行的 pytest 本来也读不到那些目录）。用例："列 conftest 候选时容忍不可读的目录（agent chmod 000）：不让作业停下，照样删掉覆盖人写测试的 conftest"。变异：列候选时不容忍（用例红）。

### 清进程后删残留的 index.lock（应修）

清进程恰好杀掉 agent 在途的 git 命令时会留下 `.git/index.lock`，跑批器下一次 git 操作失败、作业停下。清完进程后，容器里没有 git 进程在跑，就删掉它。两种 agent 同一函数。用例："清完进程后容器里没有 git 进程在跑，就删掉残留的 .git/index.lock"。变异：不删（用例红）。

### 验证（分步）

各项的用例文件单独跑过，符号链接与目录权限类在 Linux 容器里跑；lint、check、deps 在整合之后的头上通过；全量测试由服务器补跑。

### 已知限制

- 维护步的判定用同一个 pytest 验证门。agent 在自己目录里的 conftest（不覆盖人写测试、不会被删）可以用会话级钩子跳过人写用例，使维护步判为通过；只影响维护步（strands 5 个、本仓库 10 个），需要 agent 刻意为之。
- 由流历史重建时，断点提交不在流历史末端（导出流历史之后、写结果行之前进程被停）的一支没有用例。

## 二十六、多账号网关复核后的补修

复核确认主路径正确（pick 之后同步计数、不超上限；换号重试只在响应头阶段；中途断流计上游故障并作废；单账号 429 与 403 透明处理；全部不可用才暂停；计量只计 200；key 不外露；没有忙等）。以下各项在正式开跑前补上。

必须修：

1. 在途计数泄漏。原先读 429/403 错误正文的 `await upstream.text()` 在释放位子之前、且没有 try/finally：客户端中止或上游在错误正文中途断开时 text() 抛错，该账号在途永久多 1，两次即永久满，最坏全部账号卡死、请求永远排队。修法：每次尝试从占位到结束包在 try/finally 里，位子一定释放（只释放一次）。
2. 429 退避。原先每撞一次 429 就升一级，同时在途的几路一起撞会连跳几级；冷却定时器也不分新旧，旧定时器会提前结束新的冷却，单账号约 5 秒即可能整批暂停。修法：账号记"退避轮次"，每开始一次冷却、每恢复一次可用加一；请求记下派出时的轮次，只有本轮派出（冷却结束之后派出）的请求撞 429 才升级；轮次兼作冷却定时器的代次号，只有本轮的定时器能结束冷却；本轮之前派出的请求成功不把级数归零。口径为 5、15、45 秒逐级退避，45 秒之后仍撞才判该账号不可用。
3. 探测占额度。原先探测不经占位、不计在途，暂停时单独探测与控制器的探测会同时打同一账号。修法：探测占该账号一个在途位子（满了等空出）；同一账号同一时刻至多一路探测，其余调用复用它的结果；控制器的 `probe()` 跳过正在单独探测的账号（由那一路负责，恢复时通知控制器）。

开跑前必须完成：

4. 认证失败的账号。开跑前 `preflight()` 逐账号发一次极小请求，任一账号认证失败即拒绝开跑并报出账号编号（不含 key），额度类结果只告警、开跑后照常处理；运行中遇到 401 或认证类 403，该账号停用（记为 `auth`，不探测恢复、需人工处理），这次请求交回（正文去 key）并记为本作业的上游故障，这一步按上游故障作废重做，不以认证错误判题；全部账号都不可用时按原规则暂停，都不会自行恢复（每月额度用完或认证失败）则停下，有认证失败时停下原因说明需人工检查 key。`classifyUpstreamFailure` 把 401 归为认证。
5. 排队影响的步作废。常量 `QUEUE_VOID_MS = 30_000`（`model-limits.ts`）：正常情况下路数不超过各账号并发之和，不应排队；一步等空闲账号累计超过 30 秒，说明有账号受限（退避中、停用或降了上限），这一步受了限额事件影响，与上游故障同一口径作废重做（不看 agent 种类），计入"限额信号或上游故障累计作废"的次数。恰为 30 秒不作废。计量读出的 `queueMs` 含此刻仍在排队的请求已等的时间，agent 在排队中撞墙钟被杀的一步也能被认出。
6. 403 并发。请求派发时记下该账号当时的上限：只有在上限已是 1 时派出的请求再受限才判该账号不可用；上限只在派出之后没降过时才降（同时受限的几路只降一次）；降上限后等 3 秒（`CONCURRENCY_RETRY_DELAY_MS`）再重试。

应修：

7. 排队中的请求被客户端中止即刻出队，作业在途即时减一，排队时间只记到中止为止、不记到下一步；`resetPeak` 不受残留影响。
8. 网关的计时（退避、单独探测间隔、并发重试等待、上限回升）都经可注入的时钟，`close()` 取消全部未到的定时、提前结束等待中的 delay、中止在途探测；控制器的缺省计时在恢复、停下或 `close()` 时取消，跑批收尾调用 `limits.close()`。
9. 暂停期间某账号单独探测恢复，网关即调用控制器新增的 `recovered()` 立即恢复整批，不等下一轮探测；控制器的探测循环只管开它的那一次暂停（看暂停编号），醒来发现已恢复或已开新暂停即退出。`probe()` 全部账号可用时逐个都探。
10. 因 403 并发降下的上限每 30 分钟（`CAP_REGROW_MS`）回升 1，最多回到配置值；账号不可用期间不回升、继续等。
11. 单独探测发现账号已转为每月额度（或认证失败）即停止探测；最后一个能恢复的账号转为不会恢复即整批停下。
12. 账号配置：编号变量超过 `MAX_ACCOUNTS`（9）、`_CONCURRENCY` 指向不存在的账号、设了 `KIMI_API_KEY_1`、编号写法不对（如 `_02`）都响亮报错；空值等于没设。
13. 过时注释与测试名："并发受限降路"改为现行口径（全部账号都不可用时的整批暂停或停止；状态没变、只来了信号的例子改为"整批暂停后账号随即恢复"）。
14. 身份头：续跑时路数、账号数或各账号并发上限与最近一条不同，即在 `identity.json` 的 `infoLog` 追加一条 `{ since, info }`，结果行 `gateway.accountRequests` 的长度据此对上当时的账号数；只换跑批器代码不追加；`info` 与 `infoLog` 都不参与身份比对。

## 二十七、按剩余容量放行（决策 163）与网关的第二轮补修

背景：排队作废（一步等空闲账号累计超过 30 秒即作废重做）原以"路数不超过各账号并发之和、正常不排队"为前提。某个账号撞上 5 小时额度被停用、或并发上限被调低后，可用容量会在数小时内低于路数，几乎每步都排队超时作废，同一步作废满 10 次即停下该作业并连锁停下全部作业，每次作废前该步还跑满预算、消耗剩余账号的额度。

修法（决策 163）：

- 可用容量：网关按账号统计，等于未停用账号（额度停用、认证停用、三级退避用尽后判为不可用的）当前并发上限之和；429 退避在三级之内属秒级波动，退避中的账号照算，不计入容量下降。网关提供 `capacity()` 查询与 `subscribeCapacity()` 变化通知，在账号停用、恢复、上限降低与回升时通知。
- 放行：做在跑批器共用的"每步前等放行、agent 运行时占一路"那套机制里——限额控制器的 `acquire()`。同时在跑的 agent 数须小于可用容量且不超过配置路数，否则在步与步之间等；网关容量一变即通知控制器 `capacityChanged()` 放行。等待发生在 agent 开始之前，不计入该步的墙钟预算，不作废、不耗额度；`acquire()` 返回的释放函数带 `waitedMs`，写进结果行的 `admissionWaitMs`（stream-trial 的结果行同名字段）。
- 公平：等待的各路按先来后到放行（控制器的等待队列先进先出，空出一路或容量回升都从队首放行），不区分条件，各条件公平。
- 正式跑批与预算试跑共用：新增 `runAdmittedAgent`（`stream-runner.ts`）把"等放行 → 记限额信号数与本作业计量 → 看守排队 → 跑 agent → 算差 → 判作废"合成一处，正式跑批的 `runStep` 与预算试跑（`stream-trial.ts`）都调用它，放行、按步中止与作废判定同一口径；试跑原先不看排队超时，现随之一起作废。
- 在途中止：网关新增 `watchQueue(作业, 阈值, 回调)`，作业自登记起累计等空闲账号超过 `QUEUE_VOID_MS`（30 秒）即回调一次（有请求在排队时按"剩余额度 ÷ 在排队的请求数"定时复查，排队开始与结束时也复查）。`runAdmittedAgent` 据此立即经按步中止停下这一步：`StepAgentInput` 新增 `abortSignal`，两种 agent 与限额信号走同一条路径（Pigeon 中止 headless；最简 agent 杀掉启动器、按标记清掉容器里的进程），报被打断；回滚、作废，等放行后重做，不再等 agent 跑完才判。仍计入 `SIGNALLED_VOID_STOP`：有了放行，同一步反复排队作废说明真有故障。事后才查到超过 30 秒的（没来得及看守的）照原口径作废。
- 开跑前校验：`assertConcurrencyFits`，配置路数大于各账号配置并发之和即拒绝开跑，报出两个数（不含 key）；正式跑在写身份头、起网关与容器之前做，试跑同样。注意：只设 `KIMI_API_KEY`（并发缺省 2）时，缺省 4 路会被拒绝，须减路数或加账号。
- 全部账号不可用：沿用原有的整批暂停与停下规则（容量为 0 时控制器本已暂停）。
- 正式跑与试跑起网关与控制器改为同一个函数：控制器按网关容量放行、订阅容量变化、开跑前逐账号探测，未通过即关掉两者；试跑原先缺开跑前探测与 `limits.close()`，一并补上。

应修：

- 环境变量：`KIMI_API_KEY_` 前缀下认不出的变量名（如没有编号的 `KIMI_API_KEY_CONCURRENCY`、拼错的 `_CONCURENCY`）一律报错，只写变量名、不写取值；取值为空的也报。
- 认证分类收窄：运行中只有 401 与文案明确是认证问题的 403（authentication、unauthorized、invalid api key、api key 失效或吊销、认证失败、密钥无效等）才算认证失败、停用账号；其余认不出的 403（单写 forbidden、permission denied 等；5 小时额度用完也是 permission_error）按 other 原样交回客户端、记上游故障（这一步作废），不停用账号。开跑前探测：凡不是成功、也不是额度、并发、限流的（认证失败、认不出的回应、5xx、连不上），一律拒绝开跑，报出账号编号与原因。
- 关闭之后不再新设定时：网关的 `later()` 与控制器的 `pause()` 在已关闭时直接返回。
- 客户端断开的监听提前到读请求体之前注册，读请求体期间断开也能认出（读完即返回、不转发）。这一条没有补用例：读请求体期间断开时 Node 通常让读请求体本身抛错，旧写法同样不转发，差别只在读完与注册之间的微任务窗口，难以确定性地构造。
- hang 模式的用例去掉 80 毫秒真实等待：假上游回 429 头与半截正文后停住，用例经 undici 的诊断通道 `undici:request:headers` 得知网关一侧已收到响应头，清空一轮微任务后网关必然停在读错误正文上，再中止客户端或断开上游；drop 模式同样改为确定性断开。
- 排队作废的跑批器用例改为 Pigeon 与最简 agent 各跑一遍，绑定"不看 agent 种类"。

用例：控制器新增 3 条（放行取小与先来先放、等待时长与停下时退出、关闭后不开暂停），改写 1 条（上游失败分类按认证收窄）；网关新增 6 条（认不出的 403 按 other、前缀下认不出的变量名、开跑前路数校验、可用容量与通知、排队看守、关闭后不设定时），改写 3 条（开跑前探测改为一律拒绝、认证 403 的文案、在途不泄漏改为确定性）；整体用例 `step-admission.test.ts` 2 条（虚拟时钟：6 路、3 个账号各 2，账号 2 额度停用后同时在跑的不超过 4、排队超 30 秒的在途步被及时中止并在放行后重做、容量不足三小时不停作业不再作废、账号恢复后回到 6 路、等待的各路先来先放行、开跑前校验拒绝 7 路；429 退避期间容量与放行数不下降）；跑批器 2 条（排队作废的 Pigeon 版与最简 agent 版：在途按步中止、事后超时作废、恰为 30 秒不作废、结果行记放行等待）；最简 agent 1 条（按步中止即杀掉启动器）；试跑断言结果行记放行等待。

## 二十八、两路修复的整合

第二十五节（开跑前第五轮修复）与第二十六、二十七节（网关两轮补修与按剩余容量放行）分头进行，按先后线性合在一起，两边的行为都保留：

- 停止信号与放行队列合在同一个限额控制器上：收到停止信号即停下，放行队列里在等的全部以停止原因释放、不被放行，此后取新步一律拒绝。整合时发现一处竞态：取步者通过 ready() 之后、进入放行队列之前若恰好收到停止信号，停下时的唤醒已经发过，这个取步者会一直等下去。修法：进入放行队列之前再看一次是否已停下。用例："停止信号与放行队列：取步者刚过放行门、尚未入队时收到停止，以停止原因释放、不被放行；之后取新步一律拒绝"。变异：放行前不再看是否已停下（用例超时失败）。
- 一步的 agent 走第二十七节跑批器与试跑共用的放行与作废判定（限额信号、本作业上游故障、排队超时、agent 自报被打断），作废时按第二十五节丢弃作废尝试的痕迹；第二十五节"一步开始后收到过停止信号即作废、不写行"的检查在写流历史与结果行之前照常进行，因停止信号停下的作业留着容器。
- 试跑结果行同时带 gateway 列（第二十四节）与放行等待（第二十七节）。

### 权限报错不再被吞（必须修）

现象：第二十五节让列 conftest 候选时吞掉 find 的报错。agent 把某个目录设成能进不能列（0311），在其中可读的子目录里放一个覆盖人写测试的 conftest，find 列不出它、不删，pytest 却能按路径加载，可以把结果改成全过。写人的文件时链接删不掉也只是放过，会顺着链接写到工作区之外。

修法：
- 回到本步起点（每步开工、作废丢弃、接管都经过这里）、判题前还原人写测试之前、删 conftest 之前，先对工作区做 `chmod -R u+rwX`（跑批器与 agent 以同一身份运行，做得到；尽力而为）。
- 之后列候选不再吞报错，仍报错即抛"工作区访问错误"。
- 写或删人的文件时，路径上的链接删不掉同样抛这个错误，不顺着写出去。
- 路径上某一级是普通文件（人的树规定那里是目录）时，删掉它再建目录。
- 跑批器在判题前遇到这个错误，丢弃这次尝试、作废重做这一步，不停作业。Pigeon 在回炉验证前遇到，中止这一步、报被打断。

用例：
- "删 conftest 之前先放回属主权限：agent 把目录设成能进不能列（0311），里面可读的子目录放一个覆盖人写测试的 conftest，照样找到并删掉"（先确认目录确实列不出，否则不做断言）；
- "写人的文件时路径上的链接删不掉：报访问错误（调用方把这一步作废），不顺着链接写到工作区之外"；
- "写人的文件时路径上某一级是普通文件（人的树规定那里是目录）：删掉它、建目录再写"；
- "判题前列 conftest 候选遇到 agent 设下的访问障碍：这一步作废重做，不停作业、不写错行"。

变异（各自对应的用例红）：
- 删 conftest 前不放回属主权限；
- 链接删不掉也放过；
- 路径上的普通文件不删；
- 访问错误不转为作废。

"放回权限之后 find 仍报错"要靠另一个系统账户才能造出来，没有单独的用例；这一支由跑批器用例里注入的访问错误覆盖。

### 输出目录锁在一切动作之前取（必须修）

第二十九节已把锁提前到正式跑批与试跑的入口：先取锁，再读清单、写身份头、起网关探测、删建参考容器（参考容器名由输出目录的哈希得出，与正在跑的进程同名）。撞锁即报错退出，不做任何清理。本节不另改。

### 残留锁判定加开机编号与进程启动时刻（必须修）

90 秒硬时限走 `process.exit(143)`，断电也不执行收尾，锁文件都会留下。整机重启后，旧 pid 可能被别的进程占用，于是一直报"持有进程仍在"，每 30 秒重试一次，永远起不来。

修法：项目里的独占锁在锁文件里另记开机编号（`/proc/sys/kernel/random/boot_id`）与持有进程的启动时刻（`/proc/<pid>/stat` 第 22 列）。pid 存活但这两项任一与现在不符，即按残留接管。取不到这两项的系统，或旧锁文件里没有它们，退回只看 pid。

用例："独占锁：记下的开机编号或进程启动时刻与现在不符（整机重启、pid 被复用）即按残留接管；真在跑的持有者照常拒绝"。变异：不看开机编号；不看启动时刻（各自红）。

### 作废与接管后的剩余痕迹（应修）

丢弃作废的尝试（作废重做、接管、由流历史重建三处）补齐以下清理：
- 伪引用补上 REBASE_HEAD，并删掉 rebase-merge、rebase-apply、sequencer 目录（后者以补丁文件存着提交的完整改动）。
- HEAD 放回 main 并指向断点提交。除 main 与不超过断点的开工树引用外，全部引用一律删掉，包括 agent 建的分支、标签和 refs/stash。容器执行端下 Pigeon 的占位工作区不是 git 仓库，不建检查点引用，库里本无其他合法引用。
- worktree 登记整个删掉，工作区之内的 worktree 目录一并删掉。
- `git clean` 用两个 `-f`，删掉未跟踪的嵌套仓库，被忽略的文件照旧保留。
- 清空 reflog 之后先 `git repack -a -d` 再回收对象，被自动 gc 打进包的提交也找不到。
- 由流历史重建之后同样丢弃一遍：流历史里可能带着断点之后那一步落地的提交。
- 作业容器的 /tmp 清空（见下文闸门）。

用例：
- "丢弃作废的尝试：agent 留下的分支、标签、stash、rebase-apply、worktree 登记、未跟踪的嵌套仓库与打进包的提交，丢弃后都找不到；工作区之外的路径不碰；main 与不超过断点的开工树引用保留；不在作业容器里时临时目录不动"；
- "由流历史重建：流历史里带着断点之后那一步落地的提交……重建后同一口径丢掉，库里找不到它"。

变异（各自对应的用例红）：
- 回收前不重新打包；
- 只删多余的开工树引用；
- 不删 worktree；
- clean 只用一个 -f；
- 不删 rebase-apply 等目录；
- 删 worktree 目录不限定在工作区之内；
- 重建后不丢弃。

### 清进程不依赖标记（应修，先核对了前提）

agent 用 `env -u PIGEON_STEP_MARKER` 或 `env -i` 起的后台进程不带标记，按标记清不到。前提核对如下：
- 作业容器里没有跑批器自己的常驻进程：执行端、网关与限额控制器都在宿主上，容器里只有一次次的 docker exec。
- 每个作业独占一个容器。
- 清进程发生在 agent 跑完之后或 Pigeon 回炉验证之前，这两个时刻跑批器都没有并发的 exec。
- 例外：本机测试的假 docker 把"容器里"的脚本放在本机执行，"除 init 外全清"会杀掉本机上无关的进程。

修法：
- 跑批器起作业容器时带 `PIGEON_STREAM_CONTAINER=1`。
- 在作业容器里（见下文闸门），清进程时除 PID 1（init）、容器主命令（PID 1 最早的子进程）、清理脚本自身及其子进程外全清，僵尸进程不计。
- 不在作业容器里，仍只清带本步标记的进程。

用例："作业容器里清 agent 进程不看标记：用 env -u 起的后台进程照样清掉，init 与容器主命令不动、容器照常运行"（真 docker 容器）。变异：全清时不跳过容器主命令（容器退出，用例红）。

### 残留 git 锁文件只看工作区里的 git 进程（应修）

清完进程后，只有没有工作目录位于工作区下的 git 进程时，才删残留的锁文件，容器或宿主上别处的 git 进程不相干。原先只要有任何 git 进程在跑就不删，服务器并行跑全量测试时会因别的用例文件的 git 进程时红时绿。锁文件一并覆盖 HEAD.lock、packed-refs.lock 与 refs 下的 *.lock。接管（容器重启）之后、回到断点之前也清一次，否则 reset 被残留的 index.lock 挡住，接管退回重建。

用例：
- "残留的 git 锁文件：只在工作区下没有 git 进程在跑时删（index.lock、HEAD.lock、packed-refs.lock、refs 下的 *.lock）；别处的 git 进程不相干"；
- 接管用例的场景里留一个 index.lock。

变异（各自红）：
- 有任何 git 进程在跑就不删；
- 只删 index.lock；
- 接管前不清。

### 已停下后再收到停止信号（应修）

因每月额度或认证失败已经停下后，再收到停止信号也记下原因，作业容器照停止信号的口径保留、续跑接管，不再计信号。用例："已因每月额度停下后再收到停止信号：照样记下停止原因（作业容器按停止信号保留），不再计信号"。变异：停下后不记原因（用例红）。

### 记录补缺

- 第二十八节那条整合修复的用例改名为"停止信号与放行队列：取步者刚过放行门、尚未入队时收到停止，以停止原因释放、不被放行；之后取新步一律拒绝"，与它实际测的时间窗口相符。
- 第二十五节补了"验证（分步）"一行。
- Windows 上跳过符号链接用例的说明改为"Windows 上"。

### 清空临时目录一项在本机测试方式下的误删

- 哪一项：D 项"丢弃作废尝试时清空作业容器的 /tmp"的第一版，给正式跑批的容器工作区直接设了临时目录 `/tmp`。
- 在哪种测试方式下：stream-envs 的接管与重建用例用的假 docker 不起容器，把"容器里"的脚本直接在本机执行。
- 落到了哪里：在 Windows 的 Git Bash 下，`/tmp` 是本机当前账户的临时目录。清空脚本删掉了其中所有删得掉的内容，影响范围是本机当前账户临时目录里的全部可删内容，包括同一账户下其他进程放在其中的临时输出。删除不可恢复。
- 闸门：
  - 容器工作区默认不设临时目录，只有正式跑批的入口显式传 `/tmp`。
  - 清空临时目录与"除 init 外全清进程"两项只在确实位于跑批器起的 docker 作业容器里时才动手：必须同时满足 `PIGEON_STREAM_CONTAINER=1`（跑批器以 docker run -e 设，exec 出来的进程都继承，agent 改不了容器配置）与存在 `/.dockerenv`。本机假 docker 两者都不满足。
- 闸门的用例：
  - "闸门：不在跑批器起的作业容器里（缺环境变量或缺 /.dockerenv，或两者都缺），清空临时目录不动手"（清空目标一律是用例自建的临时目录；"只有 /.dockerenv"一种情形在 Linux 容器里跑）；
  - "闸门：本机假 docker 下（不在作业容器里）清 agent 进程只清带本步标记的，不带标记的进程不动"。
- 闸门的变异：
  - 清空临时目录不过闸门，目标是用例自建的临时目录（用例红）；
  - 全清进程不过闸门，只在一次性的 Linux 测试容器里执行（整个用例文件在那个容器里被清掉而失败）。
- "除 init 外全清进程"在事故之前没有应用到源码，未在本机执行过。

## 三十一、开跑前第七轮补修

以下各项均先补用例、再改代码，承重处做变异（改坏后对应用例精确变红，改回后通过）。用到符号链接、目录权限或以固定 PATH 执行假程序的用例在 Linux 容器里跑；真 docker 容器的用例在有 docker 与本仓库流镜像的机器上跑，缺一即跳过。

### 不跟随符号引用（必须修）

现象：agent 执行 `git symbolic-ref refs/heads/x refs/heads/main`，或建一条指向 main 的开工树引用，丢弃作废尝试时删这条引用，实际删掉的是 main。随后清空 reflog、重新打包与回收对象，把上一个完成步的落地提交也回收了，下一次回退失败，作业停下。HEAD 被设成指向某条保留引用的符号引用时，回退的 `reset --hard` 会改写那条保留引用。

修法：
- 删引用一律 `git update-ref --no-deref -d`。
- 回退时先 `git checkout -f --detach` 到目标提交，再以 `--no-deref` 让 main 指向它，然后让 HEAD 指回 main，最后 reset 与 clean。
- 把 HEAD 挪回本步起点时同样只动引用：以 `--no-deref` 让 main 指向起点，HEAD 指回 main，暂存区与工作区不动，等同 soft reset，但不经过符号引用。

用例："丢弃作废的尝试不跟随符号引用：agent 让某条引用或开工树引用指向 main，丢弃后 main 与落地提交都在；HEAD 被设成指向保留引用时，回退与挪回起点都不改写那条引用"。

变异（各自红）：
- 删引用跟随符号引用；
- 回退时不先脱离 HEAD；
- 挪回起点仍用 soft reset。

### 落地提交始终记在 main 上（应修，核对了导出与重建）

核对结果：导出流历史用 `git bundle create --all`，含全部引用；重建按断点行里记的提交号取，不按 main 取。所以 main 落后本身不会让重建丢步：只要落地提交是某条引用的末端，它就在流历史里。风险在于 agent 让 HEAD 游离之后落地：落地提交不在任何引用上，不进流历史，重建时取不到。

修法：落地前再保证一次 HEAD 在 main 上（与挪回起点同一做法），落地提交一定记在 main 上。

用例："落地提交记在 main 上：agent 切到别的分支或让 HEAD 游离后提交，挪回起点再落地，main 等于落地提交、导出的流历史里有它"。变异：落地前不把 HEAD 放回 main（用例红）。

### 跑批器在容器里的命令不经过 agent 能改的执行环境（必须修）

**PATH 与链接。** strands 镜像的 PATH 以 `/opt/venv/bin:/opt/lint/current/bin` 开头，这两个链接归 stream，`/opt` 与 `/opt/lint` 为 1777，agent 一条 `ln -sfn` 就能决定之后 docker exec 解析到的程序；docker exec 本身也按这个 PATH 找 `sh`。本仓库的 pigeon 镜像 PATH 只含系统目录，没有 agent 可控的链接。

修法：
- 跑批器与 Pigeon 执行端自己的内部命令一律经 `/bin/sh` 绝对路径执行，脚本开头把系统目录（`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`）放到 PATH 最前。覆盖范围：
  - 列候选、删 conftest、还原与写人的文件、回退与丢弃；
  - 清进程、清临时目录、清锁文件；
  - 以 root 写人的 pytest 配置；
  - 执行端的取起点、还原受保护文件、撤回。
- 采用"放到最前"而不是整个替换 PATH，原因是本机测试的假 docker 在本机执行、本机的 git 在系统目录之外。跑批器用到的工具在镜像里都位于系统目录，两种做法等效。
- 切依赖环境（select-env、select-lint）同样走固定环境，这两个脚本本身用 python 的绝对路径。
- 判题、测量、验证门这类要用所选环境的测试命令保留镜像的 PATH。每次切完环境后，核对 `/opt/venv` 与 `/opt/lint/current` 仍是链接，并解析到 root 所有的 `/opt/venvs/`、`/opt/lint/sets/` 之下。被改指或换成普通目录（切换命令改不回来）时，以 root 删掉链接再切一次；仍不对则这一步作废重做。判题前、测量与开工时三处都如此处理。
- 以 root 执行的命令同样走固定 PATH，不经过 agent 可控的链接。
- 两种镜像都做了；pigeon 镜像没有需要核对的链接。

用例：
- "跑批器在容器里的内部命令不经过 agent 能改的 PATH：镜像 PATH 最前面换成放了假 sh、find、git 的目录（相当于 /opt/venv 被改指），删 conftest、以 root 写人的 pytest 配置、执行端的内部命令与清进程都不执行它们，conftest 照样删掉"；
- "依赖环境的链接被改过（换成普通目录，切换命令改不回来）：以 root 删掉重切，链接恢复；重切之后仍不在 root 所有的目录下即报访问错误"。

变异（各自红）：
- 跑批器的内部命令按镜像的 PATH 找 sh；
- 执行端的内部命令不固定 PATH；
- 清进程按镜像的 PATH 找 sh；
- 切依赖环境后不核对链接。

"切换命令走固定 PATH"一处由本机的 shell 夹具执行，夹具不区分两种 PATH，没有单独的变异。

**git 配置。** agent 能在 `.git/config` 或家目录下的全局 git 配置里配 filter 驱动（配合 `.gitattributes`）或要求签名的 `gpg.program`，跑批器在判题前的还原与落地时（git status、checkout、add、commit）就会执行 agent 的程序，新起的后台进程可以重建 conftest、改人写测试。

修法：
- 跑批器的 git 命令屏蔽全局与系统配置（`GIT_CONFIG_GLOBAL=/dev/null`、`GIT_CONFIG_NOSYSTEM=1`），并固定不执行钩子、不跑 fsmonitor、提交不签名、提交身份固定。
- 在跑批器自己的 git 操作之前，把 `.git/config` 重写成只含无害项的一份，并删掉 `.git/info/attributes`。
  - 时机：回退、挪回起点、落地之前；Pigeon 回炉验证前清完进程之后同样处理。
  - 保留的项：仓库格式，以及 filemode、symlinks、ignorecase 三项文件系统属性，取值须为 true 或 false；其余一律丢掉。读取用 `--file`，不跟随 include。
  - 为什么不照原文"开工时留存一份"：接管一个被改过的容器时手上没有可信的副本，重写成无害项的做法两种情况都能处理。

用例："跑批器的 git 操作不执行 agent 在 git 配置里设下的程序：仓库 .git/config 与全局配置里的 filter 驱动、要求签名的 gpg.program 都不起作用；配置被重写成只含无害项"。

变异（各自红）：
- 挪回起点与落地之前不清 git 配置；
- 不屏蔽全局 git 配置。

"固定不签名"与"删掉 info/attributes"两项，单独去掉时重写配置已清掉签名与 filter 定义，检不出，属多一道防线。

### 其余应修

- 清空测量副本之前（建副本、清产物两处）先放回属主权限：agent 在副本里放一个带文件的 0555 目录，原先 rm 失败、作业停下。用例："清空测量副本之前放回属主权限：副本里有 agent 放的不可写目录（0555，里面有文件），照样清空、不让作业停下"。变异：清空前不放回（用例红）。
- 清空临时目录补正向用例（真容器）："作业容器里（真容器）：丢弃作废尝试时清空临时目录；清 agent 进程时被 init 收养的孤儿进程照样清掉，主命令不动"。镜像自带、归 root 的内容（node 的编译缓存目录、uv 的锁文件）以 stream 身份删不掉，也不是 agent 留下的，用例只断言 agent 留下的被清掉。变异：清空改成空操作（用例红）。
- 清进程补孤儿进程情形：`sh -c 'sleep 1000 &'` 起的进程由 init 收养（父进程为 1），照样清掉，主命令不动（同上一条用例）。变异："PID 1 的子进程一律放过"（用例红）。
- 以 root 运行时的用例守卫："链接删不掉"一条在 root 下跳过并写明原因；0311 一条在目录读得到时改为显式跳过、写明原因，不再静默返回。真容器用例里的 docker exec 以镜像的默认身份 stream 执行。
- 闸门失效告警：
  - 续跑时只接管带 `PIGEON_STREAM_CONTAINER=1` 起的容器，从 docker inspect 的环境变量里看；先前未带标志起的由流历史重建。
  - 开好容器后在容器里探一次闸门，不成立（Podman、rootless 等没有 `/.dockerenv`，或缺环境变量）即向标准错误告警一次，说明后果：不清空 /tmp，清进程退回只按本步标记。
  - 用例："续跑时先前未带标志起的容器（闸门在里面不成立）不接管，改由流历史重建；闸门不成立时告警一次并说明后果"。
  - 变异（各自红）：接管不看标志；不告警。
- worktree 路径先规范化再比较：`cd` 进去取 `pwd -P`，删的也是规范化后的路径，防止 `工作区/sub/../../外面` 这类写法按字面落在工作区前缀下。用例："丢弃时 worktree 路径先规范化：登记里写成 工作区/sub/../../外面 的路径不按字面当作工作区之内删掉"（sub 须是已提交的目录，回退后仍在，这种写法才解析得到外面）。变异：不规范化（Linux 容器，删的是用例自建的目录，用例红）。
- 第二十九、三十节的措辞改为中性写法。
- 本机测试的假 docker 补上跳过 `-u`（以哪个身份执行，本机照常以当前身份执行）；stream-envs 的假 docker 在 Windows 上把 `/bin/sh` 换成 `sh`，并记下 `-e`、inspect 报出环境变量。

### 已知限制

- 引用清理的口径仍是"除 main 与不超过断点的开工树引用外全删"：agent 在已完成步里自己建的分支、标签、stash，会在后续任一步作废、接管或重建时消失，重做看到的库与不中断时不同。只影响 agent 自建的引用，不影响 main 与代码内容。
- 带 `.keep` 的包与 alternates 不被 `repack -a` 处理，刻意藏匿的作废提交可能留存。
- 列候选的 find 超时（被忽略的目录里文件极多）按访问错误作废，连续作废可能停下作业，概率低。
- 预算试跑不清 /tmp（每步新开容器，影响小）。
- Pigeon 回炉验证用镜像的 PATH 执行 agent 所在环境里的验证命令，agent 改指链接只能骗过自己的回炉判定（影响是否撤回），判题与测量前会重切环境并核对链接。

### 标识生成改为单调

现象：`listSessionIds` 按 ULID 字典序列出会话，默认字典序即时间序；但同一毫秒内生成的两个标识，随机部分无序，先生成的可能排在后面。event-log 的对应用例在 Linux 上单独跑 20 次挂 11 次。

修法：
- ULID 生成改为单调：记住上一次的毫秒与 80 位随机部分。
- 同一毫秒或时钟回拨时，沿用上一次的毫秒、随机部分加 1；加到溢出则毫秒进 1、随机部分归零。
- 编码仍是 10 位时间加 16 位随机的 Crockford Base32，与现有解析兼容。
- event-log 的用例不改。

用例："ULID 单调：同一毫秒内连续生成 1000 个严格递增；时钟回拨仍递增；随机部分加到溢出时毫秒进 1、仍递增"。变异（各自红）：去掉单调；溢出时不进位。event-log 的对应用例改后连续跑 20 次全过。
