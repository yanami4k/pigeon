# 接入 DeepSeek 与最简 agent 修复（决策 194、200、203、234、235，基线 0fa108b）

范围：网关与模型接入改走 DeepSeek 的 Anthropic 兼容端点；错误分类按 DeepSeek 的状态码与 OpenAI 形状的错误正文重写；错误文本脱敏覆盖上游回显的密钥末四位；新增人民币计价模块、网关逐请求计价、全局花费累计落盘与花费上限；最简 agent 修三处（容器内 rc 文件权限报错、输出上限、思考开关）；eval 与 stream 的缺省 provider 与模型换成 DeepSeek；另加日常使用的 DeepSeek 模型接入模块。基线为 formal-v2 分支 0fa108b，分支 r1-deepseek，代码提交 f0d5390。

## 一、接入参数

| 项 | 取值 | 位置 |
|---|---|---|
| 上游基址 | `https://api.deepseek.com/anthropic`（常量，请求路径 `/v1/messages`） | `src/pi-runtime/deepseek-model.ts` 的 `DEEPSEEK_ANTHROPIC_BASE_URL` |
| 协议与线路 | 网关照旧说 Anthropic Messages；Pigeon 用 pi-ai 的 anthropic-messages 线路 | `gateway-stream.ts` |
| 模型对象 | 自构：`id`/`name` 为 `deepseek-flash`，`api` 为 `anthropic-messages`，`provider` 为 `deepseek`，`reasoning` 为真，`input` 为 `["text"]`，`contextWindow` 1000000，`maxTokens` 16384，`cost` 四项全为 0 | `deepseekModel()`，网关线路与日常线路共用这一份 |
| 账号环境变量 | `DEEPSEEK_API_KEY` 为账号 1，`DEEPSEEK_API_KEY_2`…`_9` 为后续账号（多账号代码保留）；并发变量 `DEEPSEEK_API_KEY_<编号>_CONCURRENCY` | `model-gateway.ts` 的 `gatewayAccountsFromEnv` |
| 账号缺省并发 | 2500（官方 `deepseek-flash` 单账号并发上限） | `DEFAULT_ACCOUNT_CONCURRENCY` |
| 网关探测请求 | `model` 为运行配置的模型名（缺省 `deepseek-flash`），`max_tokens` 1，`thinking` 为 `{"type":"disabled"}` | `stream-experiment.ts` 的 `startGatewayAndLimits` |
| 缺省 provider 与模型 | `eval stream` 的 Pigeon 条件 provider 为 `deepseek`，`--model-id` 缺省 `deepseek-flash` | `cli/index.ts`、`stream-experiment.ts` 的 `effectivePigeonSettings` |

模型设置（决策 203）：Pigeon 各条件的推理档位缺省 off、温度缺省 0（`eval stream` 原有的 `streamTemperature`）、单次输出上限缺省 16384，均未改动；`reasoning` 为真使 pi-ai 在未请求推理时显式发 `thinking: {"type":"disabled"}`（DeepSeek 不发 `thinking` 即默认开思考）。复盘与上下文压缩摘要尚未实现，它们经 Pigeon 的模型接入（同一 streamFn 与同一组包装）时沿用同一设置。

`cost` 填 0 的理由：花费统一由网关按人民币价目与高峰时段逐请求计（第四、五节），pi-ai 按 `model.cost` 算出的 `usage.cost` 不作为花费来源；结果行的 `usage.cost` 与改动前一样恒为 0。

温度门控：`application/runtime.ts` 与 `pi-runtime/sampling.ts` 中"推理与温度在该线路上互斥"的注释改为按新线路写明：anthropic-messages 线路开思考时不发 `temperature`，DeepSeek 思考模式下温度也不生效；行为未改。

用量读法：`usageOf` 在 SSE 的 `message_delta` 里带输入与缓存字段时以它为准（与 pi-ai 的读法一致；DeepSeek 实测 `message_start` 与 `message_delta` 两处数值相同）。`input` 为缓存未命中部分，命中在 `cacheRead`。

## 二、错误分类

状态码口径按 DeepSeek 错误码文档（https://api-docs.deepseek.com/zh-cn/quick_start/error_codes），错误正文按 OpenAI 形状 `{"error":{"message","type","param","code"}}` 解析（`parseUpstreamError`，Anthropic 形状 `{"type":"error","error":{…}}` 同样取得出）。

| 上游回应 | 分类 | 网关处理 | 对这一步的影响 |
|---|---|---|---|
| 401 | `auth` | 该账号停用、不探测恢复；这次请求原样交回（已脱敏）并记上游故障；全部账号都不会自行恢复即停批 | 作废重做（单账号时随即停批） |
| 402 余额不足 | `balance` | 该账号不再使用、不探测；请求换号；全部账号都不可用即停批（与原"每月额度用完"同一停下路径）；错误正文去密钥后记一次日志 | 限额信号使这一步作废，续跑时重做；不交给 agent 当真失败 |
| 429 | `rate-limit` | 该账号逐级退避 5、15、45 秒，退避期间请求换号；用满仍撞即暂时不可用、按 5 至 30 分钟间隔探测恢复 | 不作废（退避用满且全部账号不可用时整批暂停，信号使在途步作废） |
| 503 服务器繁忙 | `busy` | 与 429 同一退避与恢复机制（共用退避级数） | 同上；改动前 503 记上游故障、直接作废 |
| 500 服务器故障 | `server` | 不动账号；这次请求按 2、8、30 秒退避重试（`SERVER_ERROR_RETRY_DELAYS_MS`），仍是 500 即原样交回并记上游故障 | 重试后成功即照常；用满即作废重做 |
| 403 | 文案认并发即 `concurrency`，文案明确是认证即 `auth`，其余 `other` | 并发：降该账号上限、稍候重试，上限已是 1 仍受限即暂时不可用；其余 403 原样交回、记上游故障 | — |
| 其他 5xx | `other` | 原样交回、记上游故障 | 作废重做 |
| 400、422 等 | `other` | 原样交回 | 由 agent 一侧处理 |

删去的 Kimi 语义：403 按文案区分 5 小时、每周、每月三种额度窗口；额度停用的最短停用期（封顶规则 30→60 分钟、按正文重置时刻停用）与重置时刻解析 `quotaResetAt`；`LimitKind` 的 `5h`、`weekly`、`monthly`。`LimitKind` 现为 `concurrency`、`rate-limit`、`busy`、`auth`、`balance`。

开跑前逐账号探测：认证失败、余额不足、认不出的回应（含 500 与认不出的 403）与连不上即拒绝开跑并报出账号编号；429、503 与 403 并发只告警、开跑后按常规处理。

限额控制器新增 `spendLimitReached(totalCny, limitCny)`：计一次信号、停下（与余额不足同一停下路径）、通知看守；停止原因写明累计花费与上限。

`isQuotaError` 保留：外部基准的双 key 探针（`spikes/key-failover.mjs`）仍从这里取文案口径，网关的分类不再用它。

## 三、脱敏

| 规则 | 覆盖 | 位置 |
|---|---|---|
| 配置的 key 逐个替换为 `[key]` | 原有 | `scrubKeys` |
| 三个以上星号紧跟 1 至 8 位字母数字（`\*{3,}[A-Za-z0-9_-]{1,8}`，后面不再接字母数字）替换为 `[key]` | 新增：DeepSeek 401 正文 `Your api key: ****abcd is invalid` 回显所交 key 的末四位 | `scrubKeys` |
| `api key`、`access key` 允许中间是空格（原规则只认 `api_key`、`api-key`、`apikey`），其后的值替换为 `[已去除]` | 新增 | `redactBody` |
| Bearer 凭据、`sk-` 类前缀串、20 字以上字母数字相混的串、只取前 200 字 | 原有 | `redactBody` |

`scrubKeys` 用于交回客户端的错误正文与网关转发失败的说明，`redactBody` 先经 `scrubKeys` 再加上后几条，用于日志；因此交回 agent 的正文（可能进结果行的错误信息）与日志都不含回显的末四位。余额不足与认证失败停用账号时，日志写 `type：code：message`（取自解析出的错误正文，经 `redactBody`）。

## 五、花费累计与上限

- 网关计量 `GatewayMeter` 新增 `costCny`：这个作业成功请求的花费；`meterDelta` 按步做差。
- 跑批器写结果行：`gateway` 字段新增 `costCny`（本步 agent 的花费）与 `reviewCostCny`（本步复盘的花费，单列；复盘尚未接入，恒为 null）。旧结果行没有这两个字段，类型上为可选。
- 全局累计：网关记下全部成功请求（含网关自己的探测，探测不归任何作业）的花费总额、请求数与按高峰价计的请求数；`ModelGateway.spend()` 读出。每记一笔即整份写入输出目录下的 `gateway-spend.json`（先写临时文件再改名）；同一输出目录续跑时网关启动即读入、接着累计。文件存在但认不出（缺 `totalCny`）即拒绝启动。
- 上限：`eval stream --spend-limit-cny <元>` 给出（正数，缺省不设）。每记一笔后累计达到上限即调用限额控制器的 `spendLimitReached`：计一次限额信号、状态为已停止，在途的步按限额信号作废（续跑时重做），之后网关对新请求一律 529、不打上游。开跑前累计已达上限即拒绝开跑（不发探测）；调高上限即可在同一输出目录续跑。
- 计入范围：所有经网关的请求（Pigeon 各条件、最简 agent、网关的开跑前探测与恢复探测）；复盘与压缩摘要接入后经同一网关，同样计入。
- 上限的超出量：到上限时已在途的请求照常完成并计入，累计可能略超上限（每条请求的量级）。

单次请求输入峰值：`GatewayMeter` 另记 `peakInputTokens`，为这个作业每个成功请求的 `input_tokens` + `cache_read_input_tokens` + `cache_creation_input_tokens` 取最大（不累加），`resetPeak` 时与在途峰值一起清零（跑批器在每步开始时调用），`meterDelta` 取步末的值，计量快照 `meter(job)` 给出；Pigeon 各条件与最简 agent 的请求同样计入。结果行尚未记录它（留给跑批器）。

## 六、最简 agent 三处修复（`eval/stream/mini/run_mini.py`）

1. 交卷识别：去掉 mini-swe-agent SWE-bench 配置里的 `BASH_ENV=/root/.bashrc`。容器以非 root 用户执行命令时读不了 `/root/.bashrc`，`bash -c` 每条命令输出的第一行都是权限报错，交卷标记（要求在第一行）认不出。本项目的镜像用 `ENV` 设好 PATH，不依赖 rc 文件。
2. 单次输出上限：litellm 参数 `max_tokens` 16384（未设时 litellm 对 Anthropic 接口缺省 4096）。
3. 关思考：`thinking` 为 `{"type":"disabled"}`，另在 `allowed_openai_params` 放行 `thinking`——litellm 1.102.1 的 anthropic 线路只对它认得出"支持推理"的模型接收 `thinking`，`deepseek-flash` 不在它的表里，配置里的 `drop_params: true` 会把它静默丢掉。
4. 同时设温度 0（决策 203 要求全部条件温度 0）。

模型串仍为 `anthropic/<模型>`，经网关；`cost_limit` 保持 0（不设成本上限，由网关统一封顶）。参数构造抽成 `build_configs` 与 `model_kwargs`，`python run_mini.py --identity` 打印 mini-swe-agent 与 litellm 的版本及实际生效的模型参数（不含网关地址与占位 key）；`stream-experiment.ts` 的身份头改由它取值，记录的是覆盖后的生效值（改动前记的是 SWE-bench 配置原值）。

输出上限、温度与思考开关写在 run_mini.py 的常量里，未经请求文件从跑批器传入（请求文件由 `stream-agents.ts` 写出，属跑批器一段）。

## 七、日常使用的 DeepSeek 接入

- 新增 `src/pi-runtime/deepseek-stream.ts`（工厂 `createDeepSeekStreamFn(env)`）与入口 `src/pi-runtime/deepseek-stream-fn.ts`（默认导出 StreamFn）。直连 `https://api.deepseek.com/anthropic`，模型对象取 `deepseekModel()`，与网关线路同一份定义；忽略 CLI 传入的占位模型。
- key 只从环境变量 `DEEPSEEK_API_KEY` 读，缺失或为空即在加载时报错（`缺少 DEEPSEEK_API_KEY 环境变量…`）；不打印、不落盘。
- 思考档位按 Pigeon 的 `--thinking` 经调用选项透传：未给即 off，pi-ai 发 `thinking: {"type":"disabled"}`；给了档位即发 `thinking` enabled。温度沿用 Pigeon 的 `fixTemperature` 包装，单次输出上限沿用 `limitOutputTokens` 包装（缺省 16384）。
- Kimi 的 `spikes/real-stream-fn.mjs` 原样保留，缺省值不改。

用法（在仓库根目录）：

```
DEEPSEEK_API_KEY=<key> PIGEON_STREAM_FN=src/pi-runtime/deepseek-stream-fn.ts node src/cli/index.ts run "<任务>"
node src/cli/index.ts run "<任务>" --stream-fn src/pi-runtime/deepseek-stream-fn.ts   # DEEPSEEK_API_KEY 已在环境里
```

TUI（`src/tui/main.ts`）同样按 `--stream-fn` 或 `PIGEON_STREAM_FN` 指定。

测试 `src/pi-runtime/deepseek-stream.test.ts`（离线，用假的 streamSimple）：缺 key 报错；发出的模型对象逐字段核对、key 取自环境变量；未给思考档位时不带 `reasoning`、给了原样带上，温度与输出上限经 Pigeon 的两层包装传入；入口经 `loadStreamFn` 按文件路径加载得到函数，缺 key 时另起进程加载即报错且报错不含其他环境变量的值。网关线路实际发出的请求体（`model`、`thinking` disabled、`max_tokens` 16384）由 `model-gateway.test.ts` 的"Pigeon 的模型接入经网关走通上游 SDK"一例经真实 pi-ai 核对。
