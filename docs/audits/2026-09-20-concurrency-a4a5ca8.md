# 并发缺口修复与三处领域逻辑下沉（基线 a4a5ca8）

本轮全是缺陷修复与重构，不新增裁决。四处并发缺口各自先补红测试再改；三处领域逻辑下沉要求零行为变化。

## 一、独占锁的建锁竞态

### 机理

`persistence/exclusive-lock.ts` 的建锁原本分两步：先以 `wx` 独占创建锁文件，再往这个文件描述符里写持有者记录。两步之间锁文件已经存在、但还是 0 字节。

另一个进程此刻来取同一把锁，`wx` 创建撞上 EEXIST，转去读锁文件内容，读到空串 → `JSON.parse("")` 抛 → 判为"内容畸形" → 按残留锁直接删掉，再自己创建成功。于是两个进程同时认为自己持有这把锁，而这把锁挡的恰恰就是这个。

会话打开锁（`session-lock.ts`，决策 040）早就避开了这条路：先把持有者记录写进临时文件，再硬链接到锁路径，锁文件一出现就是完整内容。独占锁是后加的，没有沿用这个手法。

### 窗口有多宽

不是理论风险。探针实测：父进程反复取放同一把锁，子进程紧盯锁文件——3057 次取锁期间，子进程 18872 次读里有 **2827 次**读到不完整内容（约 15%）。另一个探针让三个进程各取 200 轮锁、每次持锁 10 毫秒并用 `wx` 哨兵文件检测重叠，一轮跑出 **2 次两个进程同时持锁**。

### 修法

照抄会话锁的建锁方式：临时文件写好再 `linkSync` 到锁路径，成功即持有，EEXIST 即他人先到，无论成败都清掉临时文件。读侧与残留接管口径一字未动——建锁原子之后，0 字节锁文件不可能再由本实现产生。

### 红测试

`独占锁：建锁原子性——锁文件一出现就是完整内容，另一个进程读不到半截锁`：起一个子进程紧盯锁文件并统计"存在但不是完整持有者记录"的次数，父进程期间反复取放 400 次。断言子进程确实读到过这把锁（否则用例什么都没测），且不完整次数为 0。修复前该用例报 190 次不完整。

## 二、批准与撤销无锁

### 机理

`application/candidate-decision.ts` 的四个决定动作（批准 / 拒绝 / 撤销 / 取代）全程不取任何锁，而同一条候选的验证是取锁的。两个进程同时批准与撤销同一条候选时：两条决定记录落进各自的会话文件，先后随机；落点文件则可能被撤销那一方删在最后。状态投影按"最后一条决定"算，于是算出已激活——文件没了，状态却说它激活着。

### 修法

四个决定动作与验证共用同一把按候选内容哈希取的锁。锁路径从 `verify-command.ts` 的 `verifyLockPath` 挪到 `candidate-lookup.ts` 的 `candidateLockPath`（两边都已依赖这个模块），落点由 `.pigeon/verify-locks/` 改名 `.pigeon/candidate-locks/`——它不再只服务验证。锁文件是瞬时的，改名不涉及任何迁移。

取锁排在任何写入之前：连本次命令自己的会话文件都还没打开。释放在 `finally` 里，异常路径同样放锁。

**取锁之后重新定位**：第一次定位只为把选择器解成内容哈希（不解就不知道该锁哪一把），取到锁之后按内容哈希重新建一次索引、重新算一遍状态。否则闸判据用的是取锁之前的投影，那段窗口里别人可能刚批准或刚撤销过，锁等于白取。代价是每次决定命令多一次治理根全扫。

诚实边界：这一条"取锁后重新定位"没有直接用例钉死——要构造它需要在定位与取锁之间插进另一个进程的完整决定，本轮没有为此加测试用的缝。它目前只由代码结构保证。

### 红测试

- `决定互斥：这条候选的锁被占着时，四个决定动作一律被拒`，并断言被拦下时落点目录不出现（取锁确实排在写入之前）；
- `决定互斥：锁放开后照常走通，并且自己用完会放锁`（批准后紧接着撤销不被自己刚才那把锁挡住，锁文件不留下）；
- `决定互斥：异常路径同样放锁`（被拒的批准抛出后，后面的拒绝照常走通）。

## 三、会话树重建与写穿没有跨进程保护

### 机理

`pigeon tree rebuild` 先删整棵树文件再从账本重导，而另一个进程的写穿队列可能正在追加同一棵树。树文件没有任何跨进程锁；写穿失败又只告警、不进账本（决策 080：树是可重建的派生缓存，失败的后果由重建入口补齐）。两者撞上的结果就是树错乱，而且没有任何记录说它错乱过。

### 修法

`rebuildSessionTree` 按根会话号取一把跨进程锁（`.pigeon/tree-locks/<根会话号>.lock`），取不到即明确报错说明"该会话树正被另一个进程写入或重建"。锁排在删树之前，`finally` 释放。放在 `rebuildSessionTree` 而不是只放在命令入口，是因为它才是那个destructive 的函数，两个调用方都经过它。

### 写穿侧不取锁的取舍

写穿侧**不**取这把锁，理由三条：

1. **代价与收益不匹配**：写穿是会话运行期间持续发生的后台追加，每批取放一次锁在本平台实测约 3 毫秒；而它换来的保护很有限——重建是"删掉再重导"，写穿即使每批都取锁，也只能保证单批不被撕开，挡不住"重建刚把树换成新的、写穿还按旧的内存序号继续追加"这个真正的错乱来源。
2. **失败模式更糟**：本项目的锁撞上即拒绝、不排队。重建持锁期间写穿批次会被拒，而写穿失败按 080 只告警不落账本——等于把"可能错乱"换成"确定丢几批"，而且丢的那几批同样要靠重建补回。
3. **树是派生缓存**：账本与内容文件才是权威。重建侧拿住锁，已经足以保证"重建期间没有第二个重建在跑"，以及"人在重建时能明确知道有会话正在写这棵树、该等它收尾"。剩下的偏差由再跑一次重建补齐，这正是 080 给这类失败安排的出路。

如果以后写穿改成对树做增量更新而不是尾部追加，这个取舍要重新盘。

### 红测试

- `树重建：这棵树的锁被占着时，重建明确报错，不删任何东西`（并断言树目录未被创建/触碰）；
- `树重建：锁放开后照常重建，并且自己用完会放锁`。

## 四、放权配置的读改写丢更新

### 机理

`persistence/grants-config.ts` 的追加与移除都是"读出整份 → 改数组 → 原子写回"。原子替换只保证读到的文件不撕裂，挡不住丢更新：两个窗口同时固化放权时，后写的那一份是基于**旧内容**算出来的，会把先写的那条整份覆盖掉。这是老代码，不是本轮引入的。

### 修法

读与写收进同一把锁：新增 `grantsConfigLockPath`（`.pigeon/grants.json.lock`）与内部的 `withGrantsConfigLock`，追加与移除都改成"取锁 → 读出当下这一份 → 算出新的一份 → 原子写回 → 放锁"。重复升格的去重检查也挪进锁里——它判的就是即将被写回的那个基准。

读侧（`loadGrantConfig`，会话启动装载）不取锁：原子替换保证它读到的要么是完整的旧一份、要么是完整的新一份。

语义口径：撞上即明确拒绝，不排队重试。这与本项目其他三把锁（会话打开锁、候选锁、树重建锁）一致，不是新立的口径。代价是两个窗口同时固化时后一个会看到一句"正被另一个窗口写入，等它收尾后重试"，而不是静默丢掉其中一条。

### 红测试

- `放权配置：写入锁被占着时，追加与移除都被明确拒绝，文件一个字节都不动`；
- `放权配置：依次写入互不覆盖，并且每次用完都放锁`；
- `放权配置：异常路径同样放锁`（重复升格被拒之后，下一次追加照常）。

既有的 `grants.json 原子替换：升格写到一半崩溃` 用例断言配置目录下只剩 `grants.json`——它同时钉死了异常路径不会把锁文件或临时文件留在原地，本轮改动后仍然通过。

## 五、三处领域逻辑下沉

要求零行为变化；既有测试的断言一字未改，只改了导入路径。

### 1. 模型输出里的结构化结果 → `state/structured-result.ts`

`application/workers.ts` 里的 `structuredResultOf`：零依赖零 IO 的纯文本解析，提炼器与审阅器共用同一口径。原样搬下，头注释补齐了它认的三种形态与"以 ``` 开头却没有可解析围栏就直接判无结果"的理由。对应测试文件一并从 `application/` 挪到 `state/`。

### 2. 行级 diff → `state/line-diff.ts`

`application/candidates-list.ts` 里自己实现的最长公共子序列（DP 表加回溯）是算法不是渲染，搬下为 `lineDiff`。留在原处的 `diffSection` 只保留"多大算超限"与三句中文文案。

**顺带确认的事**：写工具的审批预览没有第二份 diff 实现。`tools/hashline.ts` 的 `buildEditDiff` 解决的是另一个问题——它的输入是**已知坐标的编辑**（改了哪几行是输入，不需要推断），输出是带 hunk 头与上下文的 unified-ish 文本；而 `lineDiff` 要从两段文本自己推出改动。两者没有可合并的公共部分，强行合成一份只会让前者绕道去重新推断它本来就知道的东西。两个模块的头注释各自点明了这个区别。

### 3. `governance.ts` 的三段判据

- **熔断计数键的构造** → `state/breaker.ts` 的 `breakerCountKey`：`tool` 粒度按工具名、`fingerprint` 粒度按 工具名+参数 JSON，畸形参数序列化失败时退化为固定串并入同一桶。
- **上游拦截连击的计数状态机** → 同文件的 `InterceptStreak`：只管连击（同名连续才累加、换名从 1 起算、非拦截收尾清零），"是不是被上游拦截"这个判据仍由 Controller 给出，落闸动作（abort、留证）也留在 Controller。
- **receipt 的组装** → `state/receipt.ts` 的 `buildReceipt`（该文件此前只有 schema，没有构造函数）：`executed` 判据、摘要文案、exec/mcp 字段取舍都搬下。证据的获取（从工具实例上取一次即删、try/catch 兜底）留在 Controller——那是 IO。实测目标现状哈希以回调传入，`buildReceipt` 只在 `executed` 为真时调用它：这个顺序是判据的一部分，不是调用方的自由。

`state` 是叶子层（分层规则 `state-is-leaf`），三个新模块都不引用 `src` 下的其他目录；exec 证据的类型按结构在 `receipt.ts` 里声明为 `StagedExecEvidence`（就是回执里的 exec 再加一个只服务判定的进程启动标记），不从 `tools/` 取类型。分层规则无需改动。

## 变异反向验证

九条单点变异，全部精确变红：

| 变异 | 精确变红的用例 |
|---|---|
| 建锁退回两步（先独占创建空文件、再写内容） | 建锁原子性：锁文件一出现就是完整内容，另一个进程读不到半截锁 |
| 决定动作不取锁 | 决定互斥：这条候选的锁被占着时，四个决定动作一律被拒 |
| 树重建不取锁 | 树重建：这棵树的锁被占着时，重建明确报错，不删任何东西 |
| 放权配置写侧不取锁 | 放权配置：写入锁被占着时，追加与移除都被明确拒绝，文件一个字节都不动 |
| 熔断计数键：指纹粒度退化为按工具名 | 人工拒绝保留指纹计数：模型改参重提是期望的修订循环，不触发熔断 |
| 拦截连击：非拦截收尾不清零 | 幽灵熔断是连续语义：正常工具调用重置连击，未连续达阈值不中止 |
| 回执组装：executed 判据丢掉进程启动标记 | executed：出错但进程已经启动过（超时终止、被中止）按可能发生记 |
| 行级 diff：回溯丢掉尾部删行 | 行级 diff：旧的比新的长，尾部多出来的行要逐行记删 |
| 结构化结果：围栏取第一个而不是最后一个 | 分析文字在前、json 围栏在后：取最后一个能解析的围栏块 |

最后两条起初**没有变红**：`executed` 判据的两个例外分支（出错但进程已启动、出错但 server 已返回）与行级 diff 两侧长度不等时的尾部收尾分支，此前都只被端到端用例间接走到，没有任何断言钉住。下沉成纯函数之后补了两个直测文件（`state/receipt.test.ts`、`state/line-diff.test.ts`），补齐后这两条变异精确变红。这不是下沉引入的缺口，而是下沉让原本看不见的缺口露了出来。

## 落点与时序变更后的断言回看

本轮动了锁的取用时机（四处）与三个模块的所在位置，按前两轮的教训逐条回看了可能因此变成恒真的断言：

- **锁的落点**：新增的三类锁文件分别落在 `.pigeon/candidate-locks/`、`.pigeon/tree-locks/` 与 `grants.json.lock`，都不在任何被遍历的目录里；`.pigeon/trees` 与 `.pigeon/candidates` 的目录条数断言不受影响。唯一会被波及的是 `grants-config-atomic.test.ts` 里"配置目录下只剩 grants.json"那条——它正好反过来成了锁清理的证据，本轮通过。
- **取锁时机**：三条新用例分别断言了"被拦下时落点目录不出现""被拦下时树目录不被创建""被拒后锁不留在原地"，都不是只断言抛错就完事。
- **模块位置**：三处下沉的既有断言一字未改，只改导入路径；`renderLineDiff`、`receiptExecOf` 的旧名在 `src` 下已无残留引用。
- 另外扫了一遍全仓"对某个会话断言某物不存在"形态的断言，本轮没有改动任何记录族的落点，无新增空转。
