## 第 1 件：命令行续跑没有任务清单工具

- 现象：`pigeon run` 开的会话有 `update_tasks`、`list_tasks`，用 `pigeon resume` 续跑后这两件工具不在。
- 原因：任务清单只在调用方给出 `taskList: true` 时注册（`application/session-runtime.ts` 交给 `buildRuntime`）。
  `pigeon run` 与终端界面（开局、`/resume` 换绑、`/reload`）都按编排配置传了；`pigeon resume` 进的 REPL 与 `pigeon --line`
  两处调用 `openSessionRuntime` 时没传。
- 改法：`cli/index.ts` 两处补上 `taskList: orchestrationSettingsOf(flags, settings).taskList`（与 `pigeon run` 同一来源，
  缺省开）。续跑时清单由已有的 `restoreContext` 从会话记录里最后一次 `update_tasks` 的结果还原，不另改。
- 续跑入口之间的差别（照旧，不改）：有人对话的入口注册写记忆的工具（决策 331），`pigeon run` 不注册。因此 `pigeon run`
  开的会话改用 `pigeon resume` 或终端界面续跑时，广告的工具集与上一个 Run 不同：首个请求的提示缓存失效一次，
  同时按决策 361 算作免费时机，Run 开始后的第一次请求之前一次裁光全部裁剪候选。
- 测试：`cli/spawn-worker-cli.test.ts` 加一条端到端（子进程，假模型）：`pigeon --line` 里模型调 `update_tasks` 记两项，
  再用 `pigeon resume <会话号>` 续跑、模型调 `list_tasks`；从会话记录读两次工具结果里的清单，都为同样两项（编号、标题、状态）。
  这同时核实了跨入口续跑后清单状态从会话记录接上。
- 变异（本机）：去掉 `pigeon resume` 处的 `taskList`，用例红在 `list_tasks` 的断言；去掉 `--line` 处的，红在 `update_tasks`
  的断言。各自还原后与原文件逐字一致（`cmp`）。终端界面的入口本就传了且本次未改，没有入口级的新用例（`tui/main.ts`
  的装配不由测试驱动）。

## 第 2 件：沙箱交回的分支带进 `.pigeon/.gitignore`

- 现象：沙箱交回的分支里多出 `.pigeon/.gitignore`；仓库没跟踪它时，合并会与主工作目录里同名的未跟踪文件相撞。
- 原因：这个文件由 `persistence/settings.ts` 的 `ensurePigeonGitignore` 在第一次建程序状态目录时写出。拍工作目录快照
  （`execution/workdir-snapshot.ts` 的 `workdirTree`）在临时索引上 `add -A` 之后，只把 `PROGRAM_OWNED_PATHS`
  （`.pigeon/state`、`.pigeon/settings.local.json`）还原到 HEAD，没有撤它。于是它进了快照提交，容器从快照起步，
  交回脚本（`sandbox.ts` 的 `COMMIT_SCRIPT`）的分支相对 HEAD 就含有它。
- 涉及的路径：`workdirTree` 是沙箱开工快照、本机派 worker 的起点快照（`application/workers.ts` 的 `workerStartPoint`）、
  脚本快照（`execution/script-snapshot.ts`）与 worker 结果叠加（`execution/worker-overlay.ts` 用它写 worker 工作树的树对象）
  共用的一处。容器里与 worker 工作树里不另写这个文件，所以只改这一处即覆盖沙箱与 worker 两条交回路径。
- 改法：`workdirTree` 在 `add -A` 之前查临时索引（复制自用户索引）里有没有 `.pigeon/.gitignore`；没有（仓库没跟踪）就在
  `add -A` 之后从临时索引里撤出（`rm --cached`），有则照常带上（含未提交的修改）。路径常量 `PIGEON_GITIGNORE_REL`
  放在 `state/paths.ts`。不并入 `PROGRAM_OWNED_PATHS`：那份清单还用于 checkpoint 与状态块，会连仓库跟踪着的也一并排除。
- 测试：
  - 单元（`workdir-snapshot.test.ts`）：未跟踪的 `.pigeon/.gitignore` 与别的改动一起时，快照文件清单里没有它；提交跟踪后
    再改它，快照文件清单只有它，且内容是改后的。
  - 真容器（`sandbox-docker.test.ts`，已有用例加一条）：带未跟踪的 `.pigeon/.gitignore` 开沙箱，交回分支里 `.pigeon` 下没有文件。
- 变异：
  - 本机：去掉撤出那一行，单元用例红在未跟踪的断言；把"已跟踪"判定改成恒为未跟踪，红在已跟踪的断言。
  - 服务器（真容器）：去掉撤出那一行，交回断言红，实际值为 `.pigeon/.gitignore`。
  - 均还原并逐字核对一致。

## 第 3 件：job_kill 的输出混入 `sh: cannot open /proc/<pid>/environ`

- 现象：停后台作业后，作业输出里出现 shell 打开 `/proc/<pid>/environ` 失败的报错。
- 原因：`execution/container-host.ts` 的 `KILL_MARKED_FUNCTION`（按标记查杀，后台作业包装 `JOB_SCRIPT` 在命令结束后也调它）
  读 `environ` 与 `cmdline` 两行写成 `tr … < "$p/environ" 2>/dev/null`。重定向从左到右处理，输入文件打开失败时 shell
  当场报错，后面的 `2>/dev/null` 还没生效。进程恰好在扫描与读取之间退出，或文件读不了时就会漏出。
- 改法：两行改成 `{ tr … < "$p/…"; } 2>/dev/null`（与 `eval/stream-agents.ts` 的写法一致），并在函数注释里写明原因。
- 同类写法的排查：全仓库读 `/proc` 的输入重定向只有这两处是这种写法；同文件其余的输入重定向（取哈希、文件清单脚本）
  读的是指名文件或脚本自己建的临时文件，报错应当可见，不改；`stat` 那行由 `sed` 自己打开文件，报错已被它自己的
  `2>/dev/null` 收住。
- 测试：真容器（`container-host.test.ts` 已有的"超时与后台作业的停止"用例）停作业之前，用 `docker exec -d -u 1234` 在容器里另起
  一个别的用户的常驻进程（容器缺省没有 CAP_SYS_PTRACE，root 也打不开它的 `environ`，与进程中途退出走同一条报错路径），
  停作业后读作业输出，断言其中没有 `/proc/`。作业输出本身含 shell 报告被杀子进程的 `Killed`，属正常输出，不在断言之内。
- 变异（服务器，真容器）：换回修复前的脚本，用例精确变红，作业输出里是
  `can't open /proc/<pid>/environ: Permission denied` 与一条 `can't open /proc/<pid>/environ: no such file`
  （后者即进程中途退出的情形）。还原后逐字核对一致。

## 第 4 件：沙箱里 npm 每次告警 `Unknown env config "store-dir"`

- 现象：沙箱里每条 npm 命令都打出 `npm warn Unknown env config "store-dir"`。
- 原因：`execution/sandbox.ts` 的 `sandboxCacheEnv` 用 `npm_config_store_dir` 给 pnpm 指 store，随 `docker run -e` 进容器；
  npm 读全部 `npm_config_*`，不认这个键就告警。
- 文档（2026-10-05 查阅）：
  - pnpm 11.0 发布说明 https://pnpm.io/blog/releases/11.0 ：pnpm 不再读 `npm_config_*` 环境变量，改用 `pnpm_config_*`；
    `.npmrc` 只管认证与源，pnpm 自己的设置放 `pnpm-workspace.yaml` 或新的全局 `~/.config/pnpm/config.yaml`。
  - https://pnpm.io/configuring （当前版本）：以 `pnpm_config_`（或 `PNPM_CONFIG_`）开头的环境变量载入为配置。
  - https://pnpm.io/cli/config （当前版本）：Linux 上全局配置文件为 `~/.config/pnpm/config.yaml`，设了 `$XDG_CONFIG_HOME` 时为
    `$XDG_CONFIG_HOME/pnpm/config.yaml`，YAML 格式。
  - https://pnpm.io/10.x/cli/config （10.x）：Linux 上全局配置文件为 `~/.config/pnpm/rc`，设了 `$XDG_CONFIG_HOME` 时为
    `$XDG_CONFIG_HOME/pnpm/rc`，INI 格式。
  - https://pnpm.io/settings/store ：`storeDir` 的缺省位置（`$PNPM_HOME/store`、`$XDG_DATA_HOME/pnpm/store`、Linux 上
    `~/.local/share/pnpm/store`）。
  - 未在官方页面查到 pnpm 10 的哪个小版本起认 `pnpm_config_` 前缀；以下以实测为准。
- 实测（真容器，通用镜像，`pnpm store path`）：

  | pnpm | 只设 `npm_config_store_dir` | 只设 `pnpm_config_store_dir` | 只设 `PNPM_HOME` | 只写全局配置文件（rc 与 config.yaml） |
  |---|---|---|---|---|
  | 9.15.9 | 卷内 | 家目录缺省 store | `/workspace/.pnpm-store` | 卷内 |
  | 10.14.0 | — | 家目录缺省 store | — | — |
  | 10.15.1 | — | 家目录缺省 store | — | — |
  | 10.34.6 | 卷内 | 家目录缺省 store | `/workspace/.pnpm-store` | 卷内 |
  | 11.28.4 | 家目录缺省 store | 卷内 | `/workspace/.pnpm-store` | 卷内 |
  | 12.9.1 | — | 卷内 | — | 卷内 |

  "—"为未测。npm：设 `npm_config_store_dir` 时告警；设 `pnpm_config_store_dir` 或写上述文件时不告警，`npm config get cache`
  的标准错误为空。全局配置文件下 pnpm 各版本也没有告警。镜像不预装 pnpm，`npm i -g pnpm` 当时装到 12.9.1。
- 改法：
  - 093ec9e：环境变量改为 `pnpm_config_store_dir`（npm 不认这个前缀，不告警；pnpm 11 起认它）。
  - a0e866c：开容器时（root 建好缓存目录之后、建仓库之前）以运行用户执行一段脚本，在
    `${XDG_CONFIG_HOME:-$HOME/.config}/pnpm/` 下写 `rc`（`store-dir=<卷内 store>`，pnpm 10 及以前读）与 `config.yaml`
    （`storeDir: "<卷内 store>"`，pnpm 11 起读）；只写运行用户的配置目录，不写工作区；文件已存在不覆盖。环境变量保留作兜底。
    写不成只提示一行，不挡开沙箱（pnpm 照常能用，只是 10 及以前不走共用缓存）。
  - 测试替身 docker 的 exec 在本机真跑，为免写到跑测试的用户的配置目录，替身给"容器内"指了自己临时目录下的
    `XDG_CONFIG_HOME`。
- 测试：
  - 单元（`sandbox.test.ts`）：缓存环境变量的期望值改为新键；新增一条——第一次开沙箱写出两个文件且内容指向卷内 store，
    改掉 `config.yaml` 后再开一次，它保持不变。
  - 真容器（`sandbox-docker.test.ts`）：已有用例里断言 `npm config get cache` 得到卷内缓存目录、标准错误为空；新增一条，
    在联网的沙箱里装 `pnpm@10` 与缺省版本，去掉环境变量兜底后 `pnpm store path` 都在 `/pigeon-cache/pnpm/store/` 下
    （装不上时跳过并写明原因）。服务器上两版都实际安装并通过。

## 第 5 件：跑批日志反复出现 `fatal: path '…' does not exist`

- 现象：跑批日志里反复出现 `fatal: path 'strands-py/pytest.ini' does not exist in '<提交>'`。
- 原因：`eval/stream-facts.ts` 的 `gitHumanRepo` 用 `execFileSync("git", …)` 而没设 `stdio`；Node 在这种情况下让子进程的标准错误
  直通父进程。取人的某步不存在的文件（调用方已按"不存在"处理）时，git 的报错就打进了跑批日志。
- 改法：`stdio: ["ignore", "pipe", "pipe"]`。标准错误被收下，出错时 Node 把它带在抛出的错误信息里，其他错误仍能看到原因。
  判题逻辑不动。
- 测试：`stream-facts.test.ts` 新增一条：另起 Node 子进程调 `gitHumanRepo(…).show("HEAD", "missing.ini")` 并接住错误，
  子进程的标准错误为空，错误信息里有这个路径。去掉修复后该用例红（本机核对，非变异要求）。
