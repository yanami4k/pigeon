## 四、170 ④：说明按执行端与审批状态生成

生成函数 `runCommandTexts({ platform, approval })` 在 tools/run-command.ts，三处文字同出一源：

- 需要 shell 的命令经哪个 shell：执行端平台为 win32 时写 `cmd.exe`，其余平台（含容器执行端，平台为 linux）写 `/bin/sh -c`，与 `spawnPlan` 的实际分派一致。
- 审批状态 `approval`，由装配层按实际治理状态推出：委派策略或 yolo 旗标给出 yolo 时为 `yolo`（自动批准）；非 yolo 而注入了审批通道（REPL、TUI、worker）时为 `prompt`；非 yolo 又没有审批通道（无人值守的 `pigeon run`）时为 `none`（需要批准的一律拒绝，只有放权规则放行的能执行）。

三处落点：

| 位置 | yolo、容器执行端（linux）时的文字 |
|---|---|
| 工具登记描述（runtime.ts） | 在工作区根运行一条命令（普通命令直接执行，需要 shell 语义的经 /bin/sh -c 执行） |
| 系统提示里的 run_command 一句（runtime.ts） | 用 run_command 运行命令：普通命令直接执行，含管道、重定向或 && 串联的命令经 /bin/sh -c 执行；命令自动批准。 |
| 工具说明（tools/run-command.ts） | 在工作区根运行一条命令。普通命令不经 shell 直接执行；管道、重定向、&& 串联等需要 shell 的命令经 /bin/sh -c 运行。本会话的命令自动批准。可用 .pigeon/commands.json 登记的短名。结果带退出码、输出（超长截断）与执行前后的文件变化。 |

`prompt` 与 `none` 两档的逐字文字见 tools/run-command-text.test.ts。`createRunCommandTool` 新增可选的 `approval`，缺省按 `prompt`。

同一句系统提示之前的"写操作可能需要人工批准。"也属按审批状态写死的说法，一并改为按状态生成：yolo 为"写操作自动批准。"，prompt 保持原文，none 为"需要批准的写操作会被拒绝（本会话没有人工审批通道）。"。

read_file 与 edit_file 的说明（两种编辑模式）已逐条核对：只描述读写格式与锚点规则，不含执行端或审批的说法，无需改。

系统提示文字因此变化：正式跑用的容器执行端加 yolo 组合下，系统提示与 run_command 说明不再出现"不经 shell""不支持管道""每条命令都要人工批准"。runtime-edit-mode.test.ts 的逐字基准随之更新（本地、yolo）。

测试先行：run-command-text.test.ts（4 个用例，逐字断言三档文字与工具说明取执行端平台）与 application/runtime-tool-text.test.ts（3 个用例，经 headless 与装配根取模型实际看到的系统提示与工具说明，覆盖容器加 yolo、本地无审批通道、本地有人工审批三种组合）先写，在旧代码上因缺 `runCommandTexts` 导出而全部失败；实现后连同 runtime-edit-mode.test.ts 共 10 个用例通过。

## 七、第 7 项核查：本地开启回炉须是 git 工作区

行为本次未改。核查的问题是：删去结构化记忆后，还有哪些读者需要回炉时在宿主上打的快照。

- 回炉循环本身（headless-core.ts 的回炉部分、repair-loop.ts、验证、结果汇总）不读快照；成败标签、repair-step、episode、attempt-group、trace、replay 的推导也不读。
- 快照的读者只剩分叉一条线：`state/checkpoint-ref.ts` 的 `resolveCheckpointBefore` → `application/fork.ts` 的 `prepareFork`，调用方为失败自动分叉重试（`runRetryOnFail`）、分支会话（`runForkBranch`）与手动 `/fork`。
- 失败自动分叉重试与回炉互斥（`assertRepairSetup` 同开即报错）；分支会话的调用方从不带回炉轮数；交互会话与 `/fork` 由 session-runtime.ts 自己挂快照，不经 headless 的回炉检查。
- 提交流的回炉一律在容器执行端上跑，起点来自 `markStepStart`，不走本地快照；容器一侧"须能记下起点"的检查仍被验证前还原人写测试需要。
- run.started 的 `stepStart`（容器一侧的这一步起点）在结构化记忆删除后没有读者，仍照写，只作记录。验证前还原用的是内存里 `markStepStart` 的返回值，不读这条记录。

结论：删去结构化记忆后，本地回炉的 git 工作区要求与"开启回炉即挂快照"这一条件都不再有读者需要。唯一的副作用：若之后在交互界面里对一个本地回炉会话 `/fork` 到旧回炉 Run 之内的某一点，将找不到改前基线，`prepareFork` 会退回到对当前工作区现打一个快照——这与今天任何不开重试、不开分支的 headless 会话相同。是否放宽另行裁决；本次只把 headless-core.ts 里那条注释改为指向本节。
