# 缓存感知的上下文裁剪（第三波 3b）审计

基线 fa1cacc，依据决策 361。提交：b4a9741（设置与会话条目）、e472fd0（裁剪器）、8215e0b（接入运行面与各续跑路径）、4d8f4a2（配置文档）。改动只在 Pigeon 的适配层与装配层，没有改 pi 的包。

## 一、做了什么

裁剪器（`src/pi-runtime/context-prune.ts` 的 `ContextPruner`）：
- 候选：最近 `protectTurns` 轮（缺省 5；一条助手消息及其工具结果为一轮）之外、没裁过、没被中断补上的工具结果，分三类——过时读取（同一文件之后被覆盖它全部行的读取取代，或被 write_file 整体覆写；不论大小）、无事发生的结果（零命中的 grep、glob、search_sessions，无结果的 web_search，退出码 0 且没有输出的 run_command）、不小于 `minResultTokens`（缺省 500）的较大旧结果。占位比原文还大的不算。
- 只换工具结果的正文：消息、工具调用号、工具名都留着，调用与结果的配对不变；用户的话、模型正文、工具调用参数、思考内容、开工状态块与变化通道的消息（都不是工具结果）不碰。应用裁剪返回新数组，不改 Agent 持有的消息。
- 占位固定格式：`[已裁剪] 这里原是 <工具> 的结果（<对象>；约 N token；<原因>），为节省上下文已移出。找回：<方式>`。对象为读的文件与行范围、命令与退出码、搜索词或调用参数（截到 160 字符）；找回方式为重新读取（并写明覆盖前须重新读取）、命令输出的虚拟路径或重新运行、重新搜索、重新调用。
- 付费时机（每次请求之前）：从新到旧累加候选的裁掉量，逐个起点检查 裁掉量 × N ≥（价格比 − 1）× 改写点之后的量 与 裁掉量 ≥ `minBatchTokens`（缺省 1 万），取预计净省最大的起点，起点及之后的候选一起裁。无事发生的结果不当起点，不计入这两个条件，起点之后的随批裁掉。N 为 `horizonTurns`（缺省 20），不做动态预测。
- 免费时机一次裁光候选：压缩之前；Run 开始时模型、广告的工具集或系统提示与上一个 Run 不同（比 Run 开始条目的这三项；开工状态块不在系统提示里，它的变化不算）；空闲超过缓存保留时长（距本进程上一次请求，没有时距最后一条助手消息）。
- token 量按上游 `estimateTokens`（与压缩判定同一口径）。
- 每次裁剪产出一条记录；裁掉的 run_command 输出没落盘的（没截断的整段输出）经 `CommandOutputStore.save` 补落盘（临时文件独占新建、取身份、写完提交，同收集器），占位给出虚拟路径；已落盘的用原路径。裁掉的读取在上下文里再没有同一文件没裁的 read_file、write_file、edit_file 结果时，从读取记录里撤掉（`FileReadTracker.forget`），之后覆盖须重新读取。

价格比（`src/state/prune-config.ts` 的 `priceRatioOf`，重写价 / 命中价，与币种无关），取值顺序与出处：
1. 设置 `contextPrune.priceRatio`。
2. 缓存规则写明该服务方不做缓存（`mode` 为 `none`）时按 1，此时只受最小批量约束。出处：缓存规则表（`src/state/cache-rules.ts`，按实际服务方定键，每行附官方出处、取用日期与原文引句）。
3. 模型信息的价格（`modelProfile`）：重写价取未命中价与写缓存价中较高者，除以命中价；设置给了 `writeMultiplier` 时写缓存价按未命中价乘它算。出处：模型信息通路（设置手填 > 接入模块声明 > pi-ai 自带目录），各项来源记在 Run 开始条目的 `modelInfo`。
4. 缓存规则较短一档的写入、读取倍率：max(1, 写入倍率) / 读取倍率。出处同 2。
5. 都取不到按 50（`UNKNOWN_PRICE_RATIO`，价差很大，付费裁剪从严）。

保留时长：设置 `contextPrune.retentionSeconds` > 缓存规则较短一档的秒数 > 未知（不按空闲裁）。

运行面（`src/pi-runtime/adapter.ts`）：
- Agent 的 `transformContext` 在每次请求之前应用已有裁剪并按时机新裁，新裁的写一条会话记录；出错照原样发出，错误进监听错误。
- 压缩判定按裁剪后的上下文估算，并减去裁了还没随请求发出的量；超过触发点时先一次裁光候选，按裁掉的量重判，降到触发点以下即不再压缩（`ContextCompactor.exceeds`）。轮间与 Run 开始之前两处都如此；手动压缩不经裁剪。压缩摘要读的是会话记录里的原文。
- 每个 Run 开始时把模型、广告工具集与系统提示交给裁剪器比对。

会话记录与重放：
- 新条目 `pigeon.prune`（`PruneDataSchema`）：runId、时机、各项（工具调用号、工具名、原因、原来的 token 数、占位原文）、价格比、N、裁掉量、改写点之后的量、估算的代价与节省（按命中价折算的 token 当量：代价为改写点之后的量 ×（价格比 − 1），免费时机记 0；节省为裁掉量 × N）、前后的上下文 token 数、时刻。
- 组装请求时按工具调用号应用记录里的占位原文；压缩后保留段里的同一工具结果照样应用。
- 起点 `PruneSeed`（已有的占位与上一个 Run 的模型、工具集、系统提示）：续跑取会话记录主分支（`pruneSeedFromEntries`），`/reload` 取旧运行面的裁剪器，worker 续做、分叉续跑取各自会话记录，经 `RuntimeDeps.pruneSeed` 交给新运行面。
- 总开关关掉只是不再新裁，已有记录照旧重放（前缀不变）。

其他：
- 打转检测看的是上游 `turn_end` 事件里的原文，不经 `transformContext`，不受裁剪影响。
- worker 经同一个装配根与运行面，按同样的规则各自裁剪。
- 设置新节 `contextPrune`（`enabled`、`protectTurns`、`horizonTurns`、`minBatchTokens`、`minResultTokens`、`priceRatio`、`writeMultiplier`、`retentionSeconds`、`onCompaction`、`onIdle`、`staleReads`），缺省开启；工具集、系统提示或模型变化这一种免费时机随总开关。`docs/configuration.md` 加节表一行与"上下文裁剪"一节。
- 会话时间线视图不列 `pigeon.prune` 条目（不认识的自定义条目照旧跳过）。状态栏的上下文用量仍按未裁剪的消息估算。

## 补记：验收修正（9cb81b2、daaa9b7、16fc65a、48610ca、1fadd3e）

命令结果与无事发生（16fc65a、9cb81b2）：
- run_command 算无事发生须退出码 0、没有输出而且没有文件变化（`fileChanges` 的新增、删除、修改都为空，且差异完整、没有取证说明；没有 `fileChanges` 的按说不准处理，不算）。此前只看退出码与输出：带文件变化清单的结果被判为无事发生，占位写"没有结果"，清单丢了。
- 命令结果裁剪时，有文件变化（或说不准）的，占位末尾原样保留结果正文里"文件变化"一段，换掉的只是输出部分。
- 空输出不落盘，占位写"这条命令没有输出"。此前对空输出也补落盘，会落一个空文件。
- web_search 的 details 加 `answered`（后端给了非空的答案）；没有结果但带了答案的不算无事发生，算无事发生须 `answered` 为 false（旧记录没有这个字段的不算）。

找不回的命令输出不裁（16fc65a）：
- 截断了而全文没落盘的（没有 `savedOutput`，含有 `savedOutputError` 的）不当候选：上下文里的开头与末尾是唯一副本，命令可能有副作用。没有 details 的命令结果同样不当候选。
- 补落盘失败（抛错或没给出路径）的不裁；付费时机去掉它们后重新选改写起点。
- 只存了前一部分的（`savedOutput.partial`），占位写"已保存的是输出的前 N 字节（全文超过落盘上限），存为……"，不写"完整输出"。
- 落盘总量满了被清理的输出（daaa9b7）：索引另记按上限清理掉的编号（`index.json` 的 `evicted`），读到它们时报"该输出已按落盘总量上限清理，需要时重新运行命令"，编号从来没有的报"不存在（编号不对）"。命令占位的找回方式补"（若已被清理，需要重新运行）"。

先记后用与出错回退（16fc65a）：
- 裁剪器先算定各项占位与整条记录，交给写入回调写进会话记录，写成之后才生效（改内存里的占位、撤读取记录、记裁剪时刻）；写入回调抛错即不生效，错误照抛。运行面的写入回调 `#writePrune` 不再吞掉写入错误。
- 请求之前新裁出错时，运行面回退到只应用已有的裁剪（`view(messages)`），之前的占位不撤，那次请求的前缀不变；此前回退到原始消息。压缩之前的裁剪写不成时这次不裁、照常压缩。

状态栏口径的核对（第 4 条，按 a1ebb86 之后的代码）：
- 请求出错，或撞上限续跑把带新 usage 的回复移出之后：估算所用的是更早那条正常回复的 usage，其时刻早于裁剪时刻，裁掉的量按时刻比较照样减去，不偏高（a1ebb86 的测试覆盖请求出错一种）。
