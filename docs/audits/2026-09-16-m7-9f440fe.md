## 各段交付

### S1 数据层（068–072、075、077、078）

- `state/event-log.ts`：Event Log v10 → v11 加法式升版。child.spawned 加可选 `taskKey`；新增 `attempt.verified`（三值结论、命令参数数组、退出码、耗时、输出字节数与哈希及尾部、所在工作区、对应的会话与 Run，信封 Run 可缺省）、`session.forked`（分叉点的 Run 与条目号、分支会话号、分叉点快照 ref 与提交、触发方式）、`branch.header`（分支会话首条记录，指向来源会话与分叉点，工作区恒为 git 工作树）、`distill.skipped`（任务标识、原因、各尝试标签）四族；新增 `workspace.checkpoint`、`run.limit-hit`、`tree.write-failed` 三个观察族。v10 → v11 迁移对候选提出记录内嵌的候选显式升级到 v3。
- 快照与条目号的对应落在 `workspace.checkpoint` 观察记录里（ref、提交、树、首个快照的改前基线、工具调用号、对应条目号），`state/materialize.ts` 的 `checkpointAtOrBefore` 按 Run 与条目号查询。
- `state/candidate.ts`：候选 v3，v2 字段不动；来源新增"提炼器"；加法式新增对比来源块（产物形态、成败两侧尝试引用、分叉共享前缀、其余同组尝试）；v2 → v3 迁移登记进机检表。
- `state/outcome-label.ts`：五个标签纯函数与账本事实组装。判定顺序为：缺运行结束或有悬账 → 未知；有验证结论 → 通过即成功、失败即失败、未判定即未知；无验证时撞上限 → 失败、熔断 → 失败、人主动取消 → 放弃、基础设施错误单列、业务失败 → 失败、正常完成与分类未知 → 未知。验证记录可来自其他会话文件（worker 尝试的验证落在父会话）。
- 撞上限留痕：上限中止在运行终态上表现为中止，编排器与 headless 在中止前经运行面写 `run.limit-hit`，标签据此判失败。
- `state/materialize.ts`：候选两族与不可解析记录属于引用型记录，不在本会话造出 Run（提炼宿主会话引用的是别的会话甚至别的治理根里的 Run）。
- 版本钉死：四个钉 Event Log 版本、一个钉候选版本的既有断言推到新版本；cli replay 逐记录渲染补齐新族。

### S2 EpisodeBuilder（070、073）

- `state/episode.ts`：`firstRunOf` 与 `buildTaskAttempt` 取尝试会话的首个 Run（恢复追加的 Run 不计入）；`selectContrast` 只让成功与失败进对比，每侧只取一个（成功侧取总轮数最少，失败侧取最早收尾），其余进 others，全成功、全失败、凑不齐两侧分别给出跳过原因；`buildForkGroup` 产出共享前缀（来源 Run 第 1 条到分叉点）一次，来源侧从分叉点之后开始、分支侧取分支会话首个 Run，分叉点不一致拒绝成组；`collectLocalPairs` 只取人审批且理由来源为人写的拒绝，与域错误后紧跟的同工具成功重试。

### S3 验证命令（071）

- `execution/check-command.ts`：执行核心从 Eval 验证器下沉（独立子进程、超时终止进程树、输出只留尾部并记字节数与哈希、三值判决），Eval 验证器改为调用它，行为不变。会话级验证命令是人配置的一行命令，经系统 shell 执行，记录的参数数组即实际交给子进程的参数。
- 配置：`--verify-command <命令>` 与 `--verify-timeout <毫秒>`（缺省 5 分钟），cli REPL / resume、tui 与 pigeon run 接受，eval 不接受；冻结进注入快照 v7（顶层 `verify` 与 `retryOnFail`）并随 run.started 落盘。
- 执行：主会话在 Run 结束后于工作区根后台执行，记录写本会话；headless 在尝试收尾后执行，记录写本会话；并行同任务的每个尝试在各自工作树执行，记录写父会话。结果不进模型可见的消息。未配置时不跑，正常完成的尝试标签为未知。

### S4 提炼器（074、076）

- 角色：`orchestration/roles.ts` 新增 distiller，白名单只有 `distill_snapshot` 与 `distill_entry` 两个 read 档工具，与审阅快照工具同构地豁免子集约束（父策略 deny 照旧生效）；工作区规划为无工作区；派出 distiller 必须带提炼目标。
- 输入：`distillation/snapshot.ts` 沿用 M6 单条截断；每侧上限 24,000 字符，超出从最早处整条丢弃并标注；任务描述只喂一次（同任务比对时各尝试的第 1 条不再重复，分叉时只跳过任务所在那条）；共享前缀单列一次；两侧按各自条目号原样列出，不做分歧步对齐；Run 内局部对按侧单列。`distill_entry` 按侧与条目号回查，范围外与未纳入的会话一律读不到。
- 落盘：`distillation/candidates.ts` 复用 M6 的按哈希暂存、扫描与账本两族（`review/candidates.ts` 抽出 `stageCandidate`）；产出规则为流程与步骤集必须有成功侧证据，只由失败侧支撑的条目只能是教训且不得为 memory；逐项校验，不合格单项丢弃并留一条不可解析记录说明。
- 派发：`application/distill-runtime.ts`，预算 16 轮、5 分钟、80,000 token，与 Reviewer 共用全局并发闸，闸忙时排队等待；派出记录不回指 Run（宿主会话与被提炼尝试不是同一会话）。
- 自动触发：`application/attempt-group.ts` 并行同任务派发全部收尾并验证后选对，凑成两侧即提炼，否则记提炼跳过；`application/fork.ts` 的失败自动分叉重试在叶子验证完成后提炼分叉组。Eval 不自动触发。
- 入口：`pigeon distill (--task <任务标识> | --eval-results <目录>) [--force]`。`--task` 在本治理根里按派出记录找宿主会话；`--eval-results` 只读读取结果目录下的会话、按任务编号成组，宿主会话新建在本治理根；`--force` 对全失败只取最早收尾的失败侧（只产出教训），对全成功取总轮数最少的成功侧。tui 新增 `/spawn <角色> --attempts <N> "<任务>"`。
- 分层规则：distillation 从占位规则移出，新增 `distillation-below-controller`（只依赖 state、tools、persistence 与 review）；application 放行 distillation。

### S5 快照（078）

- `orchestration/checkpoint.ts`：会话首次改动之前在内存里记基线树；写档或命令档工具落定后，以用户索引为起点复制一份临时索引（`GIT_INDEX_FILE`），`add -A` 后从临时索引摘掉 `.pigeon`，`write-tree`，树与上一次不同才 `commit-tree`（首个快照的父提交是改前基线提交）并 `update-ref` 到 `refs/pigeon/checkpoints/<会话>/<序号>`；恢复的会话接着已有序号与快照链。非 git 工作区构造快照器即报错。
- `application/checkpoints.ts`：订阅 tool.proposed 与 tool.settled，只对写档与命令档工具生效；快照记录的条目号取"当前条目号 + 1"（Adapter 写死顺序执行，上游在 tool_execution_end 之后紧接着发该工具结果消息），记录同时带工具调用号可交叉核对。主会话在 git 工作区挂载；headless 只在开了失败自动重试或本身是分支会话时挂载。
- 测试断言三件事不受影响：工作区状态（含未跟踪文件）、暂存区内容与索引、当前分支与 HEAD；另有 `.pigeon` 已被忽略的仓库照常生成快照的用例。

### S6 会话树与分叉（068、077、079）

- `pi-runtime/session-tree.ts`：每个根会话一个树文件，放 `.pigeon/trees/`（上游按 cwd 编码子目录）；根会话走 main 通道，分支会话以自己的会话号为通道，在分叉条目上建出；树条目号即账本条目号。树里的消息由账本投影：正文取内容文件，助手消息的停止原因、用量与错误取同一 Run 内对应次序的 turn.completed，工具调用参数取 tool.proposed，模型身份取 run.started。未持久化或被编辑的思考块不进消息，图片只留占位文字。
- `application/session-tree.ts`：由账本重建（删树后从根会话导入 main 通道，再沿分叉记录建通道、导入分支，逐层递归）；实时写穿按批缓冲，下一条助手消息、用户消息或 Run 结束时整批投影并在后台队列追加，不 fsync、不阻塞主循环，失败只记 `tree.write-failed`；进程内共享树句柄（同一树文件只开一个 Session）；`pigeon tree rebuild <sessionId>` 可从树里任一会话出发整棵重建。
- 契约测试：`pi-runtime/session-tree-conformance.test.ts` 用 `createSessionBackendConformance` 对 JsonlSessionRepo 跑上游 30 条用例；上游用例调用 create 与 fork 时不带 cwd，按用例独立临时根包一层补上。
- 分叉：`application/fork.ts` 依次校验来源工作区是 git 工作区、定位分叉条目、选分叉点之前最近的快照（同 Run 内不晚于分叉条目的最后一个，其次更早 Run 的最后一个，再次首个快照的改前基线并补挂 ref，会话从未改过文件时取现状快照）、在来源会话文件记分叉记录、建树或加通道、从快照开独立工作树（沿用工作树管理，分支名 `pigeon/fork-<会话号后 8 位>`）、经 buildSessionContext 还原分支消息。续跑以 headless 核心装配：分支会话头先写，Agent 以还原的消息为初始状态；分叉点末条是用户消息或工具结果时不给新输入直接续跑（Adapter 新增 `continueRun`，对应上游 `continue`），末条是助手消息时必须给新输入；分支会话实时写穿，释放前等队列落完。
- 手动分叉：cli REPL 与 tui 主会话 `/fork [--at <条目号> | --at <Run 号前缀>:<条目号>] ["新输入"]`，缺省分叉点是最近一次 Run 的任务开始处；分叉后来源会话此后实时写穿。恢复分支会话时回到它自己的工作树。
- 失败自动分叉重试：`--retry-on-fail <K>`（缺省 0）在 cli REPL / resume、tui 与 pigeon run 接受，冻结进注入快照与 run.started；尝试标为失败时从该 Run 第 1 条分叉，以 `continueRun` 续跑、不注入任何提示，某次不再是失败即停，最多 K 次；主会话在后台进行，pigeon run 在同一进程内顺序进行；并行同任务派发不叠加。
- 上游版本探测：`pi-runtime/upstream-version.ts` 读取 pi-agent-core、pi-ai、pi-tui 的实际版本与已验证的 0.84.4 比对，cli、tui 启动时不一致或读不出即向标准错误输出告警。

### S7 收尾期间补的缺陷（均先补红测试或断言再修）

- 结构化结果解析：真实模型在 JSON 前写分析文字再给 json 围栏，原解析只接受整段 JSON，提炼器以完成收尾却被判"没有交回结构化结果"。改为取最后一个能解析成对象的围栏块，其次首个 `{` 到末个 `}`；Reviewer 同样受益。提炼结果改为逐项校验（真实输出里有一项把种类写成不存在的值）。
- 验证命令收尾：超时终止后孙进程仍占着输出管道时 close 迟迟不来、拉不起进程时只有 error 没有 close，判决会无限等待（变异执行时在负载下暴露为该用例挂到测试超时）。改为 error 在未拉起时立即收尾、超时终止后 5 秒宽限内仍无 close 即销毁管道按超时收尾。
- 施工中由测试暴露并修正的实现缺陷：`.pigeon` 已被忽略时排除路径写法使 `git add` 报错（快照静默失败）；临时索引上摘除 `.pigeon` 需要跳过暂存内容安全检查；turn.completed 由助手消息的 message_end 归一化而来、早于该轮工具调用，写穿原先按 turn.completed 入队丢了工具参数，与重建不一致；进程内对同一树文件的重复导入。

## 收口修复

本节只追加，不改动上文。三处缺陷在 M7 交付之后复核发现，修法一律先补红测试再改。

### 一、快照 ref 序号竞态（同一会话出现两个快照器实例）

机理：快照器的序号计数在实例的内存里，构造时从 `for-each-ref` 读到当前最大序号作为起点。主会话运行时由 `application/checkpoints.ts` 挂了一个实例；`application/fork.ts` 的 `prepareFork` 又对同一个来源会话新建了一个实例，构造时读到同一个起点。随后两个实例都会写 `refs/pigeon/checkpoints/<会话>/<n+1>`，而 `update-ref` 不带旧值，后写者静默覆盖前一个。分叉本身用的是账本里记的提交号，不会立刻开错工作树；被覆盖的那个 ref 指向的提交（典型是分叉时为改前基线补挂的 ref）从此没有任何引用，可能被 git 回收，之后从同一分叉点再分叉就取不到该基线。

修法：

- `prepareFork` 新增可选的快照器入参，调用方传入运行面已挂的实例；只有拿不到实例时（冷会话上的分叉）才新建。`ForkBranchRequest` 与 `runRetryOnFail` 一并透传。落点：`application/fork-command.ts`（手动分叉，cli REPL 与 tui 同走这一份）、`application/session-runtime.ts`（主会话后台失败重试）。`application/headless.ts` 的重试发生在单次运行的运行面释放之后，来源会话此时没有在场的实例，仍按冷会话新建。`session-runtime.ts` 上 `OpenedSessionRuntime.checkpoints` 这个字段至此有了生产消费者。
- `orchestration/checkpoint.ts` 的 ref 写入改为一律带旧值守卫：新建传空旧值（git 语义即"该 ref 必须不存在"），更新传旧提交号做比较交换，冲突时抛 `CheckpointError`，不静默覆盖。守卫由 git 的 ref 锁执行，跨进程同样生效。

红测试（`application/closeout-fixes.test.ts`）：

- 「分叉复用运行面已挂的快照器……」：主会话改一次文件（快照 1）→ 从任务开始处分叉（改前基线补挂快照 2）→ 来源会话再改一次（快照 3），断言该会话名下恰有三个 ref、编号 1–3 连续、指向三个不同提交、逐个能解析，且快照器内部错误清单为空。
- 「快照 ref 旧值守卫……」：同一会话构造两个实例各写一次，断言后写者明确报错且先写的 ref 原样还在。

### 二、并行同任务派发里验证记录落盘失败被吞

机理：`application/attempt-group.ts` 中 `verifyAttempt` 的返回值被直接丢弃，其 `recordError`（账本写失败）既不进错误清单也不上抛；同一函数在 `application/attempt-verify.ts` 的主会话挂载里是进错误清单的，两处口径不一致。后果是并行派发下验证跑过但记录没落库时运行面完全不知情，尝试随后按"未知"标签参与选对。

修法：两处统一到主会话挂载的口径——`AttemptGroupResult` 新增 `errors`，`recordError` 在场即入列，不改变尝试结果。

红测试：「并行同任务派发：验证记录落盘失败进错误清单，不被吞掉」——账本的验证记录写入必定抛错，断言两次尝试的失败都在结果的错误清单里且错误信息可见。

### 三、快照器与提炼派发器的内部故障无人读

机理：`application/checkpoints.ts` 的 `errors()` 与 `application/distill-runtime.ts` 的 `errors()` 在生产代码里都没有消费者。快照生成失败（例如临时索引拷贝撞上并发的 git 操作）、候选落盘失败在运行时完全静默。

修法：不新增账本记录族（账本只记运行事实，内部故障属运行时诊断）。新增 `application/warnings.ts`：按故障类别去重的告警器，缺省写标准错误，口径与上游版本探测的启动告警一致——文案说明后果，一次运行里同一类故障只说一次。故障类别取错误类型加首个"："之前的摘要，git 失败里的一次性内容（临时索引路径等）不进类别。两处接上：

- 快照：`工作区快照告警：<原因>（该时点没有快照，从这里分叉会回退到更早的快照）`
- 提炼：`经验提炼告警：<原因>（这次提炼的候选没有落库，不影响运行）`，编排器侧的故障另给一条说明该次提炼没有产出。

红测试：

- 「去重告警器：同一类故障只说一次，不同类各说一次」。
- 「快照器内部故障：向标准错误告警一次，文案说明后果；错误仍进内部清单，运行照常收尾」：挂载之后把工作区的 git 目录移走，使快照必定失败（真实故障，不是桩），跑两个 Run，断言标准错误上该类告警恰好一条、含后果说明，内部错误清单仍记录全部故障，文件改动照常落地。
- 「提炼派发器内部故障：候选落盘失败向标准错误告警一次，同时进错误清单」。

### 顺带：分叉成组时来源侧的空区间

机理：`state/episode.ts` 的 `buildForkGroup` 用"分叉点加一"作为来源侧的条目范围起点，而 `buildTaskAttempt` 的范围终点取"起点与末条号的较大者"。分叉点恰是该 Run 最后一条时，来源侧在分叉点之后没有独有条目，范围被算成"从 n+1 到 n+1"的一条，写进候选对比来源块里是失真的。

修法：在成组时判定——来源 Run 的末条号不大于分叉点时，来源侧只贡献共享前缀，不作为一次可对比的尝试进组。条目范围的语义因此不必放宽下界，候选 schema 不动。同时把"Run 末条号"抽成 `lastRunSeqOf`，成组与建尝试共用一份口径。

红测试（`state/episode.test.ts`）：「分叉：分叉点是该 Run 最后一条时来源侧没有独有条目，不进组（不造出空区间）」。

### 一、写穿失败改走告警，删掉 `tree.write-failed` 记录族（077 修订 + 080）

依据：会话树是可重建的派生缓存，写穿失败的后果是树落后于账本，可由重建入口随时补齐，不需要事后从账本取证；Event Log v11 尚未入库，此时去掉记录族为零迁移成本。原结论中"写穿失败只记观察记录"这半句作废，"失败不影响运行"仍然有效。

改动：

- `application/session-tree.ts` 的写穿队列改为调用 `application/warnings.ts` 的去重告警：`会话树写穿告警：<原因>（会话树落后于账本，可用 pigeon tree rebuild <根会话号> 补齐）`。同一类故障（磁盘满、文件被占）会在每一批上复发，去重后一次运行只说一次。入队函数不再需要 Run 号，随之去掉。
- 记录族整个删除，不保留解析兼容：`state/runtime-events.ts` 去掉观察族枚举项与 payload schema，`state/event-log.ts` 去掉记录 schema 与观察族联合成员（`ObservationInput` 的映射类型随之收窄，任何遗留的追加调用都编译不过），`state/materialize.ts` 去掉物化字段与归集分支，`cli/replay.ts` 去掉逐记录渲染分支。迁移完整性机检按版本化 schema 枚举，不按记录族枚举，故无需登记改动；v11 记录联合少一支后，`parseEventRecord` 对该 kind 直接拒绝——因为 v11 未入库，没有任何历史数据会命中。决策索引里 077 的锚点行一并去掉该族。

红测试（`application/fork.test.ts`，由原"只记观察记录"用例改写）：写穿必定失败的树句柄上跑两个 Run，断言标准错误上该类告警恰好一条、含可重建补齐的说明，账本里没有任何该族记录，两个 Run 都照常完成。

### 二、子集校验按角色取豁免集合（040 修订）

依据：第二道校验的意义是发放侧写错也能拦住；用合并的只读工具集合会让它比发放侧更宽，拦不住的恰是发放侧最易犯的错（新增只读角色时把作用域工具发串），而角色还会继续增加。

改动：`orchestration/roles.ts` 的 `assertPolicySubset` 增加必填的角色参数，豁免集合改为复用发放侧已有的按角色表——Reviewer 只豁免审阅的两个只读工具，提炼器只豁免提炼的两个，其余角色一个都不豁免。合并集合常量删除。生产唯一调用点在 `orchestration/workers.ts` 的派出路径，派出时角色已知。

红测试（`orchestration/distiller-role.test.ts`）：「子集校验按角色取豁免集合……」——reviewer 策略里混入提炼快照工具、提炼器策略里混入审阅条目工具、不带作用域工具的角色拿到审阅快照工具，三种都断言拒绝；两个角色各自由发放侧正常构造出的策略仍断言通过。

### 三、候选里的产出会话字段改中性命名（065 修订）

依据：该字段原以审阅命名，现同时承载提炼器会话，M8 还将加入验证器一类产出方；v3 尚未入库、迁移本就要跑一遍，此时改名零额外成本。

改动：候选来源里的 `reviewSessionId` 改为 `producerSessionId`（含义是产出该候选的会话，产出方类别仍由 `origin` 区分）。落点是 schema（`state/candidate.ts`）、两个写入侧（`review/candidates.ts` 的审阅候选、`distillation/candidates.ts` 的提炼候选）、装配层（`application/review-runtime.ts`）与两处渲染（`application/candidates-list.ts`、`cli/trace.ts`，标签由"审阅会话"改为"产出会话"）。v2 → v3 迁移在原本的纯版本推进之上改写字段名，值不变；v1 迁移而来的保留形状没有来源块，不受影响。

红测试（`state/candidate.test.ts`，由原 v2 → v3 用例改写）：构造带旧字段名的 v2 候选，断言迁移后新名在场且值不变、旧名不再保留、其余字段原样、迁移结果通过当前 schema 校验。

### 四、共享前缀单独设 12,000 字符上限（076 修订）

依据：两侧是对照物本身，削任一侧都使对比失真；前缀是背景，削它最安全。最坏总量由约 72,000 字符降至约 60,000。

改动：`distillation/snapshot.ts` 的分段函数增加上限入参——两侧仍各 24,000，共享前缀按新增的 12,000 常量。超出的处理方式不变：从最早处整条丢弃，标注省略条数与字符数，可用提炼条目工具按条目号回查。

红测试（`distillation/snapshot.test.ts`）：「共享前缀上限 12,000 字符……」——构造约 40,000 字符的共享前缀与约 40,000 字符的来源侧，断言前缀留下的字符数不超过 12,000、最早的条目先被丢弃、省略标注与回查提示在场，同时断言来源侧留下的字符数在 24,000 以内且明显多于 12,000（两侧不受前缀上限影响）。

## 第三批收口：不可解析记录族的字段改名（065 修订）

本节只追加，不改动上文。

依据：结构化结果不可解析记录族的 payload 里记产出会话的字段原以审阅命名，而该族同时由审阅器与提炼器写入，与候选来源侧是同一个概念；065 的修订要求产出会话字段统一为中性命名。上一节把候选侧改到位后，这一族是最后一处以角色命名的产出会话字段。

改动：

- `state/runtime-events.ts` 的 payload schema 字段改为与候选侧同名的 `producerSessionId`。
- 与候选侧不同，这一族是 M6 已入库的形状，旧记录必须真的改写：`state/event-log.ts` 的 v10 → v11 迁移新增一支——记录 kind 是该族时，把 payload 里的旧名原样搬到新名，值不变，其余字段照旧；已是新名的原样返回。迁移链只在末尾按当前 schema 校验一次，改写必须落在链上（与内嵌候选、内嵌 receipt 同一处理方式）。
- 两个写入点（`review/candidates.ts` 的审阅侧、`distillation/candidates.ts` 的提炼侧，后者含逐项丢弃留痕）与两处渲染（`cli/trace.ts`、`cli/replay.ts`）一并同步；渲染措辞由"审阅结果不可解析／审阅会话"改为"结构化结果不可解析／产出会话"，与该族同时承载两种产出方的事实一致。
- `/review` 命令路径上表示审阅 worker 会话的局部变量与返回字段仍以审阅命名：那是审阅专有的派发接口，不是记录形状，未改。

红测试（`state/contrast-records.test.ts`）：「v10 的不可解析记录经迁移链升到 v11……」——构造带旧名的 v10 记录，断言升到 v11 后新名在场、值不变、旧名不再保留、通过当前 schema 校验。同一文件里 v10 内嵌候选的夹具一并订正为旧名（此前误用了新名，使候选侧的改名迁移在事件日志链上未被覆盖），并补断言：内嵌候选的产出会话字段也已改名。
