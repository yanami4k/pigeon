# 回炉：验证不过就在同一会话里接着修，到上限撤回（决策 142、143、147、154，基线 aaa59a8）

范围：只做 headless 路径（`pigeon run` 与评测跑批经 `runHeadless` 走的那条）。REPL/TUI 与并行 worker 路径、结构化记忆、验证命令分步、跑批器、容器执行端的"回到这一步起点"均不在本次范围内。不新增账本记录种类。

## 一、开启与互斥

- 轮数来源：启动参数 `--repair-rounds <N>`（只有 `pigeon run` 接受）> 项目验证配置 `.pigeon/verify.json` 的 `repairRounds` > 0。参数给 0 即关闭，压过项目配置。`verify.json` 的 `repairRounds` 为加法式可缺省字段，v1 旧文件逐字有效，不升版本。解析在 `application/launch-flags.ts` 的 `resolveRepairRounds`，读取在 `persistence/verify-config.ts` 的 `loadProjectRepairRounds`。
- 缺省 0 即关闭：不打快照、不在释放之前验证，验证仍按原口径在会话释放后独立执行，行为与基线一致。
- 启动即报错（`application/headless-core.ts` 的 `assertRepairSetup`，在装配运行面之前）：
  1. 设了轮数而没有验证命令；
  2. 与 `--retry-on-fail` 同时开启，文案说明两者对同一次失败各有一套处理，叠加后这一步的成败与撤回无法判定；
  3. 没有可用快照：注入了执行端（容器），或工作区不是本地 git 工作区（154②）。

## 二、流程

`runHeadlessOnce` 在同一个运行面句柄上循环：

1. 一次 Run 结束后，在释放之前经运行面的会话文件落一条 `attempt.verified`（与原验证同一个 `verifyAttempt`）。
2. 通过：结束。无法判定（超时、被信号杀掉、进程起不来）：不回炉，记为未知，结束。
3. 失败：轮数未满且预算未耗尽时，把回炉反馈作为新一轮输入，在同一会话里开一个新 Run。反馈由 `application/repair-loop.ts` 的 `buildRepairFeedback` 生成：轮次（第 i/N 轮）、验证命令、退出码、输出末尾（沿用验证记录的 16 KiB 尾部，截断时注明）、"修正代码直到验证通过，不要修改测试文件。"。末尾留附加内容注入点 `repairAppendix`，缺省为空。
4. 轮数用满或预算耗尽仍失败：按快照撤回，这一步记为失败。

预算（147）：轮次、token 与墙钟计数器在整个循环里只建一次，各轮与首次共用；墙钟定时器覆盖验证命令的耗时。任一上限触发后不再回炉，按撤回处理，结果标注 `budgetExhausted: true`。

## 三、撤回

- 开启回炉时强制挂快照（与分叉会话同一个 `attachCheckpoints`）。撤回起点由账本现算：本会话首个带改前基线的快照记录的 `baseCommit`，即第一个 Run 首次改动之前的工作区状态。没有这样的记录即这一步一次文件都没改过，无需恢复。
- 恢复实现为 `orchestration/checkpoint.ts` 的 `restoreWorkspaceTo`：先删掉范围内、目标提交里没有的文件，再经临时索引（`GIT_INDEX_FILE`）把目标提交的文件逐个写回。工作区所在仓库的 HEAD、暂存区与分支不动。
- 范围（154③）与快照相同：受跟踪的文件，加上未跟踪且未被忽略的文件；被忽略的文件与治理目录 `.pigeon/` 不动。
- 可重复执行：已一致时再执行一次，结果不变；恢复不写账本，进程崩溃在最后一次验证之后、恢复之前时，续跑按账本推出已撤回，再调用 `restoreStepStart` 即可。恢复抛错时，结果的 `errorMessage` 注明"可重复执行恢复"，这一步仍记为撤回。

## 四、账本中的表达（154①，含 2026-09-23 修订）

- 不新增记录种类。`run.started` 载荷增加可选字段 `repairRounds`（开启时在场，最小值 1；一步里的每个 Run 同值），注入快照同步增加该字段。`EVENT_LOG_VERSION` 14 → 15，`INJECTION_SNAPSHOT_VERSION` 9 → 10，两级迁移均为纯版本推进。各测试文件里钉当前版本的断言同步改为 15 或 10。
- 一步的组成（`state/repair-step.ts`）：回炉开启的会话里全部 Run 即一步；一步的身份是首个 Run（`runId` 字段）。
- 撤回推断 `repairStepOutcome`：回炉开启，且这一步最后一个 Run 有验证记录、结论为失败，即已撤回。最后一个 Run 没有验证记录即这一步未收尾，推为未撤回、`verdict` 缺省。不区分轮数用满还是预算耗尽。
- 推断的几种进程中断时点：

| 中断时点 | 账本状态 | 推断 | 标签 |
|---|---|---|---|
| 某轮回炉 Run 结束之后、其验证落盘之前 | 最后一个 Run 有 `run.ended`、无验证 | 未撤回（未收尾） | 未知 |
| 某轮回炉 Run 进行中 | 最后一个 Run 无 `run.ended`、无验证 | 未撤回（未收尾） | 未知 |
| 最后一次验证（失败）落盘之后、恢复之前 | 与正常撤回相同 | 已撤回；续跑重新恢复 | 失败 |
| 验证失败落盘之后、下一轮 `run.started` 之前 | 最后一个 Run 有失败验证 | 已撤回 | 失败 |

最后一行是剩下的一个推错窗口：这一步实际还要接着回炉，工作区未恢复，推断却为已撤回。它与"修满后撤回"在账本上无法区分：两者都是最后一个 Run 带失败验证，差别只在当时是否还有剩余轮数与预算，而预算用量不在账本上（154 未选"按账本时间戳冷算预算"）。本次未新增记录，待裁。续跑时推为已撤回、再执行一次恢复，工作区回到这一步起点，这一步记为失败；与实际应得的结果（接着修，可能修好）不同。

## 六、可观测

headless 结果（`runHeadless` 返回值，`pigeon run --json` 原样输出）与评测结果行（`results.jsonl`）在回炉开启时带同名字段 `repair`：

| 字段 | 含义 |
|---|---|
| `repair.rounds` | 用了几轮回炉（首个 Run 不算） |
| `repair.verdict` | 这一步最后一次验证门的结论（`pass` / `fail` / `undetermined`）；运行面没装起来时缺省。评测行里它与判据的 `verdict` 是两回事 |
| `repair.reverted` | 是否撤回 |
| `repair.budgetExhausted` | 撤回是否因预算耗尽而提前 |

回炉关闭时不带该字段，行形状与基线一致。`pigeon run` 的文本收尾摘要追加"回炉 N 轮 ｜ 最终验证 X"，撤回时再加"已撤回"，预算耗尽时注明"（预算耗尽提前撤回）"。评测跑批经 `runEval` 的 `verify` 与 `repairRounds` 选项开启；`pigeon eval` 命令行未接这两个参数。

## 七、测试

`application/repair-loop.test.ts`（真实 git 仓库、真实装配根、可编排的假模型；验证命令是仓库里的脚本，`a.txt` 为 `fixed` 时通过）：

- 一轮修好：第一次失败、第二次通过；同一会话两个 Run、两条验证记录，`run.started` 冻结轮数；从首个 Run 取标签与对比尝试标签均为通过；指标按整步汇总。
- 整步失败分类：首个 Run 撞输出上限（业务失败），回炉一轮修好，结果的失败分类为正常收尾、标签为通过。
- 反馈内容：验证命令、退出码、输出末尾、修正要求与轮次；注入点缺省为空，给了就附在末尾。
- 三轮都失败：撤回后，快照范围内与第一个 Run 之前逐字一致（改过的受跟踪文件还原、新建的未跟踪文件删除）；被忽略的文件不动，HEAD 不动；不开第四轮；账本推出已撤回；再恢复一次结果相同。
- 崩溃窗口一：会话文件截到最后一条验证记录之前（最后一个 Run 已结束、验证未落盘），推为未撤回；标签从首个 Run 与对比尝试两条路径现算均为未知。
- 崩溃窗口二：撤回之后把工作区弄回恢复之前的样子，账本推出已撤回、标签为失败；从账本找到起点连续恢复两次，结果与第一个 Run 之前一致。
- 无法判定（验证超时）：不回炉，记为未知，不撤回。
- 预算耗尽：总轮次 3，首次用 2 轮，回炉第一轮撞上限后不再回炉，提前撤回并标注。
- 缺省关闭：验证失败不回炉、不撤回、不打快照，`run.started` 不带轮数。
- 三处启动即报错，均在装配之前拒绝、没有模型调用。
- 轮数来源：参数优先于项目配置，参数 0 关闭，负数被拒，其他入口不接受该参数。

`eval/runner-repair.test.ts`：

- 开启回炉修好：结果行带 `repair`，判据在回炉结束后照常判分，轮次按整步。
- 开启回炉撤回：首个 Run 以出错的工具结果收尾（不算自报完成），回炉那一轮直接自报完成，最后判据判失败，误报为真、失败分类为正常收尾。
- 缺省关闭：行不带 `repair`。
