# 回炉：验证不过就在同一会话里接着修，到上限撤回（决策 142、143、147、154，基线 aaa59a8）

范围：只做 headless 路径（`pigeon run` 与评测跑批经 `runHeadless` 走的那条）。REPL/TUI 与并行 worker 路径、结构化记忆、验证命令分步、跑批器、容器执行端的"回到这一步起点"均不在本次范围内。不新增账本记录种类。

## 一、开启与互斥

- 轮数来源：启动参数 `--repair-rounds <N>`（只有 `pigeon run` 接受）> 项目验证配置 `.pigeon/verify.json` 的 `repairRounds` > 0。参数给 0 即关闭，压过项目配置。`verify.json` 的 `repairRounds` 为加法式可缺省字段，v1 旧文件逐字有效，不升版本。解析在 `application/launch-flags.ts` 的 `resolveRepairRounds`，读取在 `persistence/verify-config.ts` 的 `loadProjectRepairRounds`。
- 缺省 0 即关闭：不打快照、不在释放之前验证，验证仍按原口径在会话释放后独立执行，行为与基线一致。
- 启动即报错（`application/headless-core.ts` 的 `assertRepairSetup`，在装配运行面之前）：
  1. 设了轮数而没有验证命令；
  2. 与 `--retry-on-fail` 同时开启，文案说明两者对同一次失败各有一套处理，叠加后这一步的成败与撤回无法判定；
  3. 没有可用快照：注入了执行端（容器），或工作区不是本地 git 工作区（154②）。

## 二、流程

`runHeadlessOnce` 在同一个运行面句柄上循环：

1. 一次 Run 结束后，在释放之前经运行面的会话文件落一条 `attempt.verified`（与原验证同一个 `verifyAttempt`）。
2. 通过：结束。无法判定（超时、被信号杀掉、进程起不来）：不回炉，记为未知，结束。
3. 失败：轮数未满且预算未耗尽时，把回炉反馈作为新一轮输入，在同一会话里开一个新 Run。反馈由 `application/repair-loop.ts` 的 `buildRepairFeedback` 生成：轮次（第 i/N 轮）、验证命令、退出码、输出末尾（沿用验证记录的 16 KiB 尾部，截断时注明）、"修正代码直到验证通过，不要修改测试文件。"。末尾留附加内容注入点 `repairAppendix`，缺省为空。
4. 轮数用满或预算耗尽仍失败：按快照撤回，这一步记为失败。

预算（147）：轮次、token 与墙钟计数器在整个循环里只建一次，各轮与首次共用；墙钟定时器覆盖验证命令的耗时。任一上限触发后不再回炉，按撤回处理，结果标注 `budgetExhausted: true`。

## 三、撤回

- 开启回炉时强制挂快照（与分叉会话同一个 `attachCheckpoints`）。撤回起点由账本现算：本会话首个带改前基线的快照记录的 `baseCommit`，即第一个 Run 首次改动之前的工作区状态。没有这样的记录即这一步一次文件都没改过，无需恢复。
- 恢复实现为 `orchestration/checkpoint.ts` 的 `restoreWorkspaceTo`：先删掉范围内、目标提交里没有的文件，再经临时索引（`GIT_INDEX_FILE`）把目标提交的文件逐个写回。工作区所在仓库的 HEAD、暂存区与分支不动。
- 范围（154③）与快照相同：受跟踪的文件，加上未跟踪且未被忽略的文件；被忽略的文件与治理目录 `.pigeon/` 不动。
- 可重复执行：已一致时再执行一次，结果不变；恢复不写账本，进程崩溃在最后一次验证之后、恢复之前时，续跑按账本推出已撤回，再调用 `restoreStepStart` 即可。恢复抛错时，结果的 `errorMessage` 注明"可重复执行恢复"，这一步仍记为撤回。

## 四、账本中的表达（154①，含 2026-09-23 修订）

- 不新增记录种类。`run.started` 载荷增加可选字段 `repairRounds`（开启时在场，最小值 1；一步里的每个 Run 同值），注入快照同步增加该字段。`EVENT_LOG_VERSION` 14 → 15，`INJECTION_SNAPSHOT_VERSION` 9 → 10，两级迁移均为纯版本推进。各测试文件里钉当前版本的断言同步改为 15 或 10。
- 一步的组成（`state/repair-step.ts`）：回炉开启的会话里全部 Run 即一步；一步的身份是首个 Run（`runId` 字段）。
- 撤回推断 `repairStepOutcome`：回炉开启，且这一步最后一个 Run 有验证记录、结论为失败，即已撤回。最后一个 Run 没有验证记录即这一步未收尾，推为未撤回、`verdict` 缺省。不区分轮数用满还是预算耗尽。
- 推断的几种进程中断时点：

| 中断时点 | 账本状态 | 推断 | 标签 |
|---|---|---|---|
| 某轮回炉 Run 结束之后、其验证落盘之前 | 最后一个 Run 有 `run.ended`、无验证 | 未撤回（未收尾） | 未知 |
| 某轮回炉 Run 进行中 | 最后一个 Run 无 `run.ended`、无验证 | 未撤回（未收尾） | 未知 |
| 最后一次验证（失败）落盘之后、恢复之前 | 与正常撤回相同 | 已撤回；续跑重新恢复 | 失败 |
| 验证失败落盘之后、下一轮 `run.started` 之前 | 最后一个 Run 有失败验证 | 已撤回 | 失败 |

最后一行是剩下的一个推错窗口：这一步实际还要接着回炉，工作区未恢复，推断却为已撤回。它与"修满后撤回"在账本上无法区分：两者都是最后一个 Run 带失败验证，差别只在当时是否还有剩余轮数与预算，而预算用量不在账本上（154 未选"按账本时间戳冷算预算"）。本次未新增记录，待裁。续跑时推为已撤回、再执行一次恢复，工作区回到这一步起点，这一步记为失败；与实际应得的结果（接着修，可能修好）不同。

|---|---|

## 十一、复核后补修

本节追加于复核之后，前十节除第五节标题外原样保留；前文与本节不一致处以本节为准。补修前先把分支变基到 main 的 988438b，没有文本冲突。main 上的 a7abdf2 已让第九节第 5 条所说的路径解析用例不再依赖临时目录里的 outside.txt：占位文件删除后，在不含该文件的临时目录下这条用例通过。

### 1. 恢复先写回、后按还原后的忽略规则删除

原实现先删后写回，删除集按 agent 改过的忽略规则计算。agent 删掉一条忽略规则（如 `node_modules/`）时，原本被忽略的依赖目录被当作多余文件删掉，违反 154③；agent 新增一条忽略规则时，被它隐藏的新文件本次不删，恢复不是一次到位。另外，未跟踪的嵌套仓库在 `ls-files` 里列成"目录/"，原实现对它调用不带递归的删除会抛错，且抛在写回之前。

改法（`orchestration/checkpoint.ts` 的 `restoreWorkspaceTo`）：先经临时索引把目标树的文件（含 `.gitignore`）写回；再按还原后的忽略规则列出范围内的文件，删掉目标里没有的；"目录/"条目整个递归删除，目标里有文件落在它下面时不动。治理目录照旧不在范围内。

### 2. 回炉反馈附加内容注入点抛错

原实现里注入点抛错会落到外层异常处理：这一步既没撤回，账本又因最后一个 Run 带失败验证而推为已撤回、标签为失败。现在注入点调用包一层异常处理，向标准错误发一条按类别去重的告警（"回炉反馈附加内容告警：……本轮反馈不带附加内容，回炉照常进行"），以空附加内容继续本轮回炉。不新增账本记录。

### 3. 推错窗口的准确描述（更正第四节）

回炉开启时，下列情况都能从账本推出：

- 已用轮数 k 等于 Run 数减 1，上限 N 冻结在 `run.started` 里；k = N 必为修满撤回；
- 轮次与 token 预算冻结在 `run.started` 里，可由各 Run 的 `turn.completed` 计数与用量推出是否耗尽；
- 墙钟在某个 Run 进行中到点时，该 Run 以中止收尾，留有撞上限记录。

真正残余的只有一种：k < N、轮次与 token 未耗尽、最后一个 Run 没有撞上限记录、且设了墙钟上限时，"墙钟在最后一次验证期间到点"（应撤回）与"验证失败落盘之后、下一轮 `run.started` 之前进程中断"（不应撤回）在账本上不可区分。正常路径上这两条记录之间只有一段同步代码（判定是否撤回、调用注入点、组装反馈、开始下一个 Run），只有硬杀、断电或进程内异常能落进这个窗口。第 6 小节的"回炉途中出现异常"用例正落在这个窗口里：运行结果报告这一步未收尾，而账本推断为已撤回。

结论：推断规则不改，接受为已知限制（决策 160）。跑批器对被打断的步骤整步重做，不依赖这一推断。

### 4. 给跑批器用的结构化结果

`repair` 字段（headless 结果与评测结果行同形）增加三项，并收紧一项：

| 字段 | 含义 |
|---|---|
| `closed` | 这一步是否收尾：通过、无法判定、撤回为收尾；回炉途中出现异常，或没有 Run 可验证，为未收尾 |

## 十二、第二轮补修

本节基线为 9b437e3（第十一节补修之后的提交）。前十一节原样保留，前文与本节不一致处以本节为准。

### 1. 起点前就有的未跟踪嵌套仓库不再被递归删除

快照用 `add -A` 生成基线树：带提交的未跟踪嵌套仓库（或挂在工作区内、未被忽略的 linked worktree）以 gitlink 收进基线，`ls-tree -r` 列出的名字是 `sub`，不带斜杠；而 `ls-files --others` 基于真实索引，列成 `sub/`。第十一节的实现只拿 `sub/` 去比对，比不上，于是连同 `.git`、未推送的提交、未提交的改动一起递归删掉，数据丢失不可逆。第十一节之前这里是不带递归的删除，遇到目录会抛错，数据反而是安全的。

改法：目录条目先看去掉末尾斜杠的名字是否在目标树里，在就跳过；递归删除前先 `lstat`，只有真目录才递归删，符号链接或 junction 只删链接本身，不碰它指向的内容。

### 2. agent 新建的 .gitignore 先删掉，再列删除清单

第十一节写的"一次恢复即被删掉"只对 agent 改动已有 `.gitignore` 的情形成立。agent 新建的 `.gitignore` 在写回之后仍留在工作区，照样影响删除清单：pytest 的 `.pytest_cache/.gitignore`（内容为 `*`）、虚拟环境目录自带的 `*` 会让整个目录永远删不掉；在新目录里写 `/target` 这类规则时，要恢复两次才删得掉。

改法：写回之后、列删除清单之前，用不带 `--exclude-standard` 的 `ls-files --others` 找出目标树里没有的 `.gitignore`，由浅到深处理。判断所在目录是否被外层规则忽略时，要先把这个 `.gitignore` 拿掉：`git check-ignore` 判断目录时会把目录自己的 `.gitignore` 也算进去，内容为 `*` 时目录会被判为已忽略。目录被外层规则忽略（依赖目录里自带的 `.gitignore` 之类）就原样写回；否则删掉。之后再按还原后的规则列清单、删除。

已知限制：`.git/info/exclude` 与全局忽略配置不在快照范围内，agent 改了它们时，删除清单照改后的规则算。

### 3. 首次记基线失败后，不再恢复到改到一半的状态

第十一节第 4 小节把"起点晚于这一步起点、仍报 restored: true"的触发条件写成"快照故障发生在首个快照之前"，范围写宽了。首个快照之前 `afterChange` 失败时，改前基线仍留在内存里，下一次快照照样带上正确的改前基线。真正的触发条件只有一种：首次写档或命令档工具提议时，`beforeChange` 记基线失败，之后 `afterChange` 把改后的树当成了基线。

改法：`createCheckpointer` 记下"基线丢失"。此后不再产出改前基线；基线丢失后首次看到改动，照样打一个不带改前基线的快照，账本因此留下"有快照记录、没有改前基线"的痕迹。撤回走第 4 小节的"起点丢失"路径：`restored: false`，带 `restoreError`，并发去重告警。

### 4. 有快照、没有改前基线即起点丢失

`restoreStepStart` 在会话里有快照记录、或 git 里有这个会话的快照 ref，却取不到改前基线时，返回 `startLost: true`，不动工作区。headless 据此报 `restoreError`（"快照记录里没有改前基线，撤回起点丢失，工作区未恢复"）并告警。这条判断只依赖账本与 git，不依赖本进程的错误清单，因此：

- 续跑时，前一进程的快照故障清单已经没有了，也能认出起点丢失；
- 前一进程崩在快照 ref 写入之后、快照记录落盘之前时，由快照 ref 认出。

仍认不出的：文件由不打快照的途径改动时（非写档与命令档的工具，例如 read 档的 MCP 工具；验证命令的副作用），会话里既没有快照记录也没有快照 ref，按"一次文件都没改过"处理，报 `restored: false`、不带原因。这是已知限制。

### 5. git 输出上限

`orchestration/checkpoint.ts` 的 git 调用把 `maxBuffer` 放大到 256 MiB。原先是缺省的 1 MiB，`ls-tree` 或 `ls-files` 的输出超过它就报 ENOBUFS；如果抛在写回之后，工作区只恢复一半，而且每次必然复现。

### 6. 内容没变的文件不重写

原先的临时索引是新建的，没有文件状态信息，`checkout-index -f` 会把每个文件都重写一遍：全树的修改时间被刷新，大仓库很慢；Windows 上任何被占用的文件，哪怕内容没变，也会让写回失败。现在先把真实索引复制到临时路径，再对目标提交做单树合并（`read-tree -m`，内容相同的条目沿用其文件状态），然后 `update-index -q --refresh`，内容没变而文件状态过期的条目也会被识别为未改动，`checkout-index -f` 因此跳过它们。

固有限制：`core.autocrlf` 开启时，被改动而写回的文件，其换行按 git 的检出规则处理，这是基于 git 快照恢复的固有限制。

### 7. 恢复失败的评测行不计入成败

原先 `restoreError` 只进了 `row.error`，`status` 不是 `error`，而结果读取方只按 `status` 识别错误行，这一行照常计入成败。现在二选一选了"记为错误行"：`restoreError` 在场（且不是内容审核拒答、模型服务故障）时不判分，`status` 记为 `error`，`verdict` 记为 `undetermined`，`error` 写"基础设施错误（回炉撤回时工作区未恢复，终态 …）"。与模型服务故障同口径：不占续跑键，重跑时补跑。工作区既不是这一步的起点，也不是 agent 的最后结果，判分没有意义。

### 1. 回归与根因

第十二节第 2 小节的做法（先删掉目标树里没有的 .gitignore，再判断是否写回）引入了回归：起点前就有、自带内容为 `*` 的忽略规则文件的目录（uv venv 或 Python 3.13 及以上的 venv 建的 `.venv/`，以及 `.pytest_cache/`、`.mypy_cache/`、`.ruff_cache/`），它们的 `.gitignore` 不在基线树里，被当成 agent 新建的删掉，随后整个目录失去忽略、被删光；根目录的 `.gitignore` 如果本身未跟踪、经 `.git/info/exclude` 被忽略，也会被无条件删掉，它原本护着的 `.env` 等文件随后被删。根因是快照不含被忽略的文件，恢复时无从区分被忽略的东西是开工前就有，还是 agent 新弄出来的。第十二节第 2 小节的描述已被本节的做法取代。

### 2. 按开工忽略清单判定删除集（决策 154 修订）

- 记录：每一步开工时（首次写档或命令档工具提议、快照器记基线之后），另记一份当时已被忽略的路径清单：`git ls-files -z --others --ignored --exclude-standard --directory`（目录折叠）。清单写成 blob（`hash-object -w`），挂在该会话专用的 ref `refs/pigeon/start-ignored/<会话>` 上，与快照同在仓库里。这个会话已记过就不覆盖。记录失败不影响基线。
- 取回：`restoreStepStart` 从该 ref 读出清单（`cat-file blob`），不靠进程内存，进程重启后同样取得到。
- 撤回：
  1. 先写回目标树（保留第十二节第 6 小节的"复制真实索引 → read-tree -m → 刷新 → checkout-index"）；
  2. 候选：现存的全部未跟踪路径（`ls-files --others --directory`，不带 `--exclude-standard`），加上已暂存却不在目标树里的条目（`ls-files --cached` 去掉目标里有的，冲突条目去重）；
  3. 在目标树里的、是治理目录或在其下的、是开工忽略清单中的路径或在其下的，一律不动；起点里的嵌套仓库（以 gitlink 收进、名字不带斜杠）同样不动；
  4. 候选是目录、且其下有目标树里的文件或开工忽略清单中的路径时，不整删，逐层下探，只删不受保护的部分；
  5. 其余删除：递归删除前照旧 `lstat`，链接只删链接本身；已暂存的 gitlink 与文件同样按 `lstat` 处理。
- 清单里目录条目的含义：实测 git 对"目录里只有被忽略的文件"（如 `logs/` 只含被 `*.log` 忽略的 `app.log`、自带 `*` 的 `.venv/`）会同时列出目录名和其中每个文件；对"目录本身被规则忽略"（如 `node_modules/`、`build/`）只列目录名。据此，目录条目下面若还列了别的条目，只按逐个文件保护；否则整棵子树都保护。于是开工已有 `logs/app.log`、agent 新建 `logs/new.txt` 时只删 `new.txt`；开工已有 `node_modules/` 时，agent 往里加的文件也不动。
- 取不到清单（旧快照，或清单丢失）：退回保守做法，现存被忽略的路径一律不删，只删未被忽略且不在目标里的路径；`restoreStepStart` 返回 `startIgnoredMissing: true`，headless 发一条去重告警："回炉告警：开工忽略清单缺失，agent 新建的被忽略文件未清理（撤回照常，被忽略的文件一律没动）"。保守做法下候选不折叠目录：`--directory` 不看目录里面，目录本身没被忽略就整个列出，里面全是被忽略的文件（如自带 `*` 的 `.venv/`）也会被连带删掉；实现中用例因此变红后改为逐个列出未被忽略的文件。
- "逐字一致"的范围不变。开工时已被忽略的内容若在这一步里被改动或删除，不在恢复范围内。

### 3. 真实索引里有未解决的冲突时

agent 执行 `git stash pop` 或 `merge` 留下冲突后，真实索引里有未合并的条目，复制过来做 `read-tree -m` 必定失败，第十二节的实现因此每次都恢复失败。现在 `read-tree -m` 失败时删掉临时索引，退回普通 `read-tree <目标提交>`，再刷新文件状态、全部写回。

### 5. 已知限制与事实

- 起点前就有、一个提交都没有的嵌套仓库会让快照的 `add -A` 失败，快照每次都失败，这一步永远撤不回；评测里每次都是错误行，补跑会一直重复。
- 起点前就有的嵌套仓库，agent 在里面做的提交和改动不会被还原。
- 起点丢失的判断以会话为范围，前提是每个回炉步骤都用新会话；现有调用方都满足。
- 异常路径上 `repair.verdict` 取的是上一轮的结论，而账本推出的是"没有结论"。
- `.git/info/exclude` 与全局忽略配置不在快照范围内（第十二节第 2 小节已记）；开工忽略清单按开工时的规则列出，agent 之后改这些配置不影响清单本身。
- 第十一、十二节引用的决策 160 与 154 修订已随 main 的 1040f9a 入库；本分支已变基到该提交之上。
