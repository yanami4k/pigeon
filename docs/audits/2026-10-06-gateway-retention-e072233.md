# 网关逐请求留存与高峰自动暂停（决策 393、394）

基线 e072233（main，含决策 394 的记录）。分支 worktree-agent-ab069985c20bf3ad5。依据决策 393、394 与被 394 修改的 372。

## 现状（改前）

- 网关（`src/eval/model-gateway.ts`）读完整个请求体再转发；200 时逐块透传，同时把正文累积成文本读用量。请求与回复不落盘。
- 放行在限额控制器（`src/eval/model-limits.ts` 的 `LimitController`）：每步 agent 开始前 `acquire`，同时在跑的数小于配置路数与网关可用容量才放行。全部账号不可用时整批暂停（`state` 为 paused，网关以 529 拒绝，在途的步作废），总等待上限 6 小时，这是跑批里唯一的整批时限。等放行的时间不计入每步墙钟预算（agent 的墙钟在放行之后起算），记进结果行 `admissionWaitMs`。
- 高峰时段判定在 `src/state/model-pricing.ts` 的 `isPeakAt`：北京时间工作日 9–12、14–18 时，法定节假日全天平价，调休上班日按工作日；节假日表只录了 2026 年，表外年份只按周一至周五判。

## 改法

### 逐请求留存（394）

新模块 `src/eval/gateway-retention.ts`：`GatewayRetention`（网关与跑批器各调一处）、`readRetention`（读取）、`removeRetention`（清理）。

- 接入：网关加 `setRetention`（给了才记）与 `retainStep`。`handle` 在读完请求体、核对 model 之后打开一次交换，各条交回的路上（200 透传、非 200 交回、暂停 529、客户端中止、中途断流）把状态码、正文、用量或错误记进 `outcome`，`finally` 里落盘。转发用的请求体不经留存，字节不变。跑批器在 `runStep` 调 `runAdmittedAgent` 之前 `retainStep(作业, 作业目录, 步序)`，这一次尝试结束（含作废、抛错）后调用返回的结束函数；`StreamModelGateway` 加可选的 `retainStep`。不在一步之内的请求不记。
- 布局：`streams/<作业>/gateway/step-<步序>/try-<第几次>/` 下 `requests.jsonl`（请求读完即写一行）、`responses.jsonl`（结束时一行）、`replies.gz`（各次回复的原始正文，一次一段 gzip，按偏移与长度取）、`large.gz`（大字段，同样按偏移取）；`gateway/blobs/<sha256>.json` 存系统提示与工具定义的整段，同一作业只存一份。作废重做与续跑在第一次有请求时另开下一个 try。
- 请求增量：每条消息按 JSON 序列化逐条链式取 sha256；同一次尝试里此前某次请求的完整 messages 恰为本次的前缀时（取最长的），只存其后新增的消息，记下那次的编号（`base`）；找不到即存全量并标 `full`。另记 messages、system、tools 以外的顶层字段（模型与参数）、system 与 tools 的 sha256 与字节数（tools 另记条数），以及原始请求体的字节数与 sha256。
- 大字段：messages、system、tools 以外的顶层字段，序列化超过 16 KiB 的（外部 agent 每次请求附带的增量会话日志一类）不进参数，记字段名、字节数与 sha256，内容 gzip 后追加进 `large.gz`；一题里大字段至多用掉单题上限的四分之一，用满后只记大小与摘要（不再压缩）。转发照样逐字。
- 回复：原始正文（SSE 或非流式 JSON）gzip 后追加进 `replies.gz`；`responses.jsonl` 记交回的状态码（客户端中止为 0）、耗时、用量（与计量同一读法）、停止原因（SSE 取 `message_delta` 的 `delta.stop_reason`，非流式取正文的 `stop_reason`）、中途断流的错误；非 200 记错误正文的前 2000 字。中途断流时存已收到的部分。
- 鉴权：请求头名字含 auth、key、token、secret、cookie、password 的一律不存（`x-api-key`、`authorization` 在内），其余请求头照记；落盘的每段文字（请求行、回复行、整段、大字段、回复正文）先经 `scrubKeys` 去掉配置的 key 与上游回显的打码密钥片段。
- 上限：单题（同一步各次尝试合计，开 try 时接着该步目录已有的量算）与单作业（第一次开步时接着作业 `gateway/` 已有的量算，续跑同理）的落盘字节，缺省 32 MiB 与 512 MiB。放不下的请求只记一行摘要（编号、时刻、字节数、sha256、消息条数，标 `truncated: task-cap|job-cap`），放不下的回复正文不存、标 `truncated`；摘要行与回复行总是写。每个作业、每次尝试各告警一次。
- 读取：`readRetention(作业目录, 步序?)` 按步、按 try 列出每次请求：记录本身、回复记录、还原出的完整请求体（沿 `base` 链拼回 messages，取回 system、tools 与存了的大字段；键序不保证与原文相同），还原不全的部分列在 `missing`；`reply()` 取原始回复正文。转成 Scout 转录不在本段。
- 清理：跑完、转换之后删掉各作业的 `gateway/`（`removeRetention`）。
- 写入出错（如磁盘满）只告警一次，照常转发。

### 高峰自动暂停（393）

- `LimitController.enablePeakPause({ marginMs, isPeakAt?, setTimer?, onChange? })`：缺省判定为 `isPeakAt`，缺省定时为真实定时。不调用即与改前相同。
- 判定：`peakClearFrom(t, marginMs)` 为从 t 起最早的时刻 R，使 [R, R + marginMs] 里没有一刻在高峰（高峰按分钟判定，逐分钟查，至多查 31 天）；R 大于 t 即此刻停止放行新的一步，直到 R。余量 30 分钟时，工作日 8:30 起停到 12:00，13:30 起停到 18:00；余量为 0 时只在高峰时段内停。
- 放行：`acquire` 与 `admit` 多一个条件"此刻不在高峰暂停中"。不改 `state`、不计限额信号、不通知订阅者，所以在途的步照常跑完、网关照常转发、不作废。
- 定时：暂停中定时在恢复时刻；可放行时定时在下一次停止放行的时刻（下一个高峰分钟减去余量，一天内没有即一天后重查）；定时一到即按当时时刻重算并放行等待的各路，定时迟到时同样按当时时刻重算。`close()` 取消定时。
- 时限：每步墙钟本就在放行之后起算，等待记进 `admissionWaitMs`；整批暂停的 6 小时总等待扣除与高峰暂停重叠的时间。
- 记录：每次暂停与恢复各写一条告警（北京时间、余量、预计恢复时刻、暂停时长）；`onChange` 交给跑批器写进输出目录的 `peak-pauses.jsonl`（`event` 为 pause 或 resume，`startedAt`、`until`、`endedAt`）。
- 节假日表照旧只覆盖 2026 年，跨年使用前须补表；表外年份的法定节假日会被当作工作日暂停（只多停，不多花）。

### 装配、参数与身份头

- `StreamExperimentOptions` 加 `gatewayRetention?`（单题、单作业上限）与 `peakPause?`（余量），给了才开；程序调用不给即不开。开法都在 `startGatewayAndLimits` 返回之后（`setRetention`、`enablePeakPause`），该函数未改。
- CLI（`pigeon eval stream`）缺省两项都开：`--gateway-retention on|off`、`--retention-task-mb <n>`（缺省 32）、`--retention-job-mb <n>`（缺省 512）、`--peak-pause on|off`、`--peak-margin-min <n>`（缺省 30，可为 0）。关掉一项时再给它的取值参数即报错。
- 身份头 `info`（只记不比）：开了留存记 `gatewayRetention: { version: 1, maxTaskBytes, maxJobBytes }`，开了暂停记 `peakPause: { marginMs }`；续跑时开关或取值有变即按既有规则在 `infoLog` 追加一条。两项都关时 `info` 不多出任何项（`retentionAndPeakInfo` 返回空对象）。
- 两项都关时：身份头与改前逐字相同，网关不打开交换，限额控制器没有高峰状态，跑法与改前相同。正式跑的跑法用 `--gateway-retention off --peak-pause off` 复现。冻结标签 formal-run-v1 未动。

## 留存体积估算（对比评测：79 题、两组、各两遍，共 4 条流）

估算，未在真实上游上实测；第一次试跑时按题量一次 `gateway/` 的实际体积核对。

- 回复：合成的 SSE（每个增量事件带 2–6 个字符的正文，正文取自仓库的源码与文档）实测原始约 125 字节/事件，gzip 后约 5–6.5 字节/事件（压缩比约 20–26 倍）。开思考时每轮回复按 1,000–2,000 个增量事件估，压缩后约 5–13 KiB/轮。
- 请求增量：每轮新增上一轮的回复与工具结果，按 10–15 KB/轮估（不压缩）。
- 轮数：按上一轮预算校准，每步轮数的第 90 百分位 78 轮，中位按约 40 轮估。
- 每题：约 40 轮 × 约 20 KB ≈ 0.8 MiB；第 90 百分位约 1.6 MiB。外部 agent 组另加附带的大字段，按每次请求压缩后约 5 KB 估，约 0.2–0.4 MiB。
- 每条流：79 题约 80 MiB；题题都按第 90 百分位约 160 MiB；作废重做另加约一成。

## 局限

- 大字段按顶层字段判定：嵌在别的顶层字段里的大内容随该字段一并按大字段处理。
- 增量只在同一次尝试内找前缀；上下文被压缩改写后的那次存全量。还原出的请求体与原文深比较相等，键序不保证相同；原文的字节数与 sha256 另记。
- 被截断的请求还原不出；其后的请求仍按前缀找此前全文落了盘的请求，多半照样还原得出。
- 留存在网关进程内同步写（含 gzip），一次回复的压缩在毫秒级；附带 8 MiB 大字段的请求在转发前多一次压缩，在百毫秒量级（未实测）。
- 高峰暂停期间，等放行的那一步已开好容器、切好依赖（与按容量放行同一位置），加上预开的下一步容器，每个作业至多两个容器空等，至多数小时。
- 结果行的 `wallMs` 从开容器算起，含等放行的时间（高峰暂停可达数小时）；`agentWallMs` 不含，`admissionWaitMs` 单列。

## 补充：cache_control 与增量

基线 1720f75（集成线，含上文各提交，快进合入本分支）。修复提交 bbdca0a。

### 现象与原因

- 试跑中 Pigeon 组第 49 步：77 条请求记录里 73 条存了全量，requests.jsonl 32.7 MB，撞单题 32 MiB 上限截断 4 条；外部 agent 组同一步 141 条请求只存了 2 条全量，消息增量合计约 0.8 MB。
- 原因：Pigeon 每次请求把 cache_control 断点挪到最新的消息上，上一次带断点的那条消息这次不带了，前缀逐字比对对不上。相邻两次请求的消息前缀逐字比对 72 次全不相等，去掉 cache_control 后 72 次全部相等。

### 改法

- 比对前缀与存的增量一律用去掉 cache_control 的消息（`stripCacheControl`：消息本身与 content 各块上的 cache_control，不改原对象、其余键的先后不变）。
- 每次请求另记 `cacheControl`：全部 cache_control 所在的消息下标、内容块下标（在消息本身上则没有）、在该对象里是第几个键、取值；另记 `order`：顶层字段的先后。
- 读取：沿 `base` 拼回去掉 cache_control 的消息，按 `cacheControl` 放回原键位（`applyCacheControl`），顶层字段按 `order` 排；新增 `exact`：还原出的请求体紧凑序列化后的 sha256 与原文相同（原文带空白排版时为 false）。
- 留存格式版本 2（身份头 `info.gatewayRetention.version` 随之为 2）。第 1 版的记录（增量里原样带 cache_control，没有 `cacheControl` 与 `order`）照常读，键序同改前。
- `docs/configuration.md` 的留存一节补写。

### 测试与变异

- `src/eval/gateway-retention.test.ts`：增量一条改为带挪动的 cache_control（每次在最新的消息上，一次排在块的键中间，一次两处断点，一次在消息本身上），断言只有真对不上的三次存全量、其余按前缀存增量，每次请求逐字还原（紧凑序列化相等，含 cache_control 的键位与顶层字段先后），紧凑原文的 `exact` 为真；新增一条第 1 版记录照常读。
