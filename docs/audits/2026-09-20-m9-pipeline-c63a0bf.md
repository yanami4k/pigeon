## 二、执行端接口（098）

`src/tools/workspace-host.ts` 定义接口：平台、工作区根、路径围栏、判常规文件、读、写、同步读（回执落盘时实测哈希用）、执行、文件清单、启动器脚本解析；快照与分叉为占位的可选成员。三个工作区工具（read_file、edit_file 的两种模式、run_command）只调接口。`src/tools/local-host.ts` 是本地实现，进程执行、文件清单与 .cmd / .bat 解析自 run_command 原样平移，既有测试断言未改。`src/execution/container-host.ts` 是容器实现，经 docker CLI 的 exec 进容器。执行端由装配根注入（`RuntimeDeps.workspaceHost`），缺省为工作区根上的本地实现。

容器边界四件事，逐件验证（`src/execution/container-host.test.ts`，替身层任何机器都跑，真容器层对 busybox 容器）：

| 事项 | 做法 | 验证 |
|---|---|---|
| 超时杀干净 | 超时与中止一律"杀 exec 客户端，再重启整个容器"，等重启完成才交还结果；容器以 `--init` 启动；重启失败按环境错误上抛 | 真容器：`sh -c 'sleep 600 & sleep 600 & echo started; wait'` 限时 1.5 秒，超时后容器内 `ps` 不见 `sleep 600`，超时前写入的文件仍在，随后的命令照常执行。替身：超时与中止后最后一次 docker 调用必为 `restart -t 0` |
| 退出码保真 | 原样带回 exec 的退出码；OCI 运行时报"程序不存在"还原为 ENOENT、"不可执行"为 EACCES；守护进程层面的失败上抛为环境错误，不冒充命令退出码 | 真容器：0、3、255、`kill -9 $$` 得 137、不存在的程序得 ENOENT；经 run_command 表现为"命令不存在"。替身：命令自己退出 127 时原样保留 |
| 输出截断 | 与本地实现共用同一个收集器：全量计字节数与 sha256，只留开头 | 真容器：输出 220,000 字节、上限 1000，保留部分恰为前 1000 字节，字节数与哈希等于全量 |
| 路径映射 | 模型给的路径在容器内按工作区根解析（符号链接解析后）再判包含；宿主路径不参与 | 真容器：相对、工作区内绝对、内部符号链接可解析；`..` 逃逸、根外绝对路径、指向根外的符号链接拒绝为越界；不存在的路径与 Windows 风格路径按不存在拒绝；名字以两个点开头的文件不误判 |

另验：读写往返对 UTF-8、CRLF、无末尾换行、空文件、1 MB 内容与含引号反引号的内容逐字节保真，同步读与异步读一致；文件清单不含版本库元数据，命令造成的新增、修改、删除出现在 run_command 的文件变化里；宿主环境变量不进容器。

变异反向验证：把"重启容器"改成空操作（只杀客户端）——真容器层"超时杀干净"变红，容器内留下 `sh -c ...` 与两个 `sleep 600` 共三个进程；替身层"中止信号与超时同一条路"同时变红。均由该变异直接解释。

真容器层暴露并已修的三处缺陷：OCI 的报错实测落在标准输出而非标准错误（改为两路各留开头识别）；同步读经 `spawnSync` 的缺省 1 MB 缓冲读大文件报 ENOBUFS（上限提到 256 MB）；`find -printf` 与 `realpath -e` 为 GNU 专有（改为 `find -exec stat -c` 与 `[ -e ] && readlink -f`，busybox 与 GNU 通用）。

不要改测试文件这条约束在工具边界上挡住：`withReadonlyPaths` 包装执行端，受保护路径经 edit_file 的写入以域错误拒绝并说明原因，读不受影响；同一文件换个写法的路径同样拦住（按解析后的规范路径比对）。经命令造成的改动拦不住，由任务源在取 diff 时排除同一批路径兜底。测试：`src/tools/workspace-host.test.ts`（本地执行端）、`src/eval/swebench-source.test.ts`（真容器）。

已知边界：快照与分叉尚未迁到该接口；按路径限定的 grant 以宿主路径判定，对容器工作区不会命中（不匹配即回落后续排律，不放宽）。

## 三、任务源接口（102）与外部基准实现（097）

`src/eval/task-source.ts` 定义四样东西：实例清单、环境准备（交回宿主侧工作区根与可选的执行端）、判据命令（参数数组、工作目录、超时、备好的材料、可选的"判据自身出错"退出码）、元数据（难度、holdout、对应能力）。runner 只认该接口；自造冒烟题（`local-source.ts`）与外部基准（`swebench-source.ts`）各一个实现。判据仍是"执行一条命令、三值判决"（096 ②）：外部基准的判据命令是 `eval/swebench/judge.py`，退出码 0 已解决、1 未解决、2 判分设施出错。

外部基准实现的三处口径：

- 取 diff 相对仓库根、相对基准提交上的镜像初始状态。sphinx 一类镜像在基准提交之上自带未提交改动（`setup.py`、`tox.ini`），评测容器里同样有；直接对基准提交取 diff 会把它们带进补丁并在判分时打不上。做法是准备环境时以独立索引文件把初始工作区写成一棵树，收工后再写一棵，取两棵树之差；不动 HEAD 与仓库索引。
- 官方测试补丁涉及的路径在取 diff 时排除，并经执行端写保护。
- 判分前先移除工作区容器再起评测容器；工作区容器带输出目录标签，续跑前按标签清理残留。

真容器测试（sphinx-doc__sphinx-9367 的评测镜像）：改一处源码、经命令改测试文件、新建文件、向 `setup.py` 追加一行——取出的补丁只含源码改动、新文件与追加的那一行，不含测试文件与镜像自带改动；判分前工作区容器已移除；残留容器按标签清理。

判据脚本的一处设施缺陷与修复：官方判分器生成 django 一类题的测试规格时，会从代码托管站的原始文件地址取该仓库的依赖清单（即使用预构建镜像），请求不带超时；该地址不可达时判分进程永久挂起、不起评测容器。首次 5 题跑批中三道 django 题因此卡在判分。修法：判据脚本改为进程内调用判分器，对这类地址加磁盘缓存、超时与同内容镜像地址回退；全部失败以退出码 2 结束，不伪造内容。验证：对已取出的三份补丁单独判分，72 秒判完，均为已解决。

## 四、续跑跳过键

`src/eval/results.ts`：续跑键（任务、条件、编辑模式、次序）只由非错误行占用；错误行留在文件里不删不改；读侧（报告与对照）同键取最后一条非错误行，只有错误行的键取最后一条错误行以保持可见。错误行口径（101 ①）：环境准备失败、运行抛错、模型服务故障（请求层抛错即失败分类为基础设施，或流内以错误收尾即终态 failed；此时不判分）、判据设施出错（备料失败、拉不起来、约定的出错退出码）。验证器超时不算错误行——可能正是改动把测试改挂了，属于该次运行的真实结果。

用例：`results.test.ts`（键与读侧的纯函数）、`runner.test.ts`（预置一条错误行与一条判决为失败的正常行——错误行的键补跑、正常行跳过、错误行逐字节保留、报告不把错误行计入分母）、`task-source.test.ts`（五类实例各一：准备失败、备料失败、判据出错退出码、任务判失败、任务通过；设施恢复后重跑只补跑前三类）。变异：让错误行也占键——两条断言"错误行不占键"的用例变红，其余不变。

真实场景的一次验证：上述 5 题跑批中三道 django 题因判分挂起被记为错误行；修复判据脚本后在同一输出目录重跑，本次运行 3 次、跳过已有 2 次，三题补跑后均通过，结果文件共 8 行（3 条错误行保留）。

## 五、模型接入的备用 key

`spikes/real-stream-fn.mjs` 支持可选的第二个 key，逻辑在 `spikes/key-failover.mjs`：限额类错误（HTTP 429 或响应体表明配额、额度、频率超限）才切换，切换后保持使用；手上的 key 都撞限额时退避 5、15、45 秒各一次，仍失败才交回错误；并行的请求共用当前 key 与同一段退避；只在请求的首个事件即为错误时重试；认证失败、模型不存在、请求格式错不切换。每次切换与退避向标准错误输出一行告警，告警与交回的错误文本里不出现 key 及其片段。第二个 key 缺失时启动与成功路径无任何告警。

脱网自检 `spikes/key-failover.selfcheck.mjs`（假上游流）七项全过：切换并保持、认证失败不切换且错误文本里的 key 被抹掉、两个都撞限额时三次退避后交回错误、退避后恢复、单 key 无告警、五个并行请求只告警一次切换、告警不含 key 片段。

对真实接口的两次手工验证：

| 验证 | 配置 | 结果 |
|---|---|---|
| ① 认证失败不切换 | 无效主 key 加有效备用 key | 0.4 秒返回 401 认证错误并原样交回；没有切到备用 key（若切换会得到成功响应）；标准错误零输出 |
| ② 无回归 | 两个有效 key | 1.4 秒正常返回；标准错误零输出 |
| ② 补充 | 仅主 key | 1.3 秒正常返回；标准错误零输出 |

跑批暴露并已修的一处口径漏洞：runner 原先只在失败分类为基础设施时把运行记为错误行；模型流内以错误收尾（连接中断、服务端报错）的运行终态为 failed、失败分类为未知，会被照常判分并占用续跑键。修法：终态 failed 同样记错误行且不判分。红测试 `task-source.test.ts`「模型流以错误收尾……同样记错误行且不判分」——先改完文件、再在下一轮以流内错误收尾，修复前该用例得到终态 failed 的正常结果行。为此假模型夹具新增"流内以错误收尾"的剧本字段。

运行环境的一处事实：WSL2 在没有任何客户端进程连着时，十几秒后即终止整个发行版，其中的 systemd 单元、docker 守护进程与容器一并结束。首次中断是唯一的客户端命令被回收（宿主空闲内存约 3 GB）；改用 systemd 临时单元后，在启动命令返回与等待命令接上之间的空窗里再次发生。处置：宿主侧先起一个独立的常驻客户端进程保活，再启动单元；跑批结束后关闭。

已知瑕疵：评测在没有版本库元数据的代码副本里运行，结果行的 harness 版本记为 unknown；跑批期间代码副本冻结在开跑时的版本，上述口径修复未参与本次跑批。

## 十、判分容器接代理后重判四道外网题

做法：判据脚本新增可选的 `--proxy`（任务源选项 `judgeProxy`、命令行 `--judge-proxy`）。给了才向评测容器注入 http_proxy / https_proxy / no_proxy（大小写两套），不给则一字不加。注入发生在判据进程内——只拦官方判分器创建的、名字以 `sweb.eval.` 开头的评测容器。no_proxy 为本机回环（localhost、127.0.0.1、::1，官方测试自起的本地服务走这里）加判分时从 docker 现取的全部容器网段（本次为 172.17.0.0/16）。代理地址支持 `gateway:端口`：每次判分时现取默认路由的网关（`ip route show default`），不缓存、不落配置；该地址在宿主重启后可能变化。取不到网关按判分设施出错（退出码 2）处理。

agent 一侧未改：工作区容器由任务源经 docker 命令行创建，与判据进程内的注入是两条路，不共用配置。测试 `swebench-source.test.ts`「判分代理只出现在判据命令里」以假 docker 记录全部调用——配了与没配判分代理的两个任务源建出的工作区容器参数除容器名外逐字相同，所有 run / exec / rm 调用里不出现代理字样，也不出现任何网络参数（绊线：要动 agent 一侧的网络设置须先经裁决）；判据命令给了才带 `--proxy`。变异（把代理一并塞进工作区容器的创建参数）精确变红。

## 十一、工作区容器断网与断网条件下的 50 题重跑

### 断网

agent 的工作区容器改为无网络：任务源创建工作区容器时恒带 `--network none`（只留本机回环），不提供开关；调用方的附加参数里出现网络类（`--network`、`--net`、`--add-host`、`--dns`、`--publish`、`-p` 等）或代理类环境变量即在构造任务源时拒绝。判分阶段的代理链路（第十节）未动。

测试 `swebench-source.test.ts`「agent 的工作区容器无网络」：以假 docker 记录调用，断言创建参数里恰有一处网络参数、取值 none、排在镜像名之前；十种会打开网络或带入代理的附加参数逐个被拒。变异（网络改回 bridge）变红两条——本条，以及「判分代理只出现在判据命令里」中"网络参数只许是 none"的断言，均由该变异直接解释；实现之前（走默认网络）本条同样为红。真容器层：容器内 `/sys/class/net` 只有 `lo`，取软件包索引失败（断网前同一请求返回 200）。

### 三条口径的落实

## 十二、收口：清理历史泄漏、固定采样、冻结条件与两轮同条件基线

### 本节落实的改动（均测试先行）

- 仓库历史清理（109）：环境准备时在工作区容器内删全部标签与 HEAD 所在分支之外的一切引用、删远端、过期 reflog、清不可达对象，只留 HEAD 可达的历史；先清理、再建取 diff 用的初始树；清完自验，不过即准备失败并移除容器。判分侧不动。实测耗时 django 约 16 秒、sphinx 约 6 秒，内存不到 100 MB。测试 `swebench-source.test.ts`「环境准备先清掉基准提交之后的仓库历史再建初始树」：断言清理先于建初始树、四个清理动作俱在、三种自验不过（仍有标签、仍有 HEAD 之外可达的提交、后续提交对象仍在）各自报错且不再继续；实现之前（即"不清理"）该用例为红。真容器层自验三件：标签数 0 且全部可达提交数等于 HEAD 可达数、引用只剩 1 个；基准提交仍在、HEAD 可达历史完整、取出的补丁与清理前同口径；同一镜像另起的干净容器里标签仍在（评测镜像未被改动）。两轮基线开跑后对在跑的工作区容器抽查，均为无网络、标签 0、全部可达提交数等于 HEAD 可达数。
- 采样温度（110）：温度 0，经装配层包装 streamFn 传入，冻结进注入快照 model 段（快照 v9）并随 run.started 落盘（Event Log v13，加法式）；缺省不设时调用选项与账本均无此键，既有运行逐字不变。真实接口实测接受温度 0。上游只在未请求推理时把温度交给 provider；温度目前只接到无父会话的运行面。
- 连续指标：结果行新增 `testProgress`——目标用例（这次改动应当修好的）与回归用例（原本就过、不应弄坏的）各自的通过条数与总条数，取自判据命令尾行 JSON 的约定字段 `progress`；形状不对一律不收。空补丁不跑测试，只有目标用例的 0/N（总数取自数据集）。判决仍是三值，连续指标只回答"离通过有多远"。报告对失败的运行列出这两项。
- 任务说明（111）：逐字等于数据集的 issue 原文，不加包装。system prompt 与工具说明仍是中文，模型处在中文指令加英文任务的混合语境，这是本 harness 的真实特性。
- 容器工作区的放权护栏（112）：非本地执行端的运行面带审批通道或装了按路径限定的固化放权规则时，装配即报错；本地工作区与无审批通道的无人值守运行照常。
- 结果行字段（113）与旧行不追溯（114）：`wallMs` 列入必有字段、读侧容忍旧文件缺失，`difficulty` 可选；按旧口径写下的行读回来不重新解释。

### 工作方式指令（116）

纯 issue 原文下，模型会把 issue 当成提问来回答、不动手：该条件下跑出的 12 题里 4 题 1 轮收工（sphinx-doc__sphinx-10323、sphinx-doc__sphinx-10673、sphinx-doc__sphinx-11510、django__django-11964），均为空补丁。那一轮中途停止，数据单独存放，不作基线。

补一句工作方式指令，追加为 system prompt 的最后一段，随整段 system prompt 冻结进注入快照（run.started 记其哈希，全文在内容文件的 system 记录里）。逐字如下：

> Your task is to make changes to non-test files in the repository at /testbed in order to fix the issue described in the user message, in a way that is general and consistent with the codebase.

措辞取自公开最简实现（mini-swe-agent 的 SWE-bench 配置）中说明任务的同一句："Your task is specifically to make changes to non-test files in the current directory in order to fix the issue described in the PR description in a way that is general and consistent with the codebase."——改动三处：去掉 "specifically"，"the current directory" 换成 "the repository at /testbed"，"the PR description" 换成 "the user message"。它只说工作方式，不含任何 issue 内容，不进用户消息；任务说明里也不含它。这句话属于被测条件，换一句分数就可能变。测试 `swebench-source.test.ts`「工作方式指令」逐字钉住措辞，`task-source.test.ts` 断言它进了模型实际看到的 system prompt、不进用户消息、去掉它其余 system prompt 逐字相同而冻结哈希不同。

## 十三、第二阶段开工前的修复

本节的改动均测试先行；每条新增或改写的断言都做了单点变异（改一处实现、跑对应测试、确认变红的正是该用例，再还原），结果列在本节末尾。门禁 `npm run verify` 全绿：960 条测试 958 通过、0 失败、2 条跳过（需要 docker 的真容器用例），依赖检查无违规。

### 回放与分叉重试沿用采样参数（087 修订、110）

- 回放计划从原尝试的 run.started 取出温度与工作方式指令，交给验证器运行面；原尝试没设温度就不带（缺省即"未设"，与原尝试一致）。推理开启时温度未生效，原尝试记的是"请求了但未生效"，回放照原样请求同一个值，由同一条规则决定是否生效。取不到 run.started 的尝试照旧拒绝验证。
- 回放派发器交给验证器运行面的是整组采样参数（模型参数与工作方式指令一起），调用点无从漏传其中一项。
- 失败自动分叉重试沿用来源尝试的温度与工作方式指令：重试那次的每一次模型调用与 run.started 都与来源尝试一致。
- 已知缺口：温度没有加入 091 的失效判定封闭清单——模型参数变了的候选不会因此被判失效。按裁决不在本轮处理。

### 外部基准入口的温度（110）

- `eval swebench` 缺省温度 0，只能经 `--temperature` 显式改。其余入口不接受 `--temperature`，按未知参数拒绝，不静默忽略。
- 推理开启时上游不把温度交给 provider：账本不再记温度 0，而是在 run.started 的模型段记"温度未生效"与请求值（原因：推理开启），调用选项里也不带温度。

### 报告模板（113 修订）

报告只维持一套模板，条件取自在场的行（按 none、candidate、approved 的固定次序），标题写明题源与条件形态：单条件时为"单条件 none"，不出条件对照一节，条件说明只讲在场的条件；多条件时列出条件并只对在场的条件两两相减。第十二节"已在本节落实"一句中关于第九节第 7 条的说法已改正：该条的结果行字段一半在第十二节落实，报告模板一半在本节落实。

### 确定性错误（119）

模型请求以上下文超长收尾时，这次运行不记错误行、不补跑，照常判分，结果行带 `deterministicError` 标注，报告"标注"一节单列。识别用上游 pi-ai 按各 provider 报错文案的判定（含 kimi-for-coding 的文案），限额类文案先排除。此前各轮的结果文件里没有出现过上下文超长：错误文案只有请求超时、请求中止、连接中断、判据自身出错四类。认证失败、泛化的 400、模型不存在三类的处理待裁（见 119）。

### 空转断言

- 报告测试里"拒答行格子为空"一条：单条件下原断言匹配的是任何报告都有的固定字面量。改为只在成功率一节内按整行匹配（拒答题的格子为破折号、合计分母不含拒答）。
- 结果文件读侧测试里删除了两个从没设过的字段再断言"缺失也能读"：改为先设上、确认在场、再删，并同时写一条带这两个字段的新行，断言新行原样读回、旧行缺省。
- 任务源测试里四处"某字段不在场"的断言在整行缺失时也会通过：改用"行必须存在"的取行助手；其中一处原先取的是结果文件末行，同一目录里前一题的行也可能是末行，改为按题取行并确认终态。

### 容器执行端的次要修复

- 装配护栏（112 的延伸）：注入了执行端时，失败自动分叉重试、会话验证命令、分支会话一律在装配前拒绝、不写账本——三者都作用在宿主侧的工作区目录上，容器执行端下那只是占位目录。
- 写保护包装：解析受保护路径失败时，原先所有错误一律当作"目标不存在"放行写入；现在只有"不存在"放行，执行端不可用、越界、不可读时拒绝这次写入并说明原因。本地与容器两个执行端对"不存在"抛专门的子类。
- 双 key 限额切换：包装层内部出错时原先只结束流、调用方拿到空响应，现在交回一个带原因的错误事件（不含 key）；并行请求共用的退避原先挂着第一个请求者的中止信号，那个请求一中止，所有一起等待的请求都被当成中止，现在共用的等待不挂信号、各请求按自己的信号退出。自检脚本新增两条用例覆盖。
- 工作区容器的附加参数校验：原先漏掉与取值粘连的 `-p8080:80` 与 `--env-file`（文件内容无从检查，可能带代理），现已拒绝；另加一组不打开网络的参数确认不误拦。

### 工作队列与断供

runner 内部本来就是各路共用的工作队列；此前每批 10 题的等待来自外层跑批脚本——它按批判定"模型服务持续不可用"。现把断供判定移进 runner：按完成顺序连续若干次模型服务故障即全体暂停一段再取题，暂停次数用满仍连续故障就停止取新题（已完成的行保留，摘要写明原因，外部基准入口以退出码 3 结束），任何一次非故障结果把计数清零。外部基准入口缺省连续 8 次暂停 10 分钟、最多 3 次，与原外层口径一致。外层脚本因此一次交全部题，不再分批等待。新增三条测试钉住：慢题不挡住其余各路（按批等待时会变红）、每题结果行在回调之前已落盘且中途停下后续跑只跑剩下的、断供的暂停与停止。外部基准入口本身没有测试，断供接线只有缺省值与退出码两行。

提炼器按 `pigeon distill --eval-results` 读合并后的来源集结果，按题分组、每组取一成一败；四个分片并行，写进同一个经验根。先后四次：

|---|---|---|---|
| 1 | 16 轮、5 分钟、80,000 token | 4 对全部撞 token 上限，0 候选 | 3 对撞 token 上限、4 对完成，0 候选 |
| 2 | 同上、token 上限 600,000 | 按 120 中途停止，不计 | — |
| 3 | 不设 token 上限（120） | 1 对撞轮数上限、3 对第 1 轮即交空结果，0 候选 | 4 对撞轮数上限、3 对完成但未产出，0 候选 |
| 4 | 快照进首轮输入、空结果必须附理由、40 轮 12.5 分钟（121） | 2 对各产出 1 个候选；1 对附理由的空结果；1 对空结果未附理由（判为不合格式） | 4 对共产出 9 个候选；1 对附理由的空结果；1 对空结果未附理由；1 对只有被丢弃的项 |

第 1 次的原因：提炼器每轮只输出几十个 token 的读取调用，但每轮都重送整段上下文，按累计 token（含缓存命中）计的上限 5 到 8 轮就用完。第 3 次撞的是轮数而不是墙钟；另有 3 对的提炼器第 1 轮就回答空结果——没有调用读取快照的工具，整个会话只输出 15 个 token。

来源集的 2 个候选：`memory/django-enum-serialization-flag-edge-case`（lesson，强度 0.9，来自 django__django-11815）与 `memory/django-pk-default-save-regression-fix`（lesson，强度 0.9，来自 django__django-12209）。

噪声压力测试：7 对取自两轮干净基线里同条件一过一不过的题（django__django-11815、12209、12325，sphinx-doc__sphinx-10466、10673、8265、8638），提炼进独立的治理根，不参与验证与激活。

### 本轮的发现

1. **提炼器为噪声编造因果。** 噪声 7 对的差别来自同条件下的采样，提炼器仍从其中 4 对产出 9 个候选，并给出因果解释。例：sphinx-doc__sphinx-10673 的一条教训断言失败侧漏改了收集器"正是本任务隐藏验证失败的原因"，而原文里没有判分失败原因的依据；sphinx-doc__sphinx-10466 的一条教训自己写明"顺序问题未导致失败侧被判错"，仍把它作为教训产出。附理由的空结果在两组里各只有 1 对。
2. **经验退化为答案。** 来源集的 2 个候选都是本题的修法：enum 那条给出 `EnumSerializer.serialize` 的完整实现代码，pk-default 那条给出本题补丁的具体改法与改动位置，可迁移的部分只有"以实证代替回忆""用 git stash 区分预存失败"这类常规做法。噪声组 9 个候选中 6 个同样是具体题目的修法（toctree 特殊条目 3 个、enum 序列化 3 个），其中一个附了完整实现代码；泛化的只有"尽早收敛设计""去重时保序"与"用 runtests.py、git diff 收尾"几条。这正是 118 所说的"经验变成答案"：在来源题上即便验证通过，也只是上界，不说明对未见过的题有用。
3. **同一材料两次提炼不同。** django__django-11815 与 12209 的来源集对子与噪声组对子是同一对尝试：来源集那次各产出 1 个候选，噪声组那次分别产出 3 个与 2 个，内容也不同；第 3 次提炼时这两对一个撞轮数上限、一个完成而未产出。提炼器的产出本身不稳定，单次提炼的结果不能当作"这对尝试里有没有可学的"的判断。
4. **编造引用。** 噪声组的 `skill/fix-django-model-save-regression` 正文引用了 `avoid-recalling-upstream-fix-from-memory` 与 `converge-design-and-implement-early` 两个候选名；前者不存在，后者是同一次提炼里另一个候选，并非已有经验。
5. **含修法的经验回放判回归。** enum 那条候选（含本题修法代码）经四组、每组 5 次的回放验证，结论为回归：不带经验时失败侧与成功侧各 5 次全部通过，带上这条经验后两侧都只过 1 次，正回放差与负回放差均为 −0.80（门槛 0.4）。被验证的"失败尝试"在回放中 5 次全过，说明原先的失败来自采样噪声；而带上经验反而大幅变差。按裁决回归不可批准，未激活。

### 回放验证（容器）

外部基准的尝试没有宿主 git 工作树，M8 的回放原先写死了宿主工作树。本轮新增任务源上的回放：每次回放在经验根下建临时根并按 085 播种经验（带经验组另放入候选），由任务源对同一实例重新准备容器，照原尝试的整把尺子（模型参数、温度、工作方式指令、预算、工具名单、编辑模式）重跑，用任务源的判据命令判分，会话收回经验根；四组交错发起、可并行。

- `memory/django-enum-serialization-flag-edge-case`：结论回归（见发现 5），回执已落。
- `memory/django-pk-default-save-regression-fix`：这道题每次回放 15 到 20 分钟，四组各跑了 1 次（均通过）后按指示停止，没有结论、没有回执；回放验证不支持续跑，要出结论须从头重验。

## 十五、基线账本的浪费分析：agent 在哪里花了冤枉功夫

方法：对两轮最终基线（final-a、final-b）的会话账本逐条统计 `run_command` 回执与 `edit_file` 工具结果；命令按首词分为测试命令（runtests.py、pytest、manage.py test 等）、探索类（find、grep、ls、cat 等）、python 脚本类、git 与其他；失败按退出码非 0 或 isError 计；编辑报错按工具结果正文归类。会话数多于 50 是因为包含断网补跑产生的运行。对照组为 M9 前置的自建题基线（模型不熟的本仓库，8 题各 5 次），只有结果行的工具计数、无账本。

| | 第一轮 | 第二轮 | 自建题（对照） |
|---|---|---|---|
| run_command 总次数 / 失败率 | 1590 / 5.7% | 1698 / 4.5% | 422 / 1.4% |
| 测试命令次数 / 失败 | 351 / 3 | 344 / 3 | — |
| 有跑测试的会话中首次测试命令即失败 | 0 / 50 | 1 / 47 | — |
| 探索类失败率 | 5.9% | 5.2% | — |
| python 脚本类失败率 | 15.8% | 12.0% | — |
| edit_file 次数 / 报错率 | 195 / 15.9% | 183 / 14.2% | 84 / 4.8% |

命令失败的构成：无输出的失败 32 条中 grep 退出码 1 占 12、find 占 8（均为"无匹配"的正常退出）、cd 到不存在目录占 8；有输出的失败以 agent 自写复现脚本的异常为主（settings 未配置、属性不存在、断言失败）。

编辑报错的构成：第一轮 31 次中 25 次、第二轮 26 次中 22 次为试图修改判分用的测试文件、被工具围栏拦下；锚点未找到与不唯一合计每轮 3–4 次；无改动每轮 1–3 次。

结论：

- "agent 在重新发现代码库事实（测试怎么跑、命令怎么用）上浪费"这一前提在两类仓库上都不成立：知名仓库上模型首次即用对测试命令；自建仓库上命令失败率更低。
- 可见的浪费集中在三处，均不属于代码库知识：反复试图修改判分用测试文件（任务规则，已有围栏，可把提示写硬）；自写复现脚本出错（模型写代码的能力）；探索类命令（每题十余次 find/grep，是正常工作而非失误）。
- 由此 124 判定"越用越省"在知名仓库上无可测余量，第二版方向暂缓。
- 本节的统计口径应做成评测报告的固定一节，使后续每轮跑批自动产出，无需事后从账本手工挖掘。
