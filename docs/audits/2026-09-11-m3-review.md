## 当前应记录的问题

### P2-1：循环熔断覆盖面存在三个死角（与已收口的幽灵熔断同类）

spike S4 证明上游无循环护栏，Pigeon 自建了两级熔断：hook 级 `#blockWithBreaker`（adapter.ts:553-562）与事件级幽灵熔断 `#countPhantomAndMaybeBreak`（571-588）。以下三条路径两者都不计数：

1. **参数校验失败循环（最现实）**：上游 `prepareToolCall` 内 `validateToolArguments` 先于 hook（agent-loop.js:399-448 源码核读确认：校验抛错 → catch → immediate error result，hook 未运行；sequential 执行器 293-317 对 immediate 结果照常发 `tool_execution_start`/`tool_execution_end`）。模型反复给**已广告**工具发畸形参数时，`#countPhantomAndMaybeBreak` 的判据 `payload.isError && !this.#tools.has(toolName)`（adapter.ts:572）把这类 settled 判为"非幽灵"并**重置**连击——无任何护栏，循环永续。触发场景：模型持续给 `edit_file` 发缺 `snapshot` 的参数。每轮有校验错误文本反馈，良模型会自愈，但幽灵熔断收口的正是同类"反馈在、循环不止"场景。
2. **审批闸内部异常 fail-closed 循环**：`#governToolCall` 外层 catch（adapter.ts:349-361）直接返回 block，不经 `#blockWithBreaker`，`#blockCounts` 不计数。账本写盘持续失败（磁盘满等）+ 模型坚持 = 无限阻断循环。
3. **指纹级计数被参数微变绕行**：hook 级熔断以 `工具名 + JSON.stringify(rawArgs)` 为指纹（adapter.ts:554-556），deny/拒绝后模型微调任意字段即重置计数。决策 1 本就鼓励模型改参数重提，此取舍有设计依据；但 yolo+deny 组合下无人介入，顽固模型可无界空转。

定级 P2：阻断本身的可靠性未被破坏（治理/证据链完好），缺口在"上游无护栏"这一 Pigeon 自认责任区的覆盖度。修复方向：Run 级总阻断预算或工具名级计数（幽灵熔断已是名字级）。

### P2-2：receipt 写盘失败窗口内 tool.settled 事件从内存事件日志丢失

`#recordAndForward`（adapter.ts:270-311）在 `this.#events.push`（300 行）之前做账本联动：`#persistReceipt`（294）抛错 → 外层 catch → `listenerErrors`，**该条 tool.settled 事件本体不入 `#events` 也不通知 listener**；而内存 ToolExecution 已先推进到 settled（292-293）。结果：磁盘故障窗口内事件日志缺一条 settled，与内存账本不一致。冷启动对账结论不受影响（intent 无 receipt 仍正确归 OutcomeUnknown，崩溃点②测试证明），但决策①承诺"事件日志是审计轨迹"在此窗口缺一行。定级 P2（观察口一致性缺口，非证据链破坏）。

### P2-3：deny 分支"阻断生效"断言不可观测（测试强度缺口，非产品行为缺陷）

反向验证变异 A（闸口三处 block 全部改放行）实证："deny 清单绝对"（adapter-tools.test.ts:275-311，用 read 层工具，无可观察副作用）与 persistence 的 "deny 清单路径"/"未配置审批通道 fail-closed"（adapter-persistence.test.ts:194-266，edit 参数故意拿过期锚点——即便放行执行也必然预检失败、文件不动）**全部仍绿**。即若未来有人单独把 deny 分支的 `return this.#blockWithBreaker(...)` 改成放行，现有 deny 测试不会变红。缓解事实：block 原语的阻断效力已被"审批拒绝"测试实证（变异 A 下变红），deny 分支与其共享同一原语，实际逃逸风险低。建议：deny 测试补一条"toolResult 文本为 deny 理由而非文件内容/执行成功"的断言。
