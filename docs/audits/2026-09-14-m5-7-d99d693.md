### filesystem 真实链路（spikes/mcp-acc/run-filesystem.mjs，Kimi For Coding + ConPTY）

- 两个 implementer（fs-a、fs-b）并行，各自的 filesystem server 以其工作树为 roots。每个 worker 恰好两次工具调用：list_allowed_directories（read 档，自动放行，无 intent）、write_file（write 档，人工批准，intent approvedBy human）。
- 审批面板原文（剥离 ANSI 的输出流摘录，路径以占位代替）：

```text

 工具：mcp__filesystem__write_file
 参数：
 {
   "content": "written-by-fs-a\n",
   "path": "<验收工作区>\\.pigeon\\worktrees\\<fs-a 会话>-fs-a\\notes-fs-a.txt"
 }
 批准执行？[y] 批准一次 / [n] 拒绝 / [a] 本会话允许 / [d] 本会话允许(仅限当前调用所在目录)
```

  fs-b 的审批块同形，来源行为 `worker fs-b（implementer）`；输出流中两个来源行各出现一次。

- 主仓库已跟踪文件零改动，主工作区根目录无 notes 文件。
- 主会话 run_command `npm --prefix app test`：面板显示"经 cmd.exe 启动器运行：<npm.cmd>"，人工批准；exec receipt launcher true、shell false、argv 为 `cmd.exe /d /s /c ""<npm.cmd>" --prefix app test"`、退出码 0、输出含 fs-acc-test-ok。

## 已知边界与偏差（如实登记）

- 原定口径为"工具集下个 Run 生效"，§2 规则 4 原文为"运行中产生的新 Memory、Skill 或 Policy 只能从后续 Session 开始生效"，Adapter 的注入快照按会话冻结：实现为清单变更只记录、本会话工具集不变、下个会话生效，比"下个 Run"更保守；换 Run 间工具集需要按 Run 重建快照与治理实例的工具表，不在本里程碑。
- implementer 继承父策略全部 MCP 工具、其余角色不继承：施工中为 S5 两个 worker 用 filesystem 写文件而定，收口后经项目负责人认可，记为 decisions.md 041 修订（只读与测试角色暂不接）。
- worker 有 MCP 配置时运行面在 run 时异步就绪：会话头写不进或装配失败按 worker 失败收尾，而非 M5.5 同步路径的派出失败，父会话照样落 child.spawned 与 child.settled 两条记录；无 MCP 配置时行为与 M5.5 相同。收口后经项目负责人认可，记为 decisions.md 040 修订。
- 注解冲突对"声明只读而未逐工具配置"的工具同样标出，缺省 write 的 server 冲突项多，trace 头与启动警告会很长。
- 审批在调用之前：server 已不可用时写档调用仍先问人，批准后报环境错误。
- filesystem 的返回不带 evidence 键，真实链路回执的 serverEvidence 缺省；收入与 16 KiB 截断由单元测试与内存夹具覆盖，真实 server 未覆盖。
- 重启计数是本会话总次数：多次掉线后重连成功也计入上限。
- mcp 块的 argsHash 按上游校验后交给工具执行体的参数计算（即实际发给 server 的参数）；上游对参数做类型强制转换时可能与 intent 原始参数的哈希不同，不一致本身即如实暴露差异。
- streamable HTTP 传输只经类型与构造路径，未对真实 HTTP server 实跑。
- 需要参数的 prompt 不进目录；resources 读取、sampling、elicitation、HTTP 鉴权与 OAuth、第二种隔离形状、沙箱、Pigeon 作 MCP server 按开工范围不做。
