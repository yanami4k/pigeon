# 延续式跑批器：出题与环境（决策 127、141、148、153，基线 aaa59a8）

范围：延续式实验（126）跑批器的第一、二部分——按写死的规则从人的提交历史生成流清单，以及每条流的断网容器工作区（起点、逐步覆盖人的测试、落地提交、回到本步起点、续跑导出、全量测量副本）。四个条件的运行、限额统一处理、结果行与报告、最简 agent 不在本轮。

## 一、出题规则

纯规则在 `src/eval/stream-manifest.ts`，两个仓库的配置在 `src/eval/stream-profiles.ts`；输入是逐提交的事实（文件改动、Linux 容器里测得的判题探针、格式化比对），输出是清单。规则与取事实分开，便于用已知测量做回归检查。

每个提交按下列顺序定性，先命中者为准：

| 顺序 | 条件 | 类型 |
|---|---|---|
| 1 | 仓库配置判为重置点 | 重置：该提交的代码为下一条流的起点 |
| 2 | 不碰被测代码（源代码、测试、测试辅助、环境文件都没有） | 跳过 |
| 3 | 没有源代码改动（只改测试、测试辅助或环境文件） | 套用：程序写入人的版本 |
| 4 | 带测试改动，测试打到父提交上失败、打到本提交上通过 | 题 |
| 5 | 对父提交跑格式化后与本提交逐字一致 | 跳过 |
| 6 | 其余 | 维护步：题面为提交信息，只用验证门判 |

红测试对（127）：提交自身带的测试在自身上不过、放到下一个提交上通过，两次提交合为一题。父提交取先者的父，题面为两段提交信息加两次提交测试文件的并集，判题集为并集；不跨重置点合并。只改测试的提交同样要有判题探针，因为红测试对的先手正是只改测试的提交。缺探针或缺格式化比对即报错，不默认定性。

题面：提交信息原文，其后逐个附上该步新增或修改的测试文件全文（每个文件前一行 `--- 路径 ---`），不加任何包装措辞，与 M9 外部基准的做法一致。

每步清单记：步序、类型、提交与父提交、红测试对的两个提交、题面、程序写入的人的文件（路径、写入或删除、文件类别）、判题测试集、定性理由；清单另记验证门命令与按重置点切出的各条流（起点提交与步序范围）。

### 文件归类

| 类别 | 本仓库 | strands |
|---|---|---|
| 源代码 | `src/` 下除测试与测试辅助外的文件；机检配置 `tsconfig.json`、`.dependency-cruiser.js`、`biome.json`（与源代码同属 agent 的活，不覆盖） | `strands-py/src/**/*.py` |
| 测试 | `src/**/*.test.ts` | `strands-py/tests/` 下的 `test_*.py`、`*_test.py` |
| 测试辅助 | `src/` 下文件名为 `fixtures.ts`、`*-fixtures.ts`、`testing.ts` 的（流区间内为 `pi-runtime/fixtures.ts` 与 `tui/testing.ts`，生产代码不引用它们） | `strands-py/tests/` 下其余文件（conftest、夹具、数据），`strands-py/tests_typing/` |
| 环境文件 | `package.json`、`package-lock.json`、`.gitattributes`、`.gitignore`、`.nvmrc`、`.npmrc` | `strands-py/pyproject.toml` |
| 其余 | 文档、探针脚本等 | 其他语言部分、站点、文档、CI、`tests_integ`（需要网络） |

只改环境文件的提交归套用：容器断网，agent 装不了依赖，由程序写入人的版本；strands 在写入后离线切换到满足当前依赖声明的冻结依赖组合。

### 重置点与验证门

- 本仓库：逾 20 个文件（按全部文件计）的提交处重置（141）。验证门 `npm run verify`。
- strands：源代码改动逾 3,000 行处重置；其余提交在"逾 20 个文件"上只数源文件，源文件逾 20 个亦重置（153）。验证门按其 CI 定义（`python-test-lint.yml` 与 pyproject 的 hatch 脚本）：`ruff format --check`、`ruff check`、`mypy ./src ./tests_typing`、单测 `pytest tests`，在 `strands-py` 下执行；被测包以源码目录（`PYTHONPATH=src`）直接导入，不做可编辑安装；`tests_integ` 不在单测范围内。

### 格式化比对

"只有格式变化"的判定：检出父提交，对该提交改动的文件跑格式化，与该提交逐字比较；该提交有增删文件的一律不算。本仓库用 `biome check --write --linter-enabled=false`（格式化加 import 整理，不含 lint 自动修复）：`57dc322`（Apply biome formatting to replay slice files）在格式化之外整理了 import，只用 `biome format` 会误判为非格式提交。strands 用 `ruff format` 加 `ruff check --select I --fix`（import 排序），口径相同。

## 二、取事实与探针

`src/eval/stream-facts.ts`：

- 人的仓库只读：主线提交（`--first-parent`）、逐提交文件改动（关闭改名检测，改名记一删一增）、取文件内容、生成某提交可达历史的 bundle（临时引用，用完删除）。
- 参考工作区：一个断网容器，装入人的完整历史到区间终点，按需检出任意提交、写入人的文件、跑命令。它只用于出题，不是 agent 的工作区。
- 探针按规则需要才测：带测试改动的提交测"父提交加该提交的测试、测试辅助与环境文件"与"本提交"两次；本提交上也不过的，再测"下一个提交加本提交的测试"；改了源代码且不成题的测格式化比对；重置点不测。strands 每次检出与写入后先离线切换依赖组合。每次探针的退出码、是否超时、输出尾部都记下，与清单分开存为 `<清单名>.probes.json`。

`src/eval/stream-generate.ts` 与命令：

- `pigeon eval stream-manifest --repo-profile pigeon|strands --repo <人的仓库> --range <起点>..<终点> --image <镜像> --out <清单文件> [--test-timeout-sec N]`：起参考容器（`--network none`），取事实、出清单、写清单与探针记录，结束时移除容器；标准输出为各流步数与类型分布摘要。
- `pigeon eval stream-image-context --repo-profile pigeon|strands --repo <人的仓库> --out <目录> [--lock-rev <提交>]`：组装工作区镜像的构建上下文。

## 三、流工作区

`src/eval/stream-workspace.ts`。工作区的一切动作都是在工作区根执行的一段 sh 脚本，经 `StreamShell` 下发：生产实现走 `docker exec`（`dockerStreamShell`），测试用本机 sh 在临时目录里真跑同一批脚本（`stream-shell-fixtures.ts`）。

| 动作 | 做法 |
|---|---|
| 起点 | 宿主把"起点提交可达历史"打成 bundle 经标准输入送入，`git fetch` 取出起点提交并检出；再跑与外部基准同一份历史清理脚本并自验（109），检出结果必须等于起点提交。bundle 只含起点可达的历史，未来对象本来就不在容器里；清理脚本是第二道。工作区根里预装、被 `.gitignore` 忽略的依赖目录保留（两条流起点的 `.gitignore` 均忽略 `node_modules/`） |
| 写入人的文件 | 内容由宿主从人的提交里取、经标准输入送入（可为二进制）；删除即 `rm -f`。容器里没有未来提交的对象 |
| 验证门与命令 | 容器内以 `timeout -s KILL` 限时；退出码 137 且用满墙钟才记超时（137 也可能是内存超限） |
| 落地 | `git add -A` 后以该步提交信息提交一次（无改动也提交，步与提交一一对应），提交者为程序身份 `pigeon-stream` |
| 回到本步起点 | 每步起点即 HEAD：`git reset --hard HEAD` 加 `git clean -fd`（不带 `-x`），复原被跟踪文件、删掉未忽略的未跟踪文件，被忽略的依赖目录不动（154） |
| 续跑导出与恢复 | 每步落地后导出整条流历史为 bundle 存到宿主；容器丢失时由镜像加 bundle 恢复到断点 |
| 测量副本 | 从 HEAD 克隆到另一目录（`core.autocrlf=false`），依赖目录以链接接上，在副本里写入人的文件后跑全量测试；工作区本身不受影响（145、148） |

共用约束收拢：断网参数与校验、历史清理脚本与自验原在 `swebench-source.ts` 内部，移到 `src/eval/container-workspace.ts`，外部基准与延续式跑批都从这里取，只此一份实现（096）。`containerExec` 增加可选的标准输入（字符串或二进制，带 `-i`）与原始字节输出，既有调用方不受影响。

## 四、全量测量

`src/eval/stream-measure.ts`：用例结果统一取自 junit 报告——`node --test --test-reporter=junit` 与 `pytest -o junit_family=xunit1 --junitxml`（xunit1 带文件路径）同一解析。用例标识为"相对仓库根的文件路径 :: 分组路径 :: 名称"；测试文件加载失败在两种报告器里都是一条失败用例。

- 按条数：分母为人的代码在同一提交上通过的用例，数 agent 代码上同样通过的；agent 那边缺失（加载失败、被删）算没过，多出来的用例不计。
- 按题：截至该步做过的题里，其判题测试文件中人的代码上通过的用例在 agent 代码上全部通过的比例；判题文件在人的基准里已无通过用例（被人删掉或改名）的题不计入分母。

## 十、跑批主体（第三、四、六节）

`src/eval/stream-runner.ts`、`stream-agents.ts`、`stream-results.ts`、`stream-report.ts`、`stream-attribution.ts`、`stream-experiment.ts`；工作队列 `src/eval/work-queue.ts`。

作业：每条流乘以每个条件乘以第几遍为一个作业，共用工作队列并行（缺省 4 路）。外部基准跑批原有的逐题队列改为同一份工作队列（096）。

四个条件：

| 条件 | agent | 回炉轮数 | 撤回 | 记忆 |
|---|---|---|---|---|
| full（完整 Pigeon） | Pigeon | 3 | 是 | 开（记忆尚未建，等同于关） |
| no-memory（去掉记忆） | Pigeon | 3 | 是 | 关 |
| no-gate（去掉验证门与回退） | Pigeon | 0 | 否 | 关 |
| minimal（最简 agent） | mini-swe-agent | 0 | 否 | 关 |

回炉按决策 142、143 与 154 接入（容器上的回炉见回炉一侧的审计）。回炉字段在结果行里名为 `repairRounds`、`finalVerdict`、`reverted`。撤回按 154 的推断口径：条件开启撤回且回炉最后一次验证失败即撤回。

每一步的流程：

1. 回到本步起点（上一步结束时的提交；复原被跟踪文件、删除未忽略的未跟踪文件）。
2. 写入该步人的测试、测试辅助与环境文件；strands 离线切换依赖组合。
3. 按条件运行 agent（题：题面为提交信息加测试全文；维护步：提交信息）。每步总预算缺省 150 轮、30 分钟，可配置（147）。
4. agent 在容器里自己提交的，把 HEAD 挪回本步起点、改动留在工作区。agent 动过的测试与测试辅助文件：本步由程序写入的恢复为人的版本，其余恢复为本步起点的版本；agent 新建的测试文件保留（全量测量只跑人写的测试）。
5. 判定：题跑判题测试，维护步跑验证门。
6. 撤回（回到本步起点，该步留空）或以该步提交信息落地提交。
7. 全量测量：从 HEAD 克隆测量副本，按 blob 哈希补齐人截至该步的全部测试与测试辅助文件（被撤回题的测试也在内），跑人写的全部测试；按条数与按题两种通过率，回归数（上一步在 agent 代码上通过、本步不再通过的人的用例），机检三项计数（本仓库：tsc 错误、biome 格式错误、depcruise 违规；strands：mypy 错误、ruff 格式错误，无分层规则）。人的代码在同一提交上的用例结果由参考容器算出，按提交缓存，各条件共用。
8. 失败归因（第 16 条）：从判定输出里提取测试加载时找不到的文件或名字（node 与 pytest 两种文案），与此前被撤回的题、此前维护步里人新建的文件与顶层定义比对。优先级：缺前置 > 维护步接口不同 > 回归 > 没做出来。
9. 导出流历史（bundle）与本步的测量基线，再追加结果行。两者之间崩溃时，断点行仍指向上一步，导出的历史里也有上一步的提交，续跑从断点恢复。

跳过步不落地、不跑 agent，结果行沿用上一步的测量。结果行字段见 stream-results.ts 的字段清单（决策 142 至 145）；被打断的一步不留行，因此没有错误行。

报告（决策 145、146）：每条流一张健康度曲线表（全量测试通过率按条数随步序，第一遍）、各条件终点值（多遍给均值与范围）、次要指标表、失败归因分布、补跑判定（任意两个条件第一遍终点相差小于 10 个百分点即提示各补跑到 3 遍）。试跑模式 `--max-steps K` 只跑每条流前 K 步，报告标题注明。

命令：`pigeon eval stream --manifest <清单> --repo <人的仓库> --image <镜像> --out <输出目录> --conditions … [--streams] [--attempts] [--concurrency] [--max-steps] [--max-turns] [--wall-clock-min] [--model-id] [--mini-python] [--container-memory] [--yolo]`；同一输出目录重跑即续跑。

## 十一、模型网关与限额（第 17、18 条，决策 155）

`src/eval/model-gateway.ts`、`src/eval/model-limits.ts`、`src/pi-runtime/gateway-stream.ts`。

- 网关：跑批进程内置，只听 127.0.0.1，Anthropic Messages 协议；作业路径前缀 `/j/<作业>/`；请求里的 key 是占位，真 key 只在网关里注入（取自 `KIMI_API_KEY` 与可选的 `KIMI_API_KEY_2`）。200 的响应原样流式透传，同时从 `message_start` 与 `message_delta` 事件读出用量按作业计量；交回客户端的任何文本里都不出现 key。
- 429：双 key 轮换加共享退避（5、15、45 秒），切换后保持使用新 key；退避用满仍撞即按频率限制整批暂停。
- 403：按文案分类——并发受限；额度（正文含"月"为每月、含"周"为每周、其余额度类为 5 小时）；其余为认证，原样交回。每周与每月额度的上游原文没有样本，分类按关键词，拿到原文后只需改两个正则。
- 限额控制器：额度暂停时整批暂停，探测用极小的请求，间隔 5、10、15、20、25、30 分钟后保持 30 分钟，总等待上限 6 小时；每月额度直接停止并告警；并发受限先降一路，已是 1 路则暂停；告警去重。暂停期间网关以 529 拒绝请求、不打上游。
- 跑批接入：每步前等控制器放行；agent 运行期间占一路在途名额；这一步前后控制器收到过限额信号即作废（已回到本步起点、不留行），恢复后重做同一步，暂停记录挂在该步结果行上。四个条件的轮数（成功转发的模型请求数）与 token 一律取网关计量。
- Pigeon 的模型接入：`gatewayStreamFn` 用上游目录里的真实模型元数据，只把基址换成网关给该作业的地址。上游模型目录在运行时按需加载（其类型声明以 JSON 导入写成，在本仓库的 NodeNext 设定下过不了类型检查）。
- 最简 agent：`eval/stream/mini/run_mini.py` 原样使用 mini-swe-agent 2.4.6 的 SWE-bench 配置（系统与题面模板照旧），只改三处：步数上限设为同一轮数、不设成本上限（上游模型不在 litellm 的价目表里）、墙钟由跑批器计时。命令经 `docker exec` 在该流已有的断网容器里执行；模型经 litellm 的 anthropic 线路发往网关。限额暂停时跑批器杀掉启动器，该步作废重做。
- 限额识别口径（明说用量上限的 403 算限额、其余 401/403 算认证、上下文超长不算）、去 key 与退避间隔只留一份在 `model-limits.ts`；`spikes/key-failover.mjs` 改为从这里引用，其自检照旧通过。外部基准的 `eval swebench` 仍用探针那条模型接入，本轮未改。

## 十五、strands 清单生成与断点续测

strands 清单在容器里生成（镜像 `pigeon-stream-strands:v1`，参考容器内存上限 4g），第二次开跑到第 66/195 个提交时，本机内存严重不足，任务被系统停掉；前 66 个提交的判定与产率测量一致（如 `2a4fc5d35` 父提交上已通过且只有格式变化）。随后给取事实加了断点文件：每测完一个提交即追加一行（探针结论与原始记录），同一条命令重跑时已测的提交直接取回、不再动参考容器。新增变异"已测的提交不从断点取回"变红：取事实与出清单……端到端判对，探针原始记录随附。被停的那一次没有断点文件，重跑需从头测。

内存来源的查证：探针命令为 `python -m pytest -q -p no:cacheprovider <本题测试文件>`，不带 `-n`；窗口内五套依赖组合对应的 pyproject 里 pytest 的 `addopts` 均不含 `-n`（只有 `--junit-xml`，V0 另有两个 `--ignore`），`-n auto` 只在不经由探针的 hatch-test 环境里。pytest-xdist 已安装，但不带 `-n` 时不起 worker，因此探针一直是单进程执行，命令不需要改，此前已测提交的判定也不存在单进程与多进程之别。

第三次开跑（带断点，第 1 至 92 个提交取自断点）测到第 93 个提交 `534692a8a` 时，判为"父提交失败、本提交也不过"，与产率测量的"成题"不一致。本提交上 179 个用例中 2 个失败，均为 `test_mcp_client_client_info_passed`：被测代码经 `importlib.metadata.version("strands-agents")` 取 SDK 版本号，而镜像不安装被测包（经 `PYTHONPATH` 从源码目录导入），取不到；产率测量时被测包为可编辑安装，取得到。这一差异同样会让 strands 的验证门与全量测量逐步多出失败。修法：每套依赖环境只放一份被测包的占位元数据（名称与版本 `1.0.0+stream`，不含代码），在记下依赖清单之后写入，不参与依赖组合的选择；代码仍从工作区或测量副本的源码目录导入。镜像改为 `pigeon-stream-strands:v2`。此前在缺元数据的环境里测得的 97 个提交作废，断点文件另存备查，重测后逐个比对。

本仓库镜像的同类检查：本仓库代码只在 `pi-runtime/upstream-version.ts` 读取包清单，读的是上游依赖（在镜像预装的依赖目录里），自身模块之间全为相对路径引用，没有"须先安装被测包"的环节；试跑时参考容器算出的人的基准在三个提交上均为全部通过（25、26、26 条），没有环境缺口造成的失败。

v2 镜像的建法：按仓库 Dockerfile 完整重建时，第二阶段往五套环境装包期间本机内存告急、构建被系统停掉。改为以 v1 为底只加一层：该层的命令与仓库 Dockerfile 里写入占位元数据的那几行逐字相同，层大小 325 字节。核对：五套环境都读到版本 `1.0.0+stream`；五份依赖清单的校验和与 v1 逐一相同（占位元数据未混入依赖组合的选择）；v2 里恰有五个被测包的元数据目录，v1 里为零。由此 v2 的内容等同于按仓库 Dockerfile 完整重建的结果；仓库 Dockerfile 仍是正式定义。

第四次开跑（v2，从头）测到第 110 个提交 `7b0f874c8`（fix(bidi): bedrock nova sonic reconnect）时，参考容器内存到达 4 GiB 上限：容器内唯一的大进程是 `python -m pytest … tests/strands/experimental/bidi/models/test_bedrock.py`，常驻约 4,076 MB，属于该提交的父提交探针（父提交代码加本提交的测试）——父提交尚未修复重连问题，本提交新增的测试在其上失控、内存持续上涨。仓库在 pyproject 里给 pytest 设了每条 90 秒的单测超时，但缺省的信号方式打断不了这类异步循环。处理：

- 判定口径：探针退出码为 137（容器内存上限触发的结束，或墙钟超时由 timeout 杀掉）或超时，一律记为环境错误，不作父败或本败判定，该提交不再做其余探针；环境错误的提交在出清单时单列并报错，处理方式待定之前不出清单。新增用例"探针被杀……记为环境错误……"；变异"探针被杀不记环境错误"变红该用例。
- 失控用例：strands 的探针、全量测量与验证门调用 pytest 时加 `-o timeout_method=thread`，单测超时（仓库设定的 90 秒）改由线程方式结束整个进程，不另设超时时长。
- 断点里已测的 108 个提交没有任何探针超时或被杀，`timeout_method` 只作用于超时的用例，这些结论不受影响，保留不重测。

内存：Docker 虚拟机内部实际占用不大，但读文件留下的页缓存不及时交还宿主，宿主侧一度被占去数 GB。清单生成期间在仓库之外用一个后台脚本按断点文件的进度每约 10 个提交、以及镜像构建结束后，让虚拟机丢弃页缓存；这属于本机环境的处置，不写入跑批代码。

## 十六、逐用例判定、收集出错续跑与分母口径

第十五节里"改用线程方式结束超时用例"的做法撤回：线程方式超时即结束整个 pytest 进程，同一次运行里其余用例的结果全部丢失，一条失控的用例会让整个文件、整次全量测量都拿不到结果。

信号方式的实测（`7b0f874c8` 的父提交探针，参考容器上限 4 GiB，内存每约 3 秒采样一次）：仓库设定的 90 秒单测超时按信号方式打断了失控的 `test_receive_ends_when_stream_closed`，其余用例照常跑完，报告写出，汇总为 1 败 46 过（113.68 秒）；此后进程不退出，内存停在上限附近，最终被杀。由此：退出码不能作为判定依据，报告写出后进程是否退出与结果无关。

改为逐用例判定，探针、判题、全量测量与人的基准共用一个入口（`runCases`）：

- strands：pytest 在后台跑，带 `-v`、`--continue-on-collection-errors` 与 xunit1 报告；外壳每秒检查一次，报告写出后等 5 秒杀掉进程，到墙钟也杀掉。写出了报告即以报告为准。报告写出前被杀（容器内存上限、墙钟）时，从 `-v` 的逐行进度收回已完成的用例，把正在跑、没有结果的那条记为失败（卡死），以 `--deselect` 排除两者续跑剩下的；没有任何进展即停下，记为未完成。
- 本仓库：`node --test` 的 junit 报告写到文件，同时 spec 报告写到标准输出。失败归因（缺前置、维护步接口不同）从报错文案里取找不到的文件与名字；只写 junit 文件时标准输出为空，归因会全部落成"没做出来"。改造途中由用例"完整 Pigeon：回炉最终不通过即撤回……"发现，已修正。

- 用例标识与 pytest 的 nodeid 一致（文件::类::用例），收集出错的文件记一条"文件::<collection>"失败。

收集出错：不带 `--continue-on-collection-errors` 时，一个文件导入失败即中断整次运行，一条用例都不跑。用本机 pytest 9.1.1（与镜像同版本）对照：两个文件其一导入失败，不带该选项时退出码 2、报告里只有那条收集错误；带上后另一文件的通过与失败照常记录，收集错误以 `<error>` 元素出现。探针、全量测量与验证门都加上该选项。此前产率测量里 `7b0f874c8` 父提交一侧"47 条失败"的数，来自测试目录整体运行时 `test_google.py` 收集出错中断；容器里只跑本题测试文件，父提交上真实失败为 1 条。

验证门：通过与否改看报告里有没有 `<failure>` 或 `<error>` 元素，不依赖计数属性；pytest 的简短汇总会写明超时的用例（`Failed: Timeout`）与收集出错的文件，即给 agent 的反馈。

## 十八、人的基准提前单独算

人的基准（每步的提交上跑人截至该步的全部测试，跑两遍）不依赖回炉与记忆，可在清单出来后先算。新增 `eval stream-baseline`：

- 目标：清单里需要全量测量的步（题、维护步、套用）的提交，按清单顺序去重；跳过与重置沿用上一步的测量，不在其内。每个提交的测试文件与全量测量取自同一个函数（该提交上人写的全部测试文件），两边的用例集一致。
- 每路一个独立的参考容器，与作业的参考容器分开（缺省 1 路、2g）；哪一路空了就取下一个提交。
- 每个提交的结果原子落盘为一个文件；同一目录重跑时已落盘的跳过，加路数即带更大的并行数重跑。一个提交出错记下来、接着算其余的，结束时列出出错的提交并以非零退出。
- 每个提交一行日志：用例数、每遍都过的条数、时过时不过的条数、每遍墙钟与内存峰值、最慢用例。
- `eval stream --baseline <目录>`：正式实验读这个目录，不再现算。

## 十九、conftest 导入失败

strands 清单重测（v2、1 路、2g）测完全部 195 个提交后，出清单时被一个环境错误挡下：`534692a8a` 的父提交探针"没拿到全部用例的结果"。原始记录显示，这不是环境问题：父提交上 `tests/strands/tools/mcp/conftest.py` 导入 `strands.tools.mcp._compat` 失败，而 `_compat` 正是本提交新建的模块。pytest 遇到 conftest 导入失败时，在收集前整次中止（退出码 4），不写报告，`--continue-on-collection-errors` 也管不到；韧性运行因此"没有任何进展"，落成了环境错误。全量测量中这一缺口更严重：一个坏掉的 conftest 会让整次测量一条结果都拿不到。

用本机 pytest 9.1.1 对照：conftest 里的 ImportError 与语法错误都报成 "ImportError while loading conftest '<路径>'"，退出码 4，不写报告；把该目录下的文件从参数里去掉后，其余文件照常跑完。

修法与单个文件收集出错同一口径：韧性运行识别这句报错，本次请求的测试文件中落在该 conftest 所在目录下的，各记一条"文件::<collection>"失败，其余文件去掉它们续跑；请求的文件全在该目录下即直接算完整。`7b0f874c8` 这次得到正常的逐用例结果（父败，卡死的用例记失败），不再是环境错误。

新增用例"韧性运行：conftest 导入失败时整次中止、不写报告——该目录下的测试文件各记一条收集失败，其余文件去掉它们续跑"。变异均变红该用例：conftest 导入失败不处理；出错目录下的文件不从续跑里去掉；文件全在出错目录下不算完整。

## 二十、以非 root 用户执行（v3 镜像）

v2 上 `518113356` 被判为维护步：本提交上 175 条中 2 条失败，均在 `test_local_file_storage.py`（`test_write_error_raises_storage_error` 期望写 `/nonexistent/...` 报错，`test_read_error_raises_storage_error` 期望 `chmod 000` 后读取报错）。容器里以 root 执行，两件都不会报错。这类用例在人的代码上同样恒失败，验证门因而恒不通过。

处理：两个镜像都建非 root 用户 `stream`（uid 10001）并设为镜像的缺省用户。跑批器对容器的一切调用都经不带 `-u` 的 `docker exec`，因此探针、判题、全量测量、人的基准、验证门、agent 的工具调用与撤回时的 git 操作都以它执行，文件属主一致。工作区 `/testbed` 与测量副本目录 `/measure` 归它所有；strands 另把 `/opt` 目录与 `/opt/venv` 链接归它（切换依赖组合时在 `/opt` 下替换该链接）；依赖目录保持 root 所有、只读使用。测量副本改为只清空 `/measure` 里的内容再克隆进去，不删目录本身（非 root 用户写不了 `/`）。

v3 镜像以 v2（strands）与 `aaa59a8`（本仓库）为底只加一层，该层命令与仓库 Dockerfile 新增的几行逐字相同（约 9 kB）。在 v3 里核对：`id -u` 为 10001；`/testbed`、`/measure` 归 `stream`；以 `stream` 身份 `mkdir /nonexistent` 被拒；能在 `/testbed` 里 `git init`；strands 以 `stream` 身份执行 `select-env` 成功，`/opt/venv` 指向所选组合。

以 root 算出的人的基准作废（开跑约 5 分钟，没有落盘任何结果）。strands 与本仓库两个清单在 v3 上从头重测；人的基准在 v3 上从头算，先用当前清单的提交集合开跑：基准按提交落盘、与步类型无关，v3 清单若因红测试对或"只有格式变化"改变了要测量的提交集合，用新清单重跑同一命令即只补缺的提交。

新增断言：重建测量副本时以点开头的文件同样清掉。变异"清空副本漏掉点文件"变红：测量副本：从 HEAD 克隆、依赖目录接上，写入人的文件不影响工作区。
