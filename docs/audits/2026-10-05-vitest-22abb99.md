## 二、改法

### 批量改写（node:test → Vitest）

一次性改写脚本放在仓库外，按语法树改，字符串字面量里的内容不动（`stream-profiles.test.ts` 里有三处测试用的
`node:test` 源码字符串，原样保留）。

- 引入：`node:test` → `vitest`；`before` → `beforeAll`、`after` → `afterAll`（只改作被调用者的引用，同名的局部变量不动；
  共 32 处），`mock` → `vi`。
- 按平台或环境跳过：`test(名称, { skip: 条件 }, fn)` → `test.skipIf(条件)(名称, fn)`，`describe` 同理，共 68 处。
  条件表达式原样保留，原因字符串留在代码里，跳过的平台条件不变。
- `describe(名称, { concurrency: true }, fn)` → `describe.concurrent(名称, fn)`，4 处。
- `t.diagnostic(…)` → `await t.annotate(…)`（5 处，所在测试都是 async）；`mock.method(fs, "writeSync", …)` →
  `vi.spyOn(fs, "writeSync").mockImplementation(…)`，还原改为 `mockRestore()`（1 处）。
- `t.skip(原因)` 9 处照旧可用：Vitest 的 `t.skip` 会立即中止该测试，原因出现在报告里。这 9 处都是跳过后即收尾，行为不变。
- 断言保持 `node:assert/strict`，不改写成 `expect`。理由：它是 Node 标准库，在 Vitest 里原生可用，不是垫片；
  改写约 8 千处有语义差异（`Object.is` 与 `===` 在 NaN、±0 上不同；`throws` 的类、正则、断言函数三种形式；第三个参数的失败信息），
  风险大，收益只是风格统一。`docs/testing.md` 写明新测试可用 `node:assert` 或 `expect`，同一文件里统一一种。
- 改写后由 biome 统一引入顺序与折行（78 个文件）。`pigeon-paths-boundary.test.ts` 去掉一个只在本文件里用的 `export`
  （从 vitest 引入后 biome 把它认作测试文件，测试文件不得导出），并把基准文件（`*.bench.ts`）和测试文件一样排除在
  "非测试源码"之外。

### 配置（`vitest.config.ts`）

- 快慢档沿用 `scripts/test-tiers.mjs` 的清单，`scripts/run-tests.mjs` 经环境变量把档位交给配置；脚本名不变：
  `npm run test`、`test:slow`、`verify`、`verify:full`；CI 照旧跑 `verify:full`。`TEST_CONCURRENCY` 映射为 `--maxWorkers`；
  给了文件或 glob 只跑这些文件，其余参数交给 `vitest run`。
- `pool: "forks"`；测试文件之间不隔离（见下节），`PIGEON_TEST_ISOLATE=1` 切回每个文件隔离。
- 单个测试与钩子的超时上限 10 分钟（node:test 不限时；Vitest 缺省测试 5 秒、钩子 10 秒，会把长用例误判超时）。
- `describe.concurrent` 的组内并发上限 64（node:test 的 `concurrency: true` 不设上限；Vitest 缺省 5）。
- 覆盖率 provider 为 v8（`npm run coverage`，报告写到 `coverage/`，不进 verify）；基准文件为 `src/**/*.bench.ts`。
- 类型检查仍由 `npm run check`（tsc）把关。Vitest 经 Vite 转译测试与被测代码，与产品运行时（Node 原生剥类型）的编译方式不同，
  写进 `docs/testing.md`。

### 隔离方式与依赖预打包的实测

服务器无别的测试进程时，两档全部（1821 项），并发 6：

| 配置 | 耗时（秒） | 加载模块占比 | 结果 |
|---|---|---|---|
| forks、每个文件隔离、依赖外置 | 85.0、85.0、85.2、85.1、85.2、85.1 | 26% | 6 次全过 |
| forks、不隔离、依赖外置 | 58.5、59.0、58.7、58.1、58.4、58.3、57.7、58.3 | 2% | 8 次全过 |
| forks、每个文件隔离、依赖内联并预打包 | 88.7、89.5 | 27% | 2 次全过 |
| forks、不隔离、依赖内联并预打包 | 60.0、59.7 | 2% | 2 次全过 |

- 不隔离的稳定性另测：并发 3（105.9 秒）、并发 2（156.9 秒）、并发 6 打乱文件顺序两次（64.2、67.4 秒），均全过。
  不隔离累计 15 次运行，没有一次出现文件之间串扰导致的失败。
- 选不隔离：快约三成且稳定。`docs/testing.md` 写明新测试不要依赖进程级的全局状态（环境变量、当前目录、模块级单例、全局打桩），
  要用就在测试里还原；怀疑串扰时用 `PIGEON_TEST_ISOLATE=1` 切回隔离复查，或打乱文件顺序复现。
- 不做依赖预打包，与决策 369 的原话有出入：依赖保持外置（Vitest 缺省）时预打包的配置不生效；改为内联再预打包，
  两种隔离方式都慢 2–4 秒（转译占比由 2% 升到 4%）。不隔离之后加载模块只占约 2%，预打包没有可省的。

### 量具

- `scripts/test-timing.mjs`：改为跑一次 Vitest，经报告器 `scripts/timing-reporter.mjs` 取每个文件与每个测试的耗时。
- `scripts/test-coverage.mjs`：每个文件单独跑一次 Vitest 的 v8 覆盖率（lcov），独有行的算法不变。

### 基准（`npm run bench`，不进 verify，按文件串行）

Vitest 5 的写法：基准写在 `*.bench.ts` 的测试里，从测试上下文取 `bench(名称, fn).run(选项)`。一次运行的数字
（服务器，当时另有别的会话在跑测试；同一台机器、负载相近时比较前后）：

| 文件 | 基准 | 平均 |
|---|---|---|
| `src/tools/file-changes.bench.ts`（决策 348） | git 工作区一次命令的文件变化报告 | 39.3 毫秒 |
| 同上 | 参照：同一工作区退回整树扫描 | 322.7 毫秒 |
| 同上 | 非 git 工作区（跳过 .venv、dist 等） | 42.5 毫秒 |
| `src/execution/container-round-trips.bench.ts`（决策 349、368） | read_file / edit_file / write_file / run_command / grep / glob 各一次（假 docker，每次 exec 加 20 毫秒） | 81.6 / 155.7 / 305.4 / 111.9 / 387.0 / 383.4 毫秒 |
| 同上 | 每次调用的 exec 次数 | 1 / 2 / 4 / 1 / 5 / 5 |
| `src/application/checkpoints.bench.ts`（决策 350） | 一轮 edit_file → 下一次请求（模拟模型延迟 300 毫秒） | 约 330 毫秒；工具结束到下一次请求中位 14.0 毫秒 |
| `src/cli/bundle-startup.bench.ts`（决策 351） | 打包产物启动到第一个请求 | 318.5 毫秒 |
| 同上 | 参照：源码入口 | 709.6 毫秒 |
| `src/application/parallel-reads.bench.ts`（决策 353） | 一轮 8 个 read_file（每次读 50 毫秒） | 60.1 毫秒 |
| 同上 | 参照：一轮 1 个 read_file | 57.6 毫秒 |
| `src/pi-runtime/context-prune.bench.ts`（决策 361） | 每次请求前的裁剪计算：缺省设置不裁 / 裁一批 | 0.30 / 0.47 毫秒 |

read_file 1 次、edit_file 2 次、run_command 1 次 exec 与 `container-round-trips.test.ts` 的断言一致；write_file、grep、glob
的次数没有测试断言，以这次为基线。打包产物的基准在 `dist/pigeon.mjs` 不存在时整组跳过（先 `npm run bundle`）。
