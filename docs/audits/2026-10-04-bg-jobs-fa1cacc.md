# 单次超时与显式后台作业（决策 365）施工审计

基线 fa1cacc。分支 bg-jobs，提交 c70fb77、5ae1d6c、5458490、c5ec8bb，另加本审计所在的提交。

## 一、单次超时（提交 c70fb77、5ae1d6c）

- run_command 新增可选参数 `timeout_seconds`。缺省 120 秒、上限 600 秒，设置 `tools.runCommand.timeoutSeconds`、`maxTimeoutSeconds` 可改（缺省大于上限时按上限）。给得超过上限即拒绝执行并说明上限，不悄悄压到上限。工具说明写明缺省、上限与到时终止整个进程组。
- 本机：沿用原有的整组终止（Linux/macOS 独立进程组 SIGKILL，Windows `taskkill /T /F`）。
- 容器执行端不再重启容器：
  - 经观测脚本跑的命令以 setsid 另起进程组，环境里带一个每次随机的标记变量 `PIGEON_RUN`。setsid 与 env 从系统目录解析；没有 setsid 时不另起组，仍按标记查杀。
  - 直接执行的命令（钩子等）经 `docker exec -e` 带上标记。
  - 到时或中止，宿主另发一次辅助调用，执行 KILL_MARKED_SCRIPT。它扫 /proc 下环境里带该标记的进程，组长带标记的整组杀，再逐个杀，扫两遍。观测脚本照常收尾，命令后的取证照取。
  - 客户端在宽限内（观测时按辅助调用限时，直接执行时 5 秒，可注入）没有结束才强行断开。
- 超时与中止后不再做内存超限判定（137 由按标记杀所致）。
- 本地假 docker 夹具改为把 `-e` 给的变量并进环境。

## 二、显式后台作业（提交 c70fb77、5ae1d6c）

- run_command 新增参数 `background`，以后台作业启动，立即交回作业号（每会话 j1、j2…，续跑时接着上一进程用过的号）。不能与 `timeout_seconds` 同用，后台作业不受单次超时约束。
- 执行端接口新增可选的 `startJob`：
  - 本机 Linux/macOS 以独立进程组拉起，Windows 停止时杀进程树；
  - 容器里经包装脚本以 setsid 起组、带标记，停止时按标记查杀，客户端在宽限内没结束再断开；
  - 进程退出后孙进程仍占着输出管道的，宽限过后销毁管道、按退出码结束；
  - Pigeon 正常退出时与其他子进程一同终止（process-tree.ts 的兜底）。
- 输出持续落盘：写进本会话落盘目录（决策 356）的下一个编号。单个文件超过 `backgroundOutputMaxBytes`（缺省 16 MiB）时，在同一文件里砍掉前一半，记下砍掉的字节数，新增输出按逻辑偏移读。作业结束时算出 sha256，按写下的身份记进落盘索引，此后 read_file 可按虚拟路径读全文。在跑时只经 job_output 读本进程持有的同一个文件描述符；描述符在结束状态交给模型之后或运行面释放时释放。
- 新工具：
  - `job_output`：给作业号时交回状态与上次查看之后的新增输出（至多 32 KiB，多了只留末尾）；`wait_seconds` 至多 600；不给作业号时等任意一个结束或列出全部。
  - `job_kill`：停本会话的作业。
  - 两者登记为读档、免审批。job_output 登记在 tool-execution-modes.ts 的并行名单里；job_kill 不登记，缺省串行。
  - 执行端没有 startJob 时两件工具都不注册，run_command 说明里也不提后台作业。
- 上限：每会话同时在跑缺省至多 2 个（`maxBackgroundJobs`）；整次运行（同一进程里的主会话与各 worker 共用一个作业池）缺省至多 8 个（`maxBackgroundJobsTotal`）。超出直接拒绝并列出在跑的作业，不排队。
- 审批与钩子同前台命令：background 不改变治理层的判定。PostToolUse 在启动时触发，这时的结果是启动回执，文档写明。

## 三、通知与收尾（提交 5458490）

- 作业结束经运行面的通知队列告诉模型，与 worker 完成通知同一条队列：
  - 还没递出时又有作业结束的，撤回重发、合并成一条；
  - 结束状态已由 job_output 或 job_kill 交回的不再通知（还没递出的撤回，其余重发）；
  - 终端界面里通知显示在消息区，模型空闲时叫醒它。
- 无人值守收尾（headless 与 worker 的运行面）：
  - 一次运行正常结束后还有作业在跑的，先交一条"本次运行即将收尾，N 个后台作业仍在跑……"让模型处理一轮（每个会话一次），再等剩下的作业、把结束通知交给模型跑一轮，直到没有在跑的作业。
  - 收尾总时限 `backgroundCloseoutSeconds`（缺省 600）从收尾开始起算，同一会话多次进入收尾共用一个总时限，计入运行的墙钟预算。墙钟、上限或外部中止即不再等，运行按中止交回。
  - 收尾的每一轮照常计入轮数与 token 上限。总时限到了停掉余下的作业（来由 closeout），把通知交给模型跑一轮，此后拒绝新开作业。
  - headless 主会话在 worker 的 drainWorkers 与后台作业之间交替，直到两边都没有可做的。
- worker 的作业归 worker 会话，worker 运行面的收尾同样先等。
- 跑批器：Pigeon 条件同样带后台作业，工具清单多出 job_output、job_kill。新参数 `--background-closeout-seconds` 缺省 600，实际取值记进身份头 `agents.pigeon.backgroundCloseoutSeconds`；加这一项之前写下的身份头没有它，续跑即判为不同。

## 四、交叉处理（提交 5ae1d6c、5458490）

- 期间变化：作业开始时取一次证，结束时再取一次比出变化（与 observedRun 同一取法与 git 加固参数），扣除这期间 Pigeon 已知的前台改动，注明可能不精确。已知的前台改动包括前台 run_command 报出的路径，以及 edit_file、write_file 结果里的路径（换成相对工作区根）。
- 有作业在跑时，前台 run_command 的变化报告括注加提示；内存超限时另起一行列出期间在跑的作业。
- 代码快照的条目新增可选的 `backgroundJobs`，记拍摄时在跑的作业号。
- job_output 列入打转检测的缺省豁免（与 wait_workers 同列）。不带等待时长的连续查询另计：连续 5 次、作业都没变化即拒绝；带等待、作业结束或别的工具调用清零。
- worker 卡住监控的自带超时工具名单加 job_output。
- 沙箱交回：收尾交回之前有作业在跑先提示一行（终端界面与命令行两处）；`/export` 时提示作业仍在跑。

## 五、善后（提交 c70fb77、5458490）

- 会话或运行结束（disposeRuntime）先停掉本会话全部在跑的作业，来由 aborted，结束记录落在会话存储关闭之前。
- `/reload` 把作业表连同落盘目录对象交给新运行面，会话记录改写到新运行面，旧运行面释放时不停掉；重建失败时作业留在旧运行面。
- 记录文件：每个在跑的作业在 `.pigeon/state/jobs/<标记>.json` 记所属进程号、会话、作业号、命令与认进程的信息，作业结束即删。认进程的信息：
  - 本机为进程号、启动时间与标记，Windows 另记命令行；
  - 启动时间取法：Linux 用 /proc 的 starttime，macOS 用 ps lstart，Windows 用 CIM 的 CreationDate；
  - 容器为容器名与标记。
- 崩溃后下次启动（每个进程每个治理目录一次，后台进行）：清理所属进程已不在的记录。
  - 本机：核对启动时间与标记（Windows 为命令行）一致才杀整组或进程树，Linux 另扫带标记的子孙；不一致即当作进程号已被复用，不杀、只删记录。
  - 容器：按标记查杀。
  - 记录在工作区里、命令改得动：清理只认进程号、标记（24 位十六进制）与容器名（字母数字开头，只含字母数字与 `_.-`），不采用记录里的任何程序路径或 docker 调用前缀。
  - 每项结果给人报一行。
- 续跑（openSessionRuntime 的续跑）：会话记录里只有启动、没有结束的作业，经通知告诉模型已丢失，并给人报一行。
- 会话记录新增条目类型 `pigeon.background-job`，作业启动与结束各一条。pigeon trace 的时间线显示它。

## 六、模型可见文字

数值随设置代入。

- run_command 说明（接在原说明之后）：单次超时缺省 120 秒，可用 timeout_seconds 另设，至多 600 秒；到时整个进程组（命令和它起的子进程）都被终止。开发服务器、watch、长构建这类长时间运行的命令可带 background: true 在后台运行：立即交回作业号，输出持续落盘，结束时会通知你；用 job_output 查看状态与新增输出（可带 wait_seconds 等它结束），用 job_kill 停掉。后台作业不受单次超时约束；本会话同时在跑的至多 2 个，超出即拒绝。后台作业与之后的命令同时运行，可能互相干扰（改同一批文件、占同一个端口），这期间的文件变化报告也会因此不精确。人按 Esc 中断当前一轮时后台作业照跑，会话结束时全部停止。
- job_output 说明：查看本会话后台作业（run_command 带 background 启动的）的状态与新增输出。给 job_id：交回这个作业的状态与上次查看之后的新增输出，已结束的另给退出码、全文位置与作业期间的文件变化；带 wait_seconds（至多 600）先等它结束，到时没结束也照样交回。不给 job_id：带 wait_seconds 等任意一个作业结束，不带则列出本会话的全部作业。要等作业就带 wait_seconds，不带等待的连续查询至多 4 次。
- job_kill 说明：停掉本会话的一个后台作业（连同它起的子进程），交回最后的状态、输出位置与作业期间的文件变化。
- 后台启动的结果：已在后台启动作业 j1：$ <命令>；输出共 0 字节，持续写入 <虚拟路径>（作业结束后可用 read_file 读取；在跑时用 job_output 读新增的）；用 job_output 查看状态与新增输出（可带 wait_seconds 等它结束），用 job_kill 停掉；作业结束时会通知你。
- 状态句，各取一种：
  - 在跑（已 N 秒）
  - 已结束（退出码 0，用时 1 分 2 秒）
  - 已用 job_kill 停止（退出码…，用时…）
  - 会话结束时停止（…）
  - 无人值守收尾的总时限到了，已停止（…）
  - 没有启动：命令不存在
- 结束通知：[后台作业通知] 作业 j1 已结束（退出码 0，用时 12 秒）：$ <命令>；输出共 N 字节，全文存为 <虚拟路径>，可用 read_file 按 offset 读取；作业期间的文件变化：新增 a / 删除 b / 修改 c（作业开始与结束时的取证比出，已扣除这期间 Pigeon 已知的前台改动；作业与前台改了同一个文件、或有不经 Pigeon 的改动时不精确）；输出末尾：<末尾 2 KiB>。合并时开头为"N 个后台作业已结束："。
- 收尾：[后台作业通知] 本次运行即将收尾，N 个后台作业仍在跑：j1（<命令>，已跑 3 分 5 秒）、…；需要它们的结果就用 job_output 等，不需要的用 job_kill 停掉。
- 续跑：[后台作业通知] 上一个进程启动的后台作业已随它结束而丢失（没有结束记录）：j1（<命令>）。残留的进程已按记录清理或会在下次启动时清理；需要的话重新启动。
- 拒绝与报错：
  - 本会话同时在跑的后台作业已达上限（2 个），拒绝启动、不排队。在跑的作业：……。可以用 job_output 等它们结束，或用 job_kill 停掉不需要的
  - 整次运行同时在跑的后台作业已达上限（8 个，含 worker 的），拒绝启动、不排队。……
  - 不再接受新的后台作业：无人值守收尾的总时限已到
  - timeout_seconds 至多 600（给的是 N）；更久的命令请用 background 在后台运行
  - 后台作业不受单次超时约束，不要同时给 timeout_seconds 与 background；要停掉作业用 job_kill
  - 命令超时（120 秒）已终止整个进程组：<命令>
  - 已连续 5 次不带 wait_seconds 查询后台作业，作业都还在跑、没有变化。要等它们就带 wait_seconds（会在作业结束时提前返回），或者先去做别的事，作业结束时会通知你
- 前台命令：变化报告括注加"有后台作业在跑（j1），这里的变化可能含作业所做的"；内存超限时另起一行"期间在跑的后台作业：j1（<命令>），内存也可能是它们占用的"。
- 给人看的：
  - 交回沙箱前停掉在跑的后台作业：……；交回的是它们停下时的工作区
  - /export 时：交回时后台作业仍在跑：……；交回的改动可能是作业做到一半的样子
  - 崩溃清理：上次异常退出时留下的后台作业 j1（<命令>）：已停掉 / 进程已不在 / 进程号已被别的程序复用，没有动它 / 容器已不可用

## 九、已知局限

- 容器里命令前的取证卡住、或中止落在命令开始之前时，按标记杀不到（命令还没带标记），只强行断开客户端；之后才开始的命令留在容器里，直到它自己结束或会话结束。
- 镜像里没有 setsid 时，容器命令不另起进程组，只按标记逐个杀；清空了环境变量的子孙进程认不出。
- Windows 本机的崩溃清理按命令行与 CreationDate 认进程，取它们要起一次 PowerShell；macOS 用 ps 读环境，只认得同一用户的进程。
- 续跑提示只接在 openSessionRuntime 的续跑上，worker 的补批续做与 headless 不提示，崩溃清理照常。
- `/reload` 时旧运行面里还没递出的作业结束通知不随作业表转交。
- 期间变化扣除的前台改动只含前台 run_command 报出的路径与写工具结果里的路径，不经 Pigeon 的改动无从扣除，因此注明可能不精确。
