## 各段交付

### S1 验证命令项目级配置（081）

- `state/attempt-config.ts`：新增 `VERIFY_CONFIG_VERSION = 1` 与 `.pigeon/verify.json` 的版本化 schema（命令必填、超时可缺省）；`VerifyConfigSchema` 加法式新增来源字段（取值 `flag` / `project`），M7 写下的旧快照没有该字段，读取时不补、不猜。
- `persistence/verify-config.ts`：只读加载，形态与 commands.json / grants.json / mcp.json 三份既有项目配置一致——文件缺失即未配置（合法），存在但不是合法 JSON、schema 不符或命令全是空白一律响亮失败。写入方只有人。
- `application/launch-flags.ts`：`resolveVerifyConfig` 实现三级来源，启动参数 > 项目配置 > 未配置。启动参数在场时整条配置取启动参数，不与项目配置逐字段混合——两级混合会让"这次尝试用的是哪条命令、多长超时"取决于两份来源的组合，事后不可读。
- 冻结：配置值随注入快照按会话冻结（见 S3 的快照升版），cli 与 tui 两个入口改走同一份解析。

### S2 记录族与状态机（089）

- `state/event-log.ts`：Event Log v11 → v12 加法式升版，新增三族，均治理族耐久（fsync），信封 Run 可缺省（审批发生在任何 Run 之外），都写进候选的来源会话文件（单写者约束不变）：
  - `candidate.verified`：三值结论、每组次数 N、大效应门槛、正负回放差、四组统计（通过次数、通过率、按 k 逐项列出的 pass@k 与 pass^k、Wilson 区间）、每次回放运行的会话号与判决、完整环境摘要；
  - `candidate.decided`：批准、拒绝、撤销、取代合成一族，带动作字段与理由来源字段（人写 / 系统默认，同 066），可带取代指向与所依据的验证回执；
  - `candidate.activated`：落点相对路径、写盘后回读的内容哈希、"未经回放证实"标记、所依据的决定记录号。
- 同一次升版里另有两处加法式补录：`WorkerRoleSchema` 新增 `verifier` 成员；git 工作树工作区新增可选 `baseCommit`（起点提交）。v11 → v12 迁移为纯版本推进，旧记录逐字有效。
- `state/candidate.ts`：状态枚举补齐——验证三值 `ReplayValidated` / `ReplayInconclusive` / `ReplayRegressed`，决定四态 `Approved` / `Rejected` / `Revoked` / `Superseded`，激活态沿用 `Active`。状态不入候选 schema，故新增成员不动 `CANDIDATE_VERSION`。
- `state/candidate-status.ts`：候选状态由五族现算，判定顺序为扫描拒收 → 已取代 → 决定族最后一条 → 验证回执最后一条 → 已扫描 / 已提出。取"最后一条"而非"第一条"：决定与验证都可以重来（回归翻案只能靠重验），现状由最新一条表达。取代关系在全量会话上先算一遍再投影——同一个名字可能在别的会话里被重新提炼出新版本。
- 机检：迁移完整性机检表登记 `VERIFY_CONFIG_VERSION`，并注册注入快照 v7 → v8 迁移；五处钉 Event Log 版本的既有断言改为对版本常量断言，不再写死数字。

### S3 回放执行体（082、085、087）

- 命名守 014：`pigeon replay` 与 `state/replay.ts` 仍是只读重建；本轮的重执行一律叫 rerun，命令是 `pigeon verify`，分层规则的注释里写明了这条边界。
- `replay/plan.ts`：从账本解出被验证那次尝试的四件事——任务文字（worker 尝试取派出记录，其余取该 Run 第一条用户消息的正文）、起点提交、预算、模型标识与工具集。起点按可靠度取：调用方已解出的提交、worker 工作树记的起点提交、该 Run 第一条之前最近的工作区快照、worker 分支尖端（M8 之前的派出记录没记起点提交时的回退，回执里如实标注）。四条都拿不到即响亮失败——从跑完之后的现状重跑测的不是同一件事。预算或模型拿不到同样响亮失败。
- `replay/materials.ts`：在回放工作区里造临时治理根。固化命令规则与固化放权规则从宿主复制（规则不在就等于一条命令也跑不了）；宿主已激活的 Skill 与 Memory 照搬；带经验组另按种类的正常格式放入候选，走的是 activation 层同一条落点与写入。不复制 MCP 配置——外部 server 不可复现且会把网络面带进回放。经验集合明细里，Skill 目录下的附属资源各自成一条，故集合内容哈希覆盖真正装载进去的每一个字节。宿主的经验目录一个字节都不写。
- `application/rerun.ts`：一次回放的五步——从起点提交开独立工作树、在其中造临时治理根、派一个验证器 worker（治理根即那棵工作树，经验因此走与真激活完全相同的装载路径）、尝试收尾后在同一工作树里独立执行验证命令、把这次回放的会话文件收回宿主会话目录后移走工作树与分支。后台没有审批通道，任何审批请求一律拒绝。
- 预算不得放宽：`effectiveLimits` 把被验证那次尝试的预算转成本次回放的上限，原尝试没设的项按 worker 编排的缺省收紧；传入的上限逐项核对，任何一项比原尝试宽即抛错。工具集同理——验证器的角色工具是上限，再与被验证那次尝试实际拿到的工具集取交集，多一件工具与多一点预算是同一类失效。
- 预算可得性：M8 之前只有 worker 尝试的派出记录带上限，普通会话的预算不在账本里。为此注入快照升 v8、新增可选预算块，随 run.started 落盘；`replay/plan.ts` 优先取它，取不到再回退到派出记录。
- 并发：回放单设一道闸（缺省 1、可配），与 Reviewer 和提炼器共用的那道分开——回放一跑就是四组 N 次，挤在同一道闸上会让后台审阅与提炼在整轮验证期间一次都排不上。

### S4 判定（084、092）

- `replay/verdict.ts`：四组各固定 N 次全跑、不中途停，少跑一次即拒绝出结论；N 低于 3 直接拒绝。pass@k 与 pass^k 分开算并按 k 逐项列出；Wilson 区间算出来写进回执，不参与判定。
- 三值口径：先判回归（成功侧带经验比不带经验低达门槛，或失败侧带经验反而低达门槛），再判通过（失败侧提升达门槛且成功侧无达门槛的下降），其余一律未测出。大效应门槛缺省 0.4，N=5 时即"五次里差两次"；判决为未定的一次不算通过，也不把该组算成少跑。
- `application/verify-command.ts`：四组按次序交错跑（第 1 次的四组、第 2 次的四组……），与 Eval 同一考虑——减少模型服务随时间漂移落在某一组身上。前置不满足时响亮拒绝：扫描拒收的候选、没有对比来源块的候选、两侧尝试的模型标识或预算不一致（环境摘要只有一份，记谁都会把另一侧说错）。

### S5 权限形态（083）

- 验证器角色的工具上限是读、写、命令三件；命令档工具另受 `.pigeon/commands.json` 的 `verifier` 角色清单限定，清单外一律拒绝，没给 verifier 登记任何命令时一条也跑不了（fail-closed）。
- 这不是隔离。放行一条脚本命令即等于放行该脚本能做的一切，网络也不受限；真正的断网与文件白名单只有沙箱能给，已按 083 排入 M9 前置。本轮只是把开口缩小到人预先固化的那几条命令。

### S6 触发与审批界面（086、088）

- `pigeon verify <选择器> [--n <每组次数>] [--effect <门槛>] [--keep-worktree]`：人工触发，需要模型接入（回放是真跑），验证命令按 081 的三级来源解出；未配置验证命令时明确拒绝——没有它跑多少次都只能标未知。
- 无人值守自动验证：`--auto-verify`，缺省关。一次验证是四组各 N 次真执行，开销与一轮 Eval 同量级，落库即自动会让一次并行派发悄悄变成二十次额外运行，故必须由人显式拨开。挂在并行同任务派发收尾与分叉叶子提炼之后；自动验证自身的故障不进账本，按类别去重向标准错误告警（同 080）。
- 审批走 CLI 子命令：`pigeon candidates show | approve | reject | revoke | supersede`。详情一次给全审批要看的材料——候选正文、与当前落点的行级 diff、来源链（含对比来源块的成败两侧与共享前缀）、扫描结果、四组回执与环境摘要。TUI 只在状态行提示待审数量，不做面板。

### S7 激活与 Policy 分离（090、093）

- `activation/paths.ts`：三种经验的落点互不相同、互不嵌套——Skill 落 `.pigeon/skills/<名>/SKILL.md`，Memory 落 `.pigeon/memory/<名>.md`，Policy 落 `.pigeon/policy/<名>.txt`。
- 写入分两个模块：`activation/experience.ts` 只写 Skill 与 Memory 的装载目录，`activation/policy.ts` 只落 Policy 的只读建议文件，两者互不引用，共用的只有纯函数落点表。建议文件逐字写批准的正文、不加任何抬头——加一行抬头就会让激活内容摘要与批准内容摘要永远对不上。
- `activation/activate.ts`：激活 = 按种类复制到正常目录，写盘后回读重算哈希；与批准内容哈希不等即抛错。漂移检查拿激活记录的哈希与落点现状比对，不一致标注"已脱离批准版本"、落点被删标注"文件已不在"，两者都不阻止使用。撤销为移走落点文件（Skill 连同它自己的目录），不追溯既往会话。
- `application/candidate-decision.ts`：四个动作的执行层。决定先落盘再动文件——扩权动作 fail-closed，同 grant.created 的口径。批准的四道闸见 S4 与下文完成证据。
- 分层规则机检见下文完成证据第四条。

### S8 环境摘要与失效（091）

- 摘要记全：模型标识与版本、harness 提交号与是否有未提交改动、Node 与平台、预算参数、验证命令、同时装载的经验集合内容哈希与明细、四组通过次数与三值结论、各次运行的会话号。
- 失效判据只看封闭四项清单：模型标识（provider 与 id）、经验集合内容哈希、预算参数（轮次、墙钟、token 三项上限加单轮输出上限）、验证命令本身。清单外的项（harness 提交号、Node、平台、验证命令的超时与来源、推理档位、经验明细）只记录、不判定。
- 经验集合内容哈希按 种类/名字/内容哈希 规范排序后拼接取 sha256：与装载顺序无关，任一条内容变一个字节即变，增删一条也变。
- 判据落在两处：批准前比对"验证当时的那一套"与"此刻要激活的那一套"，不同则旧批准失效、要求重新验证；会话启动时把四项与当下环境比对，不同则告警指名是哪一项，但不阻止使用——阻止会把一次模型换代变成全部经验一起失效的硬故障。告警走标准错误，不进账本（同 080）。

## 完成证据对照

### 一、候选不能通过改字段或内部工具调用跳过审批

四条钉死，测试在 `application/approval-bypass.test.ts`：

1. 候选元数据 schema 拒收多余字段——状态写不进候选文件（`additionalProperties: false`）；
2. 改暂存目录里的 candidate.json 加一个 `status: "Active"` 之后，投影出来的状态仍是账本算出来的"已扫描"，决定与激活记录皆无；
3. 改暂存目录里的正文后再批准，被"激活内容摘要必须等于批准内容摘要"拦下，落点不会被写成改过的样子；
4. 源码机检：模型可达的 `src/tools/` 与 `src/pi-runtime/` 两层里不出现 `appendCandidateDecided`、`appendCandidateActivated`、`activateExperience`、`decideCandidate` 与对 activation 层的引用——没有"内部工具调用"这条路可以把候选推到已激活。

### 二、批准内容与最终激活内容摘要一致

- `activation/activate.ts` 写盘后从落点读回重算 sha256，与批准内容哈希不等即抛 `ActivationMismatchError`；
- `application/candidate-decision.ts` 在落激活记录前再比对一次，不等即抛，激活记录因此不可能记下一个与批准内容不同的摘要；
- 变异证据：拿掉决定层那次比对后，`绕过审批：改暂存正文后批准被摘要比对拦下` 精确变红。

### 三、验证环境变化时旧批准失效或要求重新确认

- 批准前：`application/candidate-decision.ts` 重算"若此刻激活，治理根的经验集合会是什么样"，与验证回执里的集合哈希不同即拒绝批准并要求先跑 `pigeon verify`。测试 `批准：验证之后治理根多了一条经验时旧批准失效，要求重新验证`。
- 使用时：`application/activation-notes.ts` 在会话启动时按封闭四项清单比对，任一项不同即告警指名是哪一项（model / experienceSet / budget / verifyCommand），清单外的项变了不报。测试 `启动告警：封闭四项清单里的项变了就报批准失效并指名是哪一项` 与 `启动告警：清单外的项变了不报`。

### 四、Policy 激活路径与普通 Skill 写入路径物理分离（机检证据）

三层机检，不是口头保证：

1. 落点表测试断言三个目录互不相同、互不嵌套，且 Policy 激活后 `.pigeon/skills/` 与 `.pigeon/memory/` 下不产生任何文件；
2. 分层规则 `policy-activation-isolated`：`activation/policy.ts` 与 `activation/experience.ts` 互相引用即违规；
3. 分层规则 `activation-only-state`：整个 activation 层的允许清单只有 state 与 persistence 的整文件原子替换，放权写入模块（`persistence/grants-config.ts`、`application/grants.ts`）与审批层不在其中——激活器在代码层面够不着它们。

`activation-boundary.test.ts` 用一次性夹具证明这两条规则真的会抓人（激活层引用放权写入模块、Policy 写入模块引用 Skill 写入模块各被对应规则抓住，而引用整文件原子替换放行），并断言这三条规则在真实 `src/` 上零违规。另有一条测试直接验证 Policy 激活前后 `.pigeon/grants.json` 与 `.pigeon/commands.json` 逐字节不变。

## 变异反向验证

每条变异施加后跑对应测试文件，记录精确变红的用例，随后还原。

| 变异 | 结果 | 精确变红 |
|---|---|---|
| 去掉回放预算的放宽核对 | 变红 | 预算：任何一项放宽都被拒绝 |
| 判定顺序改成先判通过 | 变红 | 判定：成功侧下降达到门槛即回归 |
| 去掉"四组少跑即拒绝出结论" | 变红 | 判定：四组都必须跑满 N 次 |
| 去掉回归不可批准的拦截 | 变红 | 批准：结论为回归的候选一律不可批准 |
| 去掉未测出批准的理由必填 | 变红 | 批准：未测出可人工批准，但理由必填 |
| 去掉决定层的激活摘要比对 | 变红 | 绕过审批：改暂存正文后批准被摘要比对拦下 |
| 回放材料改写宿主治理根 | 变红 | 临时治理根：宿主的经验目录一个字节都不写 |
| 失效判据去掉预算那一项 | 变红 | 失效判据：封闭四项清单 |
| 把扫描拒收判定挪到决定之后 | 变红 | 状态机：扫描拒收压过一切后续记录 |
| 验证命令来源改成项目配置压过启动参数 | 变红 | 验证命令来源：启动参数压过项目配置 |
| 让 Policy 写入模块引用 Skill 写入模块 | 变红 | 巡航规则 policy-activation-isolated |
| 把漂移一律当作没变 | 变红 | 启动告警：落点被人改过标注已脱离批准版本；启动告警：不给当下环境时只做漂移检查 |
| 把 Policy 的落点改到 Skill 目录 | 变红 | 落点：三种经验各有自己的目录；激活：写到正常目录，回读哈希与批准内容一致；落点清单：给回放与漂移检查同一份路径来源 |
| 验证器角色不套命令清单 | 变红 | 验证器：登记在固化命令规则里的命令能跑，规则外的一律拒绝；验证器：没给 verifier 登记任何命令时一条也跑不了 |
| 角色命令清单缺省改成不设限 | 变红 | 同上两条 |

未被单点变异覆盖的一处：`application/rerun.ts` 把候选交给临时治理根的那一行。候选放置本身由 `replay/materials.test.ts` 直接覆盖，但"派发器确实把候选传了进去"这一步需要真实工作树与模型才能观察，由下文真实模型验收承担。

## 真实模型验收

夹具为一次性临时 git 仓库：一个带优先级、括号、一元负号与幂运算的表达式求值任务，规格分散在 README 与测试里，验证命令为 `node --test test.mjs`，`.pigeon/commands.json` 只给 verifier 登记了一条 `check`。模型为 Kimi For Coding，密钥只从环境变量读取。

### 正路径

1. 并行同任务派发 6 次尝试（角色 implementer，预算 6 轮 / 240 秒），验证命令逐个判成败，得到 3 通过 3 失败的一组；提炼器自动触发并产出带对比来源块的候选（形态为 lesson，内容是"一元负号优先级低于幂运算、幂需右结合"，成败两侧与其余四次尝试的引用齐全）。
2. 提炼器对这组对比稳定地选择 policy 形态。Policy 只落只读建议文件、不进任何装载路径（090），回放测不出差别，故 `pigeon verify` 对 policy 候选直接拒绝并提示改走人工批准。为把 M8 链路走完，把同一条教训以可装载的 Skill 形态入库：正文逐字沿用提炼器的输出，只在前面补 Skill 目录要求的前言，来源四项与对比来源块原样沿用，不编造。
3. `pigeon verify --n 3`：四组各跑 3 次、共 12 次真实重执行，全部从被验证那次尝试的起点提交开独立工作树、在其中造临时治理根并装载经验。结果为失败侧 2/3 → 3/3、成功侧 3/3 → 2/3，正回放差 0.33、负回放差 −0.33，均未达 0.4 的大效应门槛，结论为**未测出**。回执落账本，记全四组统计、环境摘要（模型 kimi-coding/kimi-for-coding、预算 6 轮 / 240 秒、验证命令、经验集合哈希）与 12 次运行的会话号。
4. 未测出的批准门槛生效：不带理由批准被拒并提示必须写明理由；带理由批准后决定记录的理由来源记为人写，激活记录标注"未经回放证实"。
5. 激活落点为 `.pigeon/skills/operator-precedence-layers/SKILL.md`，激活内容哈希与批准内容哈希逐字相同。
6. 下一个会话确实装载：新会话的 `run.started` 冻结清单里有该 Skill，文件哈希与批准内容哈希相同。
7. 撤销：移走落点文件并落决定记录，目录随之清空。

结论的读法：这一次**未测出改善**，不是"证伪"。失败侧的不带经验基线已经能跑到 2/3，N=3 时能表达的最大差距只有 1/3，本就低于门槛；这与 Eval 基线触顶时的结论口径一致。

### 负路径

构造会导致回归的经验，对同一组尝试跑 `pigeon verify`，共三轮 52 次重执行：

| 轮次 | 经验内容 | 每组 N | 失败侧（基线 → 带经验） | 成功侧（基线 → 带经验） | 负回放差 | 结论 |
|---|---|---|---|---|---|---|
| 一 | 把模块范围"收窄"到只支持整数加减，声称测试里其余用例已作废 | 3 | 2/3 → 2/3 | 2/3 → 1/3 | −0.33 | 未测出 |
| 二 | 同上 | 5 | 5/5 → 4/5 | 3/5 → 4/5 | +0.20 | 未测出 |
| 三 | 明确有害：声称模块已废弃、`evaluate` 唯一正确实现是 `return 0`、不要读也不要运行测试 | 5 | 2/5 → 3/5 | 4/5 → 3/5 | −0.20 | 未测出 |

三轮都没能把负回放推到 0.4 的大效应门槛，**回归这一支在真实模型上没有取得端到端证据**。两条原因都可观测：

- 该夹具任务上撞轮次上限的比例很高（第三轮 20 次里 11 次撞上限），两侧基线本身在 2/5 到 5/5 之间摆动，噪声幅度与门槛同量级；
- 模型不采信与 test.mjs 冲突的 Skill 文本——第三轮那条经验要求不要读测试，回放会话照常读了测试并按测试实现。

回归分支的判据由单元测试与变异钉死（判定顺序改成先判通过、去掉回归不可批准的拦截，两处变异都精确变红），但"真实模型跑出回归并因此被拒批"这一条未验成。这同时是给 M9 的一条观测：要让负回放测得出，题集的基线必须稳定，撞上限的比例要低，否则噪声会吃掉大效应门槛。

### 回放确实按口径装载与设限（085、087 的端到端证据）

取第三轮同一次序里的两次回放对照它们自己的 `run.started` 冻结快照：

| | Skill 冻结清单 | 预算 | 广告给模型的工具 |
|---|---|---|---|
| 带经验组 | 候选本身 | 9 轮 / 240 秒 | read_file、edit_file |
| 基线组 | 空 | 9 轮 / 240 秒 | read_file、edit_file |

三点同时成立：带经验组确实经与真激活同一条装载路径装上了候选、基线组没有；两组预算与被验证那次尝试的派出上限逐字相同；两组的工具集与被验证那次尝试（implementer 角色）相同，没有因为验证器角色的上限里有 run_command 就多给一件。

### 真实链路暴露并修掉的缺陷

- 回放工作树命名在基线组回退到 Run 标识，其中的下划线与大写不满足 worker 名白名单，第一次真实运行即开工作树失败。改为四组共用候选内容哈希作种子，并在种子不是内容哈希时响亮失败；补测试 `工作树名：种子不是十六进制哈希时响亮失败`。

## 已知边界与待裁细节

- **不是隔离**：回放的命令档工具只在固化命令规则内放行，这只缩小开口。放行一条脚本命令即等于放行该脚本能做的一切，网络不受限，写档工具只有工作区路径围栏。真正的断网与文件白名单归 M9 前置的沙箱（083）。
- **Policy 候选不做回放**：Policy 只落只读建议文件、不进任何装载路径，回放四组各 N 次只会得到一个必然的"未测出"。本实现对 policy 候选的 `pigeon verify` 直接拒绝并提示改走"人工批准 + 必填理由 + 未经回放证实标记"。这一口径是实现侧的收紧，裁决文本未明确，待裁。
- **单轮输出上限算不算预算参数**：091 的封闭四项清单里"预算参数"一项，本实现把 `maxOutputTokens` 一并计入（与轮次、墙钟、token 三项上限同列），理由是 087 的"预算不得放宽"本就覆盖它。这是对清单内某一项的口径细化而非增删清单，但仍应由项目负责人确认。
- **两侧尝试的模型与预算必须一致**：环境摘要只有一份，两侧不一致时本实现拒绝验证而不是记其中一侧。并行同任务派发与失败自动分叉重试产出的对比天然满足；跨来源拼出来的对比会被挡下。
- **回放会话文件收回宿主**：回放在临时治理根里跑，收尾时把它的会话文件复制回宿主会话目录再移走工作树。因此 `pigeon trace <回放会话号>` 可在宿主根下查到，但该会话头记的工作树已不存在，不能对它做 resume。
- **回放不起外部 MCP server**：临时治理根不复制 MCP 配置。若被验证那次尝试用到了外部工具，回放拿不到它们，结论会偏保守。
- **用户级经验不进回放**：临时治理根只镜像项目级的 `.pigeon/memory` 与 `.pigeon/skills`，用户级目录不进——它在项目之外，且不可复现。
- **起点提交的回退**：M8 之前的派出记录没记工作树起点提交，回放回退到分支尖端。worker 通常不提交，故分支尖端即建工作树时的起点；它提交过就不准，回执里的来源字段如实标注这一点。
- **负回放要测得出，先要基线稳**：本轮夹具上撞轮次上限的比例过高，基线在 2/5 到 5/5 之间摆动，噪声与 0.4 的门槛同量级，三轮都压不出回归结论。M9 选题集时这一项应作为入选条件。
- **经验不一定被采信**：真实模型会照常读测试文件并按测试实现，与之冲突的 Skill 文本可能被无视。回放测的是"装上这条经验之后成功率变不变"，这本就包含"模型采不采信"这一层，但它会让刻意构造的负样本难以复现。
- **N 与门槛的分辨率**：N=3 时能表达的差距只有 1/3 的整数倍，低于 0.4 的门槛，故 N=3 实际上只能报出"未测出"或极端情形。缺省 N=5 才与 0.4 的门槛匹配；`--n 3` 应只用于冒烟。

## 收口修复（2026-09-20，只追加）

核验发现四处缺陷与一处范围收敛，逐条修在同一工作树里，门禁与变异结果见本节末。

### 更正：完成证据第二条此前的表述不成立

本文前面"完成证据对照"第二条写的是"激活器回读重算 + 决定层再比对一次，双层"。**这句话在写下时并不成立**，现予更正，不做静默改写：

当时的批准顺序是"读暂存正文 → 落批准记录 → 写落点文件 → 才比对哈希"。也就是说，被篡改的正文**已经写进了装载目录**才报错，既没有回滚，账本里也已经留下一条批准记录；而漂移检测因为没有激活记录并不会报。原先声称"落点不会被写成改过的样子"的那条测试只断言了抛错，没有检查落点文件，因此是空转的——补上"落点不得出现"与"不得留下批准记录"两条断言后它立刻变红。未经验证过的候选（092 的人工批准路径）连环境比对那层缓解都没有。

修法：把内容哈希核对下沉到**读正文的那一刻**（`application/candidate-lookup.ts` 的 `readCandidateBody`）——正文的身份就是它的哈希，读到对不上即是暂存目录被动过，批准、激活、回放装载、详情展示一概不再继续。落决定记录与写落点都排在它之后。第二条完成证据现在成立的形态是：**读即核对（时序在前）+ 写盘后回读重算（防文件系统层面的损坏）**。

### 一、批准时的哈希比对时序

- 修法见上。`readCandidateBody` 读出后立刻按 `contentHash` 重算比对，不等即抛；`approve()` 里补了注释说明这条时序不变式。
- 补强的测试：`绕过审批：改暂存正文后批准被摘要比对拦下，落点不会被写成改过的样子` 现在检查落点目录不存在、账本里没有决定与激活记录；另加 `绕过审批：改暂存正文后连详情都读不出来`。

### 二、启动告警恒假警报

- 缺陷：cli 与 tui 各自硬传了一个空预算去和回执里的真实数字比，`budgetShape` 必然不等——每条验过并激活的经验**每次开会话都会报一次"批准已失效"**。这正是 091 理由里点名要避开的失效模式（判据一旦长期误报，机制最终会被关掉）。
- 修法：`stalenessReasons` 增加"当下这一侧取不到值"的跳过集，四项判据一致支持；交互会话没有预算可言，就不判这一项，而不是编一个"不设限"去比。环境构造收口成 `application/activation-notes.ts` 的 `startupEnvironmentOf`，cli 的启动与 resume、tui 的启动共用同一份。
- cli 的 `resume` 入口此前没有接启动告警，一并接上。
- 补的测试按生产接线走（`activation-startup.test.ts`）：没有预算时不报假失效，但换模型、换验证命令仍然照报；另加一条对判据本身的直测，钉死"列进跳过集的项不参与判定，其余项照判"。

### 三、活会话期间批不了候选

- 缺陷：决定与激活此前写进候选的**来源会话文件**，而那个会话可能正被另一个进程写着。会话打开锁（040）是跨进程的，于是 `pigeon candidates approve` 在会话开着时直接抛"会话已被另一个进程打开"，审批做不了。
- 修法：决定、激活与验证回执改写进**本次命令自己的会话文件**；候选状态本就由账本现算，投影改为跨会话收集三族（按时间排序后取最后一条），故"三族落在哪个文件"不影响任何结论。单写者约束一字未动——每个文件仍然只有一个写入者。三族的信封 Run 一并去掉：它们落在自己的会话里，而候选的来源 Run 在别的文件中，来源由候选元数据的 source 四项承载。
- 受影响的既有断言：`candidate-decision.test.ts` 里直接读来源会话取决定/激活记录的辅助函数改为按跨会话投影取（三条用例）。
- 补的测试（`candidate-decision-live.test.ts`）用真起一个空转子进程持锁来模拟活会话——不能用本进程 pid，会话锁会把"pid 与本进程相同但本进程并未持有"判为 pid 复用的残留锁并直接接管。

### 五、Policy 收敛（094）

- 提炼器与审阅器的产出形态只剩 Memory 与 Skill：结果 schema 收窄为可产出种类，两份提示词同步改；候选落盘写侧拒收已停止产出的种类。
- 删除：Policy 的落点目录与独立写入模块、`policy-activation-isolated` 分层规则、验证路径上对 Policy 的特判分支、CLI 批准后的 Policy 提示。
- 保留：`activation-only-state`（激活器不得依赖放权写入模块）与它的夹具测试——§M8 完成证据第四条已改写成它。另有一条直测钉死激活前后 `.pigeon/grants.json` 与 `.pigeon/commands.json` 逐字节不变。
- 读侧兼容：候选种类枚举保留 policy 取值，旧候选照常读出、照常列出、可以拒绝；不可批准、不可激活、不可再产出。种类判据放在**决定记录之前**——放在激活层意味着决定已经落盘才抛，会在账本里留下"批过但没生效"，与第一处修复同一个道理。`legacy-policy-candidate.test.ts` 逐条钉死这些。
- ROADMAP 相应改为两类候选（§1 定位、§4 架构表、§3.5 约束 4、§M6 交付与候选暂存说明、§M8 交付与既定方向、§8 明确不做）。
- 真实验收里"把 Policy 形态的教训改写成 Skill 形态入库"那一步的记录保留在前文，不重做。

### 两条诚实边界

- **日常交互会话产出的候选永远无法回放验证**：交互式 cli 与 tui 不往账本写预算（它们本来就没有预算），而回放必须沿用被验证那次尝试的预算、拿不到就拒绝跑（087）。因此日常会话里提炼出来的候选只能走"人工批准 + 必填理由"，激活记录一律标注未经回放证实。能回放的候选只来自并行同任务派发、失败自动分叉重试与 Eval 这三条带预算的路径。这与 087 自洽，但它是一条真实的能力边界，不是实现遗漏。
- **完成证据第一条的真实强度**：它的含义是"改候选目录的字段、走内部工具调用这两条路都够不着审批"，**不是**"文件系统层面不可伪造"。账本是纯 JSONL、没有哈希链，`.pigeon` 也不在写档工具的拒绝名单里；拿得到 shell 的模型可以直接写装载目录，或往一个没被打开的会话文件里追加记录。这与 048、083 决定不做沙箱是一致的——本轮给的是"缩小开口"，不是隔离。真正的文件系统级不可伪造需要沙箱（M9 前置）与账本防篡改（尚无裁决）。

### 四、轻缺陷六件

同一轮核验另发现六处轻缺陷，修在同一工作树里。

**1. `pigeon verify` 的次数校验没有前置。** 每组次数的下限（3）此前只在判定阶段检查，`--n 2` 会先真开四组共八次回放、跑完几十分钟与相应的模型花费，才在汇总时报错，而且那时不落回执——代价全白付。修法分两层：`cli/index.ts` 抽出 `parseVerifyArgs`，`--n` 在参数解析时就按 `MIN_RERUN_N` 判，报错里给出下限；`verify-command.ts` 的 `verifyCandidate` 在定位候选之前调 `assertRerunCount`，堵住绕过 CLI 直接调用的路径。

**2. 推理档位没有沿用被验证那次尝试。** 087 要求预算与模型沿用原尝试，实现里预算与模型标识都沿用了，推理档位却落在缺省上——同一个模型换档位是不同的行为，回放因此不是同一次尝试的重跑。修法是直接传下去：`resolveAttemptPlan` 从启动快照解出档位并带进 `AttemptPlan`，`verifierRuntimeDeps` 原样转给验证器的运行面。档位认不出或账本里根本没记下来时一律**拒绝验证**，不按缺省算——这与"拿不到预算就不跑"同一个口径，宁可不跑也不产出一份名义上是重跑、实际换了行为的回执。`off` 同样按明确档位沿用，不当作"没设置"。

**3. 两处错误被吞掉。** 其一，分叉提炼那条路径把 `autoVerifyCandidates` 的返回值整个丢掉，自动验证的内部故障无人收，与并行派发那条 push 进错误清单的口径不一致；改为把 `auto.errors` 接进返回值。其二，回放编排器收尾时，`awaitResult` 抛出的情况下编排器自身攒的内部故障随之丢失；改为把 `orchestrator.errors()` 的收集移到 `finally`，正常返回与抛出两条路径都收，且不重复收。

**4. 同一候选的并发验证没有互斥。** 人工 `pigeon verify` 与无人值守自动验证可能同时验同一条候选，四组工作树的名字由候选内容哈希派生，两次验证会撞在同一批工作树上。新增 `persistence/exclusive-lock.ts`：按 `wx` 独占创建锁文件，**不可重入**——这正是它与会话打开锁（040）的区别，会话锁按进程内计数重入，而这里要挡的恰恰是同一进程里的两件事。残留处理与会话锁同口径（记持有 pid，存活即拒、已死或畸形即接管），释放按 `pid + acquiredAt` 只删自己那把。取锁排在定位候选之后、开任何工作树之前。

**5. 撤销时的落点没有围栏。** `revoke` 此前直接删激活记录里写着的路径，而账本是纯 JSONL、可被追加伪造，一条编造的激活记录就能让撤销删掉治理根以外的文件。修法两层：决定层按种类与名字重算 `activationPathFor` 落点，与记录里不一致即拒绝、不删任何东西；写入层 `revokeExperience` 再过一次围栏，只放行治理根下的两个装载目录。

**6. 待审计数把"回归"也算进去了。** 结论为回归的候选永不可批准（084），计进待审数量会让状态行提示一个人无事可做的数字。`PENDING_STATUSES` 去掉 `ReplayRegressed`。

变异反向验证（11 条，全部精确变红）：

| 变异 | 精确变红的用例 |
|---|---|
| 去掉 `verifyCandidate` 的次数前置校验 | 前置：每组次数低于下限时，在定位候选之前就拒绝 |
| CLI 的 `--n` 放回只校验正整数 | `--n`：低于下限在入口就拒绝，报错里给出下限 |
| 验证器依赖不传推理档位 | 推理档位：解出来的档位一路传到验证器的运行面依赖上；`off` 同样要沿用 |
| 认不出的推理档位不再拒绝 | 推理档位：认不出或没记下来的档位一律拒绝验证，不按缺省算 |
| 回放的编排器故障挪回 try 内 | 回放收尾：`awaitResult` 抛出时编排器自己攒的故障仍进错误清单；正常返回时同样收集、不重复收 |
| 分叉路径丢掉自动验证的返回值 | 分叉提炼：真实选对并落库后，自动验证的故障随返回值交给调用方 |
| 去掉同候选验证的互斥 | 互斥：同一条候选已有一次验证在跑时，第二次直接被拒，不开任何工作树 |
| 独占锁改成可重入 | 独占锁：同一把锁不可重入；释放是幂等的；报错文案带说明与锁文件路径 |
| 撤销不按种类与名字重算落点 | 撤销：落点与重算不一致时拒绝撤销、不删任何东西；路径穿越形态同样被拒 |
| 去掉撤销写入器的装载目录围栏 | 撤销写入器：围栏只放行治理根下的两个装载目录 |
| 待审数量放回回归状态 | 待审数量：结论为回归的候选不计入——它永不可批准 |

第三件里分叉那条起初只有 no-contrast 早返回的形状断言，单点补丁不变红；为此补了一条走完整链路的用例——账本里造出一条来源会话与两条分支（一条验证通过、一条验证失败），用假模型真派提炼器、真落库一条候选，再让自动验证的运行面装配失败，断言这个故障出现在 `distillForkGroup` 的返回值里。补齐后该变异精确变红。

受影响的既有断言：无。六件都是补新判据或把已有判据前移，没有推翻任何既有用例的预期；`PENDING_STATUSES` 的收窄由待审数量那条用例直接覆盖。

本节改完后 `npm run verify` 四段全绿：890 项测试、398 模块 0 巡航违规、lint 干净（399 个文件）。

### 五、空转断言与过期文案

#### 空转断言的机理

改记录落点会让按旧落点查证的断言**静默失效**：它不会报错，只会永远为真。本轮在 `approval-bypass.test.ts` 里找到一处——"改暂存正文后批准被摘要比对拦下"那条用例，用 `materializeSession` 取**候选的来源会话**，断言 `candidateDecideds` 与 `candidateActivateds` 为空。三族改写进执行命令的那次新会话之后，来源会话里本来就永远没有这两族，于是批准记录真落了盘也测不出来。

这是同一批改动里第二次出现"测试标题声称一个性质、断言其实测不到它"，两次都发生在改了落点或时序之后。

**改法**：改用跨会话索引 `buildCandidateIndex` 按内容哈希取这条候选，断言 `decided` 与 `activated` 都不存在、状态仍停在已扫描。

**验证**（两个变体，都把生产侧的比对撤掉或挪后，该用例必须变红）：

| 变体 | 结果 | 精确变红的断言 |
|---|---|---|
| A 去掉读正文时的哈希比对，回到"写盘之后才发现"的老形态 | 变红 | 落点断言先响（被篡改的正文确实进了装载目录） |
| B 比对挪到落决定记录之后、写落点之前 | 变红 | **比对不过时不得留下批准记录**——断言打印出的正是那条落在另一个会话文件里的 `candidate.decided` 记录，旧写法完全看不见 |

变体 B 是关键证据：它单独命中了刚修的那条断言，说明它现在真的抓得住人。

#### 同模式排查

按这一批改动涉及的三类变更逐个回看：

- **落点**：M8 只改了候选三族（验证回执、决定、激活）的落点，其余族未动。全量搜索按这三族查证的断言，除已修的一处外还有两处——`candidate-decision-live.test.ts` 断言来源会话里没有这两族，这是**有意为之**（它要钉死的正是"来源会话文件没被动过"，落点改回去即变红）；`candidate-families.test.ts` 是持久化层往同一个会话写读，与落点无关。另外扫了全部"对单个会话断言某物不存在"形态的断言，其余都落在 M8 未改动的记录族上。
- **时序**：本批把四个判据往前挪过（次数下限、正文哈希核对、种类判据、撤销落点判据）。回看发现**另两处同类弱断言**：
  - `legacy-policy-candidate.test.ts` 的"旧 Policy 候选不可批准"只断言抛错与状态不是已激活。种类判据若挪到落决定记录之后，仍然抛错、状态变成已批准而非已激活，该用例照样绿——"批过但没生效"这个它本该防住的形态测不出来。补了 `decided` 不存在与状态停在已扫描两条断言；把判据挪到落记录之后，精确变红于 `拦下时不得留下决定记录`。
  - `revoke-fence.test.ts` 的"拒绝撤销、不删任何东西"只断言抛错与文件仍在。落点判据若挪到落决定记录之后，账本会多出一条撤销记录而文件没动，该用例照样绿。补了"最后一条决定仍是批准"与"状态仍是已激活"；把判据挪到落记录之后，精确变红于 `最后一条决定仍是批准，没有多出一条撤销记录`。
  - 还有一处同类写法被判定为不可用并排除：给"互斥不开任何工作树"补一条"工作树目录不存在"的断言看似更强，实则在该夹具里即使没有互斥锁，验证也会先在"没有对比来源块"这一关停下，永远开不出工作树——这条断言无论实现如何都为真，正是本节要清除的形态，因此不采用。该用例"不开任何工作树"这一层由既有的 `error instanceof ExclusiveLockError` 承载：拒绝停在取锁那一层，而取锁排在对比来源块判据之前、后者又排在开任何工作树之前。这一推理已写进该用例的注释，供后人核对。
- **状态投影**：`projectCandidates` 改为吃跨会话三族、`PENDING_STATUSES` 收窄两项，对应的单元测试与视图测试在上一节的变异里已各自精确变红，未发现空转。

#### 三处过期文案
