# 主 agent 派 worker（决策 264–268、271）实现审计

- 基线：formal-v2 的 66d329c
- 分支：agent-spawn
- 范围：给主 agent 一件派 worker 的工具 `spawn_worker`；终端界面与 `pigeon run` 注册，命令行对话、worker 自己、沙箱会话与跑批器各条件不注册；额度；`pigeon` 缺省入口改为终端界面。跑批器侧只动开关与身份头一个字段。

## 一、工具的形态（264、271，`src/application/spawn-worker-tool.ts`）

- 工具名 `spawn_worker`；参数 `role`、`task`、`name`（可选）、`attempts`（可选，整数 2 到 4）。
- 工具说明、四个参数的说明与各情形的返回文字为冻结原文，集中在 `spawnWorkerDescription`、`SpawnWorkerParamsSchema`、`SPAWN_WORKER_TEXTS` 三处。说明里的两个上限数值取自上限配置，取缺省（4、16）时与冻结原文逐字相同。
- `role` 与 `task` 在 schema 里是普通字符串：角色写错与 task 为空由工具自己检查，按冻结文字回话（同 `update_memory` 的做法）；`attempts` 的 2 到 4 由 schema 校验。
- 调用后等到 worker 收尾再返回：底层只用会话编排器现有的派出（`spawn`）与等待结果（`awaitResult`），不另写 worker 生命周期。返回文字按收尾状态取：完成、摘要截断（完成或没有做完之后补一句，带 worker 会话号）、撞上轮数或时间上限（没有做完，交回已改动的文件与摘要）、失败、被取消。文件列表以顿号相接，没有改动写"无"。
- `attempts`：走现有的并行同任务派发（`runAttemptGroup`，共享任务标识、各尝试收尾后在各自工作树里执行会话级验证命令），标签由会话现算；每份一段，段首"第 i 份（通过 / 未通过 / 未知）："，标签 Passed 为通过、Failed 为未通过，其余为未知。并行尝试的派发由装配方注入（`src/application/spawn-worker-host.ts` 的 `bindSpawnWorkers`），工具模块不直接依赖 `attempt-group.ts`，以免装配根经类型导入成环。
- 派出前检查依次为：角色、task、治理根是不是 git 仓库、本次运行的额度是否已用完、agent 派出的个数是否超上限；命中任一条即按冻结文字回话，不派出。
- 工具在注册表里登记为只读档、不触碰文件系统、可并行。
- 可并行（264）：适配器新增 `parallelTools` 选项（`src/pi-runtime/adapter.ts`），只有注册了 `spawn_worker` 时装配根才打开，上游 Agent 的工具执行方式由 `sequential` 改为 `parallel`。上游在同一批调用里只要有一个标为串行的工具就整批串行，写与命令工具（`edit_file`、`run_command`、`update_memory`、MCP 工具）照旧逐个执行、逐个审批；同批全是可并行工具（`spawn_worker`、`read_file`、会话检索、`load_skill`）时并行执行。没注册时适配器与之前逐字相同（缺省 `sequential`）。
- 等待中被中止（主 agent 撞上自己的时间上限、额度用完、人中断）：工具监听中止信号，取消本次调用派出的 worker（排队中的直接出队，在跑的走 interrupt），再按收尾状态返回。

## 二、注册范围、开关与身份头（265–267）

- 装配根（`src/application/runtime.ts`）：`RuntimeDeps.spawnWorker`（工具槽 `SpawnWorkerSlot`）在场即注册；委派策略在场（worker 会话，深度 1）或注入了执行端（沙箱、跑批器的容器工作区）时一律不注册。工具槽先随装配注册，编排器需要运行面本身，建好后再绑定到槽上（`bindSpawnWorkers`）。
- 会话运行面（`src/application/session-runtime.ts`）：请求给了槽且是主会话、非沙箱时才交给装配根，并在结果里交回槽。
- 终端界面（`src/tui/main.ts`）：`--no-spawn-workers` 关掉，缺省开着；每个打开的会话（含 `/resume` 换绑）一个槽，worker 会话由装配层略过。编排器与 `/spawn` 共用。
- `pigeon run`（`src/cli/index.ts`、`src/application/headless-core.ts`）：headless 选项 `spawnWorkers`（缺省关）与 `spawnWorkerLimits`；`pigeon run` 由启动参数缺省打开、`--no-spawn-workers` 关掉。开着时在运行面装起来后建一个编排器并绑定。注入了执行端（`--sandbox`）或是分支会话（失败自动分叉重试、手动分叉）时不注册；失败自动分叉重试不转交这一项。
- 命令行对话（`pigeon --line`）与 `pigeon resume`：不给槽，不注册；`--no-spawn-workers` 在这两处是未知参数。
- 启动参数解析（`src/application/launch-flags.ts`）：`LaunchFlags.spawnWorkers` 缺省 `true`，只有声明 `spawnWorkers` 的入口接受 `--no-spawn-workers`。
- 跑批器：`src/eval/stream-agents.ts` 新增常量 `STREAM_SPAWN_WORKERS = false`，调用 headless 时明确传入（不依赖缺省）；身份头 `core.agents.pigeon` 新增 `spawnWorkers`，记实际生效值（关），由 `effectivePigeonSettings` 给出。与压缩配置、记忆上限同一口径：加这一项之前写下的身份头没有它，续跑即判为不同。

## 三、额度（268）

- 同时在跑的上限：编排器（`src/orchestration/workers.ts`）新增 `maxConcurrent`（缺省不限）。有空位即在派出时同步开跑（与不设上限时的行为一致），否则按派出顺序排队；排队中的 worker 状态为 `queued`（`/workers` 显示"排队中"），派出记录、工作区与运行面照常在派出时建好，墙钟从开跑时起算。收尾让出空位，队首接着开跑。排队中取消即出队、不开跑，按取消收尾。终端界面与 `pigeon run` 的会话编排器都设为 4；一个会话里人用 `/spawn` 派的与 agent 派的共用同一个编排器，因而一并计算。
- 一次运行里 agent 最多派 16 个：`SpawnWorkerBudget` 只在工具路径上计数，人用 `/spawn` 派的不经过它、不计入。多份尝试按份数计，超过余量即整次拒绝。"一次运行"在 `pigeon run` 为整个运行，在终端界面按运行标识（每条输入一次运行）换算，运行标识变了即从零计。
- worker 的 token 计入本次运行的总额度：编排器新增 `onWorkerTokens`，worker 每收尾一轮回报本轮 token；headless 把它加进本次运行的 token 计数，给了 `maxTokens` 时一并比较。撞上限即：主 agent 以 token-limit 中止、额度标为用完（此后再派按冻结文字拒绝，等待中的派出交回"额度用完"的文字）、停掉排队中与在跑的 worker。花费上限目前没有入口参数，未接。
- 每个 worker 保留自己的轮数与时间上限（编排器现有 `DEFAULT_WORKER_LIMITS`），撞了交回已改动的文件与摘要，按"没有做完"的文字返回。
- 主 agent 撞上自己的时间上限：headless 的中止请求使工具收到中止信号，正在等的 worker 一并取消。headless 释放运行面之前另停掉仍在跑的 worker 并等其收尾记录写进本会话。
- 两个数值可配置：`SpawnWorkerLimits`（`maxConcurrent`、`maxAgentSpawns`），headless 选项 `spawnWorkerLimits` 与工具槽构造参数；没有新增启动参数。

## 四、审批（266）

- 不新增机制。终端界面：worker 的审批照旧经编排器汇聚到审批队列与面板。
- `pigeon run`（无人值守）：会话编排器不给审批入口时，worker 装配不接审批通道（`WorkerRuntimeDeps.unattended`），与 headless 主会话同一口径——审批模式继承主会话（`--yolo` 即全部放行），固化放权规则照常生效，其余需要人批的调用 fail-closed 拒绝。编排器的汇聚审批回调在这种情况下是按拒绝处理的兜底，不会被走到。
- `spawn_worker` 本身为只读档，不经审批。

## 五、缺省入口（267，`src/cli/index.ts`、`src/tui/main.ts`）

- `routeTopLevel`：第一个参数是子命令（eval、run、trace、replay、session、resume、sandbox）照旧；`--help`、`-h`、`help` 打印顶层帮助；其余情形带 `--line` 进命令行对话（`--line` 本身不交给参数解析），不带即启动终端界面。
- 终端界面以子进程运行 tui 入口（继承终端，退出码原样带回；运行期间本进程不响应 Ctrl+C，由界面自己处理），Actor 之间不互相 import。
- 帮助文字 `TOP_LEVEL_HELP` 列出终端界面、`--line` 与各子命令；终端界面的用法提示改为 `pigeon [...]` 并注明命令行对话用 `pigeon --line`；命令行对话的参数报错提示改为"pigeon --line 支持 …"；未知子命令报错附顶层帮助。
- 现有借命令行对话写的测试直接调用 `runRepl`，不经进程入口，照旧能跑。
