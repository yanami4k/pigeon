# 编辑格式对照裁决（2026-09-15 起）

- 定位：M6.5 冒烟暴露 edit_file 报错率偏高与两次长输出失控，盘编辑工具摩擦的处理路径
- 裁决：项目负责人；基线 81e37bc（M6.5 收口）

## 事实

- M6.5 冒烟 72 次运行（Kimi For Coding，yolo）共 209 次 edit_file 调用，报错 45 次（21.5%），三个条件相近（无 Skill 16/66、候选 12/71、已批准 17/72）。报错分布：锚点标签未命中 21（其中 18 次标签真实存在、仅行号不对）、参数校验失败 16（锚点缺行号或格式错）、行号越界 4、编辑无变化 2、输出上限截断 2。数据来自该次冒烟保留在本地的会话账本（`docs/audits/eval/2026-09-14-8e76567/.pigeon/`，不入库）。
- 当前 edit_file（hashline）规则：锚点 `N#TAG` 的行号与行标签必须同时命中；未命中报错不提示正确位置；编辑成功只返回新的全文件快照标签，不返回新锚点。
- 外部证据有分歧：第三方测评（三个模型、Python / TypeScript / Rust 各 20 题、一次作答）replace 总体优于 hashline，hashline 的失败主要是行号编错与内容编造；oh-my-pi 作者测评称多数模型上 hashline 不差于 str_replace，弱模型收益最大。
- oh-my-pi 主干（2026-09-15 读取）：hashline 已改为整文件标签加行号、字符串补丁语法、按快照 diff 换算行号的过期恢复；`resolveEditMode` 对 kimi、mimo、minimax、deepseek、stepfun 等模型默认改用 replace，CHANGELOG 18.1.0 记为对 Kimi 等模型关闭 hashline 编辑以提高稳定性。
- 本仓库 ROADMAP 的编辑工具口径是"参考 oh-my-pi 的 hashline 锚定与稀疏编辑格式"，定于 M3，当时没有针对 Kimi 的实测。

## 选项

| 方向 | 做法 | 评估 |
|---|---|---|
| 锚点容错 | 行号不对时按唯一行标签重定位 / 只在行号附近窗口内找 / 报错给出候选行号 / 维持严格 | 针对 hashline 规则本身；前提是继续使用 hashline，且 oh-my-pi 的恢复方式并非按标签重定位 |
| 多组对照 | hashline 现状、hashline 加容错、replace、仿 oh-my-pi 新形态、按模型选编辑模式，三组以上 | 覆盖面最全；仿新形态需实现补丁语法、语法树块定位与快照链恢复，工作量大，且对 Kimi 事前证据不看好 |
| 收窄对照 | 只加一组 replace 式编辑工具，与 hashline 比较编辑报错率、轮次、输出 token、失控次数 | 直接回答"对 Kimi 与本仓库这类小改任务，哪种编辑方式摩擦更小"；成功率已触顶，比较以过程指标为主 |
| hashline 基线 | 新版本上 hashline 与 replace 交错重跑 / 复用 M6.5 冒烟无 Skill 条件 24 次 hashline 运行 | 重跑排除 harness 版本差与时间漂移，成本翻倍；复用成本低，版本差与时间漂移会混入对比 |

## 裁决

1. 对照收窄为只加一组 replace 式编辑工具与 hashline 比较；锚点容错、仿 oh-my-pi 新形态、按模型选编辑模式本轮不做，锚点容错搁置到对照结果出来后再议。编辑工具默认是否改用 replace，按对照数据另行裁决。
2. 只跑 replace 一组，hashline 基线复用 M6.5 冒烟无 Skill 条件的 24 次运行，不在新版本上重跑；两组之间的 harness 版本差与时间先后差异作为已知局限写进审计与报告。
3. replace 式编辑工具口径参照 Claude 文本编辑工具 str_replace 的惯例：参数为路径、原文、新文；原文必须在文件里恰好出现一次，精确匹配、不做空白宽松，未找到与不唯一均拒绝并说明（不唯一时给出出现次数与各处起始行号）；不带快照参数；工具名沿用 `edit_file`，策略、grant 与角色清单不变；replace 模式下 read_file 输出不带行标签与快照标签，每行形如 `行号| 内容`；成功回执形状与 hashline 版对齐，不回传 diff 或锚点。
4. 编辑工具默认改用 replace，hashline 保留为可选编辑模式；hashline 当前维持现有严格规则；锚点容错、编辑后回传新锚点、参数改为字符串补丁、参考 oh-my-pi 的过期恢复与块操作等 hashline 优化本轮不做，留作后续优化方向，在有使用方（接入行号定位能力强的模型、大文件或大块移动类任务、并行编排下文件被外部改动）时再盘，优化后以 Eval 对照验证。依据：061 对照（条件 none，Kimi For Coding，各 24 次）编辑报错率 hashline 24.2%（66 次调用 16 次报错）、replace 4.7%（64 次 3 次）；按运行算至少出一次编辑错误的运行 9/24 对 2/24；成功率都是 24/24，未测出差异；replace 平均多 1.5 轮、总 token 多约 15%，多出部分集中在一道题的命令循环。设计出处 oh-my-pi 也对 Kimi 等模型默认用 replace。hashline 的主要报错是锚点格式错与锚点未命中，replace 下这两类不再出现。局限：单一模型、8 道小改题、两组 harness 版本与运行时间不同；以后接入其他模型或 M9 任务集建成后复核。

## 施工口径（不裁决）

- Eval 条件在 Skill 维度之外加编辑模式维度；运行面按编辑模式装配编辑工具，缺省仍为 hashline。
- 结果行补编辑模式、Pigeon 版本与过程指标（各工具调用数与报错数、输出上限截断轮数），过程指标由同一段代码从 Event Log 汇总；hashline 基线的过程指标用同一段代码从保留的会话账本复算，不用临时脚本。
- replace 式编辑工具接入与 edit_file 相同的写档治理、审批预览 diff 与内容证据（改前与预期改后哈希）。
