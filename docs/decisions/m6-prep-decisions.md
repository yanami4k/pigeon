# M6 前置裁决（2026-09-16 起）

- 定位：M6 受限后台 Reviewer 开工前的四件前置：Reviewer 接入形态、候选暂存与约束、TUI 拒绝理由通道、tui/shell.ts 拆分与 cli / tui 装配收拢
- 裁决：项目负责人；基线 a2e8ebf
- 依据：ROADMAP §M6、§3.4、§3.5、§3.6、§8、§M5.5；decisions.md 006、029 修订、040、042、043、054、059；docs/audits/2026-09-15-health-7818dee.md
- 说明：前两件是设计裁决，实现随 M6 主体；后两件本轮施工

## 第 1 件：Reviewer 接入形态

### 事实

- ROADMAP:517 已定 Reviewer 是"只读、无工作树的 worker"；§M6 已定独立 Agent 与一次性 ReviewRun、主会话不可变快照、不建 lane、不写主会话、精确工具白名单、两路模型路由、候选暂存与扫描筛查。
- 派 worker 必建工作区，`WorkerWorkspaceSchema` 只有 `git-worktree` 一个成员且 `branch` 必填（src/state/event-log.ts:358-362）；决策 054 已写明形状封顶三种、以加法式联合扩展。
- reviewer 角色默认工具只有会话检索与条目读取两项（src/orchestration/roles.ts:21），检索范围是整个会话目录（src/application/runtime.ts 装配处），无读 Trace 与 Receipt 的工具。
- worker 策略必须是父策略子集，超出即拒（src/orchestration/roles.ts:47-53）；新增写档工具无法通过该校验。
- 无审批通道时 prompt 档 fail-closed；只读工具属 read 档自动放行，Reviewer 可不进审批队列。
- 编排器目前只在 TUI 装配（src/tui/main.ts）。

### 选项

| 方向 | 做法 | 评估 |
|---|---|---|
| 复用 worker 编排器 | 工作区加"无工作区"成员、补只读快照工具、收尾结果带结构化内容 | 会话文件、派出与收尾配对记录、取消、trace 入口、冷恢复复用既有实现；需加法式扩两处 schema |
| 另写第二实现 | 以 headless 装配内核另做 Reviewer 调度 | 不碰工作树；驱动循环与记录族重复一份 |
| 进程内直接跑不留会话文件 | — | 与 §3.5"状态必须能从 Event Log 重新物化"冲突，无 trace 与恢复 |
| 独立进程子命令 | — | 隔离最强；040 否决多进程的理由（IPC、存活、信号、复杂度）仍成立 |

### 裁决

复用现有 worker 编排：工作区类型加法式新增"无工作区"成员；reviewer 角色补只读快照工具；worker 收尾结果允许携带结构化内容，候选由 Controller 从收尾结果落盘，Reviewer 自身不持有任何写档工具；另加 `pigeon review <sessionId>` 薄壳，复用 headless 内核，供事后补审冷会话与实验会话。理由：路线图已把 Reviewer 定为 worker，复用可直接获得会话文件、配对记录、取消与冷恢复；"模型交结果、程序落盘"使 Reviewer 天然只读，且不新增审批或放权语义（与 039 后的方向一致）。先例：oh-my-pi 的 task 以结构化结果交回，Claude Code 子代理独立上下文、工具白名单、结果回交主会话，Hermes 后台 review 的产物先落待审目录由 harness 写入。

### 待裁决（M6 开工前）

触发时机；纳入自动审阅的会话范围；模型路由缺省与摘要格式；Reviewer 预算与并发上限；只读快照工具绑定冻结副本还是全目录；记录族复用 child.* 还是另开 review.*。

## 第 2 件：候选暂存与约束

### 事实

- §3.4：候选默认进持久化暂存区；§3.5：Candidate 状态属于必须能从 Event Log 与快照重新物化的状态，Controller 是唯一权威写入者；§8：不允许任何后台流程写 grants.json；§M8：Policy 候选的激活路径与普通 Skill 写入路径物理分离。
- 候选 schema v1 只有 id、状态、来源引用、摘要与两个时间戳（src/state/candidate.ts），无种类、内容哈希、扫描结果与来源条目。
- 暂存目录约定目前只有 Skill 一种（decisions.md 059 修订）：`.pigeon/candidates/skills/<name>/`，缺省不加载。
- 代码中没有任何不可见字符或注入扫描实现；既有净化只处理终端控制序列（决策 036）。

### 选项

| 方向 | 做法 | 评估 |
|---|---|---|
| 目录内状态文件 | 一候选一目录，状态写入并就地改 | 人可直读；文件成为第二事实源，与 §3.5 冲突 |
| 状态进账本、正文按哈希不可变 | 正文写入 `.pigeon/candidates/<种类>/<名字>-<哈希>/`，写入后不再修改；状态由记录现算；改内容即新候选并标记取代 | 与 §3.5 及会话文件只追加口径同构，账本可直接供 M7 / M9 消费；列候选需跨会话扫描 |
| 全局 JSONL | 单文件追加 | 列表便宜；破坏每会话一文件口径，多写者需加锁 |

### 裁决

取"状态进账本、正文按哈希不可变"。正文写入暂存目录且写入后不可变，同哈希即同候选（天然去重），内容修订产生新候选并在记录中标记取代关系；候选状态由账本记录现算，不在候选目录中保存可变状态。M6 阶段生命周期只走到提出、已扫描、证据已核，回放验证与审批归 M8。安全扫描用确定性规则（不可见字符、注入与外泄模式、可执行脚本目录标记），模型筛查只作建议。账本新增提出与筛查两族记录，批准、拒绝、激活归 M8；不新增任何审批或放权语义。

### 待裁决（M6 开工前）

候选 schema v2 字段集与是否新增"扫描拒收"状态；Policy 候选在 M6 是否只出文本；Memory 候选粒度；扫描命中是丢弃还是暂存标记；是否提供只读候选列表命令。

## 第 3 件：TUI 拒绝理由通道

### 事实

- TUI 四键单按即决议，[n] 不带理由，由治理层落默认文案（src/tui/approval.ts:18、src/application/governance.ts 拒绝分支）。
- CLI 会询问拒绝理由，留空同样落默认文案（src/cli/approval-ui.ts:88-91），因此账本层面两个 Actor 都无法区分人写理由与系统兜底文案。
- 决定记录有可选 reason 字段，但无字段标明理由来源（src/state/tool-execution.ts:30-51）。
- 审批发生在运行中，运行中提交被 busy 拒绝，理由输入需要新增输入模式（决策 031 当时以此否决逐行问答）；worker 审批与主会话共用队列，输入期间后续审批排队。

### 选项

| 方向 | 做法 | 评估 |
|---|---|---|
| [n] 打开理由行 | 回车留空跳过 | 与 CLI 一致；改变 029 的单按即决议手感 |
| 保留 [n]，新增 [r] | [r] 拒绝并写理由 | 对 029 为加法式修订；不写理由的拒绝仍无信号 |
| 决定记录加理由来源字段 | 标明人写或系统默认 | 一次解决两个 Actor 的数据可信问题；不新增审批语义 |
| Episode 按来源 Actor 标注 | — | 需新增治理元数据，TUI 侧仍拿不到真实理由 |

### 裁决

取"保留 [n]，新增 [r] 拒绝并说明"与"决定记录加理由来源字段"两项。[r] 打开理由行，Esc 回面板不算拒绝，回车提交，理由逐字回模型；来源字段加法式加入决定记录、不升 Event Log 版本（口径同 052），迁移完整性机检同步覆盖；双击 Ctrl+C 的退出布防在理由行期间照旧生效。理由：拒绝理由是 006 定的负样本监督信号，当前 TUI 恒为默认文案会让 M7 学到噪声；来源字段保证数据可信，[r] 提供真实信号，两者都不新增审批语义。先例：Claude Code 与 Codex 的审批交互均把"拒绝"与"拒绝并说明"分为两个动作。

## 第 4 件：shell.ts 拆分与 cli / tui 装配收拢

### 事实

- src/tui/shell.ts 937 行，主体为单一壳类，含消息流、审批面板、按键路由、斜杠命令分发、worker 命令、resume 与历史、事件渲染七块；9 个 tui 测试文件从该文件导入壳类与类型。
- 三个入口的模型占位缺省不一致：cli 为 custom / cli，tui 为 unknown / unknown，headless 为 custom / headless；该值进注入快照与 run.started，按入口分组会把同一模型算成三个。
- `PIGEON_STREAM_FN` 仅 tui 读取，cli 参数解析不读，但 cli 报错文案称支持该变量（run 与 eval 子命令同受影响）。
- buildWithMcp 在 cli 与 tui 各有一份相同实现；resume 装配与 grants 上下文构造重复；MCP 启动提示输出口径不一。

### 选项

| 方向 | 做法 | 评估 |
|---|---|---|
| 按职责拆五个文件 | 消息流、模态与按键、斜杠命令、worker 视图、resume 视图；壳保留布局与启停并重导出公开符号 | 粒度贴合 M6 新增视图；测试导入不变；零行为变化 |
| 拆三个大文件 | 上次架构审计原建议 | 较粗，M6 后仍会增长 |
| 抽装配模块 | 新增启动参数模块与会话运行面模块，统一新建与 resume 装配 | 一处改动三个入口受益；是 M6 挂 Reviewer 调度的落点 |
| 只去重不统一缺省 | — | 缺省漂移与环境变量缺陷保留 |

### 裁决

按职责拆五个文件，并抽出启动参数模块与会话运行面模块。三个入口的模型占位缺省统一为同一常量（provider 与 model 均为 custom），真实模型元数据由 streamFn 插件提供，历史会话标签不做映射；cli 补 `PIGEON_STREAM_FN` 回退，使行为与既有报错文案一致。施工顺序：先做零行为变化的拆分，再落第 3 件的理由行（只改模态文件），装配收拢与前两者不相干可并行。不给 cli 与 headless 装 worker 编排器（M6 需要时另裁）。
