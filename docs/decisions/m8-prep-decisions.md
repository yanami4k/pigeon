# M8 前置裁决（2026-09-19 起）

- 定位：M8 Candidate 验证、审批与激活开工前的十三件前置
- 裁决：项目负责人；基线 615683e
- 依据：ROADMAP §M8、§3.5、§3.9、§6、§8；decisions.md 006、014、029、039、042、043、048、054、058、065、066、071、072、074、075、077、078、079、080

## 事实

- M7 交付后候选状态只走到已扫描；没有验证、审批与激活路径，提炼出的经验一条也不会生效。
- 成败判定目前只有两个来源：Eval 任务目录里的验证器，以及会话启动参数 `--verify-command`。日常会话不配即标未知，进不了对比也进不了回放判定。
- 仓库已有三套项目级配置文件机制（命令规则、放权、MCP），均在治理根下，原子替换现成。
- 沙箱：代码中零实现；048 明确把沙箱后置，理由是逐次审批加完整命令显示可接受。现有隔离只有 git 工作树的文件级隔离，写档工具有工作区路径围栏，`run_command` 工作目录固定在工作区根、环境变量走白名单，但进程能力无约束。
- 后台并发闸目前由 Reviewer 与提炼器共用，限额 1。
- M7 已具备回放所需的三样：从任务起点分叉、独立工作树、验证命令判成败。

### 沙箱选型调研（2026-09-19，宿主为 Windows 11 Home + WSL2）

- WSL2 内核（linux-msft-wsl-6.18.y）编入 seccomp、user/net namespace、overlayfs、cgroup v2 与 KVM 模块，未编入 Landlock、AppArmor 与 SELinux：Landlock 路线不可用；bubblewrap 与容器可用且不会被 AppArmor 的非特权用户命名空间限制拦截。
- 可落地的三条路：WSL2 内 rootful 容器（五项需求全满足，每容器启动数百毫秒，需常驻容器加 exec）；WSL2 内 bubblewrap（毫秒级启停，无资源上限，需另叠一层）；Windows 原生的进程容器方案（有 TypeScript SDK，断网与路径白名单由系统防火墙与 ACL 强制，但无 CPU 与内存上限且当前不宜作为安全边界）。
- 硬隔离（微虚拟机）在 WSL2 内无任何官方背书，须先实测虚拟化设备是否可见。
- 已知坑：WSL 2.9 的 rootless 回归使 rootless 容器起不来（用 rootful）；mirrored 网络模式与容器端口冲突（保持 NAT）；宿主 Windows 盘目录挂载进 Linux 容器走 9P，海量小文件场景慢数倍且收不到文件变更事件。
- 超时终止在容器形态下由内核保证：PID namespace 的 1 号进程终止时，内核向该 namespace 内所有残余进程发 SIGKILL；但经 exec 起的进程在杀掉客户端后会成为孤儿，超时须终止整个容器。

## 裁决

| # | 事项 | 选项 | 裁决 |
|---|---|---|---|
| 1 | 验证命令的可得性 | 项目级配置文件 / 自动推断 / 只服务回放 / 配置加推断 | 项目级配置文件：人配一次，本项目所有会话继承，启动参数可覆盖；不做自动推断 |
| 2 | 回放执行体 | 复用 worker 新增验证器角色 / 复用 Eval runner / 另起执行体 | 复用 worker 机制新增验证器角色，起点用 M7 的快照回到任务开始处，统计沿用 Eval 的结果行格式 |
| 3 | 回放的权限形态 | 接受现状 / 固化命令规则 / 容器沙箱进 M8 / 不给命令工具 | M8 用固化命令规则（现成机制），沙箱排入 M9 前置；选型前先跑三个探针：容器 exec 单次往返延迟、WSL2 内虚拟化设备是否可见、跨边界调用的退出码保真度 |
| 4 | 回放判定口径 | 严格区间比较 / 只跑带经验侧 / 分级筛 / 三值加大效应门槛 | 三值判定（通过 / 未测出 / 回归）加大效应门槛，四组固定 N（缺省 5）全跑、不中途停；pass@k 与 pass^k 分开报，Wilson 区间进回执但不作判据；N 可配，低于 3 禁用 |
| 5 | 经验在回放中的装载 | 临时治理根 / 运行面注入 / 真激活后撤销 | 在回放工作区造临时治理根，按种类的正常格式放入并走与真激活完全相同的装载路径；宿主的经验目录不写 |
| 6 | 回放触发 | 只人工 / 落库即自动 / 缺省人工可配自动 | 缺省人工 `pigeon verify`，提供显式开关以在无人值守时自动验证 |
| 7 | 预算与并发 | 共用现有闸 / 单设回放闸 / 多路并行 | 单设回放闸，缺省并发 1、可配；每次回放的预算与模型沿用被验证那次尝试，不得放宽 |

| 10 | Policy 候选的激活 | 只读建议文件 / 生成权限补丁 / 直接写放权文件 | 只落只读建议文件，目录与 Skill、Memory 分离，永不自动改放权文件或命令规则；分离由分层规则机检钉死 |
| 11 | 验证回执与环境摘要 | 严格全项失效 / 开放式分级 / 封闭清单 | 摘要记全（模型、harness 提交号、Node 与平台、预算、验证命令、同时装载的经验集合哈希、四组通过次数与结论、各次运行会话号）；失效判据只看封闭四项清单：模型标识、经验集合内容哈希、预算参数、验证命令；增删清单须单独裁决 |

## 权衡要点

- 第 1 件：自动推断的验证命令一旦把未被测试覆盖的改动判为通过，会把失败尝试标成成功，污染的是学习素材的标签；072 的口径是宁可标未知，不可标错。
- 第 3 件：M8 的价值是判据而非隔离；固化命令规则只是缩小开口，不是隔离——放行一条脚本命令即等于放行该脚本能做的一切，网络亦不受限。真正的断网与文件白名单只有沙箱能给，故明确排入 M9 前置而非含糊后置。
- 第 4 件：N=5 时置信区间宽到只有极端分布才不重叠，若以区间不重叠为判据，实质门槛就是大效应，却披着统计的外观；直接把门槛写成大效应更诚实。"未测出"必须与"无效"分开，同 Eval 基线触顶时的结论口径。
- 第 5 件：运行面注入会造出第二条装载路径，验证形态与激活形态的细微差异最难发现；真激活后撤销则在崩溃时留下已激活的经验，与"不能跳过审批"冲突。
- 第 7 件：回放若获得比原尝试更宽的预算，成功率提升将来自预算而非经验，且这种失效隐蔽。
- 第 8 件：候选审批是离线决策，内容为长文；工具审批是在线短决策。二者形态不同，混入同一界面会把该慢的决定塞进快节奏上下文。
- 第 10 件：由人对机器生成的权限补丁点确认，实际审查强度低于亲手编辑；工具审批处已出现同类现象（单按拒绝导致账本充满默认文案，故 066 补理由来源字段）。
- 第 12 件：负回放是唯一可直接观测到"经验有害"的证据，可被理由覆盖则该门失效；未测出一刀切禁止则会排除价值不体现在单任务通过率上的经验。
- 第 13 件：完成证据中"批准内容与激活内容摘要一致"约束的是激活那一刻，不应读成禁止人后续编辑；可见性（漂移标注）与项目一贯做法（悬账、崩溃残留、截断标注）一致。
