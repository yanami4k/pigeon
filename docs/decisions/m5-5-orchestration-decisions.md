- 定位：039 重定位后，第一个主角"无人值守的并行执行"的形态，以及与之相关的外部工具链接入方式与 Eval runner 方向
- 裁决：项目负责人；原则是时间盒不作为高权重考虑项，按正确且完整的设计给推荐，工程量只作信息列出

## 第 1 件：并行 worker 编排（索引 040）

### 事实核对

- edit_file 执行前重算整文件快照标签，与读取时不一致即拒绝："互相感知"已由现有机制兜住；拒绝理由无法说明是谁改的，属措辞非机制缺口。
- grants.json 为整文件 writeFileSync 加 fsync，无临时文件改名：风险是写到一半崩溃留下半截文件，下次启动读到畸形即响亮失败；并发写不是现实场景。
- 会话文件无重复打开守卫：两个进程恢复同一会话都能追加，幂等索引按进程各一份，可能写出重复 resolution，下次打开报损坏。
- ROADMAP §8 与 §M5.5 已明文禁止同一工作区并行写入者（既定）。
- "多会话审批汇聚入口"即 003 所说的 Remote 形态，不是新语义。
- 装配根 buildRuntime 每次调用构造独立的 Adapter、事件日志、工具注册表与 grant 存储，无进程级全局状态，同进程多实例可行；.pigeon/ 目前放在 workspaceRoot 下，治理根与工作区根尚未分离。

### 先例

- 主流 coding agent 的并行分两套：子代理同进程（各自上下文、工具受限、可选工作树隔离、权限提示走父界面）；多会话多进程零协调（各在工作树，人合并）。两套都只隔离代码，不做治理。

### 选项

- 轻档：同进程多 Adapter；每 worker 一个 git 工作树与一个会话文件；审批进同一面板带 worker 标签；父会话记 child.spawned / child.settled；结果为分支加结构化摘要。约 6 到 8 天。
- 重档：轻档加 childPolicy 子集校验在 Controller、token 预算与单独取消、adoption 记录、Job 抽象。约 12 到 15 天。
- 进程模型：同进程（审批是函数调用、装配根已支持多实例、故障隔离差距被每 worker 会话文件冷恢复兜住）对多进程（IPC 协议、存活探测、鉴权、Windows 信号语义，复杂度两到三倍，当前无跨机器需求）；worker_threads 折中第一版不取。

### 裁决

- 轻档、同进程。orchestration/ 对外只暴露 spawn / cancel / status / awaitResult 四动作加审批请求回调，即 §3.6 的 Job 边界，第一版只留接口不做第二实现。
- 一个窗口一个进程：关闭窗口全体 worker 停止，各自会话文件冷恢复。多窗口即多进程各自独立：窗口内治理加编排，窗口间只保共享文件安全（会话打开锁、grants.json 临时文件加改名原子替换、工作树目录名带会话编号），不做共享审批或调度。
- worker 并行 = N 个完整 agent（Agent + Adapter + 上下文 + 策略 + 会话文件 + 工作树）同进程并发；worker 内部仍是工具串行与 run() 互斥。
- 演进三阶段共用四动作：人以 /spawn 派；父 agent 经受治理的 spawn 工具自派（默认审批、子集校验、深度 1）；确定性脚本流水线。不做 worker 直接互通（§3.5）与深树（§8）。
- 排期：M5.5 紧接 M5；§5 时间盒措辞改为规划参考而非裁决权重。

## 第 2 件：外部工具链接入（索引 041）

### 分析

- 三个非 coding 工具链场景（Unity 资产装配管线、数据分析 agent）逐项对表现有机制，共同前置为：Receipt 证据泛化（从单文件哈希到子树清单或调用与返回摘要）、隔离单位泛化（工作树只是实现之一）、exec 沙箱、预算档。计划级审批（装配管线）与账本敏感数据脱敏（数据类）按接入类型触发。
- 为工具链另造 agent 运行时无价值：通用循环已商品化；领域特有控制流是工作流不是运行时，由计划级审批与脚本调四动作覆盖；独立演示用现成宿主。
- 工作流的归属：步骤定义与领域顺序归工具链（复合工具、MCP prompts 或 Skill、声明式管线文件；有副作用的步骤不塞进复合工具），执行引擎归 Pigeon。
- 工具链的协议层薄，复杂度在领域层与面向模型的工具设计（参数形状、错误信息引导自纠、截断、幂等）。

### 裁决

- 仓库内工具直接注册 Registry（拿得到证据钩子）；外部工具链只经 MCP 接入（stdio 与 streamable HTTP 传输都算）；不做私有插件 SDK，不做 OpenAPI 或子进程包装的第二种接入。经验规则：需要改前改后哈希级证据的工具做成内部工具，其余走 MCP。
- 新增 M5.7 里程碑：MCP 客户端适配；注解只当线索、档位以本地配置为准、未配置一律 write 档审批；Receipt 证据泛化；隔离单位泛化；四项前置按接入类型触发不单独立项。
- 同日修订（联网核实）：oh-my-pi 支持 stdio / HTTP / SSE，桥接进 CustomTool 注册表，管生命周期与重连，继承 .claude / .cursor / .codex 等目录的 MCP 配置；pi 本体无内置 MCP，走扩展（earendil-works/pi#563）。据此定：M5.7 配置兼容读取 Claude Code 的 .mcp.json；oh-my-pi 的 MCP 桥接作为设计参考阅读，不引其包。
- 串行顺序：M5 → M5.5 → M5.7 → M6.5 → M6 → M7 到 M9 → 工具链独立仓库（路线图外）→ 集成演示。

## 第 3 件：Eval runner 方向（索引 046）

### 分析

- Pigeon 的 Eval 是三向对照实验（无 Skill、候选 Skill、已批准 Skill），核心问题是"学习有没有带来提升"。硬要求：经 Pigeon 运行面跑、指标从账本算、三向对照靠 042 / 043 的注入冻结开关、§3.8 成败只认确定性验证器、需要 headless 运行入口。
- 外部工具两类（截至 2026 年中的了解，使用前联网核实）：评测框架（promptfoo、Inspect AI、DeepEval：用例矩阵、断言、报告、CI；面向输入到输出，读不到账本，默认 LLM 打分）；公开基准 harness（SWE-bench、Terminal-Bench：任务集、容器、可比分数；测不了学习增益）。

### 选项

- A 全自建：贴合但统计与报告重复造轮子。
- B 评测框架作核心：Pigeon headless 包成 provider，三向对照与 M9 统计规范得在断言里绕，主干别扭。
- C 自建薄 runner + 任务格式对齐公开基准 + 外部 harness 作可选适配。

### 裁决

- C。runner 四件事：读任务目录、准备仓库快照、经 headless 入口跑 Pigeon 若干次、调验证器并从账本出 JSONL 结果；统计按 M9 规范自写；报告先出 markdown 表；任务目录格式对齐 Terminal-Bench 形态；适配器可选；M6.5 在本机工作树跑，容器隔离随 exec 沙箱考虑；headless 入口与 M5.5 worker 共用。
- 先例：SWE-bench 与 Terminal-Bench 都是自家 harness 加数据集、agent 经适配器接入；Claude Code 的 plugin eval 是自带 JSON 套件的小 runner。

### 前置一：治理编排搬家（索引 049）

### 前置二：exec 工具（索引 048）

- 通俗说明：exec = 跑 shell 命令的工具；它难管是因为没有路径可围，路径围栏对命令无意义；证据形态也不同（命令、退出码、输出哈希，而非文件哈希）
- 沙箱重量：macOS sandbox-exec 与 Linux bubblewrap 轻量；Windows 无对应原语，Docker 路线约三天加启动与 IO 代价，原生 AppContainer 一到两周且易假安全，WSL 路线是 Docker 变体；设工作目录、清环境、超时、截断不算沙箱
- 候选"固定命令名单"（模型只选名字，无自由文本入口；先例 sudoers、npm scripts、CI 命名步骤、MCP 命名操作）因日常体验过重否决：主会话跑临时命令要先改配置。取简化版：自由命令加逐次审批（面板显示完整命令，与 Claude Code 在 Windows 上的体验一致），[a] 精确命令串会话 grant（确定性匹配，§3.9 不动，不被 && 绕过，代价是带参数版本各放行一次），/grants save 升格，yolo 照旧；commands.json 降为可选便利与角色默认权限；沙箱后置、按平台适配、fail-closed
- yolo 与能力边界：yolo 只改审批不改能力；工具集由注册表与 allow 清单决定；自由命令沙箱工具只在沙箱可用时注册
- 临时命令快速加白：[a] 本会话，/grants save 跨会话，/revoke 撤销，均为既有流程；"[a] 加 save 一键"留作后续 UX 改进
- 复杂度约一天；两版工程量相当，差别只在体验与严格度的取舍

## 补充：设计权衡与工程笔记（2026-09-14）

### 与路线图原版 M5.5 的关系（040）

原版 M5.5 的定义是父 Run 在同一 Session 内创建 Child Run，深度 1、最多 2 个、默认串行写入同一工作区、排在 Eval 冒烟之后。040 保留了原版的大半，改了三处。

保留：深度 1 不派孙代理；子代理权限必须是父策略子集；子代理只交回结构化结果、不直接改父 Session；预算、取消、有界输出统一归 Controller；写操作照样经审批与回执；角色表 reviewer / explorer / implementer / tester。

| 原版 | 040 | 理由 |
|---|---|---|
| 默认串行写入同一工作区，最多 2 个 | 每 worker 一个工作树，N 个并行写 | 原版的并行只能并行读，一写就排队；§8 禁止的是同一工作区多写入者，工作树隔离后禁令原样成立 |
| Child Run 挂在父 Session，共用一个会话文件 | 每 worker 独立 Session 与会话文件，父会话只记 spawned / settled | 崩溃后每个 worker 单独冷恢复；/resume、/search、trace 按 worker 单独可用；装配根本就是一次调用产一个 Session，零新机制。代价是父子关系靠两条记录跨文件对上。"父子同文件"方案评估过：一条 trace 天然完整，但恢复、检索、渲染全按 Session 为单位写，塞进一个文件要到处加按 runId 分组的逻辑；未采纳 |
| 排在 Eval 冒烟之后，前置含 per-tool 并发演进 | 紧接 M5，per-tool 并发不再是前置 | 每 worker 各有 Adapter，worker 内部串行够用，不需要改 002；排期变化按"时间盒不作为高权重项"的口径 |

名字随之改：原版叫 Child Run 是准确的，因为它是父 Session 里的一个 Run；改成独立 Session 后再叫 Child Run 名不副实，故叫 worker。术语层级：执行体一层有三种，工具调用、worker、后台 Reviewer（M6，只读无工作树的 worker）；主会话本身也是没有父级的 worker；lane（§3.7）是同一 Session 树内的分叉，与 worker 正交；角色是 worker 的参数不是执行体。

### 进程模型的复杂度对比（040）

同进程多 Adapter 与多进程的差别不是"多写点代码"，是多出好几类之前不存在的问题：

| 问题 | 同进程 | 多进程 |
|---|---|---|
| 审批 | 函数调用 | 定协议、序列化、跨进程往返、超时语义 |
| 状态观察 | 直接订阅 Adapter 事件 | 经管道转发，处理丢包与乱序 |
| 取消 | 调 abort | 发信号，Windows 无 SIGTERM 语义 |
| 存活 | 不存在 | 心跳、僵尸回收、Controller 挂了 worker 变孤儿 |
| 崩溃 | 一起崩，各自冷恢复 | 单边崩溃的感知与处置要定 |
| 安全 | 不存在 | 本机管道要鉴权，否则任何进程可冒充 worker 发审批 |
| 测试 | node:test 直接跑 | 起真实子进程，慢且平台差异 |

粗估两到三倍工程量，换来的只有单 worker 崩不拖累别人（已被每 worker 会话文件冷恢复兜住大半）与将来跨机器（当前无需求）。worker_threads 折中：线程异常不拖垮主线程，但审批与事件要跨线程传消息，第一版不取。"一个窗口崩了会带崩其他"的准确说法：同进程只有一个窗口，worker 不是窗口；关窗口全体停，各自会话文件冷恢复；多窗口即多进程各自独立。

### 048 修订的过程（2026-09-14）

起因：Windows 上 npm、npx、node_modules/.bin 全是 .cmd 垫片，不经 cmd.exe 无法运行，Node 因 BatBadBut 漏洞的修法直接拒绝不带 shell 的 .cmd spawn（EINVAL）；048 原文下的处理是如实拒绝并提示改用 node 加脚本路径，正确但使 tester 在 Windows 上不可用。

四条路：

| 路 | 做法 | 安全性 | 便利 |
|---|---|---|---|
| A 维持拒绝 | 现状 | 最高 | 每条 JS 工具命令都要写 node 加脚本路径 |
| B 登记命令可开 shell | commands.json 条目加 shell 标记，经 cmd.exe 运行 | 命令串是人写的，注入前提不存在 | 只解决登记过的命令 |
| C 自动解析垫片 | 读 .cmd 内容改写为 node 调用 | 高 | 垫片格式不统一，脆 |
| D 受限字符集经 cmd.exe 启动器 | 参数只允许字母数字与 `_ . - / : = @`，全部通过才用 `cmd.exe /d /s /c` 拉起 | BatBadBut 依赖的字符全在白名单外；/d 关自动运行，/s 固定引号解析 | npm test、npx tsc 等都能跑 |

D 为主、B 为补。B 的授权来源有手写清单与审批面板确认两种形态，取审批面板：需要 shell 语义的命令在面板上标"经 shell"、显示完整命令串，人批准即以 shell 跑这一次；[a] 创建带 shell 标记的精确命令串会话 grant；/grants save 升格为带 shell 标记的固化规则；commands.json 退回只做短名与角色允许清单。守住四条：屏幕字节与执行字节一致、精确匹配、面板明说"经 shell"、经 036 净化。UI 确认比手写少一步预先配置，风险是人在面板上不看就按，只能靠显眼标记。

yolo 不设例外。否决方案"yolo 下无既存精确 grant 的 shell 命令拒绝"：与 004 的 yolo 定义不一致。yolo 是批发授权，deny 之外一律免审，shell 命令照放，Receipt 标"经 shell"。去掉例外后 yolo 下剩余的保护：deny 清单、熔断计数、D 的字符集校验不放宽、工作树隔离兜住仓库不兜住机器、回执留痕；风险与 Claude Code 在 Windows 上开 bypass 模式相同。

### 工具链与治理的关系（041 补充）

工具链经 MCP 接进 Pigeon 后，治理与学习作用在"用工具链的 agent"身上，不作用在 server 进程里。

| 方向 | 内容 |
|---|---|
| 工具链直接获得 | 每个 MCP 工具调用过六档排律；账本与回执；trace / replay 能回答"那次导入为什么失败"；Session Search 能翻到上次怎么修的；M7 从含工具链调用的会话提炼"怎么用这套工具"的 Skill，M9 用工具链任务做 Eval |
| 工具链主动可做 | 供证据：返回里带结构化字段，Pigeon 原样记并哈希（落为 053 的 serverEvidence 约定）；供规程：MCP prompts 随 server 发布，Skill Catalog 吃进 |
| 工具链拿不到 | server 看不见账本，不能在内部子步骤上请求审批，审批粒度是一次工具调用；读不到 trace 与搜索 |
| 候选 | Pigeon 自己也作只读 MCP server，暴露搜会话、读原文、Run 的 trace 摘要，让 Claude Code 里跑的工具链 agent 也能查 Pigeon 历史；只读故治理安全，约两天，不在路线图，M5.7 之后候选 |

对工具链自身的唯一要求：操作拆成合理粒度的工具，一个工具做一件事，返回里带上它改了什么。垂直工具链比通用 coding 更需要治理，因为操作慢、贵、不可逆。

场景对表（压缩）：Unity 资产管线，六档与目录限定 grant 合身，Receipt 改前改后哈希不合身要泛化为子树清单，崩溃对账非常合身（Editor 常崩、操作几分钟），并行 worker 不合身（每工作树一份 Library 缓存），Skill Catalog 很合身，逼出的新语义是计划级审批（批准一份清单后连续执行）。数据分析 agent，read 档自动放行合身但靠数据库只读账号兜底而非 Pigeon 解析 SQL，写操作对账很合身（提交后断网），代码执行是 exec 问题要沙箱，并行 worker 合身且隔离单位是输出目录加只读连接而非工作树，Memory / Skill 与血缘 trace 价值更高，结果标签最弱只能靠可复现性与数据质量断言，逼出的新语义是预算档与账本敏感数据脱敏。为工具链另造 agent 运行时无价值：通用循环已商品化，领域控制流是工作流不是运行时，独立演示用现成宿主；工作流的步骤定义归工具链、执行引擎归 Pigeon。

### 运行开销与潜在瓶颈（M5.5 收口后的工程笔记）

冷侧（trace、replay、会话列表、resume、Session Search）只在人主动看时跑，对任务零开销。热侧每次调用：六档排律与 grant 匹配微秒级；治理族落盘 intent / decision / receipt 同步写加 fsync 各一到几毫秒；观察族亚毫秒；熔断内存计数；人工审批是设计上的等待。两处例外：run_command 执行前后的工作树清单差异大仓库几百毫秒，可按命令关闭；审批等人。并行 worker 各自独立不互相阻塞。想要数字看 trace 里 tool.proposed 到 tool.settled 的时间戳差。

潜在瓶颈按最先咬人排序：

| 序 | 瓶颈 | 触发 | 缓解 |
|---|---|---|---|
| 1 | 会话数膨胀拖慢会话列表 | 每个 worker 就是一个会话；`/sessions` 对全部会话整读物化（015） | 列表只读头尾摘要，或按 015 口径补可重建的摘要缓存；M5.7 之后最先该盘 |
| 2 | 每 worker 一个工作树的准备成本 | 大仓库 worktree add 数秒，装依赖数分钟 | junction 挂主检出 node_modules，040 施工已如此；跨平台写进工作树管理 |
| 3 | provider 限流 | N 个 worker 同时打模型 | worker 数上限加简单退避，等真实碰到 |
| 4 | 单事件循环 | worker 超过十来个且密集调工具 | worker 数上限；再往上是多进程 |
| 5 | 人是串行的 | 审批队列一次一个 | 设计如此，靠 [a] 与 yolo 减少询问 |
| 6 | run_command 清单差异 | 大仓库 | 按命令关闭 |
| 7 | Session Search 线性扫描 | 总正文过百 MB | 038 触发条件：单次超两秒再建索引 |
| 8 | 内容文件体积 | thinking 默认存 | 只影响第 7 条 |
| 9 | 开会话给全部 Skill 算哈希 | 上千文件 | 几乎不会到 |

Windows 特有：NTFS 上 fsync 与 git 操作比 Linux 慢，放大第 4 条不新增瓶颈。结论：无硬瓶颈，全是线性增长项，各有触发点与不重构的缓解；M5.5 之后主动处理的只有第 1 条。
