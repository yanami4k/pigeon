# Terminal-Bench 对比分析计划（第二次，预注册）

本文写定优化后的 Pigeon 与对照 harness 在 Terminal-Bench 2.1 上第二次整体比较的设置、主判据、检验方法、报告措辞与规则，于冒烟开始之前提交。提交之后的改动只能在文末以带日期的修订行追加，且须在看到任何 agent 结果之前；只依据环境检查的追加不受此限，但同样以修订行记录。报告引用本文提交时的提交号。

立场同第一次（`tbench-comparison-plan.md`）：研究型项目，负结果照实报告；差距在本设计分辨不了的范围内时如实写，不找有利的解释。

## 0 设置

- **问题**：优化后的完整产品 Pigeon 与对照 harness，原样拿来用，在 Terminal-Bench 2.1 上谁做得更好；同时报告输入 token、花费与用时。只比整体，不拆机制。
- **题目**：与第一次相同的 76 道有效题（数据集、镜像、排除清单见第一次计划的附录 A.1、A.4，本次不变），官方超时与资源不改。
- **两组**：
  - P：Pigeon 打包产物（提交号与产物摘要见附录 A），在任务容器里以 `pigeon run --yolo --no-web --json --thinking high` 跑；不传墙钟预算；每个 trial 新建家目录与治理目录，不跨 trial 保留会话。
  - D：对照 harness 与第一次相同的锁定版本与配置（思考档位 high、放权运行、联网工具关，其余按缺省）；每个 trial 新建家目录。
  - 两组共用：同一模型 deepseek-flash，经同一个模型网关（同一价目）；以 Harbor 的容器内 agent 方式接入；两家的联网工具都关，agent 在终端里可以联网；下载来源与第一次相同（第一次计划的附录 A.2）。
  - 两组都不获知每题的限时（与官方设定一致）。
- **与第一次的不同**：
  1. P 换成优化后的版本（附录 A）。
  2. 撞 agent 超时时，适配器先停掉容器里的 agent 本身（杀掉从 agent 安装目录启动的进程，不再发起新的模型请求与工具调用），再进入判分；agent 已启动的命令与后台服务保持原状。两组同一段代码。这一处偏离官方框架（官方超时后不停 agent、照常判分）：第一次里超时后 agent 在判分期间仍改写文件，相关 trial 的分数存疑。
  3. agent 程序以非零退出码结束时，适配器报 Harbor 官方的 NonZeroAgentExitCodeError（Harbor 照常判分）。
  4. 并发每组 3（第一次为 2）；每遍两组各一个作业、同时启动。
  5. 每题 5 遍，跑满，不因结果中途停止或加遍。
- **版本冻结**：两组的版本在冒烟开始之前写入附录 A，各遍之间不改；不依据本实验任何 agent 运行（含冒烟）的结果修改任何一方。
- **冒烟**：正式各遍之前，两组各在 6 道事先指定的题上跑一次（附录 A），只核对能否跑通、网关计量与判分是否正常、看图题能否把图交给模型；冒烟结果不进结论，不计算、不查看两组之差。冒烟暴露的只能是接入与环境问题，修正限于适配器与环境，以修订行记录。
- 记号：题 i = 1…n；遍 r = 1…5；y(g, i, r) ∈ {0, 1} 为组 g 第 r 遍第 i 题的官方 reward。

## 1 每个 trial 的计量与出错归类

同第一次计划的第 1 节（归类顺序：网关记有上游故障或被拒绝转发 → 基础设施故障、重跑；判分给出 reward → 取该 reward；agent 超时或自身出错退出而没有 reward → 记 0；其余已知的基础设施异常 → 重跑，每个 trial 最多重跑 2 次，仍失败记缺失；未列出的异常类型标为"未归类"并逐个列出）。撞 agent 超时之后、agent 已被停掉再判分得到的 reward 照常取用。

## 2 主判据

同第一次计划的第 2 节：ȳ(g, i) 为组 g 第 i 题 5 遍的平均（各遍等权），d(i) = ȳ(P, i) − ȳ(D, i)，Δ 为 d(i) 在全部有效题上的平均；按题配对的符号翻转置换检验（100,000 次、双侧、5%），按题自助法 95% 置信区间（10,000 次），稳健性对照为线性概率混合模型 y ~ 组 + (1｜题)，设计灵敏度 M = 2.80 × sd(d) ÷ √n。有效题与缺失的定义同第一次。

## 3 次要判据（探索性，p 值不做校正）

每个 trial 计以下各项，报两组的中位数、90 分位与合计，以及按题配对差（先按题取 5 遍平均）的中位数：

- 输入 token（网关计量：未命中 + 命中 + 缓存写入）与其中的命中比例；
- 输出 token；
- 花费（网关计价，按非高峰价折算）；
- agent 墙钟（Harbor 记录的 agent 执行时长）与模型请求数；
- 超长回复数（单条输出超过 1 万 token，按网关逐请求留存计）；
- agent 超时数、基础设施故障与缺失数。

另报一项与第一次的对照（探索性）：P 的新版本相对第一次 a2c5ea1 的通过率、输入 token、花费与墙钟的变化。两次的并发不同、第一次只有 1 遍，只作参考，不下结论。

## 4 报告的固定措辞

同第一次计划的第 4 节（显著且 P 更好 / D 更好、不显著且区间落在 ±M 以内、不显著且区间超出 ±M、两组都 ≥ 85% 时注明接近上限）；花费、token 与用时的结论单独成句，不与通过率合并。

## 5 规则

1. 冒烟通过后跑满 5 遍。每遍跑完只核对基础设施故障与缺失的比例，不计算、不查看两组之差。
2. 某一遍基础设施故障与缺失超过该遍全部 trial 的 10%：停下查明；修好后该遍作废重跑，作废的结果不进结论。
3. 5 遍跑完、基础设施故障按第 1 节重跑完之后，一次性运行分析脚本出结论。

## 6 花费与时段

- 不设会中途停批的总花费上限。
- 不暂停高峰时段；报告写明各遍落在高峰时段的 trial 比例。花费比较一律按非高峰价折算。

## 7 分析代码

- 主判据与第 1 节的归类沿用第一次冻结的分析脚本；第 3 节新增的各项由一个补充脚本计算。两份脚本在冒烟开始之前冻结并在附录 A 记下摘要；正式结果出来后只允许修脚本的缺陷，每处修改在报告里列出。
