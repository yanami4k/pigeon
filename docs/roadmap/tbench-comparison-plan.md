# Terminal-Bench 对比分析计划（预注册）

本文写定两家 harness 在 Terminal-Bench 2.1 上整体比较的主判据、检验方法、报告措辞与第 1 遍之后的规则，于第 1 遍开始之前提交。提交之后的改动只能在文末以带日期的修订行追加，且须在看到任何 agent 结果之前；只依据参考解（oracle）与环境检查的追加不受此限，但同样以修订行记录。报告引用本文提交时的提交号。

立场：研究型项目，负结果照实报告；小样本不下变好变差的结论；差距在本设计分辨不了的范围内时如实写，不找有利的解释。

## 0 设置

- **问题**（385、406）：完整产品的 Pigeon 与对照 harness，原样拿来用，在 Terminal-Bench 2.1 上谁做得更好。只比整体，不拆机制。
- **题目**（406）：Terminal-Bench 2.1 全量 89 题，官方超时与资源不改。来源、摘要核对与镜像取法见附录 A。参考解跑不过、确认为环境本身坏掉的题，在任何 agent 运行之前预先登记排除（附录 A），两组同样排除。
- **两组**：
  - P：Pigeon 打包产物（提交号与产物摘要见附录 A），在任务容器里以 `pigeon run --yolo --no-web --json --thinking high` 跑；每个 trial 新建家目录与治理目录，不跨 trial 保留会话。
  - D：对照 harness 的无人值守模式，版本锁定；思考档位 high、放权运行、联网工具关，其余按缺省；每个 trial 新建家目录。
  - 两组共用：同一模型 deepseek-flash，经同一个模型网关（同一价目）；以 Harbor 的容器内 agent 方式接入；两家的联网工具都关，agent 在终端里可以联网。
  - 下载来源（只换来源，不改题目、判分脚本与判分逻辑；两组与参考解完全相同，取值与摘要见附录 A）：本机访问境外的下载站很慢（GitHub、PyPI、Debian 源约十几 KB/s）。解题阶段：每个 trial 在 agent（或参考解）开工之前，于容器里写入同一份系统级配置，让 pip、uv 与 apt 经宿主上的下载服务取包（该服务优先取国内镜像，缺了回落原地址）；不设任何环境变量，两组与参考解走同一段代码。判分阶段：经环境变量把 uv、Python 与 PyPI 的下载来源换到同一下载服务。
- **版本冻结**：两组的版本（Pigeon 的提交号与产物摘要、对照 harness 的版本）在第 1 遍开始之前写入附录 A，各遍之间不改；不依据本实验任何 agent 运行（含冒烟）的结果修改任何一方。
- **冒烟**：第 1 遍之前，两组各在 5 道事先指定的题上跑一次，只核对能否跑通、网关计量与判分是否正常；冒烟结果不进结论，不计算、不查看两组之差。冒烟暴露的只能是接入与环境问题，修正限于适配器与环境，修正内容以修订行记录。
- **遍数**：第 1 遍全量；两家各一个作业、同时启动、同一并发。第 1 遍之后按第 5 节的规则决定；目标每题 5 遍，各遍同样两家同时、同并发。
- 记号：题 i = 1…n；遍 r；y(g, i, r) ∈ {0, 1} 为组 g 第 r 遍第 i 题的官方 reward。

## 1 每个 trial 的计量与出错归类

- 结果取官方 reward：1 为通过，0 为未通过。
- **算作 harness 表现、记 0**：agent 超时；agent 自身出错退出；判分正常完成而未通过。
- **算作基础设施故障、重跑**：镜像构建或拉取失败；容器启动失败；判分阶段下载失败或判分超时、拿不到 reward；模型网关或模型服务故障（上游 5xx、限流导致请求失败）。按同一配置重跑，每个 trial 最多重跑 2 次；仍失败的记为缺失。
- 归类依据 Harbor 记录的异常类型、判分结果与网关计量，按下面的顺序机械判定，不看两组的结果：
  1. 该 trial 在网关上记有上游故障（5xx、转发时连不上、200 之后断流、认证失败）或被拒绝转发的请求：基础设施故障，不论 reward。
  2. 判分给出了 reward：取该 reward（agent 超时或出错退出之后判分照常运行的也照此，与官方计分一致）。
  3. agent 超时或自身出错退出（含 agent 程序以非零退出码结束）而没有 reward：记 0。
  4. 其余已知的基础设施异常：重跑。未列出的异常类型标为"未归类"，在报告里逐个列出。

## 2 主判据

- ȳ(g, i) = 该组第 i 题各有效遍 reward 的平均，各遍等权。d(i) = ȳ(P, i) − ȳ(D, i)。效应 Δ = d(i) 在全部有效题上的平均，每题等权。
- **有效题**：未被排除，且两组在该题上各至少有一遍有效结果。缺失题超过有效题的 10% 时，报告置顶注明，结论降格为"探索性"。
- **检验**：按题配对的符号翻转置换检验，随机翻转 100,000 次，双侧，显著性水平 5%；按题自助法 95% 置信区间（10,000 次）；随机种子事先写定在分析脚本里。
- **稳健性对照**：线性概率混合模型 y ~ 组 + (1｜题)。与主检验方向或显著性不一致时注明"结论对建模方式敏感"；不收敛时注明，主结论照主检验。
- **设计灵敏度**：M = 2.80 × sd(d) ÷ √n。

## 3 次要判据（探索性，p 值不做校正）

- 每个 trial 的花费（网关计价，按非高峰价折算）、输入与输出 token、墙钟、请求数；报两组中位数与 90 分位，按题配对差的中位数。
- agent 超时数、基础设施故障与缺失数（分组）。
- 时间允许时，对两组通过的 trial 做同一套作弊审查（是否靠绕过任务意图拿分），只报数量，不改主判据。

## 4 报告的固定措辞

- **显著且 P 更好**："在 n 道题、R 遍下，Pigeon 的通过率比对照 harness 平均高 X 个百分点（95% 置信区间 [a, b]；按题配对的符号翻转检验，p = …）。"
- **显著且 D 更好**："……平均低 X 个百分点（……）。"照实写。
- **不显著、区间落在 ±M 以内**："在 n 道题、R 遍下，两组相当：估计差 X 个百分点（95% 置信区间 [a, b]，落在本设计能分辨的最小差距 ±M 以内）。"
- **不显著、区间超出 ±M**："在 n 道题、R 遍下，未测出两组的差别：估计差 X 个百分点（95% 置信区间 [a, b]）；不能排除约 M 个百分点以上的差距。"不写"没用""证伪"。
- **接近上限**：两组平均通过率都 ≥ 85% 时，结论后加"（两组都接近上限）"。
- 花费结论单独成句，不与通过率合并。

## 5 第 1 遍之后的规则

第 1 遍跑完，只计算下面三个量，不计算、不查看两组之差：基础设施故障与缺失的比例、P 组平均通过率、D 组平均通过率。

1. 基础设施故障与缺失超过全部 trial 的 10%：停下查明；修好后第 1 遍作废重跑，作废的结果不进结论。
2. 否则，若两组平均通过率都 ≥ 85%：停止后续各遍，按 406 另定（加 Terminal-Bench 4.0 中不需 GPU 的题作副测，或照跑），另定之前不看两组之差。
3. 否则：接着跑第 2–5 遍。

## 6 花费与时段

- 不设会中途停批的总花费上限。
- 不暂停高峰时段；报告写明各遍落在高峰时段的 trial 比例。花费比较一律按非高峰价折算。
