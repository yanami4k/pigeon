# 用 read_file / edit_file / run_command 改代码的操作要点

## 1. 编辑：先读，再按锚点改

- 改文件前先 read_file，拿到每行的 `N#TAG` 锚点与快照标签。edit_file 的 `anchor` 只填 `N#TAG`，`snapshot` 只填快照里的 16 位十六进制。
- `lines` 里只放这一行在文件里的原文。read_file 输出里 `N#TAG|` 后面那个空格是分隔符，不属于文件内容；把它带进 `lines` 会让新行多出一个前导空格——真实运行里出现过，改完的行与期望差一个空格，测试因此不过。缩进照原文件的实际缩进写。
- op 只有三种：`replace`（从 anchor 到 endAnchor）、`insertAfter`（至少一行）、`delete`。要在某行之前插入，就对它的前一行用 `insertAfter`。
- 一次 edit_file 里的多处编辑不能重叠。插入或删除行之后行号会变：下一次编辑前重新 read_file，取新的锚点与快照。
- 编辑被拒（快照过期、锚点不匹配、改完没有变化）时不要原样重发，先重新读文件。同一调用连续被拦 3 次会中止整个运行。
- edit_file 只能改已经存在的文件。

## 2. 命令：一条一条跑，不经 shell

- run_command 不经 shell：不要用管道、`&&`、`;`、重定向或 `$(...)`，拆成多条命令分别跑。
- 工作目录固定在工作区根，不能 cd；需要子目录时用命令自带的参数（如 `git -C <目录>`）。
- 跑单个测试文件用 `node --test <测试文件路径>`：不经 npm 的 .cmd 垫片，输出也短。Windows 上 npm / npx 是 .cmd，参数里带空格、引号、百分号或逗号会被当成需要 shell 的命令而拒绝。
- 输出只保留前 32 KiB，超时 120 秒：只跑与改动相关的测试文件，不要跑全量。

## 3. 收工前自检

- 需要某个工具的结果时就真的调用它，不要凭记忆写出"工具会返回什么"——真实运行里出现过没有发起调用、直接写出结果的情况。
- 改完代码后，用 run_command 跑与改动对应的测试文件；不过就继续改，不要宣布完成。
- 没有现成测试可跑时，至少重新 read_file 核对改动的那几行。
- 回复完成之前核对：改的是任务要求的文件与接口，函数名、签名、边界情况与任务说明逐项一致。
